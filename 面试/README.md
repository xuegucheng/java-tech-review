# 面试

> 复习到最后，缺的往往不是知识，而是「被问到时能不能顺着说出来」。
> 这一层把知识重新放回面试现场的顺序：**面试官怎么问 → 你会怎么答 → 会被追到多深 → 权威文章在哪**。

返回 [仓库首页](../README.md)。

## 题库定位

这是一套面向 **5 年以上 Java 后端工程师**的系统性面试题库，按两个维度组织，覆盖牛客网「面试真题」专区的主流专题维度（Java 基础、多线程、JVM、Spring、MyBatis、数据库基础、SQL、Redis 等）：

| 维度 | 目录 | 回答什么问题 |
| --- | --- | --- |
| 按技术专题 | [01-专题题库](01-专题题库/README.md) | 这类知识**怎么被问、怎么答、被追多深**——系统性覆盖 |
| 按企业与岗位 | [02-企业专项](02-企业专项/README.md) | 这家公司**偏重什么、怎么追、怎么分配复习时间**——针对性准备 |

另外两个模块是专题题库的延伸：[03-算法题](03-算法题/README.md)（题型模板与完整代码）与 [04-场景设计题](04-场景设计题/README.md)（场景题的六步答题框架与完整推导）。

## 这一层在仓库里的位置

本目录**故意不参与顶层编号**。这不是疏漏，而是一条可以一直用下去的规则：

| 判定方式 | 归属 | 例子 | 性质 |
| --- | --- | --- | --- |
| 目录名**带编号** | 知识层 | `01-Java核心`、`02-集合框架`、`03-并发编程`、`04-JVM` | 定义契约，每个概念只在这里写一次 |
| 目录名**不带编号** | 应用层 | `面试` | 只提问和指路，不定义任何新知识 |

所以以后无论知识层扩到 `05-Spring`、`06-MySQL`、`07-Redis`，编号都只表示**技术栈顺序**；面试相关内容始终留在不带编号的这一层，按「怎么被问」而不是「属于哪块技术」来组织。

这样做的代价是：这里不拥有任何技术定义。想读机制，必须顺着链接回到知识层。

## 内容边界

本层遵守以下边界，请在使用和引用时一并遵守：

- 这里整理的是**公开面经中反复出现的考察方向与典型问法**，题干由本仓库重新组织表述，答案与代码为本仓库原创。
- **它不是任何公司的官方题库**，不包含公司内部资料、招聘保密内容或笔试原卷。
- 不逐条转载他人面经原文，也不搬运他人的题解代码；引用他人观点时只做事实性转述并链接来源。
- 公司名称仅用于帮助读者了解不同团队的考察侧重，**不代表该公司当前的真实面试标准**；面试标准随部门、级别、年份持续变化。
- 所有技术结论的**唯一权威来源仍是前四个技术域**。本层只负责提问和指路，不重新定义任何契约。

## 面向 5 年以上的复习优先级

按「答不出直接减分」的程度分三档，配套不同读法：

| 档位 | 专题 | 读法 |
| --- | --- | --- |
| 第一档（必须能讲到 L3 因果层） | Java 基础、Java 多线程、集合框架、数据库基础、SQL、Redis | 每题先看导航表，只读「30 秒回答」查漏；卡住的题再读「深入理解」与追问 |
| 第二档（必须能讲到 L2 机制层） | JVM、Spring、分布式、消息队列、计算机网络、操作系统 | 排查类题（CPU 100%、Full GC、慢 SQL、消息积压）要能背出顺序 |
| 第三档（了解即可） | MyBatis 细节、各专题 P2 题 | 面试前扫一遍速记卡 |

判断标准只有一条：**同样的题，你能不能让面试官从「是什么」一路问到「为什么不选另一种」而不断档**。断档的地方就是还没读完的题。

## 一条清晰的复习路径

**面试前 4～6 周（系统轮）**：按第一档 → 第二档顺序过专题题库。每天 1～2 个专题，只看「30 秒回答」出声讲一遍，讲不出来的标记，回「深入理解」补。周末用 [04-场景设计题](04-场景设计题/README.md) 的六步框架练表达。

**面试前 1～2 周（针对性轮）**：读目标公司的 [企业专项](02-企业专项/README.md) 页面，按它的权重分布回专题题库只看对应题；把公司页的追问链示例拿出来，两层接不住的就地补。

**面试前 3 天（收口轮）**：只看每个专题的「面试前速记」+ [03-算法题](03-算法题/README.md) 的手写题保持手感；不再开新内容。

**面试前 1 晚**：过目标公司企业页的「高频失分点」表，别的不要看。

## 三种用法（按可用时间）

### 15 分钟：过一页专题

打开 [01-专题题库](01-专题题库/README.md) 的一个专题文件，**只看导航表和「30 秒回答」**，在心里（或出声）讲一遍。标了 `P0` 的题如果只能答到半句，就说明该补了。

### 1 小时：按目标公司突击

1. 读 [企业专项首页](02-企业专项/README.md) 的权重速查，找到目标公司的分布；
2. 进入 [该公司页面](02-企业专项/README.md)，找出它偏重的技术块；
3. 顺着这些技术块回 [专题题库](01-专题题库/README.md) 对应专题，只看 `P0` 的题；
4. 公司页的「追问链示例」至少要能接住两层，接不住的记下来回补。

### 1 天：题库 + 算法 + 场景

上午按 [03-算法题](03-算法题/README.md) 的题型地图刷模板题；下午练 [04-场景设计题](04-场景设计题/README.md) 的表达结构；晚上回专题题库做一轮口头模拟。

## 保鲜声明

面试内容的**唯一会过期的地方就是这里**。知识层的「HashMap 为什么线程不安全」五年后依然成立，但「某公司二面爱问什么」明年就可能完全不同。

一个真实的反面案例：GitHub 上曾经最受欢迎的按公司维度整理面试题的项目 LeetcodeTop（约 20k star），最后更新停在 2024 年 3 月左右，而它页面里的索引标题还写着「更新至牛客 2021.7.19 的面经」——读者点进去，看到的是两年多以前的样本，却不知道这件事。

本层用三个字段对抗这个问题。**每个公司页面的顶部都必须写清**：

| 字段 | 含义 | 写不出来的后果 |
| --- | --- | --- |
| 数据窗口 | 这批印象基于哪个时间段的面经 | 读者无法判断样本是否已经过时 |
| 最近核对 | 本页最后一次核对、修正的日期 | 读者无法判断这页还有没有人维护 |
| 来源性质 | 结论从哪来、强度如何 | 「归纳印象」被误读成「官方题库」 |

本层所有公司页面的来源性质统一是：**公开面经归纳或针对性整理，非官方题库**。这是底线表述，不因页面更新而改变。

## 怎么给它加新内容

这是本层最容易做错的地方。因为公司的考察侧重会一直变，如果「考察画像」和「具体某轮真题记录」混在一起写，页面会迅速变成一锅无法维护的粥。

解决办法是把三件事分开，各归其位：

| 你要加的东西 | 加到哪 | 怎么加 |
| --- | --- | --- |
| 「这道题怎么答」——题目、重要度标注、回答骨架 | [01-专题题库](01-专题题库/README.md) 对应专题文件 | **一类题一个文件**，分类名用单一概念的短名；来源能确定年份与公司时用 `{年份}-{公司}-{岗位}-{分类}.md`，否则用 `{分类}.md`；题号接在文件末尾 |
| 「这家公司整体偏重并发」这类**跨时间成立的画像** | 直接改该公司的企业专项页 | 就地更新，同时更新页面顶部的「最近核对」 |
| 「2026 春招某人被问到的具体一轮」这类**可溯源的记录** | 新增一篇独立记录页 | 标注时间、轮次、来源链接，**不混进画像页** |

判断标准很简单：**一条信息如果三个月后可能不再成立，它就不是画像，是记录。** 记录要能溯源（有链接、有时间），画像要能沉淀（跨样本归纳、标注数据窗口）。

**年份要慎写**：年份可信度不够时宁可不写。一个标着「2024」但样本实际横跨三年的文件名，比不写年份更有害——文件名是最容易被读者当成事实的东西。命名规则与题目格式的完整说明见 [专题题库首页](01-专题题库/README.md)。
