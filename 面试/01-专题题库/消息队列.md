## 专题定位

- MQ 是后端面试的必考专题：异步解耦、削峰填谷是两个最常被引用的落地场景，几乎每轮后端面试都会问可靠性。
- 面试官主要验证：是否真正处理过消息问题——只会背「至少一次」但说不出幂等设计的候选人会立刻暴露；以及对不同 MQ 的差异是否有体感。
- 四条主线（丢、重、积压、顺序）构成 MQ 题的基本盘，任何一道答不好都会连坐其他题；建议统一用「发生环节 → 防护手段 → 兜底」的结构答。
- 与相邻专题分工：事务消息的原理细节在本篇 Q07，但分布式事务六方案的选型在 [分布式.md](分布式.md) Q04；接口级幂等的完整设计在 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md)。
- 5 年以上要答到：选型能讲代价（不只是功能表）、可靠性方案能讲故障场景、顺序与积压能讲约束（分区数、扩分区的影响）。

## 题目正文

### Q01：消息丢失可能发生在哪几个环节？怎么防？ `P0` `高频`

**30 秒回答**：消息可能丢在生产端、Broker、消费端这三段中的任意一段，对应三套防线是发送确认、持久化加多副本、手动确认加重试补偿。

**深入理解**：生产端丢在「以为发出去了」——用同步发送加确认机制判断 Broker 是否真的写入成功（RabbitMQ 的 publisher confirm、RocketMQ 同步发送的 SendStatus、Kafka 的 acks=all），失败就重试或落本地消息表补偿。Broker 丢在消息还在内存就宕机——需要队列与消息都持久化，并有多副本兜底（Kafka 副本数不少于 3 且 min.insync.replicas 不少于 2）。消费端丢在「先确认后处理」或异常被吞——改成手动 ack 且业务处理成功后再确认，失败进重试队列或死信队列。结论是丢消息的概率只能压低不能归零，全链路必须再配一个对账或补偿任务作为最终兜底。

**为什么这样设计**：生产端最常被追问的取舍是「事务消息」还是「本地消息表」。RocketMQ 事务消息由 Broker 回查半消息状态来决定提交或回滚，逻辑耦合在 MQ 内部，实现简洁但强绑定；本地消息表把状态放在自己的数据库里，通用可控、不依赖具体 MQ 实现，代价是多一张表加一个定时补偿任务。

**面试官可能继续追问**：

- **Kafka 的 acks 三档有什么区别？** —— acks=0 发出即不管（最快最易丢）、acks=1 等 Leader 落盘（Leader 立即宕机会丢）、acks=all 等 ISR 多数派落盘（最稳，延迟最高）。生产默认建议 all，除非是指标类可丢数据。
- **消费端手动 ack 还丢不丢？** —— ack 发生在业务提交后就只有重没有丢；提交前 ack 才丢。Kafka 要提交位点（commitSync 失败重试，或 commitAsync + 回调记录），RabbitMQ 要 manual ack，RocketMQ 是消费成功返回 CONSUME_SUCCESS。
- **Broker 多副本就绝对不丢吗？** —— 不是。Kafka 的 ISR 机制下，min.insync.replicas 没配够、或全部 ISR 掉到仅剩 Leader 仍继续接受写入，会退化为单点；副本同步是异步的，极端场景（多副本同时故障）仍会丢。所以副本数 + ISR + 监控缺一不可。

**实际工程场景**：WMS 的出库流程里，库存扣减通过 MQ 通知下游作业系统：生产端同步发送 + SendStatus 校验，失败落本地补偿表；消费端作业执行结果回写必须幂等，否则重复通知会重复执行物理出库。真正兜底的是一条库存对账任务：定期比对「应扣」与「实扣」，发现差异补偿或告警——MQ 的确认机制把丢消息概率压低，对账把最后那一小部分兜住。跨机房容灾时还要评估同步双写与异步复制的 RPO 取舍，这不是 MQ 单层能解决的。

**容易答错的地方**：

- 「用了 MQ 就不会丢消息」——MQ 默认配置下处处可丢：acks=1、异步刷盘、自动提交位点，都是默认的坑。
- 「confirm 机制保证 exactly once」——confirm 只保证 Broker 收到，生产侧重试加消费端重复是常态，端到端 exactly once 不存在。
- 「消费端异常了消息就会重试」——要手动 ack + nack/拒绝才进重试；自动确认模式下异常等于直接丢。

> 权威内容：消息中间件可靠性当前尚未在仓库建设，可参考 RabbitMQ 官方文档的 Publisher Confirms 与 Kafka 官方文档的 Replication 章节。

### Q02：消息重复消费怎么办，怎么保证幂等？ `P0` `高频`

**30 秒回答**：消息队列只能做到至少一次投递，重复无法消除，所以正确做法是让消费逻辑本身幂等——同一条消息处理多次，结果与处理一次相同。

**深入理解**：常用手段有四种：数据库唯一索引（把消息 ID 或业务唯一键建成唯一索引，插入冲突即视为已处理）、Redis setNx 占位（带过期时间，顺带防重放）、状态机（只允许合法状态迁移，如已支付才能发货，重复消息自然被拒）、乐观锁版本号。唯一键方案必须处理「去重记录写入成功但业务处理失败」的一致性问题，通常把去重表和业务数据放在同一个本地事务里。消费端要保证 ack 发生在业务事务提交之后：提交前 ack 加崩溃会丢消息，提交后 ack 前崩溃会重复，后者正是幂等要接住的场景。边界是幂等键必须在业务上全局唯一，用 Redis 去重则要接受 key 过期后可能重复处理。

**为什么这样设计**：不追求「正好一次」的原因是，消息落库和 ack 是两个无法原子的动作，崩溃可以发生在两者之间，这个窗口无法用任何协议消除——它和分布式事务是同一个难题。所以业界把问题下沉到业务侧，用幂等换取工程上的可实现性。

**面试官可能继续追问**：

- **幂等键用什么？消息 ID 靠谱吗？** —— 消息 ID 可以被生产端重复生成（生产重试发出两条同 ID 消息），更稳的是业务唯一键（单据号 + 动作）。实在没有业务键再用消息 ID，并接受极端重复。
- **Redis setNx 和 DB 唯一索引用哪个？** —— 生产常见两级：Redis 挡高频重复（快、减 DB 压力），DB 唯一索引兜 Redis 故障/过期窗口的漏网重复。Redis 是性能层，DB 是正确性层，只做一层都有明确的失效模式。
- **批量消费怎么幂等？** —— 按批整体幂等代价高（一条失败整批重放），通常拆到单条幂等 + 批量插入用唯一索引（INSERT IGNORE / ON DUPLICATE）；批内部分成功时要记录成功位点，避免整批重放造成重复副作用。

**实际工程场景**：WMS 的 MQ 消费端（作业指令下发结果、库存同步）全部按幂等设计：业务唯一键（如「出库单号 + 操作类型」）建唯一索引，消息处理与业务写入同事务，重复消息插入冲突即跳过。跨系统的通用防重框架（Token、状态机、去重表的分层设计）见 [分布式.md](分布式.md) Q12 与 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md)，本文不重复展开。

**容易答错的地方**：

- 「保证 exactly once 是 MQ 的能力」——端到端 exactly once 不存在（落库与确认无法原子），幂等是业务层的补丁。
- 「Redis 去重永不重复」——key 过期后、Redis 主从切换丢数据期间都会重复；去重窗口要覆盖最大重试延迟。
- 「去重表独立提交也行」——必须和业务数据同事务，否则「去重成功、业务失败」会永久堵死这条消息。

> 权威内容：消息幂等与重复消费当前尚未在仓库建设，可参考 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md) 与 RocketMQ 官方文档的消费者重试章节。

### Q03：消息积压了怎么处理？ `P0` `高频`

**30 秒回答**：先判断是消费变慢还是生产暴涨，前者优化消费逻辑或扩消费者，后者先扩容把消费追上去，再单独补做被跳过或延迟的处理。

**深入理解**：定位时看生产 TPS 与消费 TPS 的差值、消费是否卡在慢调用（数据库、下游接口）或异常重试。扩容前要知道约束：Kafka 的消费者实例数不能超过分区数，扩实例前得先扩分区；RabbitMQ 直接加消费者实例即可。消费端优化包括批量拉取加批量处理、把同步慢调用改异步、减少消费逻辑里的锁竞争，但批量会放大「处理一半失败」的窗口，必须配合幂等。应急手段是先把消息临时转存到另一张表或另一个 topic，让消费端快速空跑追上进度，之后再离线补处理。长期要加监控，积压量和消费延迟要比「出事才看」更早暴露问题。

**为什么这样设计**：不能无脑加消费者，是因为 Kafka 里同一个分区同一时刻只能被同组的一个消费者消费，实例多于分区时多出来的会空闲；而且扩分区会打乱按 key 的顺序性保证。所以扩容的前提是先扩分区，并接受顺序性可能随之变化。

**面试官可能继续追问**：

- **扩分区后旧消息怎么分配？** —— 分区数变化触发 rebalance，已有数据不会自动迁移到新分区（按 key 哈希只影响新消息的分布），所以扩分区救不了「旧消息积压」，只能提升后续消费的并行度——这是常见误区。
- **消费慢是慢 SQL 导致怎么办？** —— 先看单条耗时分布：P99 慢在哪个调用（DB、下游、锁）。批量合并写、给热点行拆锁、下游改异步，都比加实例更根本；加实例只是买时间。
- **积压时直接丢弃消息行吗？** —— 只有明确可丢的场景（指标、日志类）才敢跳过一个位点段，且要记录跳过范围事后评估；业务消息跳过等于数据不一致，必须转存补做。

**实际工程场景**：WMS 的波次集中出库时生产会短时暴涨（早班集中推送），典型组合：① Kafka 按仓库维度分 topic/分区，消费组按分区扩实例；② 作业指令消费端批量拉取 + 批量下发，单条失败进重试不阻塞整批；③ 慢在下游 WCS 时先落「待下发」表快速 ack，由下发服务控速消费——本质是用一张表做缓冲换取 MQ 不积压；④ 积压量与消费延迟配告警（见 Q09），大促前按预估流量提前扩分区和实例。

**容易答错的地方**：

- 「加消费者就能追上」——Kafka 里实例数超分区数无效，且旧消息不会因扩分区而重新分布。
- 「批量消费一定更快」——批量放大部分失败的重放窗口，且单批过大拉高延迟；批量大小要按单条耗时调。
- 「转存空跑就完事」——转存的消息必须补处理，跳过不补等于换了个方式丢消息。

> 权威内容：消息积压治理当前尚未在仓库建设，可参考 Kafka 官方文档的 Consumer Groups 与 RabbitMQ 官方文档的 Consumer Prefetch 章节。

### Q04：怎么保证消息的顺序性？ `P2` `中频`

**30 秒回答**：消息队列只能保证同一个分区或队列内部有序，所以要顺序的消息必须路由到同一分区，并且该分区只有一个消费者按顺序处理。

**深入理解**：Kafka 上用相同 key 让同一业务实体的消息进同一分区，配合单分区单消费者；生产者开启幂等（enable.idempotence=true）后，重试不再造成乱序，此时 in-flight 请求数可以放宽到 5。全局有序的代价是并发度降到 1，所以大多数场景只要求「同一订单」「同一用户」有序，按业务键分区即可。消费端最容易破坏顺序，重试、异步、并发放大都会让后来的消息先处理，顺序敏感的业务通常单线程消费该分区，或按业务键散进内存队列再串行处理。顺序性实在保不住时，更常见的做法是让业务容忍乱序，用状态机或版本号把非法顺序的消息丢弃或延后重试。

**为什么这样设计**：分区有序而不是全局有序，是并行度和顺序的权衡单元——按业务 key 分区让「同一实体的消息有序」与「不同实体的消息并行消费」同时成立，代价是单分区内必须串行；真正要全局有序就把并发度降到 1，大多数业务付不起这个代价，所以退而求「部分有序」。

**面试官可能继续追问**：

- **重试一定会乱序吗？** —— 会。同分区内第 3 条失败重试、第 4 条先成功，顺序即破。解法是顺序敏感的分区单线程 + 失败即暂停该分区（block）或进延迟重试，而不是并发重试。
- **RocketMQ 的顺序消息怎么实现？** —— MessageQueueSelector 把同一 key 路由到同一队列（生产端顺序），消费端 MessageListenerOrderly 串行消费 + 失败时队列级重试（自动 incr 重试次数、超限进 DLQ），和 Kafka 的「单分区单消费者」同构。
- **消息自带序号/版本号呢？** —— 业务层版本号是最后的兜底：乱序到达时按版本号重排或丢弃旧版本（如库存变更带版本，旧版本直接丢）。适合「可容忍窗口」大的场景，实时性要求高的还是要靠队列内串行。

**实际工程场景**：WMS 里同一出库单的状态流转（下发→执行中→完成）必须有序，否则会出现「完成」先于「下发」到达导致状态回退。做法是同一单据号作 key 进同一分区，消费端单线程处理 + 状态机条件更新（非法迁移直接拒绝）；跨系统的最终手段是单据带版本号/状态机兜底。多数「顺序敏感」需求深聊下来会发现真正要的是「最终状态正确」，用状态机 + 版本号比死保顺序更稳——这也是面试里值得说的判断。

**容易答错的地方**：

- 「全局有序是默认能力」——分区模型下全局有序等于单分区，等于放弃并行，必须显式选择。
- 「扩分区不影响已有消息的顺序」——扩分区改变 key→分区的映射，新旧分区并存期间同一 key 的消息可能落到不同分区，顺序即破；扩容要在业务低峰且接受短暂乱序（靠幂等/版本号兜）。
- 「异步化消费不影响顺序」——异步线程池处理天然乱序，顺序敏感链路必须同步串行。

> 权威内容：消息顺序性当前尚未在仓库建设，可参考 Kafka 官方文档的 Message Delivery Semantics 与 RabbitMQ 官方文档的 Consumer Prefetch 章节。

### Q05：MQ 怎么选型？Kafka/RocketMQ/RabbitMQ/Pulsar 怎么比？ `P0` `高频`

**30 秒回答**：四个主流选项的定位：Kafka 高吞吐日志流、RocketMQ 业务交易（事务消息/延迟消息/顺序消息开箱即用）、RabbitMQ 复杂路由与低延迟、Pulsar 存算分离与多租户新贵。选型先看业务形态：日志/流处理选 Kafka，业务交易选 RocketMQ，复杂路由/协议（AMQP）选 RabbitMQ；再看团队运维能力——Kafka 运维重，RocketMQ 中文生态好，RabbitMQ 轻量但集群能力弱。

**深入理解**：

| 维度 | Kafka | RocketMQ | RabbitMQ | Pulsar |
| --- | --- | --- | --- | --- |
| 吞吐 | 极高（百万级/s，顺序写盘） | 高（十万级/s） | 中（万级/s） | 高（BookKeeper 存算分离） |
| 延迟 | 毫秒级（批发送可更低） | 毫秒级 | 微秒~毫秒级 | 毫秒级 |
| 顺序 | 分区内有序 | 队列内有序（MessageQueueSelector） | 队列内有序 | 分区内有序 |
| 事务消息 | 有（transactional.id，2.8 后完善） | 半消息（成熟，2012 年就有） | confirm + 本地消息表模拟 | 有（事务 API） |
| 延迟/定时消息 | 无原生（需外部） | 18 个延迟级别（4.x）/ 任意时间（5.0 定时消息） | 死信 + TTL 模拟（不可靠） | 无原生 |
| 协议 | 自有 TCP 协议 | 自有协议 + JMS；5.x 支持 gRPC/POP | AMQP 0-9-1、MQTT、STOMP | Pulsar 协议 + Kafka 协议兼容层 |
| 生态 | Flink/Spark/ClickHouse 数据管道事实标准 | 阿里电商金融场景锤炼 | Erlang 社区、AMQP 通用 | 云原生、Kafka on Pulsar 迁移 |
| 运维成本 | 重（ZK/KRaft、分区再平衡、副本） | 中（NameServer 轻量；5.0 架构大改） | 轻（单机强，集群模式弱） | 重（BookKeeper + Broker + ZooKeeper 栈） |

选型依据展开：

- 日志流/大数据管道：Kafka 是事实标准——高吞吐顺序写、保留策略（按时间/大小删除）天然适合「多消费者组各读各的 offset」，和 Flink/Spark 的集成无可替代。
- 业务交易（订单、支付、库存）：RocketMQ 的事务消息、延迟消息、顺序消息、消息回溯都是为交易场景设计的；国内互联网用得多、中文文档与社区活跃，出问题好查。
- 复杂路由（topic exchange、header exchange、RPC 式请求响应）：RabbitMQ 的 AMQP 模型最灵活，延迟低，适合对路由要求高、量级不大的场景；但集群镜像队列在大量消息下性能断崖，且 Erlang 二次开发门槛高。
- 存算分离/多租户/跨地域复制：Pulsar 的 segment 存储 + BookKeeper 让扩缩容和副本更快，适合云厂商与超大规模多租户；但组件栈深，中小团队慎入。
- 版本差异要讲清：Kafka 2.8 起引入 KRaft 模式（去 ZK，预览），3.x 生产可用，4.0 起 ZK 模式被移除——现在新部署默认 KRaft；RocketMQ 5.0 架构大改（新存储引擎、gRPC 协议、POP 消费、控制器模式切换），与 4.x 运维方式差异大，升级要单独评估。

**为什么这样设计**：MQ 之间没有「更好」，只有「更适合」——因为每个产品的架构选择都对应一类负载：Kafka 的分区顺序写盘换吞吐、RabbitMQ 的 Erlang 进程模型换路由灵活与低延迟、RocketMQ 的交易特性换场景适配、Pulsar 的存算分离换弹性。选型错误的主要代价不是性能差一截，而是「业务需要的特性没有、不需要的运维成本全背」——比如用 RabbitMQ 做日志管道（吞吐不够）、用 Kafka 做延迟消息（要自己搭轮子）、用冷门 MQ（排障无人可问）。

**面试官可能继续追问**：

- **Kafka 为什么快？** —— 顺序追加写盘（利用磁盘顺序写吞吐）、零拷贝（sendfile）、批量（批发送 + 批拉取 + 压缩）、PageCache 利用；分区模型天然并行。代价是实时性依赖批配置、分区数有上限（单机建议不超数千）。
- **RocketMQ 和 Kafka 的事务消息区别？** —— RocketMQ 半消息是「先发半消息 → 执行本地事务 → 提交/回滚，Broker 主动回查」；Kafka 事务是「transactional.id + 事务 Producer，消费端配 read_committed 隔离」，模型更接近数据库事务、能跨分区原子写，但消费端隔离级别不配会读到未提交消息。细节见 Q07。
- **团队该自建还是用云厂商 MQ？** —— 看规模与人力：日均十亿级以下用云 MQ（托管运维、SLA）通常更划算；超大规模或有强合规要求再自建。答「先算运维成本再算采购成本」显得有工程视角。

**实际工程场景**：WMS 这类业务系统（订单/库存/作业指令，量级百万级/日）的典型选择是 RocketMQ：事务消息覆盖「扣库存 + 发通知」的最终一致，延迟消息覆盖「波次超时自动释放」，顺序消息覆盖单据状态流转；大数据/行为日志另走 Kafka 进数仓，两套并存很常见——按流量特征选 MQ 而不是全公司一个 MQ。如果团队在阿里云生态，RocketMQ 托管版与开源版 API 基本一致，迁移成本低；自建要评估 NameServer/Controller 的可用性与磁盘规划。

**容易答错的地方**：

- 「Kafka 吞吐高所以什么都用它」——无原生延迟消息、事务消息语义和 RocketMQ 不同、运维重；业务交易场景用它会不停造轮子。
- 「RabbitMQ 集群和 Kafka 集群一样强」——镜像队列（经典集群模式）在消息量大时同步复制性能差，quorum queue（3.8+）改善了但吞吐仍非其强项。
- 「Pulsar 是 Kafka 的替代者」——架构先进（存算分离、分层存储）但生态与运维成熟度差距仍在，选它要接受「排障资料少、组件栈深」。
- 「RocketMQ 5.0 就是 4.x 加特性」——5.0 重写了存储与网络层、引入控制器与 POP 消费，升级与运维方式变化很大，必须分版本评估。

> 权威内容：MQ 选型当前尚未在仓库建设，可参考 Kafka、RocketMQ、RabbitMQ、Pulsar 各自的官方文档与 Confluent 的架构综述。

### Q06：消息队列的消息模型是怎样的？ `P1` `中频`

**30 秒回答**：消息模型分点对点（一条消息一个消费者）和发布订阅（一条消息多个订阅方各得一份）；Kafka/RocketMQ 的具体结构是 Topic 下分 Partition/MessageQueue 保顺序与并行，ConsumerGroup 内分摊消费、组间广播。消费方式 Kafka 是 Pull（客户端自己拉、自己管位点），RocketMQ 是 Push 壳 Pull 芯（长轮询，兼顾实时性与服务端压力）。

**深入理解**：

- 两种原始模型：点对点（队列，消息被一个消费者取走即删除，天然负载均衡）；发布订阅（Topic，消息广播给所有订阅者，每条订阅独立状态）。现代 MQ 是两者的组合：Topic 内按组分摊（组内点对点），组间广播。
- Topic/Partition/ConsumerGroup：Topic 是逻辑分类；Partition 是物理并行单元（有序 + 可扩展的最小单位）；ConsumerGroup 是消费逻辑单元——一条消息在组内只会被一个实例消费（分摊），但每个组都会收到全量（广播）。这就是「同一份订单消息，库存组和处理组各消费一次」的实现方式。
- Pull vs Push：

| | Pull（Kafka） | Push（RabbitMQ） | 推拉结合（RocketMQ 长轮询） |
| --- | --- | --- | --- |
| 实时性 | 取决于 poll 间隔 | 高（服务端主动推） | 高（有消息立即返回） |
| 服务端压力 | 客户端轮询可退避 | 要控消费者速率（prefetch/QoS） | 挂起请求省空转 |
| 背压 | 客户端按能力拉 | 难（要客户端限流） | prefetch + 挂起数控制 |

- RocketMQ 长轮询：客户端发 PullRequest，Broker 有消息立即返回，无消息则挂起请求（默认 15s 挂起、5s 检查），新消息到达或挂起超时再返回——Pull 的流量可控 + Push 的实时性，这是 RocketMQ「推模式」的真相。
- 位点提交：Kafka 由客户端提交 offset（自动定期提交 / 手动提交），自动提交的坑是「提交了位点但没处理完」（重启即丢——见 Q01）；RocketMQ 消费成功返回 CONSUME_SUCCESS 才算确认。语义上都是 at-least-once，配幂等（Q02）才是端到端可靠。

**为什么这样设计**：分区是 Kafka/RocketMQ 把「顺序」和「并行」同时交给用户的手段——顺序按分区保、并行按分区扩，用户用 key 路由在两者间选平衡点。消费组的「组内分摊、组间广播」把「横向扩容」和「多业务方消费同一份数据」两个诉求解耦：加实例只需在组内加，不会影响别的组。Pull 让客户端掌握消费节奏（背压天然），代价是实时性靠轮询间隔补——这是 RocketMQ 选长轮询的原因。

**面试官可能继续追问**：

- **ConsumerGroup 加实例后旧分区怎么分？** —— 触发 rebalance：Kafka 用 group coordinator + 分区分配策略（Range/RoundRobin/Sticky，2.4+ 新协议增量协同减少暂停消费），期间该组短暂停止消费（stop-the-world），高频 rebalance 是消费抖动主因。
- **一个分区可以被多个组消费吗？** —— 可以。不同组互不影响，各自维护位点；这就是「同一消息既驱动库存扣减又同步搜索索引」的实现——两个组各消费一份。
- **Push 模式消费者速率怎么控？** —— RocketMQ/RabbitMQ 都有 prefetch（未确认消息上限）：prefetch 大则吞吐高但客户端缓冲压力大、故障时重放多；小则相反。默认值（RocketMQ 1000 左右）在批量场景要显式调。

**实际工程场景**：WMS 的设计里「出库单消息」会被多个组消费：库存组扣减、作业组下发指令、报表组统计——用三个 ConsumerGroup 订阅同一 Topic，组内多实例分摊。位点管理上全部用手动提交 + 幂等，避免自动提交的丢消息窗口。长轮询与 prefetch 的调优点：作业指令要求秒级延迟，prefetch 调小（失败重放少、内存可控）；报表组容忍分钟级延迟，批量拉取调大 prefetch 与批量条数。

**容易答错的地方**：

- 「Push 一定比 Pull 实时」——RocketMQ 的 Push 是长轮询壳，实时性来自 Broker 侧新消息即时唤醒，不是服务端硬推；纯 Pull 的实时性取决于 poll 间隔。
- 「自动提交位点省心」——提交与处理不同步，崩溃窗口丢消息；生产一律手动提交 + 幂等。
- 「ConsumerGroup 就是负载均衡」——组内才是分摊，组间是广播；加实例只在自己组内生效，不会帮别的组分担。
- 「rebalance 只是短暂停顿」——老协议（Kafka eager 协议）下 rebalance 是 stop-the-world，全部消费者暂停再重分；分区多、实例变动频繁时累积停顿很可观，KIP-814 的协同式再平衡就是为解决它。

> 权威内容：消息模型当前尚未在仓库建设，可参考 Kafka 官方文档的 Consumer Groups 与 RocketMQ 官方文档的消费模式章节。

### Q07：事务消息的实现原理是什么？ `P1` `中频`

**30 秒回答**：RocketMQ 事务消息是半消息机制——生产者先发一条对消费者不可见的半消息，执行本地事务，成功则发 commit 让半消息可见、失败则 rollback；Broker 长时间没收到确认会回查生产者的本地事务状态来兜底。Kafka 的事务是另一套模型：transactional.id + 事务 Producer 跨分区原子提交，消费端配 read_committed 才能只读已提交消息。本地消息表是不依赖 MQ 的通用替代（详见 [分布式.md](分布式.md) Q04）。

**深入理解**：

RocketMQ 半消息流程：

1. 生产者发送 half 消息到 Broker——Broker 存下但消费者不可见；
2. 生产者执行本地事务（业务 DB）；
3. 根据本地事务结果发送 commit / rollback——Broker 投递或丢弃半消息；
4. 若 commit/rollback 丢失（生产者宕机在 2、3 之间），Broker 的回查任务定期（默认分钟级）向生产者发起 checkLocalTransaction 回查，生产者查本地事务状态并回复，Broker 据此提交或回滚；超过回查次数（默认 15 次）仍未确认的半消息进事务检查告警，需人工介入。

关键设计：半消息用专门的 op 字段标记、回查接口必须幂等且只查状态不执行业务、回查失败有次数上限与告警。

Kafka 事务：

- Producer 配置 transactional.id（结合分区寻址保证「僵尸实例」被 fencing，旧 Producer 被拒绝写入）；
- beginTransaction → send（多条消息可跨分区）→ commitTransaction 或 abortTransaction，Broker 侧用事务协调器记录事务状态；
- 消费者必须配 isolation.level=read_committed 才会过滤掉未提交（aborted/ongoing）事务的消息；默认 read_uncommitted 会读到未提交消息——这是最常见的配置坑。
- 与 RocketMQ 的语义差异：Kafka 事务保证的是「一批消息的原子写入」（跨分区），本地事务状态回查不在协议内——「本地事务与消息原子」这件事在 Kafka 里要用 Outbox 模式自己组合，而 RocketMQ 用半消息 + 回查在 MQ 侧直接解决。

本地消息表对比（展开见 [分布式.md](分布式.md) Q04）：把「业务写库」与「消息记录」放同一本地事务，扫描任务投递未发消息——不依赖 MQ 特性、通用可控，代价是业务库耦合一张表 + 扫描延迟 + 消息量大时扫描压力。选型结论：已用 RocketMQ 且量可控，事务消息最省事；多 MQ 并存或不想绑定，本地消息表；要严格跨分区原子，Kafka 事务（并接受组合复杂度）。

**为什么这样设计**：半消息的本质是把「消息可见性」推迟到本地事务确认之后——用 Broker 侧的「暂存 + 回查」替代「生产者本地事务与消息发送的原子性」（后者在分布式下无解）。回查是兜底「确认消息丢失」这个窗口：只要本地事务的结果是可查的（落库状态），Broker 最终总能问到答案，这就是「最终一致」的实现路径。Kafka 事务不解决「本地事务与消息原子」，是因为它的定位是流处理管道的原子写入（读-处理-写 pattern），本地事务状态查询超出其语义范围。

**面试官可能继续追问**：

- **回查接口的压力与幂等？** —— 回查按间隔 + 次数退避，接口必须幂等（可能重复回查）且只读本地事务状态；高并发下回查集中爆发要把回查打散（按生产者/按时间分片）。
- **半消息对消费者完全不可见吗？** —— 对，未提交的半消息不能被消费；commit 后立即可见。这也意味着 commit 前宕机的消息消费者无感，业务侧看到的是「消息晚到」而不是「消费到半个消息」。
- **Kafka read_committed 有性能代价吗？** —— 有：消费者要等事务结束才能读到该分区消息，长事务（生产者迟迟不提交）会阻塞消费者进度——所以 Kafka 事务里 commit/abort 要及时，不能把业务慢逻辑放在事务边界内。

**实际工程场景**：WMS 的「扣减库存 + 通知作业执行」是事务消息的典型场景：本地事务扣库存并记流水，发送半消息 → 本地事务成功 → commit，作业组消费后下发指令；失败则 rollback，库存回滚由本地事务保证。生产注意三点：① 回查接口独立部署、路径要短（只查事务状态表）；② 半消息 Topic 由系统管理（RMQ_SYS_TRANS_HALF_TOPIC），业务不直接碰；③ 事务消息解决「发送原子」，不解决「消费幂等」——作业端仍要幂等（Q02）。多 MQ 环境或强审计场景会退回本地消息表，选型对比见 [分布式.md](分布式.md) Q04。

**容易答错的地方**：

- 「事务消息等于分布式事务等于强一致」——它是最终一致：commit 前的窗口内消费者看不到消息，且消费端仍要幂等。
- 「Kafka 事务消息和 RocketMQ 一样」——模型不同：Kafka 是事务 Producer + 消费端隔离级别，RocketMQ 是半消息 + 回查；混着说必挂。
- 「read_committed 是默认的」——默认 read_uncommitted，能读到未提交/aborted 消息；不配隔离级别的事务用法等于没用。
- 「本地消息表被淘汰了」——恰恰相反，多 MQ、跨云、不信任 MQ 事务语义的场景里本地消息表（或 Outbox）仍是主流选择，因为它把控制权留在业务侧。

> 权威内容：事务消息实现原理当前尚未在仓库建设，可参考 RocketMQ 官方文档的事务消息章节与 Kafka 官方文档的 Transactions；与本地消息表等方案的横向对比见 [分布式.md](分布式.md) Q04。

### Q08：死信队列和重试机制怎么设计？ `P1` `中频`

**30 秒回答**：消费失败不是立刻进死信——先按策略重试（次数 + 退避间隔），仍失败才进死信队列（DLQ）等待人工处理或独立消费；RocketMQ 还提供延迟消息（4.x 18 个 level，1s~2h）实现「定时再试」。监控重点是死信堆积：堆积增长说明有系统性消费问题，必须告警。

**深入理解**：

- 重试机制：RocketMQ 消费失败返回 RECONSUME_LATER，按「重试次数」走延迟队列（同步阻塞重试的替代：1s 5s 10s 30s 1m 2m……逐级退避），超过最大次数（默认 16 次，可配）进 %DLQ% 死信 Topic；Kafka 没有内置重试——失败要么自己进重试 Topic（推荐）要么提交位点跳过（危险）；RabbitMQ 用 nack + requeue（立即）或死信 exchange（DLX，消息 TTL 过期/被拒/队列满时转入死信队列）。
- 延迟消息与重试的区别：两者机制不同但都能「以后再来」。RocketMQ 延迟消息是生产端能力（发的时候指定 level，Broker 到点投递），适合「30 分钟未支付关单」这类业务定时；消费重试是消费端能力（失败后退避再投），适合瞬时故障。别把业务定时用消费重试曲线实现（重试次数有限且语义是失败恢复）。
- RocketMQ 5.0 的定时消息：4.x 只有 18 个离散 level（改 broker 配置可自定义但仍是离散档位）；5.0 支持任意延迟时间的定时消息（新存储与定时引擎），是重要版本差异。
- 死信处理：死信消息必须可见、可查、可重放——配独立 Topic + 监控 + 处理流程（人工排查后修复重投或丢弃）。死信只进不消费是最常见的失误：进了 DLQ 没人看等于丢消息。
- 退避策略：固定间隔（简单，可能叠加重试风暴）、指数退避 + 抖动（推荐）、业务分级（核心业务重试更激进）。

**为什么这样设计**：重试放在进死信之前，是因为绝大多数消费失败是瞬时故障（下游抖动、锁竞争、网络），立刻进死信会把「等一下就好」的问题升级成人工介入；退避间隔给下游恢复时间，避免失败风暴。延迟队列（而非业务线程 sleep）承载重试，是因为 sleep 会占消费线程、阻塞同队列其他消息——用 Broker 侧的定时投递把「等待」从线程池里拿走。死信是边界：重试有成本（延迟、重复副作用），无限重试一条毒消息（poison pill，永远处理失败）会阻塞整个分区/队列，必须有出口。

**面试官可能继续追问**：

- **死信消息怎么重放？** —— 工具/脚本把死信消息重新投回原 Topic（带重放标记防重复计入），或死信 Topic 挂一个专用消费者做修复逻辑。关键是重放要幂等、要记录重放批次。
- **顺序敏感的消息重试会不会乱序？** —— 会。RocketMQ 的顺序消费（MessageListenerOrderly）失败时是队列级重试（暂停该队列、重试这条，成功才继续），保证顺序但牺牲该队列吞吐；并发消费下失败重试必然乱序。这也是顺序与可靠性的经典冲突（呼应 Q04）。
- **poison message 怎么防？** —— 消费逻辑要对「永远失败」的消息有熔断（重试 N 次进 DLQ）+ 告警；监控 DLQ 增长率比监控失败条数更早发现系统性问题。

**实际工程场景**：WMS 的作业指令消费（下发 WCS/TMS）典型配置：瞬时错误（超时、5xx）重试退避到 16 次约覆盖小时级；仍失败进死信 Topic，由运维/开发排查后人工重投。第三方接口长时间故障时，靠死信 + 告警让人介入，而不是无限重试把消费位点卡死。业务定时（如「波次 30 分钟未开始自动释放」）用延迟消息实现，不占用重试机制——两个能力分开用、分开监控。DLQ 堆积配告警（见 Q09），死信处理 SOP 要提前定好（谁看、多久处理、怎么重放）。

**容易答错的地方**：

- 「消费失败就会进死信」——先重试再死信；次数与退避可配，一失败就进 DLQ 会把瞬时故障放大成人工工单。
- 「延迟消息就是重试」——一个是生产端定时能力（业务定时），一个是消费端失败恢复，语义与实现都不同。
- 「死信队列建了就行」——没有消费/监控/重放流程的 DLQ 是消息黑洞，比没有 DLQ 更危险（看不见的丢失）。
- 「RocketMQ 延迟消息可以精确到任意秒」——4.x 只有 18 个固定 level；任意时间定时是 5.0 的能力。

> 权威内容：死信与重试当前尚未在仓库建设，可参考 RocketMQ 官方文档的消息重试与死信章节与 RabbitMQ 官方文档的 Dead Letter Exchange 章节。

### Q09：MQ 的可观测性怎么做？ `P2` `低频`

**30 秒回答**：四个层次：生产侧（发送成功率、失败原因）、Broker 侧（堆积量、Topic 分区健康、副本同步）、消费侧（消费 TPS、消费延迟 lag、重试与死信速率）、链路关联（traceId 贯通生产-消费-业务日志）。告警阈值按「业务容忍度」定而不是按经验值：堆积量看窗口增速、消费延迟看业务 SLA、死信看绝对增长。

**深入理解**：

- 核心指标：
  - 生产：发送成功率、失败分类（超时/Broker 拒绝/序列化）、发送耗时 P99。RocketMQ 有内置的消息轨迹（trace topic 记录收发链路），Kafka 靠客户端 metrics + JMX。
  - Broker：Topic 堆积量（按分区）、ISR 健康、请求延迟、磁盘水位。RocketMQ Console / kafka-lag-exporter 可看。
  - 消费：消费 TPS 与生产 TPS 的差值（积压趋势）、consumer lag（Kafka 有 consumer group lag 指标；RocketMQ 看堆积与 offset 差）、重试速率、死信增量。
  - 消费延迟：lag / 消费速率 = 预计追平时间——这个推算比绝对 lag 更贴近业务感知（lag 10 万但每秒消 5 万，等于 2 秒恢复）。
- 消息轨迹与日志关联：traceId 从生产端生成，经消息属性透传到消费端，落业务日志——「这条消息到哪了、卡在哪个服务」靠 traceId 串起来；SkyWalking 等 APM 对 MQ 的埋点自动处理跨进程传播（见 [分布式.md](分布式.md) Q11）。
- 告警阈值怎么定（本题的深度所在）：
  - 堆积量：绝对值意义不大，看「持续增长」——连续 N 个检查点递增即告警；再配一个绝对上限（磁盘/内存风险水位）。
  - 消费延迟：按业务 SLA 反推——库存同步容忍 10s、支付回调容忍 1min，阈值从业务来，不从监控经验值来。
  - 死信：增速 > 0 且持续即告警（正常应长期为 0）；绝对值阈值辅助。
  - 成功率：生产成功率 < 100% 即告警（正常应为满）；消费成功率下降即排查。
  - 分级：P0 告警打电话、P1 企业微信、P2 日报——MQ 问题多连带业务受损，核心 Topic 按 P0/P1 配。
- 巡检项：Topic 分区数 vs 消费者实例数（扩容前置，见 Q03）、死信 Topic 是否有人消费、延迟消息量异常（大促前涨是正常、平时涨是误用）。

**为什么这样设计**：MQ 的故障模式是「静默劣化」——消费变慢、lag 缓增不像接口报错那样显眼，等业务投诉时已积压百万。所以可观测性的核心是「趋势告警」而非「阈值告警」：lag 1 万不可怕，lag 每 5 分钟翻倍才可怕。traceId 贯通是因为 MQ 把同步链路切成两段，没有关联 ID 时「消息发出去了但结果没来」这类问题在生产和消费两侧各有一套日志，排查靠猜。

**面试官可能继续追问**：

- **lag 指标本身有延迟吗？** —— Kafka 的 consumer lag 依赖 offset 拉取有间隔；RocketMQ 的堆积是 Broker 侧近似实时。评估告警灵敏度要把指标采集周期算进去，别用 5 分钟粒度的数据配秒级告警。
- **消息轨迹（trace topic）本身会成为负担吗？** —— 会：轨迹也是消息，量大时占 Broker 资源；要采样（如 10%）+ 独立 Topic + 短保留。可观测系统自身被压垮是常见事故。
- **消费成功率怎么算？** —— 分母是拉到/推送的消息数，分子是成功处理数；重试中的消息不计失败但计 lag。指标口径要在团队内统一，否则各看各的数。

**实际工程场景**：WMS 的核心 Topic（库存扣减、作业指令）配 P1 告警：堆积连续 3 个检查点（1 分钟粒度）增长、消费延迟超业务 SLA（如 30s）、死信增量 > 0；非核心（报表同步）P2 日报。生产成功率配 P0——只要 < 100% 立即查（正常配置下发送失败即异常）。消息轨迹采样 10% + traceId 贯通业务日志，保证「PDA 提交了但出库单没动」这类问题能快速定位到卡在哪个服务。

**容易答错的地方**：

- 「有 Grafana 看板就算可观测」——看板不等于告警，阈值不等于有响应 SOP；核心是「谁在半夜被叫醒、多久响应」。
- 「lag 越小越好」——消费过快可能是在丢消息（跳过/位点乱提），要和生产量、成功率一起看。
- 「告警阈值拍一个经验值」——不同 Topic 业务容忍度差一个量级，统一阈值要么漏报要么狼来了；阈值要从业务 SLA 反推。

> 权威内容：MQ 可观测性当前尚未在仓库建设，可参考 RocketMQ Console 文档、kafka-lag-exporter 项目与 SkyWalking 官方文档的 MQ 插件说明。

## 面试前速记

- 丢消息三防线：生产确认（acks=all/SendStatus/confirm）、Broker 持久化 + 多副本（ISR 配够）、消费手动 ack + 重试；概率只能压低，对账兜底。
- 重复是常态：at-least-once 无法消除重复，幂等四手段（唯一索引/setNx/状态机/乐观锁），去重表与业务同事务，ack 在业务提交后。
- 积压先分「消费慢 vs 生产暴涨」；Kafka 消费者实例 ≤ 分区数，扩分区不救旧积压、影响顺序；应急转存必须补做。
- 顺序只到分区内：同 key 进同分区 + 单消费者；生产者开 enable.idempotence 防重试乱序；扩分区破顺序，靠状态机/版本号兜底。
- 选型按业务形态：日志流 Kafka、业务交易 RocketMQ（事务/延迟/顺序开箱即用）、复杂路由 RabbitMQ、存算分离 Pulsar；Kafka 2.8 起 KRaft、RocketMQ 5.0 架构大改。
- 消息模型：Topic/Partition 保序并行，ConsumerGroup 组内分摊组间广播；Kafka Pull 自管位点、RocketMQ 长轮询（推壳拉芯）；一律手动提交 + 幂等。
- 事务消息两种模型：RocketMQ 半消息 + Broker 回查本地状态；Kafka transactional.id + read_committed（不配隔离级别等于没用）；本地消息表是通用替代。
- 死信前有重试：退避（指数 + 抖动）、RocketMQ 16 次进 %DLQ%；延迟消息（4.x 18 个 level，5.0 任意时间）是生产端能力，别和重试混。
- 可观测性重「趋势告警」：lag 增速比绝对值重要、死信增量 > 0 即告警、发送成功率 < 100% 即查；阈值从业务 SLA 反推。
- 进阶判断：多数「顺序敏感」需求真正要的是「最终状态正确」——状态机 + 版本号比死保顺序更稳。
