# JVM

> 一句话定位：JVM 专题在面试里考两类能力——给你线上症状（CPU 100%、Full GC 频繁、OOM）能不能按顺序定位，以及对象、类加载、GC 的机制能不能讲到设计取舍；与「Java多线程」专题的边界是这里管运行时数据区与自动内存管理，那里管语言层并发原语。

## 专题定位

- JVM 是 Java 面试追问链最长的一块：从「内存区域划分」出发，几乎可以一路问到对象分配、GC Roots、收集器选型、线上 OOM 排查。面试官用它区分「背过八股」和「真排过障」。
- 排查题（Q01/Q02/Q08）的分水岭不在工具名，而在**顺序和依据**——先做什么、看到什么才能走向下一支；机制题的分水岭在「能不能解释为什么这么设计」。
- 5 年以上工程师要答到三层：结论（是什么）、依据（怎么做的、边界在哪）、取舍（为什么不选另一种、什么场景下这个结论会反过来）。
- 版本差异是硬门槛：JDK 8 的永久代与 PrintGCDetails、JDK 9 起的 G1 默认与 `-Xlog` 统一日志、JDK 15 起 ZGC 生产可用、JDK 21 分代 ZGC——说错版本比答不出更减分。
- 机制解释的权威来源在知识层 [04-JVM](../../04-JVM/README.md)，本层只给面试口径的压缩答案并链接过去，不复制机制讲解。

标签：`P0`=优先复习，`P1`=常见，`P2`=了解即可；追问深度取 `原理`/`源码`/`工程实践`/`排查` 之一。

## 题目正文

### Q01：线上 CPU 飙到 100%，你怎么排查？ `P0` `高频`

**30 秒回答**：先分用户态还是内核态——用户态高就抓最耗 CPU 的线程栈看它在执行什么，内核态高就查上下文切换与锁竞争；结论必须由证据反推，不能一上来就猜 GC。

**深入理解**：第一步 `top` 找到进程并看 `us`/`sy` 哪个高。用户态高：`top -Hp <pid>` 找最耗 CPU 的线程，把线程号转成十六进制，在 `jstack <pid>` 输出里搜 `nid=0x...` 定位栈顶方法，常见元凶是死循环、正则回溯、频繁 GC、大量序列化；若大量线程卡在同一处，那是锁竞争或下游变慢，不是算力问题。内核态高：通常是上下文切换过频，看 `vmstat` 的 `cs` 列，多为锁竞争或线程数过多。怀疑 GC 时用 `jstat -gcutil <pid> 1000` 看各区占用与 GC 耗时，再决定要不要 dump 堆。Java 21 环境可用 `jcmd <pid> Thread.print` 替代 `jstack`。

**为什么这样设计**：排查顺序的价值是「用最廉价的判断缩小范围」——先花十秒分清 `us`/`sy`，就避免了在两条完全不同的路径上乱找。这也是为什么面试官更在意你的顺序和依据，而不是你记住了几个工具名。

**面试官可能继续追问**：
- **`us` 和 `sy` 分别说明什么？** —— `us` 是用户态 CPU 占用，说明 Java 代码本身在消耗算力，直接去查线程栈顶；`sy` 是内核态占用，说明大量系统调用或上下文切换，重点查锁竞争、线程数过多、IO 模型问题。两者的定位路径完全不同，所以这一步必须最先做。
- **`top -Hp` 的线程号和 `jstack` 输出怎么对应？** —— `top -Hp <pid>` 显示的线程号是十进制，转成十六进制后去 `jstack` 输出里匹配 `nid=0x...`，栈顶那一帧（连同调用来源，如定时任务入口）就是最可能的元凶。
- **如果是 GC 导致的 CPU 高，怎么进一步确认？** —— `jstat -gcutil` 看 GC 频率是否异常（YGC/FGC 间隔远小于正常值）、各区占比；再看 jstack 里是否有线程停在 GC 相关栈上，以及是否有大量线程同时卡在同一个业务方法上。确认后按 Q02 的分支继续。
- **Java 21 为什么推荐 `jcmd Thread.print`？** —— `jcmd` 是统一的诊断命令入口，`Thread.print` 与 `jstack` 等价且功能持续增强（可带 `-l` 打印锁信息），`jstack` 在部分新版本中已被标记为将被移除的工具，新版本环境应优先用 `jcmd`。

**实际工程场景**：告警触发后先看监控确认是不是「CPU 高且 RT 同步劣化」，再按上述顺序动手；保留现场（jstack 多次采样 + jfr 记录）再重启，否则问题复现不了。真实案例里正则回溯与无界循环占大头，GC 与锁竞争次之——但顺序不能反，必须让证据决定走向。

**容易答错的地方**：一上来就说「先 jstack 看看」或「先 dump 堆」——没有先分 `us`/`sy`，可能在错误的路径上浪费时间；说「CPU 高一定是 GC」或「一定是死循环」——都是猜不是查；只背工具名不讲使用顺序，这是本题最常见的失分点。

### Q02：一次 Full GC 变频繁，你的排查顺序是什么？ `P0` `高频`

**30 秒回答**：先确认是不是真的 Full GC（看 GC 日志，不要凭感觉），再判断是「回收不掉」还是「分配太快」——回收不掉就查对象保留关系，分配太快就查是否有短命大对象或缓存失控。

**深入理解**：第一步开 `-Xlog:gc*`（JDK 9+）或 `-XX:+PrintGCDetails`，拿到时间戳、回收前后各区占用和停顿时长。分两支：若每次 Full GC 后老年代占用依然很高，说明有对象被长期持有——用 `jmap -histo:live <pid>` 看对象直方图找异常增长的类，必要时 `jmap -dump` 后用 MAT 看支配树与到 GC Roots 的引用链；若每次都能回收下去但很快又满，说明晋升速率太高——可能是新生代太小（短命对象被过早晋升），或存在超出预期的缓存/批量任务。新生代大小、晋升阈值、元空间扩容都会影响现象，**改参数前必须先确定是哪一支**。

**为什么这样设计**：Full GC 是症状不是原因。拆成「回收不掉」与「分配太快」两支，是因为后续手段完全不重叠——前者要改对象生命周期或引用关系（代码问题），后者要调内存布局或限流（容量问题）。先分错支，后面所有工作都是白做。

**面试官可能继续追问**：
- **怎么从 GC 日志区分这两支？** —— 看每次 Full GC 前后老年代的占用：回收后仍接近满 → 回收不掉；每次回落到低位但很快又涨回来 → 分配太快。同时看时间间隔是否均匀、与业务高峰（如定时任务）是否相关。
- **Minor GC 和 Full GC 的区别是什么？** —— Minor GC 只回收新生代，存活对象复制到 Survivor 或晋升老年代，频率高、单次停顿短；Full GC 回收整个堆和方法区，触发条件包括老年代满、元空间不足、分配担保失败、`System.gc()` 等，频率低、单次停顿长得多。
- **什么场景下不能简单调大堆？** —— 「回收不掉」那一支调大堆只会延后爆发且让单次 Full GC 停顿更长；如果是内存泄漏，扩容反而让泄漏积累得更久、爆得更猛（见 Q08）。
- **`-Xlog:gc*` 能看到什么关键指标？** —— 每次 GC 的类型、停顿时长、GC 前后各区占用变化、晋升对象大小、Humongous 分配（G1 下）、GC 原因（如 Allocation Failure、Metadata GC Threshold、System.gc()）——GC 原因本身就是分桶的重要线索。

**实际工程场景**：先补日志再排查——没有 GC 日志一切免谈，所以 Q13 里 HeapDumpOnOutOfMemoryError 和 `-Xlog` 属于上线标配而非可选项。生产中 Full GC 频繁的常见真相是「缓存无上限」和「新生代与 Survivor 配比失调」，前者改代码（限制容量、加过期），后者才动参数。

**容易答错的地方**：把 Full GC 频繁等同于「堆不够大，加内存」；不区分「回收不掉 / 分配太快」两支；不知道 `System.gc()`（RMI 等场景会触发）与显式调 `-XX:+DisableExplicitGC` 的关系；JDK 8/9 混用——老版本用 `-XX:+PrintGCDetails`，JDK 9+ 应使用 `-Xlog:gc*`。

### Q03：类加载的双亲委派为什么这么设计？能打破吗？ `P0` `高频`

**30 秒回答**：委托父加载器优先，是为了保证「同一个全限定名在整个 JVM 里只由一个加载器定义」，从而让 `java.lang.String` 这类核心类无法被同名类顶替；代价是父加载器看不见子加载器的类，需要局部隔离或跨层可见时就必须打破它。

**深入理解**：顺序是「先委托父加载器，父加载器找不到再自己加载」。它带来两个保证：核心类库不会被同名类覆盖（安全），同一个类在同一加载器下只加载一次（类身份由「加载器 + 全限定名」共同决定，同一份字节码被两个加载器加载会得到两个互不兼容的 `Class`，`instanceof` 与强转都会失败）。打破的典型场景有三类：一是 SPI 场景（JDBC 驱动、`ServiceLoader`）——接口在父加载器、实现类在子加载器，于是用线程上下文类加载器反向向下请求；二是热部署与插件隔离（Tomcat 的 Webapp 类加载器优先加载自身目录，让不同应用的同名库互不干扰）；三是 OSGi 式网状委托。

**为什么这样设计**：如果允许子加载器优先，任何人都能提供同名的 `java.lang.String` 抢先加载，整个类型系统就失去可信基础。所以「父优先」是安全底线，打破只允许发生在明确需要局部隔离或跨层可见的地方，且每打破一次都要自行承担类型身份混乱的风险。

**面试官可能继续追问**：
- **有哪些类加载器，各自加载什么？** —— Bootstrap（C++ 实现，加载 `JAVA_HOME/lib` 核心类库如 `rt.jar`/模块）、Extension/Platform（JDK 9 后，扩展模块）、Application/System（classpath）、以及自定义加载器；JDK 9 起类库以模块化 jimage 组织，但三层委派结构保留。
- **线程上下文类加载器解决什么问题？** —— 双亲委派下父加载器看不到子加载器的类，但 SPI 恰恰是「父层的接口 + 子层的实现」。`Thread.currentThread().getContextClassLoader()` 让父层代码临时借道子层加载器拿到实现类，JDBC 与 `ServiceLoader` 都依赖它。
- **Tomcat 是怎么打破的？** —— Webapp 类加载器重写 `loadClass`：先尝试自己加载（Web 应用目录优先），加载不到才向上委托；同时 JRE 核心类仍然向上委托。目的是每个 Web 应用的同名类库互相隔离，互不干扰。
- **同一个类被两个加载器加载会怎样？** —— 得到两个不同的 `Class` 对象，类型不兼容：互相赋值抛 `ClassCastException`，`instanceof` 为 false。这是插件隔离必须付出的代价，也是 OSGi 等框架复杂度的来源。

**实际工程场景**：需要类隔离的场景（容器内多应用、插件系统、热部署 agent）走自定义加载器 + 有选择地打破委派；但普通业务代码几乎不该碰委派，自己打破往往是在制造难以排查的 `LinkageError`/类型转换问题。

**容易答错的地方**：说「打破双亲委派就是不安全/不可以」——讲反了，它是被设计成可继承可重写的扩展点；说 `loadClass` 不能重写——可以，Tomcat 正是重写它（推荐的做法是重写 `findClass` 并在其中管理自己的查找逻辑）；答不出 SPI 场景下为什么需要上下文类加载器，说明只背了模型没理解动机。

### Q04：哪些对象会进入老年代？ `P1` `高频`

**30 秒回答**：四条路径——晋升年龄达到阈值的对象、`Survivor` 中同年龄对象总和超过一半的大龄对象、大对象直接分配、以及分配担保触发的批量晋升。

**深入理解**：对象在 Eden 分配，Minor GC 存活后进 `Survivor` 并使年龄加一，默认到 15（`-XX:MaxTenuringThreshold`）晋升老年代。若 `Survivor` 装不下存活对象，会走分配担保直接进老年代。「动态年龄判定」指：当 `Survivor` 中一批年龄 ≤ n 的对象总和超过 `Survivor` 空间的一半时，年龄 ≥ n 的对象直接晋升，不必等到 15——这是为避免 `Survivor` 反复溢出。超过 `-XX:PretenureSizeThreshold` 的大对象直接在老年代分配，避免在 Eden 与 `Survivor` 之间来回复制。长期存活的缓存、静态集合、线程池中未 `remove` 的 `ThreadLocal` 残留都会稳定停在这里。

**为什么这样设计**：晋升机制的本质是「用年龄作为存活概率的代理指标」——活得越久越可能继续活下去，继续放在新生代反复复制不划算。动态年龄判定是对这个代理指标的修正：当 `Survivor` 已经装不下这一批同龄对象时，还按年龄逐个判断反而更亏，不如整体送走。

**面试官可能继续追问**：
- **动态年龄判定的规则具体是什么？** —— Minor GC 时若 `Survivor` 中相同年龄的对象大小之和超过 `Survivor` 空间的一半，年龄大于或等于该年龄的对象直接晋升老年代，无需再等阈值。它让「本该晋升的一批同龄对象」不必逐个等到 15。
- **分配担保是什么？** —— Minor GC 前检查老年代最大可用连续空间是否大于新生代所有对象总空间（或历代晋升平均大小），不满足则根据 `HandlePromotionFailure` 的策略决定是否冒险执行 GC；担保失败或空间不足时存活对象直接批量进老年代，极端情况下触发 Full GC。
- **大对象阈值在哪些收集器下生效？** —— `PretenureSizeThreshold` 只在 Serial、ParNew 等分代收集器下有效；G1 有对应的大对象判定逻辑（超过 Region 一半进 Humongous 区），机制与参数都不同。
- **长期存活对象停在这里说明什么？** —— 如果老年代里堆的是缓存、静态集合、未清理的 ThreadLocal，说明这些对象的生命周期本就该由代码管理，晋升机制只是结果——排查 Full GC 频繁时要优先看这批对象（关联 Q02/Q08）。

**实际工程场景**： Survivor 偏小会导致对象「活不过一次 Minor GC」就被动态晋升，老年代被中短命对象撑爆、Full GC 频繁——这是 Q17 案例一的标准解法；反过来 Survivor 过大挤压 Eden，Minor GC 频率上升。参数只在「分配太快」那一支有意义。

**容易答错的地方**：漏掉动态年龄判定和大对象这两条路径，只答「熬到 15 岁」；说 `PretenureSizeThreshold` 对 G1 生效；把「晋升老年代」当成问题本身——它只是机制，问题在于晋升的是本该短命的对象。

### Q05：GC Roots 有哪些？可达性分析是怎么做的？ `P0` `高频`

**30 秒回答**：根集合包括虚拟机栈中局部变量表引用的对象、方法区静态属性引用的对象、方法区常量引用的对象、本地方法栈 JNI 引用的对象、活跃线程与同步监视器持有的对象；从这些根出发做可达性遍历，遍历不到的才可回收。

**深入理解**：之所以用可达性分析而不是引用计数，是因为引用计数处理不了循环引用（两个对象互相引用但都不可达时计数不为零）。遍历必须在一致性快照上进行，所以需要 Stop The World——现代收集器能把停顿压得很短，靠的是安全点与安全区域：只在安全点做根节点枚举，并把可达性分析的部分工作放到并发阶段（如 G1 的并发标记加重新标记修正）。`jmap -histo:live` 和 MAT 的支配树分析都建立在同一套根集合概念上。

**为什么这样设计**：根集合的选取标准是「一定能被程序直接访问到的位置」——栈帧局部变量、静态字段这些是程序触达世界的入口。把这批位置固定成一个小集合、并且能在安全点上快速枚举，才能在有限停顿内完成分析。这是用「枚举范围的一小部分」换「整体停顿可控」的取舍。

**面试官可能继续追问**：
- **为什么不用引用计数？** —— 循环引用是致命伤：两个对象互相持有但外部都不可达时，计数永远不为零，永远回收不掉。可达性分析从根出发做遍历，天然不受循环影响。
- **枚举根节点为什么需要 STW？不能并发吗？** —— 根节点枚举依赖 OopMap 记录哪些栈位置是引用，但生成 OopMap 要求线程停在稳定状态；若枚举期间用户线程继续改引用关系，遍历到的就是「不一致的快照」，可能把活对象判死。现代收集器只是把 STW 压缩到很短（毫秒级），并没有消除它。
- **安全点和安全区域的区别？** —— 安全点是「线程可以安全停顿的位置」（方法调用、循环跳转处），线程运行到安全点才挂起等 GC；安全区域解决「线程在 Sleep/Blocked 等不执行代码的状态」——进入时标记自己安全，要恢复前检查是否还在 GC 根枚举阶段。
- **并发标记怎么处理「标记期间对象关系变化」？** —— 典型做法是 SATB（ZGC 的快照思路）或增量更新（CMS/G1 记录删除的引用），把变化记录下来，在重新标记（最终暂停）阶段修正，用一次短停顿换并发标记的长处。

**实际工程场景**：理解 GC Roots 是内存分析的语言——MAT 的「Path to GC Roots」、`jmap -histo:live` 的存活直方图、泄漏嫌疑报告都基于此。日常定位泄漏时的动作就是「找一个不该活的对象，问它是被哪个根通过什么链路拉住」，Q08 的整个流程建立在这道题上。

**容易答错的地方**：根集合漏项（漏掉本地方法栈 JNI 引用、活跃线程本身、同步监视器）；说「引用计数完全不能用」而不谈循环引用这个具体原因；以为现代收集器消除了 STW——只是缩短，且并发标记本身要解决一致性快照问题。

### Q06：Java 有哪几种引用？各自的使用场景是什么？ `P1` `高频`

**30 秒回答**：强引用（默认，可达就不回收）、软引用（内存不足才回收，适合做缓存）、弱引用（下次 GC 就回收，适合挂「不影响对象存活」的关联数据）、虚引用（拿不到对象，只在被回收时收到通知，必须配合 `ReferenceQueue`）。

**深入理解**：`SoftReference` 适合实现内存敏感缓存，但要注意它可能在任意一次 GC 被清掉，不能当作可靠缓存层。`WeakReference` 的典型用法是 `ThreadLocalMap` 的 key，以及 `WeakHashMap` 这类「对象没了附加数据就没意义」的关联。`PhantomReference` 的唯一用途是回收通知，可用于堆外资源释放这类清理动作——`finalize` 的替代方案之一就是它。四档引用共同支撑了「对象生命周期可以分层管理」这件事。

**为什么这样设计**：这四档是「内存压力 → 回收力度」这条连续谱的离散化。语言把「能不能回收」从二值变成四档，让调用方能表达「有内存就留着、没内存再说」这类真实需求；代价是回收时机不再确定，任何依赖软/弱引用的逻辑都必须能容忍「对象随时消失」。

**面试官可能继续追问**：
- **`ReferenceQueue` 是做什么的？** —— 引用对象被 GC 清理后会进入关联的队列，通过轮询队列可以知道「被引用的对象已经死了」。弱引用清理 key、虚引用做资源释放通知都靠它；不注册队列就只能每次 `get()` 碰运气。
- **软引用什么时候被回收，能控制吗？** —— 在内存不足、即将 OOM 的临界点由 GC 统一清理（JDK 1.2 后策略还与空闲时间有关，不同版本/收集器的细节有差异）。它不能被精确控制，所以不能当「可靠缓存」——这是它最大的使用限制。
- **`finalize` 为什么被废弃，替代方案是什么？** —— `finalize` 执行时机不确定、可能拖慢回收、可能复活对象导致行为难以推理，JDK 9 起标记废弃、JDK 18 默认禁用。替代方案是 `try-with-resources` / `Cleaner`（内部基于虚引用 + `ReferenceQueue`）做显式资源释放。
- **弱引用做缓存有什么坑？** —— 「下次 GC 就回收」意味着缓存命中率完全不可控，`WeakHashMap` 适合「key 决定生命周期」的场景（如元数据、注册表），不适合当性能缓存；性能敏感缓存优先考虑有容量上限和过期策略的本地缓存（如 Caffeine）而非软引用。

**实际工程场景**：`ThreadLocalMap` 的 key 用弱引用防的是「ThreadLocal 对象本身永久滞留」，但 value 仍需手动 `remove`（见 Java多线程专题）；图片/大对象缓存、`WeakHashMap` 做注册表是经典用法；`DirectByteBuffer` 的堆外内存靠 `Cleaner`（虚引用机制）释放，这也是 Q09 直接内存排查的理论基础。

**容易答错的地方**：说软引用「内存不足才回收」就以为它很可靠——它可能在任意一次 GC 被清；把虚引用和弱引用的用途混同（虚引用 `get()` 永远返回 null，唯一价值是通知）；答不出 `ReferenceQueue` 的作用；以为 `WeakHashMap` 适合做缓存。

### Q07：G1 的 Region 和停顿预测是怎么配合的？ `P1` `中频`

**30 秒回答**：堆被拆成等大的 Region（逻辑上分 Eden、Survivor、Old 和 Humongous），G1 按「回收收益 / 回收成本」给 Region 排序，在用户设定的停顿目标内尽可能多回收——这正是「Garbage First」的含义。

**深入理解**：Region 大小由 `-XX:G1HeapRegionSize` 决定，默认按堆大小推导为 1～32MB 的 2 的幂；超过 Region 一半的大对象走 Humongous 区。收集分两支：Young GC 只收年轻代；Mixed GC 在并发标记完成后，除年轻代外再回收一批回收价值高的老年代 Region。停顿预测基于每个 Region 的历史统计（记忆集记录的跨 Region 引用数量）估算成本，据此选出本次的收集集合。

**为什么这样设计**：早期 CMS 的问题是无法同时控制碎片和停顿——全堆并发清理之后依然有碎片。G1 的思路是把回收单位从整堆降到一个 Region，于是停顿可以按「这次收几个 Region」来调节，理论上可预测。代价是记忆集要维护跨 Region 的引用关系，写屏障和额外内存开销都上来了，这也是它不适合小堆的原因之一。

**面试官可能继续追问**：
- **Humongous 区是什么，有什么问题？** —— 超过 Region 一半的大对象直接分配到连续的 Humongous Region；分配 Humongous 失败可能触发并发循环甚至 Full GC，大量大对象场景（如大数组、大 JSON）会让 Humongous 成为瓶颈，是 G1 的老问题之一。
- **G1 和 CMS 的核心差异在哪？** —— CMS 是标记-清除，不整理，靠空闲列表分配且长期运行有碎片；G1 以 Region 为单位的复制整理，碎片刻意避免、停顿可预测。但「G1 一定比 CMS 好」不成立——小堆上 G1 的记忆集开销可能吃掉收益，CMS 在部分中堆场景停顿反而稳定；CMS 已在 JDK 14 被移除，没有这个选项后选择才变成单选题。
- **停顿目标设得越小越好吗？** —— 不是。`-XX:MaxGCPauseMillis` 设得过小，G1 只能靠提高 GC 频率（每次少收）来达标，吞吐显著下降；它是软目标，实际停顿可能超过。延迟敏感场景配合 ZGC 比较更彻底（见 Q14）。
- **G1 为什么是 JDK 9 起的默认收集器？** —— 服务器级场景下停顿可预测性比 CMS 的短停顿更重要，且 CMS 维护成本高（并发失败、碎片问题多）；JDK 8 的默认仍是 Parallel GC，讲默认收集器必须带版本。

**实际工程场景**：中到大堆（数 GB 级）+ 延迟敏感接口是 G1 的主场；小堆服务（几百 MB 以内）G1 的优势不明显，参数调优收益也有限；大堆低延迟（8GB 以上、要求个位数毫秒停顿）应评估 ZGC，不要默认 G1 包打天下。

**容易答错的地方**：说 G1 物理上分了代——Region 是逻辑划分，同一 Region 的角色可变；说 G1 消除了 STW——并发标记只是压缩停顿；把「Garbage First」理解成「垃圾优先回收的对象」而不是「回收收益优先的 Region」；不讲版本说「G1 是默认收集器」。

### Q08：内存泄漏和内存溢出有什么区别，怎么定位？ `P0` `中频`

**30 秒回答**：内存泄漏是「对象本该被回收却还被引用着」的代码问题（慢性病），内存溢出是「真需要的内存超过上限」的结果（发作）；泄漏长期积累会引发溢出，但溢出也可能与泄漏无关。

**深入理解**：定位泄漏靠看增长趋势：连续几次 `jmap -histo:live` 比对对象直方图，找出实例数持续增长的类；确认候选后 `jmap -dump` 并用 MAT 看支配树和到 GC Roots 的最短引用链，定位是谁在持有。常见来源：静态集合只增不减、`ThreadLocal` 未 `remove`、监听器或回调注册后未注销、线程池与 `ThreadLocal` 的组合、无上限缓存、类加载器泄漏导致整个加载器卸载不掉。区分溢出类型也有用：堆空间不足、元空间不足（类加载器或动态代理过多）、无法创建本地线程、GC 开销超限——它们的处置方向并不相同。

**为什么这样设计**：把两者分开是因为处理方式相反——溢出常能靠调大堆或限流缓解（治标），泄漏只能改代码释放引用（治本），而扩容只会让泄漏发作得更晚、更猛。这道题真正想确认的是：你会不会把「加内存」当成万能解。

**面试官可能继续追问**：
- **怎么快速判断是泄漏还是单纯容量不够？** —— 看趋势不看单点：连续多天同时段对比老年代占用与对象直方图，业务量持平但占用持续抬升就是泄漏；占用随流量线性增长且 GC 后能回收下去，更可能是容量或峰值问题。压力测试对比也能佐证。
- **MAT 的支配树和引用链分别怎么看？** —— 支配树回答「谁持有了最大的一片对象」，快速定位聚合点；对候选对象看「Path to GC Roots（排除软/弱/虚引用）」找最短强引用链，直接指向代码里的持有者（通常是静态字段、集合、ThreadLocal）。
- **元空间溢出和堆溢出怎么区分？** —— 报错文本不同：堆是 `Java heap space`，元空间是 `Metaspace`；处置也不同——堆溢出查对象保留，元空间溢出查类加载器泄漏、动态代理/CGLIB 生成的类是否失控、反射是否泛滥。
- **`GC overhead limit exceeded` 是什么？** —— JVM 发现 GC 时间占比超过 98% 但每次回收不足 2% 堆空间时主动抛出的错误（可用 `-XX:-UseGCOverheadLimit` 关闭，但不推荐）。它通常是「内存几乎全被活对象占据」的信号，处置与堆溢出同源。

**实际工程场景**：告警体系里「老年代占用 monotonically 上升 + Full GC 后不回落」是最典型的泄漏信号；定位流程固定为「直方图找增长类 → dump → MAT 支配树 → 引用链定位代码 → 补 `remove`/注销/设上限」。修复后要观察至少一个完整业务周期确认曲线走平，而不是看一次 GC 通过就完事。

**容易答错的地方**：把两个词当同义词；只说「加内存」；只会说用 MAT 但讲不出支配树和引用链分别回答什么问题；把线程数爆掉的 `unable to create new native thread` 误判成堆问题；不提「排除软/弱/虚引用后看强引用链」这个关键操作。

### Q09：JVM 的内存区域是怎么划分的？ `P0` `高频`

**30 秒回答**：按线程私有与共享分两组：线程私有的有程序计数器、虚拟机栈、本地方法栈；线程共享的有堆、方法区（JDK 8 起实现为元空间）；此外直接内存虽不在 JVM 规范内，却会被 `OutOfMemoryError` 影响。各区域职责不同、溢出行为也不同——栈深超限抛 `StackOverflowError`，堆与元空间容量不足抛 `OutOfMemoryError`。

**深入理解**：

| 区域 | 归属 | 存什么 | 溢出行为 |
| --- | --- | --- | --- |
| 程序计数器 | 线程私有 | 当前执行字节码的行号（Native 方法时为 undefined） | 唯一不会 OOM 的区域 |
| 虚拟机栈 | 线程私有 | 栈帧（局部变量表、操作数栈、动态链接、返回地址） | 栈深超限 → `StackOverflowError` |
| 本地方法栈 | 线程私有 | Native 方法执行上下文 | HotSpot 中与虚拟机栈合并处理 |
| 堆 | 线程共享 | 几乎全部对象实例与数组，GC 主战场 | 容量不足 → `OutOfMemoryError: Java heap space` |
| 方法区 | 线程共享 | 类型信息、常量、静态变量、JIT 代码缓存（JDK 8 起实现为元空间） | `OutOfMemoryError: Metaspace` |
| 直接内存 | 线程共享（非规范区域） | NIO `DirectByteBuffer` 等堆外内存 | `OutOfMemoryError: Direct buffer memory` |

三个必须讲清的版本差异：

- **元空间替代永久代（JDK 8）**：JDK 7 及以前方法区实现为永久代（`-XX:MaxPermSize`，在堆内），类元数据与对象争空间、易 OOM、难以调优；JDK 8 起改为元空间（本地内存，`-XX:MaxMetaspaceSize`，默认几乎无上限）。好处是类元数据不再挤占堆、可按需增长；代价是**不设上限时有耗尽本机内存的风险**，生产必须显式限制。
- **字符串常量池从方法区移到堆（JDK 7）**：永久代回收效率低，`String.intern` 高频调用曾频繁引发永久代 OOM；移到堆后可正常参与 GC，也让运行时常量池的静态结构（如 Class 文件常量池）与方法区其他内容解耦。
- **`StackOverflowError` vs `OutOfMemoryError`**：前者是「栈深度超过单个线程允许的栈帧数」，是**逻辑问题**（递归失控），固定栈大小下必然复现；后者是「动态扩展/新建时拿不到内存」，是**容量问题**。HotSpot 不支持虚拟机栈动态扩展，所以实践中栈几乎只抛 `StackOverflowError`；而「无法创建新 Native 线程」（`unable to create new native thread`）是线程数/内存问题，属于 OOM 家族，不要和栈深混淆。

**为什么这样设计**：私有/共享的划分依据是「生命周期与访问方式」——随线程生死的区域（PC、栈）天然不需要同步，按线程隔离即免锁；堆作为最大且共享的区域，交给 GC 统一管理。元空间外移则是把「随类加载器增减的元数据」从对象堆中剥离，让两类内存各自按需伸缩，避免互相挤占。

**面试官可能继续追问**：
- **为什么程序计数器是唯一不会 OOM 的区域？** —— 它只是一个记录执行位置的计数器，大小固定、没有可增长的数据结构，Native 方法时值为 undefined 甚至不占空间，不存在「存不下」的可能。
- **元空间默认有上限吗？生产怎么设？** —— 默认几乎无上限（受物理内存约束），这正是线上风险：类加载器泄漏 + 动态类生成会让元空间悄悄吃光本机内存。生产应显式设 `-XX:MaxMetaspaceSize`（如 256m~512m），把它变成可控的、可预期的失败点。
- **直接内存 OOM 怎么排查？** —— 看堆外内存监控与 `DirectByteBuffer` 引用；显式设 `-XX:MaxDirectMemorySize` 把不可控变可控；常见泄漏源是 Netty 池化内存未释放、`ByteBuffer` 未走 Cleaner 清理路径。注意 dump 时堆看起来不大，容易误判。
- **JDK 9 模块化后方法区内容变了吗？** —— 规范上方法区仍是运行时数据区之一，实现仍是元空间；变化在类库组织方式（jimage/模块路径），加载来源多了模块系统，三层委派结构与「加载器+全限定名决定类身份」不变。

**实际工程场景**：容器化部署（JDK 10+ 容器感知默认开启）要用容器视角做容量规划——`-Xmx` 只是堆上限，元空间、线程栈、直接内存、JVM 自身开销都在容器 limit 内，堆设太满会把其他区域挤爆；NIO/Netty 服务必须单独监控堆外内存。

**容易答错的地方**：说「方法区就是永久代」——JDK 8 起是元空间，且永久代只是方法区的一种过时实现；说「对象存在栈上」——正常分配在堆，JIT 逃逸分析的栈上分配是优化例外（见 Q15）；说虚拟机栈会抛 OOM——HotSpot 下几乎只有 `StackOverflowError`；回答里完全不提版本。

### Q10：对象创建的过程是怎样的？ `P0` `高频`

**30 秒回答**：六步——类加载检查（`new` 指令引用的类是否已加载）、分配内存（指针碰撞或空闲列表，TLAB 分配 + CAS 防并发）、初始零值、设置对象头、执行 `init` 构造器；字节码层面是 `new`/`dup`/`invokespecial` 三连。

**深入理解**：

1. **类加载检查**：遇到 `new` 字节码，先查常量池中该类的符号引用能否定位、类是否已加载解析，没有则先执行类加载流程（Q12）。
2. **分配内存**：两种方式取决于收集器是否带压缩整理——**指针碰撞**（Serial、ParNew 等整理式收集器，已用/空闲内存各在一侧，指针一拨即可）；**空闲列表**（CMS 等标记-清除式，维护空闲内存块列表再挑选）。并发安全靠两条路：CAS + 失败重试，或 **TLAB**（`-XX:+UseTLAB`，JDK 8 默认开启，线程私有分配缓冲区，本地分配失败才走 Eden 的 CAS 路径）。
3. **初始零值**：实例字段置零值（不含对象头），保证「不赋初值也能访问」——这是实例字段默认值的来源。
4. **设置对象头**：写入 Mark Word、类型指针、数组长度（布局细节见 Q11）。对象头必须先于用户代码就位，因为 GC 标记与锁状态都依赖它。
5. **执行 `init`**：按程序员意愿初始化——字段显式赋值与构造器代码合并执行，这是对象真正「可用」的时刻。

字节码视角（`new Foo()`）：

```java
new  Foo          // 申请内存，引用入栈；此时对象未初始化，还不能用
dup               // 复制栈顶引用（invokespecial 与 astore 都要消耗一个引用）
invokespecial Foo.<init>  // 调用实例构造器 <init>，不是 <clinit>
astore_1          // 存局部变量
```

**为什么这样设计**：先零值、再设对象头、最后才执行用户构造代码，是为了让「对象头」成为并发安全的地基——GC 标记、锁状态、身份哈希都记在对象头里，必须先于任何用户可见的状态存在。TLAB 则是用少量空间浪费（线程间分配不均衡的碎片）换分配路径的无锁化——绝大多数分配变成纯本地操作，这是对象分配吞吐能跟上半 T 级业务的前提。

**面试官可能继续追问**：
- **指针碰撞和空闲列表分别对应哪些收集器？** —— 有压缩整理的用指针碰撞（Serial、ParNew、G1 的复制阶段）；CMS 标记-清除产生碎片，必须用空闲列表。选哪种由「GC 后内存是否连续」决定，不是配置项。
- **TLAB 是什么，什么时候会失效？** —— 线程私有的 Eden 缓冲区，对象在 TLAB 内分配无需同步；TLAB 剩余空间不足或对象过大时走 Eden 共享区的 CAS 分配，仍失败则触发 GC 评估。可用 `-XX:+PrintTLAB` 观察（调试用途）。
- **`dup` 为什么必须存在？** —— `invokespecial` 会消耗一个对象引用，而构造函数执行完后还要把引用存入局部变量表，两个消费者各需一份，所以 `new` 之后先 `dup` 复制栈顶。答不出这一条，说明字节码层面只是背过。
- **`new` 出来的对象一定在堆上吗？** —— 不一定。逃逸分析生效时，不逃逸的对象可能被标量替换（拆成字段根本不存在对象）或栈上分配（Q15）；此外 `clone`、反序列化、`Unsafe.allocateInstance` 走的都不是 `new` 这条路径。

**实际工程场景**：高分配速率服务的关注点不是「分配慢」而是「分配得太快引发 GC」——监控 Eden 区填充速率、YGC 频率比监控对象创建本身更有意义；TLAB 参数极少需要动，默认值已适配绝大多数负载；真正的分配优化在代码层（复用对象、缓冲池、减少临时大对象）。

**容易答错的地方**：把对象构造器 `<init>` 说成类初始化 `<clinit>`；说所有对象都在堆（忽略逃逸分析）；答不出 `dup` 的作用；只说「CAS 保证线程安全」而讲不出 TLAB 这条主路径——后者才是默认情况下大多数分配的真实路径。

### Q11：对象的内存布局是怎样的？ `P1` `高频`

**30 秒回答**：三部分——对象头（Mark Word 存哈希码、GC 年龄、锁状态，外加类型指针，数组对象还有长度字段）、实例数据（字段本身）、对齐填充（8 字节对齐的补位）。开启压缩指针后类型指针占 4 字节，普通对象头为 12 字节，`new Object()` 在 64 位 VM 下是 16 字节。

**深入理解**：

- **Mark Word（8 字节）**：非固定结构，随锁状态复用同一份空间——无锁（身份哈希码 31 位 + GC 年龄 4 位 + 标志位）、偏向锁（线程 ID）、轻量级锁（指向栈中锁记录的指针）、重量级锁（指向监视器的指针）、GC 标记。这是「一个字段按状态复用多种语义」的典型设计。
- **类型指针（4 或 8 字节）**：指向类元数据，用于 `instanceof`、方法分派。开启压缩指针（`-XX:+UseCompressedOops`，JDK 8 对 32GB 以下堆默认开启）时占 4 字节；关闭则 8 字节。
- **数组长度（4 字节）**：仅数组对象有，压缩指针下 4 字节。
- **实例数据**：默认策略是父类字段在前、相同宽度的字段聚在一起，减少 padding 浪费。
- **对齐填充**：64 位 VM 下对象大小必须 8 字节对齐，JVM 用 padding 补足；这也是对象实际占用常比字段总和大的原因。

可用 JOL（OpenJDK 的 JOL 工具）直接打印验证：

```java
// 依赖 jol-core
ClassLayout.parseInstance(new Object()).toPrintable();
// 64 位 + 压缩指针：mark 8 + klass 4 + padding 4 = 16 字节
```

**为什么这样设计**：Mark Word 复用是为了省内存——锁状态与身份哈希不会同时出现，固定结构会浪费一半以上空间；压缩指针则是 64 位下的必然选择：对象 8 字节对齐意味着低 3 位恒为 0，32 位 oop + 零基址即可寻址 32GB（2^32 × 8B），用 4 字节指针换来接近 32 位 VM 的内存密度，是「拿一点 CPU 换算术成本省一半指针内存」的取舍。

**面试官可能继续追问**：
- **哈希码存在哪，什么时候计算？** —— 存在 Mark Word，第一次调用 `identityHashCode()` 时惰性生成，之后不变；GC 移动对象或加锁时会把旧 Mark Word 内容「置换」到其他位置（ displaced ），保证信息不丢。
- **GC 年龄为什么最大是 15？** —— Mark Word 里年龄只占 4 位（0~15），这就是默认 `MaxTenuringThreshold=15` 的物理来源，不是随意定的配置。
- **压缩指针的 32GB 上限怎么来的？** —— 压缩后 oop 占 32 位，堆基址为 0 且对象 8 字节对齐，可编码寻址范围是 2^32 × 8B = 32GB；超过后 JVM 自动关闭压缩指针（堆超过 32GB 后指针回到 8 字节，内存占用明显上升）。
- **字段为什么被重排序？** —— 默认分配策略把同宽度字段（如 long/long、int/int）聚在一起，避免不同宽度字段交错造成的 padding 空洞，是纯内存密度的优化。

**实际工程场景**：评估缓存/集合的内存占用时，「一个对象多大」必须按对齐后的实际值算——估算偏差 20% 很常见；大字段密集的 DTO 值得用 JOL 验证布局；开启/关闭压缩针对内存占用的影响在容量规划时要计入（> 32GB 的堆尤其要意识到指针成本翻倍）。

**容易答错的地方**：背「对象头 16 字节」这个固定答案而不问是否开压缩指针（开了是 12 字节 + padding，`Object` 合计 16 字节；不开是 16 字节头，`Object` 合计 24 字节）；说哈希码每次调用重新计算；漏掉数组对象的长度字段；不知道 JOL 可以直接验证。

### Q12：类加载的过程是怎样的？ `P1` `高频`

**30 秒回答**：五个阶段——加载（字节流变成方法区里的运行时数据结构）、验证（字节码合法性检查）、准备（静态变量分配内存并赋零值）、解析（符号引用转直接引用）、初始化（执行 `<clinit>`，静态变量赋程序员设定的初值、执行静态块）；各阶段交叉进行，初始化只在「主动使用」时触发。

**深入理解**：

| 阶段 | 做什么 | 关键点 |
| --- | --- | --- |
| 加载 | 通过全限定名获取字节流（文件/网络/动态代理/自定义），转为方法区运行时结构，生成 `Class` 对象 | 双亲委派发生在这一阶段（Q03） |
| 验证 | 文件格式、元数据、字节码、符号引用四类校验 | 防止恶意/损坏字节码；JDK 版本演进会调整校验规则（如 nestmate 访问控制） |
| 准备 | 为**类变量（静态变量）**分配内存并置零值 | `public static int v = 123` → 准备后是 0；`final static` 常量编译期入常量池（`ConstantValue`），准备后即终值 |
| 解析 | 符号引用（`CONSTANT_Class` 等字面描述）替换为直接引用（内存地址/偏移） | 发生时机在「首次被使用前」，可能在初始化之后（晚期绑定） |
| 初始化 | 执行 `<clinit>`：合并所有类变量赋值与静态块，父类先初始化 | 触发条件是主动使用，不是「加载完成就初始化」 |

**准备 vs 初始化**是本題最常被追问的点：准备只给类变量零值（无需执行代码），初始化才执行用户设定的初值——所以准备阶段之后 `v` 是 0，`<clinit>` 执行后才是 123。

**主动使用触发初始化的六类场景**：`new`/设置/读取静态字段/调用静态方法（`new`、`getstatic`、`putstatic`、`invokestatic`）、反射调用、初始化子类时先初始化父类、启动主类（`main`）、`MethodHandle`/`LambdaMetafactory` 等解析场景。**被动使用不会触发**：通过子类访问父类静态字段、声明引用数组、访问编译期常量（已入常量池）。

阶段并非严格串行：加载与验证可能交叉、解析可能延迟到初始化后（`invokedynamic`、接口方法的晚期绑定），这是「类生命周期是过程而非流水线」的关键。

**为什么这样设计**：准备阶段只赋零值，是因为「对象可被访问前字段必须有确定值」，而零值是唯一不需要执行代码就能保证的默认值；真正执行用户代码被推迟到初始化，并由 JVM 保证 `<clinit>` 的类初始化锁（线程安全、只执行一次）。把「零值」与「初值」分开，让类在加载后立刻处于可标记、可 GC 的一致状态，而不必等用户代码执行完。

**面试官可能继续追问**：
- **类初始化是线程安全的吗？** —— 是。JVM 用类初始化锁保证 `<clinit>` 只被一个线程执行一次，其他线程阻塞等待；代价是初始化死循环会让所有访问该类的线程一起卡住。
- **接口和类的初始化规则有区别吗？** —— 接口初始化时不要求父接口全部完成初始化（只有真正用到父接口的成员才触发）；接口没有 `<init>`，只有默认方法的类文件级结构。
- **类什么时候被卸载？** —— 同时满足：该 `Class` 对象不可达、其类加载器不可达、无实例存活。元空间里类元数据随加载器一起回收——这也是类加载器泄漏会顶爆元空间的原因（Q08）。
- **双亲委派在哪个阶段生效？** —— 加载阶段。`loadClass` 的流程是 `findLoadedClass`（已加载直接返回）→ 委托 parent → 都失败才 `findClass` 自己加载，所以「同一个类只加载一次」的保证建立在委派链 + 缓存之上。

**实际工程场景**：热部署/插件靠自定义加载器实现「换一份字节码 = 换一个 `Class`」；启动加速可用 AppCDS 把类元数据归档（JDK 10+ 默认包含核心库，JDK 12+ 支持动态归档）；动态代理、Lambda、JSP 编译都靠运行期生成类，海量动态类要盯元空间（Q13 的 `MaxMetaspaceSize`）。

**容易答错的地方**：说静态变量在准备阶段就赋成 123（那是 `final` 常量的特例）；说解析一定在初始化前（晚期绑定场景不是）；把 `<clinit>`（类初始化）和 `<init>`（实例构造器）混为一谈；以为加载完成就万事俱备——初始化是懒触发的。

### Q13：常用的 JVM 参数有哪些？ `P1` `高频`

**30 秒回答**：分四类——内存（`-Xms`/`-Xmx`/`-Xmn`、`-XX:SurvivorRatio`、`-XX:MaxMetaspaceSize`）、GC（`-XX:+UseG1GC`、`-XX:MaxGCPauseMillis`、`-XX:MaxTenuringThreshold`）、诊断（`-Xlog:gc*`（JDK 9+）、`-XX:+HeapDumpOnOutOfMemoryError`、`-XX:HeapDumpPath`）、其他（`-XX:+UseCompressedOops`、`-XX:MaxDirectMemorySize`）。生产设 `-Xms=-Xmx` 是为了避免堆动态扩缩带来的抖动。

**深入理解**：

```bash
# 一份可作起点的接口类服务模板（JDK 17，按容量调整）
-Xms4g -Xmx4g                          # 初始=最大，消除扩缩抖动
-XX:MaxMetaspaceSize=512m              # 元空间显式上限（默认无上限，必须设）
-XX:+UseG1GC -XX:MaxGCPauseMillis=200  # 收集器与停顿软目标
-XX:MaxTenuringThreshold=15            # 晋升阈值，可按 Q04 策略调整
-Xlog:gc*:file=gc.log:time,uptime,level,tags:filecount=5,filesize=100m  # GC 日志带轮转
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/logs/dump/  # OOM 自动 dump
```

逐个说明取舍：

- **`-Xms`/`-Xmx` 设等值**：堆扩缩要向 OS 申请/归还内存，伴随系统调用、内存抖动和停顿峰值；等值后「可用上限确定」，容量规划、监控阈值、GC 行为全部可预期。代价是启动即占满，容器里要配合 limit 留出堆外余量。
- **`-Xmn`**：固定新生代大小；G1 下不建议设——Region 自动管理各代占比，强行指定破坏自适应调整。
- **`-XX:SurvivorRatio`**：Eden 与单个 Survivor 的比例（默认 8），影响 Minor GC 频率与对象过早晋升（Q04）。
- **`-XX:MaxTenuringThreshold`**：晋升阈值，默认 15，也是 Mark Word 年龄 4 位上限。
- **`-XX:+UseG1GC`**：JDK 9 起服务器场景默认；JDK 8 默认仍是 Parallel GC；ZGC 是 `-XX:+UseZGC`（JDK 11 实验、JDK 15 起生产可用，见 Q14）。**默认收集器必须带版本回答**。
- **`-Xlog:gc*`（JDK 9+）**：统一日志框架（JEP 158/271）替代 `PrintGCDetails`/`PrintGCDateStamps`/`PrintGC` 等零散参数，支持 level/tag 过滤、文件输出与轮转。JDK 8 仍用老参数——这是版本差异的高频追问点。
- **`HeapDumpOnOutOfMemoryError` + `HeapDumpPath`**：OOM 瞬间自动 dump。没有它，进程退出/回收后现场基本丢失，dump 是事后定位泄漏的唯一直接证据（Q08）。
- **`-XX:+DisableExplicitGC`**：屏蔽 `System.gc()`，避免 RMI 等场景的意外 Full GC，生产常开。
- **`-XX:MaxDirectMemorySize`**：直接内存上限（默认约等于堆大小），NIO/Netty 服务应显式控制（Q09）。

**为什么这样设计**：`-Xms=-Xmx` 的本质是「把不可预期的动态成本换成确定的静态占用」——动态扩容在稳态服务里只有成本没有收益（峰值前的扩容反而增加停顿），确定上限则让监控告警、GC 策略、容量规划都建立在不变量的基础上。GC 日志与 OOM dump 参数则是「为事后可分析留证据」——没有日志的线上 GC 问题只能靠猜。

**面试官可能继续追问**：
- **容器里 `-Xmx` 怎么设？** —— JDK 10+ 容器感知默认开启（`UseContainerSupport`），JVM 自行识别容器 limit；实践是 limit 的 60%~75% 左右，给元空间、线程栈、直接内存、JVM 自身和 OS 缓存留余量，并显式设 `MaxMetaspaceSize` 把元空间变成可控失败点。
- **`-Xlog` 和老参数什么关系？** —— JDK 9 统一日志取代老参数，老参数被废弃；`-Xlog:gc*` 的星号是 tag 通配，`gc*` 覆盖所有 gc 相关 tag；需要时用 `-Xlog:disable -Xlog:gc` 之类做精细开关。
- **OOM dump 为什么必须提前配上？** —— OOM 时进程随时退出，现场（存活对象与引用链）转瞬即逝；dump 文件 + GC 日志是事后用 MAT 定位持有者的唯一材料。事后补参数复现不了当时的堆。
- **`UseCompressedOops` 还要手动开吗？** —— JDK 8 起 32GB 以下堆默认开启，通常不用管；堆超过 32GB 自动关闭，此时要意识到指针成本翻倍对内存占用的影响（Q11）。

**实际工程场景**：启动参数按业务类型模板化（低延迟接口 / 高吞吐计算 / 内存受限三类），模板 + 灰度 + 指标对比是 Q17 的落地形式；任何参数改动进变更记录，防止「谁随手加了个 `-Xmx`」导致排查时基线对不上。

**容易答错的地方**：只背参数名不讲为什么（尤其 `-Xms=-Xmx`）；JDK 8/9 混用日志参数；以为元空间默认有上限；以为 `-Xmx` 可以顶到机器物理内存（容器与堆外内存都会被挤爆）；G1 下还设 `-Xmn`。

> 权威内容：JVM 参数体系当前尚未在仓库建设，可参考 Oracle 官方 HotSpot JVM Options 文档与《深入理解 Java 虚拟机（第 3 版）》调优章节。

### Q14：ZGC 的原理和适用场景是什么？ `P1` `中频`

**30 秒回答**：ZGC 用染色指针、读屏障和并发转移，把绝大多数 GC 工作放到并发阶段，停顿时间与堆大小基本无关（毫秒级以下），适合大堆低延迟场景；JDK 21 起有分代 ZGC，进一步降低堆开销、提升吞吐。

**深入理解**：三个核心机制：

- **染色指针**：从 64 位指针高位借几位做颜色位（Marked0/Marked1、Remapped 等），标记信息直接编码在指针上——**不需要移动对象、不需要改对象头就完成标记与转移状态的记录**，这是停顿与堆大小解耦的关键。
- **读屏障**：读一个引用时检查颜色位，若指向「已转移但指针未更新」的对象，由读屏障现场修正（self-healing）并传播修正。代价是每次读引用都要过屏障，吞吐略有损失（典型负载下百分之几到十几，视读密集程度）。
- **并发转移**：对象转移与用户线程并发进行，旧地址保留转发记录；转移完成后旧区域可整体回收，不产生 CMS 式碎片。

版本线必须讲清：JDK 11 引入（JEP 333，实验性）→ JDK 15 生产可用（JEP 377）→ JDK 17 完善（超大堆、动态 GC 线程数）→ JDK 21 分代 ZGC（JEP 439，年轻代/老年代分别管理）。**JDK 8 没有 ZGC**，说「我们线上用 ZGC」必须带版本。

**与 G1 的取舍**（不讲绝对化结论）：G1 停顿随堆增大而增长（大堆下数百毫秒常见），但生态成熟、参数体系完整、吞吐损失小；ZGC 停顿基本恒定（亚毫秒到毫秒级，与堆大小弱相关），但读屏障带来吞吐开销、可观测性与工具链相对新。经验分界：中等堆（数 GB）且延迟要求宽松 → G1 足够；大堆（8GB 以上，尤其几十上百 GB）+ 延迟硬指标（P99 停顿个位数毫秒）→ 评估 ZGC；极小堆 → 单代 ZGC 的优势发挥不出来，甚至可能不如 G1/Parallel。

**为什么这样设计**：传统 GC 要把「标记-清理」结果落到对象头/位图，根枚举与转移都必须在停顿内完成，停顿自然与堆大小挂钩。染色指针把标记状态搬进指针、并发转移把搬对象也并发化，STW 只剩「根集合的快速枚举与修正」——停顿只与根集合规模弱相关，与堆总量基本脱钩。代价是读屏障的常驻开销，用吞吐换停顿。

**面试官可能继续追问**：
- **染色指针和记忆集/卡表是什么关系？** —— 单代 ZGC 不做分代回收，不需要跨代引用记录，靠染色指针并发标记即可；分代 ZGC（JDK 21+）才引入类似记忆集的结构跟踪跨代引用。这是 ZGC 写屏障比 G1 轻的原因。
- **读屏障开销到底多大？** —— 取决于引用读取的密度。读多写少的负载（典型业务读链路）大部分命中已修正指针走快路径，实测吞吐损失多在个位数到十几个百分点；极度读密集且延迟不敏感的计算型负载上，这个代价可能不值得。
- **ZGC 完全不停顿吗？** —— 不是。仍有初始标记、再标记等短暂 STW，只是时长与堆大小基本无关（实践中受 GC Roots 规模影响）。面试答「零停顿」会被追问打穿。
- **从 G1 迁 ZGC 要注意什么？** —— 灰度验证：同负载对比停顿 P99、吞吐、堆外行为；确认 JDK 版本 ≥ 15（生产可用）；关注新版工具链（jcmd、GC 日志格式、JFR 事件）的适配；预留回滚参数。

**实际工程场景**：典型候选是大堆低延迟的网关、交易、风控类服务——堆十几个 GB 以上、接口 RT 敏感、G1 停顿已到瓶颈；迁移决策依据是实测数据（停顿分布、吞吐损失）而非「ZGC 是新所以更好」。中小堆服务盲目上 ZGC 常常白付吞吐成本。

**容易答错的地方**：说 ZGC「零停顿/完全并发」；不讲版本（JDK 11 是实验特性，生产至少 JDK 15）；把染色指针讲成「移动对象时改指针指向」而不提颜色位与读屏障的自修正；结论绝对化（「ZGC 一定比 G1 好」）而不谈吞吐代价与堆大小前提。

> 权威内容：ZGC 原理与版本演进当前尚未在仓库建设，可参考 JEP 333、JEP 377、JEP 439 与 Oracle ZGC 官方指南。

### Q15：JIT 编译和分层编译是怎样的？ `P2` `中频`

**30 秒回答**：HotSpot 采用解释器 + C1（快速编译）+ C2（深度优化）的分层编译：代码先解释执行，方法调用与循环回边计数到阈值触发 C1 编译，热度更高再升级 C2；优化手段包括方法内联、逃逸分析（栈上分配、标量替换、锁消除），假设失效时去优化回退。

**深入理解**：

- **层级**：0 层解释执行；1~3 层 C1（不同优化档位）；4 层 C2。`-XX:+TieredCompilation` 在 JDK 7 之后的 server VM 默认开启（JDK 8 起默认）。
- **热点探测**：方法调用计数器 + 回边计数器（循环），热度衰减后计数回落；阈值由 `-XX:CompileThreshold` 等控制。
- **OSR（栈上替换）**：大循环热度达标时，不等方法返回就把执行中的循环替换成编译后代码——解决「长循环方法整体没被编译」的问题。
- **方法内联**：把被调方法体展开到调用点，是去虚拟化、常量传播等优化的前提；受方法体积与 `-XX:MaxInlineSize` 等限制，接口多实现时内联带守卫（guard）。
- **逃逸分析**（`-XX:+DoEscapeAnalysis`，JDK 8 默认开启）：对象不逃逸出方法 → 标量替换（拆成字段，对象根本不存在）或栈上分配；锁不逃逸出线程 → 锁消除。这是 Q10「对象一定在堆上吗」的理论依据。
- **去优化（deopt）**：内联假设失效（如 CHA 记录的唯一实现后来被加载出新子类）、类型假设失效、栈上分配对象逃逸——编译代码被标记 not entrant，执行回退到解释器。这是动态优化必须保留的「安全出口」。
- **Graal**：JDK 9 起可选的 JVMCI 编译器（JDK 16+ 可用 `-XX:+UseJVMCICompiler` 启用），优化能力与编译架构不同于 C2；GraalVM 原生镜像是另一个话题（启动换 AOT，失去部分运行时 profile 优化）。

**为什么这样设计**：解释执行启动快但慢，C2 优化强但编译本身耗时；分层编译让「启动期用解释 + C1，稳态用 C2」，兼顾启动延迟与峰值性能，是「按需付费」在编译期的体现。去优化则是对「运行时 profile 驱动的激进优化」的必然配套——优化越激进，假设越多，必须允许失效回退，这是 C2 敢做内联的前提。

**面试官可能继续追问**：
- **为什么说「Java 比 C++ 慢」是过时结论？** —— 稳态下 JIT 能基于真实运行时 profile 做静态编译做不到的去虚拟化、针对性内联；短时运行的微场景才是解释执行占比高的场景。但启动期与预热期劣势真实存在，Serverless 场景明显。
- **OSR 解决什么问题？** —— 热点可能在循环而不在方法入口——方法整体调用次数不够、永远轮不到编译，但循环体执行了百万次。OSR 允许在循环回边直接替换为编译代码。
- **内联的主要限制是什么？** —— 方法体大小（超过 `MaxInlineSize` 不内联）、虚方法的去虚拟化依赖 CHA 只有单一目标实现（多实现时内联带运行时守卫，守卫失败即去优化）、递归调用不内联。
- **这对写基准测试有什么要求？** —— 必须用 JMH：防止死代码消除、常量折叠、循环展开让「假快」的结果失真，并强制预热让 JIT 达到稳态再采样。手写 `System.nanoTime()` 循环测出来的数没有参考价值。

**实际工程场景**：性能压测必须充分预热后再采数（否则测到的是解释执行）；「某接口突然变慢」的可能原因之一是去优化或编译线程饥饿；对启动延迟敏感的服务考虑 AppCDS、类数据共享，或评估 Graal 原生镜像（牺牲部分峰值性能换启动）。

**容易答错的地方**：说 C1 和 C2 并行编译同一份代码（两者是不同层级管线，编译线程数由 `CICompilerCount` 控制，分层模式默认一个 C1 线程池 + 两个 C2 线程）；说逃逸分析默认关闭；不知道 OSR 与 deopt；忽略 JMH——微基准不用 JMH 等于没测。

> 权威内容：JIT 编译与分层编译当前尚未在仓库建设，可参考《深入理解 Java 虚拟机（第 3 版）》第 11 章与 Oracle Java 性能调优指南。

### Q16：JVM 监控和诊断工具有哪些？ `P1` `高频`

**30 秒回答**：命令行有 jps/jstat/jinfo/jmap/jstack/jcmd（含 JFR 录制），交互式诊断用 Arthas，火焰图用 async-profiler，持续监控用 JMX + Prometheus + Grafana（或 Micrometer），离线堆分析用 MAT。使用原则是「先看监控确认现象，再轻量采集，dump 类操作放最后」。

**深入理解**：

| 工具 | 典型用途 | 侵入性 |
| --- | --- | --- |
| `jps` | 列出 JVM 进程与主类/启动参数 | 无 |
| `jstat` | `jstat -gcutil <pid> 1000` 看各区占比、GC 次数与耗时增量 | 无 |
| `jinfo` | 查看/调整运行中的 VM flag（`jinfo -flag`） | 低 |
| `jmap` | `-histo[:live]` 对象直方图；`-dump` 生成堆 dump | 高（live 会触发 Full GC，大堆 dump 有长停顿） |
| `jstack` | 线程栈，定位死锁/线程状态分布 | 低（Java 21 起可用 `jcmd Thread.print` 替代） |
| `jcmd` | 统一入口：`Thread.print`、`GC.class_histogram`、`GC.heap_dump`、`VM.uptime`、`JFR.start/stop` | 视子命令 |
| Arthas | `trace`/`watch`/`monitor` 观测方法入参返回值耗时，`jad` 反编译，`thread` 看线程，`ognl` 表达式 | 低（线上首选） |
| async-profiler | CPU/alloc/lock/wall 火焰图，低开销采样 | 低 |
| JFR + JMC | 低开销持续记录（分配、锁、GC、方法采样），JDK 11 起开源 | 低 |
| JMX + Prometheus + Grafana | MBean 指标持续采集与看板（堆、GC、线程、类加载、直接内存） | 无（持续） |
| MAT | 支配树、泄漏嫌疑报告、Path to GC Roots、OQL 查询 | 离线 |

**为什么这样设计**：这套工具组合覆盖的是「采集成本的分层」——`jstat`/`jstack`/JFR 几乎无侵入，适合随时采；`jmap -dump` 有 STW 与磁盘成本，必须挑时机；MAT 是离线重型分析。排查流程因此固定为「监控看板发现异常 → 轻量采集定位方向 → 必要时重量 dump 留证」，这与 Q01/Q02 的排查顺序是同一条原则：先用最廉价的证据缩小范围。

**面试官可能继续追问**：
- **`jmap -dump` 和 `jcmd GC.heap_dump` 怎么选？** —— 两者都触发 STW 并把全堆写盘，大堆下停顿可达数秒到数十秒；`jcmd` 是推荐入口（统一、可脚本化）。生产应配合 OOM 自动 dump（Q13），避免在高峰期手动 dump。
- **`jstat -gcutil` 重点看哪几列？** —— O（老年代占比）持续接近上限 → 老年代压力/泄漏信号；FGC 次数与 FGCT 增量 → Full GC 频率与累计耗时；YGC 与 YGCT 的比值 → 单次 Minor GC 平均耗时；E 区的填充速度反映分配速率。
- **Arthas 比 jstack 强在哪？** —— 能观测「方法级」事实：入参/返回值/异常（`watch`）、调用链路与耗时（`trace`）、方法内部 QPS/RT（`monitor`），还能反编译确认线上跑的版本。定位「哪段代码在耗 CPU」比纯栈采样更直接。
- **火焰图能回答什么问题？** —— on-CPU 火焰图看哪个方法占 CPU（配合 Q01 线程栈使用）；alloc 火焰图看分配热点（配合 Q02 的「分配太快」分支）；off-CPU/lock 火焰图看阻塞与锁竞争——一张图对应一类假设。

**实际工程场景**：告警 + 看板是前提（堆占用率、GC 停顿 P99、FGC 频率、线程数、元空间、直接内存）；线上问题按「Arthas/jstack 轻量定位 → 保留现场（jfr + 按需 dump）→ 修复验证」推进；保留现场的标准化动作应写进应急手册，否则每次事故都在临时想该采什么。

**容易答错的地方**：只罗列工具名，讲不出选择顺序与侵入性差异；不知道 dump 类操作有 STW/磁盘成本，张口就是「先 jmap dump」；不提 Arthas/JFR 这些现代工具；把 MAT 说成实时监控工具（它是离线分析器）。

> 权威内容：JVM 监控与诊断工具当前尚未在仓库建设，可参考 Arthas 官方文档与 OpenJDK JDK Tool Specifications。

### Q17：JVM 调优你怎么做？ `P1` `高频`

**30 秒回答**：先定目标（延迟优先还是吞吐优先、内存预算多少），再按「监控发现瓶颈 → 形成假设 → 小步验证 → 固化参数」的闭环走；没有万能的参数模板，每次只改一个变量，用数据判断效果。

**深入理解**：调优流程四步：

1. **目标先行**：延迟敏感（接口类）→ G1/ZGC + 停顿目标，关注停顿分位数；吞吐优先（离线计算、批处理）→ Parallel GC，关注吞吐量；内存受限 → 小堆 + 防 OOM 策略 + 压缩指针。目标不同，同一现象的最优解相反。
2. **监控发现瓶颈**：GC 日志与看板确认现象——停顿长？FGC 频繁？分配速率过高？老年代只涨不落？先有事实再有动作。
3. **形成假设并单变量验证**：例：假设「新生代偏小导致短命对象过早晋升，老年代被撑爆 → FGC 频繁」，则只调 `-Xmn`/`SurvivorRatio`/`MaxTenuringThreshold` 之一，同负载对比 FGC 频率、停顿 P99、吞吐。
4. **固化**：验证有效则写进启动模板与文档，纳入变更记录，防止被随意改回去。

两个完整案例：

- **案例一：GC 频繁调新生代与晋升阈值。** 现象：每天 20+ 次 Full GC，接口 P99 毛刺。日志显示 YGC 后老年代增量 ≈ 大部分存活对象、`Survivor` 占用高——对象「活不过一次 Minor GC」被动态年龄判定直接晋升（Q04）。根因：新生代 256MB 偏小、Survivor 被压得过小。动作：`-Xmn` 提到 1G 并调整 SurvivorRatio，让中等寿命对象留在 Survivor 熬过阈值。结果：FGC 降到每周 1~2 次，停顿 P99 从数百毫秒降到几十毫秒。**注意：如果老年代里是常驻缓存，这个解法无效——先按 Q02 分桶。**
- **案例二：CPU 飙高定位正则回溯/死循环。** 现象：CPU 100%，RT 同步劣化。按 Q01 顺序：`top` 看 `us` 高 → `top -Hp` 找热点线程 → 十六进制线程号匹配 `jstack` 栈顶——停在 `Pattern` 匹配/回溯的调用栈上。根因：热点路径用了灾难性回溯的正则且未预编译 `Pattern`。动作：改代码（预编译 + 修正正则），不调任何 JVM 参数。**结论：分清「JVM 问题」和「代码问题」是调优的第一道分水岭。**

**为什么这样设计**：「一次只改一个变量」是实验方法的基本要求——JVM 参数高度耦合（新生代大小同时影响 GC 频率、晋升速率、停顿时长；元空间影响类卸载），同时改多个参数会让效果无法归因，下次遇到同类问题也没有可复用的结论。「目标先行」是因为延迟与吞吐本质是取舍关系：停顿目标压得越狠，GC 越频繁、吞吐损失越大；没有先定的优先级，所谓「调优」只是随机游走。

**面试官可能继续追问**：
- **怎么判断一次调优真的有效？** —— 先定基线指标（FGC 频率、停顿 P99/P99.9、QPS、接口 RT），同一负载下对比；观察周期要覆盖完整业务周期（日峰值、定时任务），只看一次 GC 通过说明不了问题。
- **延迟和吞吐能同时优化吗？** —— 有取舍，不是无代价双赢：G1 把 `MaxGCPauseMillis` 设得极小的代价是 GC 更频繁、吞吐下降。先明确业务优先级，再在约束下找平衡点。
- **什么情况不该动 JVM 参数？** —— 代码层问题（正则回溯、无界缓存、ThreadLocal 未 remove、锁粒度过粗）——调 JVM 只是把发作推后；架构问题（单机容量、下游瓶颈）——JVM 参数无能为力。先修代码和架构，再谈参数。
- **生产改参数的安全动作是什么？** —— 灰度环境先验证同负载指标；保留旧参数可一键回滚；改动记录（改了什么、为什么、对应指标）进变更系统；避免在事故应急中凭感觉改多个参数——那会让事后复盘失去归因能力。

**实际工程场景**：启动参数模板化（低延迟接口/高吞吐计算/内存受限三类），模板由数据校准而非网上抄；调优结论（含失败的尝试）写进团队 wiki，形成「假设 → 实验 → 结论」的积累；容器环境下容量规划要整体看（堆 + 元空间 + 直接内存 + 线程栈 + OS），单看 `-Xmx` 会误判。

**容易答错的地方**：把调优等同于「调参数」而忽略代码与架构层；一次改多个参数；张口就是「万能模板/最佳实践」；只说调了什么不说怎么验证有效；案例只讲参数不讲现象与数据的对应关系——没有数据的案例在面试里不算案例。

> 权威内容：JVM 调优方法论当前尚未在仓库建设，可参考《Java 性能权威指南》与《深入理解 Java 虚拟机（第 3 版）》调优案例章节。

### Q18：垃圾回收算法有哪几种？分代收集是怎么回事？ `P0` `原理`

**30 秒回答**：基础算法只有三种——标记-清除、标记-复制、标记-整理，区别全在「回收后内存连不连续」和「要不要搬对象」；实际 JVM 按分代假设把三者组合使用：新生代存活率低所以用复制（Eden + 2 Survivor，8:1:1），老年代存活率高所以用标记-清除或标记-整理。收集器是这套组合的具体实现，**算法是零件，收集器是整机**。

**深入理解**：

| 算法 | 做法 | 优点 | 代价 | 典型使用者 |
| --- | --- | --- | --- | --- |
| 标记-清除 | 标记存活对象，直接清除未标记对象 | 实现简单，不移动对象 | 产生内存碎片；分配要走**空闲列表**；碎片累积后大对象可能提前触发 Full GC | CMS 的老年代 |
| 标记-复制 | 内存分成两块，存活对象复制到空闲块，整块清空原块 | 无碎片；分配用**指针碰撞**；只扫存活对象 | 可用内存减半（新生代用 Eden + 2 Survivor 缓解）；存活率高时复制成本爆炸 | Serial / ParNew / Parallel Scavenge；G1 的 Region 间疏散 |
| 标记-整理 | 标记后把存活对象向一端移动，清理边界外 | 无碎片，也不浪费空间 | 移动对象要更新所有引用，STW 最长 | Serial Old、Parallel Old |

三个必须串起来的机制：

- **可达性分析**：判断对象是否存活的前置步骤，根集合与实现细节见 [Q05](#q05gc-roots-有哪些可达性分析是怎么做的-p0-高频)。
- **分代假设**：弱分代假说（绝大多数对象朝生夕灭）+ 强分代假说（熬过越多次 GC 的对象越难死）。两条假设直接推出「新生代用复制、老年代用标记-清除/整理」的组合。对象晋升的四条路径见 [Q04](#q04哪些对象会进入老年代-p1-高频)。
- **并发标记的额外代价**：三色标记（白=未访问、灰=引用未扫完、黑=引用扫完）在并发标记时可能漏标，需要同时满足两个条件——黑色对象新增了指向白色对象的引用，且原本指向该白色对象的灰色引用被删除。CMS 用**增量更新**（写屏障记录新增引用，之后重新扫描），G1 用**原始快照 SATB**（记录被删除的旧引用，按快照标）。这是独立于三种基础算法的第二层技术。

收集器与算法的对应关系（**混答这一层是最常见的扣分点**）：

| 收集器 | 作用区域 | 核心算法 | 版本边界 |
| --- | --- | --- | --- |
| Serial / Serial Old | 新生代 / 老年代 | 复制 / 标记-整理 | 单线程，客户端与小堆场景仍在用 |
| ParNew | 新生代 | 复制 | Serial 的多线程版，曾是 CMS 的搭档 |
| Parallel Scavenge / Parallel Old | 新生代 / 老年代 | 复制 / 标记-整理 | **JDK 8 默认**，吞吐优先 |
| CMS | 老年代 | 标记-清除 | JDK 9 弃用，**JDK 14 移除**；碎片、并发模式失败、浮动垃圾 |
| G1 | 整堆按 Region | 局部复制 + 整体标记-整理语义 | JDK 7 引入，**JDK 9 起默认** |
| ZGC | 整堆 | 并发标记-复制（染色指针 + 读屏障） | JDK 11 实验，**JDK 15 生产可用**，JDK 21 分代 |

**为什么这样设计**：复制算法的成本与**存活对象数量**成正比，所以它天然适配「死得多、活得少」的区域；标记-清除/整理不搬或少搬对象，适配存活率高的老年代。分代不是为了概念完整，而是让每一种算法的成本落在它最便宜的地方。

**面试官可能继续追问**：
- **新生代为什么用复制，老年代为什么不用？** —— 新生代存活率通常不到 10%，复制成本低；老年代复制等于把大半堆搬一遍，还可能触发连锁晋升。判断依据只有一条：这次回收后要搬多少对象。
- **CMS 和 G1 的并发标记为什么解法不同？** —— 破坏漏标两个条件中的任意一个即可。增量更新破坏「新增引用」条件，代价是标记结束后要重新扫描被更新过的引用（CMS）；SATB 破坏「删除引用」条件，代价是可能多标已死对象（浮动垃圾），换来更短的重新标记停顿（G1）。
- **G1 到底算复制还是标记-整理？** —— 单次回收在 Region 之间做疏散（复制），局部没有碎片；整体上是标记-整理的语义，不要求连续空间。答案取决于问的粒度，见 [Q07](#q07g1-的-region-和停顿预测是怎么配合的-p1-中频)。
- **ZGC 的毫秒级停顿靠的是新算法吗？** —— 不是，核心仍是标记-复制；突破在染色指针把标记位放进指针、读屏障在访问时修正引用、转移阶段也并发化，于是停顿与堆大小弱相关。代价是吞吐下降与内存多重映射，见 [Q14](#q14zgc-的原理和适用场景是什么-p1-中频)。

**实际工程场景**：选型时先看瓶颈是停顿还是吞吐——接口延迟敏感（P99 有 SLA）走 G1 并设 `MaxGCPauseMillis`，超大堆且停顿要求极严（百 GB 以上、亚毫秒）才考虑 ZGC；批处理类走 Parallel 吞吐更高。JDK 14 之后已经没有 CMS，任何「CMS 调优」的说法都暴露环境脱节。

**容易答错的地方**：说「CMS 用标记-整理」（老年代是标记-清除，整理要靠一次 Full GC 兜底）；说标记-清除没有碎片问题，或把碎片说成内存泄漏；说复制算法固定浪费一半内存（8:1:1 下约 10%，装不下要走分配担保）；说 ZGC 完全不停顿（仍有极短的初始标记、再标记、初始转移）；版本答错（G1 默认是 JDK 9，不是 JDK 8）。

> 权威内容：JVM 垃圾回收算法当前尚未在仓库建设专门的深度文章，可参考《深入理解 Java 虚拟机（第 3 版）》第 3 章与 Oracle 官方 *Java HotSpot Virtual Machine Garbage Collection Tuning Guide*；收集器细节可对照 [Q07](#q07g1-的-region-和停顿预测是怎么配合的-p1-中频)、[Q14](#q14zgc-的原理和适用场景是什么-p1-中频)。

## 本专题常见追问链

面试官通常从一个看似基础的问题起手，逐层下钻。下面这条链覆盖本专题主干，每一跳右侧是面试官真正想验证的点——答不上这一跳，前面的结论再熟练也会被判定为「背过但没理解」。

```text
「JVM 内存区域怎么划分？」（Q09）
  └─ 验证：每个区域存什么、抛什么异常；知不知道元空间替代永久代、常量池迁移的版本差异
     └─ 「那 new 出来的对象在哪，怎么创建的？」→ 对象分配（Q10/Q11）
        └─ 验证：分配路径（指针碰撞/空闲列表、TLAB、CAS）、字节码三连、对象头布局
           └─ 「GC 怎么判断对象是活的？」→ GC Roots 与可达性分析（Q05）
              └─ 验证：根集合为什么是这些位置；为什么必须 STW；安全点/OopMap 是压缩停顿的手段
                 └─ 「对象怎么从新生代到老年代？」→ 分代回收（Q04/Q06）
                    └─ 验证：晋升的四条路径、动态年龄判定、年龄作为存活概率代理指标的取舍
                       └─ 「用什么收集器？为什么？」→ 收集器选型（Q07/Q14）
                          └─ 验证：G1 的 Region 与停顿预测、ZGC 染色指针；能否按场景取舍而不说绝对化结论
                             └─ 「线上 Full GC 频繁 / OOM 了怎么办？」→ OOM 排查（Q02/Q08）
                                └─ 验证：先分桶（回收不掉 / 分配太快）、定位手段的顺序与依据
                                   └─ 「所以你怎么调优？」→ 调优方法论（Q17）
                                      └─ 验证：目标先行、单变量验证、固化参数；以及「这该不该由 JVM 背锅」的判断力
```

链上任何一跳答「不知道」，都会掉回更基础的一层重新问——所以准备时应按链背，而不是按题背。

## 面试前速记

- 排查题先分桶：CPU 100% 先分 `us`/`sy`；Full GC 频繁先分「回收不掉 / 分配太快」——顺序和依据比工具名重要。
- 内存区域：PC/虚拟机栈/本地方法栈线程私有，堆/方法区（元空间）共享；栈深超限是 `StackOverflowError`，容量不足是 `OutOfMemoryError`。
- 元空间 JDK 8 替代永久代（本地内存、默认无上限，生产必须设 `MaxMetaspaceSize`）；字符串常量池 JDK 7 移到堆。
- 对象分配：指针碰撞 vs 空闲列表由收集器是否整理决定；TLAB 是默认主路径；字节码是 `new`/`dup`/`invokespecial`。
- 对象头 Mark Word 8 字节复用存哈希/GC 年龄（4 位 → 阈值 15）/锁状态；压缩指针下类型指针 4 字节，32GB 以下堆默认开启。
- 类加载五阶段：准备给类变量零值、初始化 `<clinit>` 才赋初值；`final` 常量准备阶段即终值；解析可延迟到初始化后。
- GC Roots 五类（栈局部变量、静态属性、常量、JNI、活跃线程与监视器）；STW 是为了一致性快照，靠安全点 + OopMap 压缩。
- 晋升四路径：年龄到 15、动态年龄判定、大对象直接进、分配担保批量晋升；年龄是「存活概率」的代理指标。
- G1 按 Region 回收收益排序（JDK 9 起默认）；ZGC 染色指针 + 读屏障，停顿与堆大小弱相关，JDK 15 起生产可用、JDK 21 分代——版本必带。
- 参数红线：`-Xms=-Xmx` 消除扩缩抖动；JDK 9+ 用 `-Xlog:gc*`；OOM 必配 `HeapDumpOnOutOfMemoryError`；容器里堆只占 limit 的一部分。
- 工具按侵入性分层用：监控看板 → jstat/jstack/Arthas/JFR → jmap dump/MAT；dump 有 STW 成本，放最后。
- 调优四步：目标先行 → 监控发现 → 单变量验证 → 固化；先分清是代码问题还是 JVM 问题，没有万能参数模板。
