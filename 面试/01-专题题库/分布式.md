## 专题定位

- 分布式是 5 年以上 Java 后端面试的主战场：CRUD 题区分度低，分布式题能直接区分「用过」和「懂」。
- 面试官主要验证三件事：方案能否说清、代价是否自知、失效场景是否想过。只背方案不答代价的候选人，通常过不了深挖。
- 这一专题的题目几乎都是组合拳：锁会追到 Redlock 与 ZooKeeper，事务会追到 TCC 空回悬，选型题会追到「你们为什么不用 X」。
- 与相邻专题的分工：Redis.md 讲 Redis 单组件的原理与缓存问题，消息队列.md 讲 MQ 的可靠性模型，04-场景设计题 讲秒杀、缓存一致性等完整方案；本专题讲跨组件的通用分布式机制。
- 答到什么深度：每个方案能给出「适用场景 + 一致性强度 + 运维代价 + 典型故障」四件套，并主动划清与相邻方案的边界。

## 题目正文

### Q01：分布式锁怎么实现？Redisson 的原理是什么？ `P0` `高频`

**30 秒回答**：分布式锁的本质是用一个所有节点都能访问的存储做互斥，并保证加锁、设置过期、校验持有者、释放这四步的原子性；Redisson 用 Redis 的 Hash 记录锁名、线程标识与重入次数，再用看门狗自动续期。

**深入理解**：最小实现是 SET key value NX PX 30000 一条命令同时完成加锁与过期，value 存唯一标识；释放时用 Lua 脚本先比对 value 再删除，避免误删别人的锁。不设过期会因宕机死锁，设了过期又可能业务没跑完锁就没了，所以要续期：Redisson 的看门狗默认过期 30 秒，加锁成功后启动后台任务每 10 秒（过期时间的三分之一）续一次，直到显式释放；只有不传 leaseTime 时看门狗才生效，传了就以传入值为准。可重入靠在 Hash 里计数实现，同一线程再次加锁计数加一，释放时递减到零才真正删 key。单机 Redis 仍有单点问题，主从异步复制下「主节点加锁成功但未同步就宕机」会短暂出现两个持有者；要更强一致性需换 Redlock 或 ZooKeeper、etcd 的临时顺序节点方案。

**为什么这样设计**：用 Hash 加 Lua 而不是简单的 String 加锁，是因为重入计数、持有者校验、续期这三件事必须在 Redis 侧原子完成，任何「先 get 再 set」的写法在高并发下都有窗口；把逻辑写进 Lua 交给 Redis 单线程执行，等于不引入分布式事务就拿到了原子性。

**面试官可能继续追问**：

- **Redisson 的看门狗什么时候不生效？** —— 只有加锁时不显式传 leaseTime 才会启动看门狗；传了过期时间就以传入值为准、不再续期。所以业务可能超过 30 秒时，要么不传 leaseTime 让看门狗续，要么自己实现续期。
- **Redis 主从切换时锁会不会失效？** —— 会有一个窗口：主节点加锁成功后未同步到从就宕机，从升主后锁消失，另一客户端可以加锁，出现两个持有者。Redlock 用向多数派实例独立加锁降低这个概率，代价是运维多套 Redis 且延迟上升；对正确性敏感的场景直接用 etcd/ZooKeeper 临时节点。
- **Redis 锁和 ZooKeeper 锁怎么选？** —— Redis 方案性能高、实现简单，但主从切换有一致性窗口；ZK 基于临时顺序节点加会话心跳，强一致、天然防误删（会话断连即删），但吞吐低一个量级且依赖会话保活。高并发互斥选 Redis，强正确性且量不大选 ZK/etcd。
- **锁的粒度和锁内耗时怎么控制？** —— 按最小业务单元加锁（如单 SKU、单位置），避免全局锁把并发打成串行；锁内不放慢 SQL 和下游调用，先查后算再写，把慢逻辑挪到锁外，否则看门狗也救不了吞吐。

**实际工程场景**：WMS 的出库、库内移位等流程里，典型做法是按库位或 SKU 维度加 Redisson 锁，防并发理货和扣减把库存写穿。注意三点：锁 key 必须含租户/仓库维度，避免跨仓互斥；锁超时按「正常业务 P99 耗时」设并留冗余；业务执行中若依赖下游慢接口，要么异步化要么容忍锁等待，否则会把线程池打满。秒杀扣减的完整设计见 [秒杀与库存扣减](../04-场景设计题/秒杀与库存扣减.md)，本文不展开。

**容易答错的地方**：

- 「SETNX 后再 EXPIRE」是经典错误：两条命令非原子，中间宕机即死锁；必须用 SET NX PX 一条命令。
- 「释放时直接 DEL」：没校验 value 会删掉别人的锁，必须 Lua 比对后删除。
- 「指定了 leaseTime 还有看门狗兜底」：看门狗只在 leaseTime<0（默认）时生效。
- 「Redlock 就绝对安全」：Redlock 依赖时钟假设，GC 停顿或时钟跳跃下仍有争议，工程上更多作为「比单机 Redis 好」的折中，不是银弹。

> 权威内容：分布式锁当前尚未在仓库建设，可参考 Redis 官方文档的 Distributed Locks with Redis 章节。

### Q02：分布式 ID 有哪些方案，怎么选？ `P0` `中频`

**30 秒回答**：主流方案有 UUID、数据库自增与号段模式、Redis INCR、雪花算法及其变种，选型取决于是否需要趋势递增、能否接受中心化依赖、以及是否容忍 ID 可被猜出生成规律。

**深入理解**：UUID 本地生成、无网络开销，但 128 位偏长且无序，作 MySQL 主键会因页分裂拖慢插入，通常只当业务幂等键用。号段模式每次从数据库取一批 ID（如 1000 个）缓存在内存，减少往返且趋势递增，缺点是有中心化依赖，实例重启会浪费未用掉的号段。Redis INCR 性能高、天然递增，但引入网络依赖，还要考虑持久化策略，掉档后可能重号。雪花算法是 64 位：1 位符号、41 位毫秒时间戳、10 位机器 ID、12 位序列号，本地生成、趋势递增、吞吐高，弱点是完全依赖系统时钟，回拨会导致重复 ID，且机器 ID 需要分配和管理。落地上中小规模、能接受中心化就用号段模式，高并发且希望本地生成就用雪花，但必须解决时钟回拨和 workerId 分配。

**为什么这样设计**：雪花算法把时间戳放在高位，是为了让 ID 的大小顺序与生成时间大体一致，写入 B+ 树索引时新记录基本落在最右侧，避免随机主键造成的频繁页分裂，同时让「按 ID 范围查某时间段数据」成为可能。代价是把正确性押在时钟单调上，所以回拨检测与等待是这套方案不可省略的部分。

**面试官可能继续追问**：

- **时钟回拨怎么处理？** —— 回拨幅度小于序列号容量时可等待追平（等时间戳恢复到上次水平再发号）；大幅回拨只能摘除实例或切换 workerId 并记录。美团的 Leaf-snowflake 用 ZK 监控机器时间，检测到回拨先摘流量再处理。
- **号段模式的号段用完了怎么办？** —— 用尽后同步取号会阻塞业务；工程上异步提前加载下一个号段（用到一定比例就后台拉取），把取号延迟对业务的暴露降到零。实例重启浪费未用号段是这套方案的固有代价，可接受。
- **雪花 10 位机器 ID 怎么分配？** —— 常见三种：配置写死（适合规模固定的集群）、ZK/etcd 注册抢占、用 IP/主机名哈希。核心要求是全局唯一且重启尽量不变，否则会撞号。

**实际工程场景**：WMS 的单据号（入库单、出库单、理货任务号）通常要求「趋势递增 + 人类可读 + 按天/仓分段」，所以实际常见组合是号段模式（保证递增与连续）加业务前缀（如 OUT-20261016-000123），而不是裸雪花。对外暴露的 URL 参数、导出文件名等场景则要避免用可猜的自增 ID。选型上没有银弹：中心化方案（号段、Redis）换来全局严格递增和运维简单，本地方案（雪花）换来无依赖和高吞吐，但要自己管时钟和机器号。

**容易答错的地方**：

- 「雪花 ID 全局严格递增」——只是趋势递增，同一毫秒内不同机器发的号不保证有序。
- 「UUID 完全随机所以不能作索引」——UUIDv4 无序确实伤 InnoDB 插入；UUIDv7 等时序 UUID 已针对排序优化，不能一概而论。
- 「Redis INCR 一定不会重号」——AOF 每秒刷盘或 RDB 快档之间会掉数据，重启后可能回退到旧值，必须配合持久化策略或补偿对账。

> 权威内容：分布式 ID 生成当前尚未在仓库建设，可参考 Twitter Snowflake 的设计说明与 MySQL 官方文档的 AUTO_INCREMENT 章节。

### Q03：CAP 和 BASE 是什么？CP 和 AP 怎么取舍？ `P0` `高频`

**30 秒回答**：CAP 指一致性、可用性、分区容错性，分布式系统必须容忍网络分区（P 事实上必选），所以真正的取舍发生在网络分区时 CP 还是 AP：CP 保一致、宁可拒绝服务，AP 保可用、容忍短暂不一致。BASE 是对 AP 的工程化延伸——基本可用、软状态、最终一致性，用「先接受不一致、后台收敛」换可用性和伸缩性。

**深入理解**：先破一个流行误读：「三者只能取二」不是随时三选二，而是平时三者兼得，只在网络分区发生的那一刻必须二选一；没分区时讨论 CP/AP 没有意义。

一致性谱系要分清，面试常混：

| 级别 | 含义 | 典型实现 |
| --- | --- | --- |
| 强一致性 | 写入完成后任何后续读都看到新值 | 线性一致存储（etcd、ZooKeeper） |
| 最终一致性 | 停止写入后一段时间内收敛到一致 | DNS、Gossip、多数异步复制系统 |
| 顺序一致性 | 所有进程看到的操作顺序一致，但不要求与真实时间对齐 | 需要全局序号/主节点的系统 |
| 因果一致性 | 有因果关系的操作保序，无因果关系的可乱 | 向量钟、因果日志系统 |

工程含义：多数互联网业务选 AP + 最终一致（库存扣减允许短延迟对账收敛），账务、配额、锁这类选 CP（etcd/ZK）。注册中心是经典例子：ZooKeeper 是 CP，Leader 挂时分区期间不可写（保护一致），适合要求强一致的配置与小规模服务发现；Eureka/Nacos 的 AP 模式强调各节点自治、peer 间异步复制，分区期间仍能提供注册与查询（保护可用），代价是可能读到已下线实例，需要客户端健康检查兜底——注意 Nacos 同时支持 AP 和 CP 两种模式（临时实例 AP、持久实例 CP），不能一句话把 Nacos 划进某一类。

BASE 三要素：Basically Available（损失部分功能保核心可用，如限流降级）、Soft state（允许中间态存在，如订单「处理中」）、Eventually consistent（中间态会收敛）。它不是一个定理，而是对「AP 系统如何工程化」的经验总结。

**为什么这样设计**：CAP 是论文里的抽象模型，用来逼你在分区时表态，而不是给你日常做选择题；BASE 补上了 CAP 缺失的工程维度——一致性不是 0/1，收敛延迟、冲突解决策略、补偿手段才是日常真正要设计的东西。所以成熟团队的表述是「默认最终一致，用一致性要求倒推哪些点必须强一致」，而不是空谈「我们 CP 还是 AP」。

**面试官可能继续追问**：

- **网络分区时 CP 系统具体发生什么？** —— 以 etcd/ZK 为例，少数派分区停止写入（失去 Leader 后无法形成多数派），读写报错或超时，直到分区恢复、重新选主。牺牲的是分区期间的可用性，保住的是「不会出现两个值」。
- **最终一致性怎么保证一定收敛？** —— 靠对账补偿：定时比对 + 差异修复，或消息重试 + 幂等消费。收敛时间是 SLA 问题不是算法问题，要对账周期和业务容忍度对齐。
- **强一致一定更慢吗？** —— 多数派写入的延迟至少是一个跨节点 RTT，且随副本数增加而上升；这就是 etcd 不适合高频写、ZooKeeper 也只管元数据不管业务数据的原因。

**实际工程场景**：WMS 的库存是典型「强一致写入 + 最终一致展示」：扣减动作本身走数据库行锁/乐观锁保证强一致（否则超卖），库存看板、报表允许秒级延迟。注册中心选型上，内部几十个服务的场景 CP/AP 差异不大，用默认即可；跨机房、大规模部署时，AP 注册中心 + 客户端缓存 + 重试的可用性收益才明显。

**容易答错的地方**：

- 「CAP 三选二」——误读，P 是前提，只在分区时二选一。
- 「用了最终一致性就没有不一致窗口」——最终一致的本质就是有窗口，BASE 承认并管理这个窗口。
- 「Nacos 是 AP 注册中心」——Nacos 临时实例走 AP（Distro 协议），持久实例走 CP（Raft），要分模式说。
- 「ZooKeeper 是 CP 所以服务发现很合适」——ZK 的 CP 模型在服务发现场景反而是缺点：Leader 切换期间注册/心跳不可用，大规模实例下写吞吐是瓶颈，Eureka 正是为这个问题而生。

> 权威内容：CAP 与 BASE 当前尚未在仓库建设，可参考 Eric Brewer 的 CAP 论文（《CAP Twelve Years Later: How the "Rules" Have Changed》）与 Nacos 官方文档的一致性模型章节。

### Q04：分布式事务有哪些方案，怎么选？ `P0` `高频`

**30 秒回答**：主流方案分两类——刚性事务（2PC/XA，强一致、同步阻塞、性能差）和柔性事务（TCC、Saga、本地消息表、事务消息、最大努力通知，最终一致、异步补偿、性能好）。选型先问三个问题：要不要强一致、并发量多大、能接受多少侵入和运维复杂度；绝大多数互联网业务用柔性事务里的 TCC 或事务消息。

**深入理解**：

| 方案 | 一致性 | 侵入性 | 复杂度 | 性能 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 2PC/XA | 强一致 | 低（协议层） | 低（数据库驱动） | 差（同步阻塞、锁持有久） | 遗留系统、单体跨库、低并发 |
| TCC | 最终一致 | 高（Try/Confirm/Cancel 三个接口） | 高（空回滚、悬挂、幂等都要处理） | 好 | 高并发核心交易（资金、库存） |
| Saga（编排/协同） | 最终一致 | 中（正向/补偿操作） | 中 | 好 | 长流程、跨系统编排（下单→物流→结算） |
| 本地消息表 | 最终一致 | 中（业务库加表 + 扫描任务） | 中 | 好 | 不依赖特定 MQ 的通用场景 |
| 事务消息（RocketMQ 半消息） | 最终一致 | 中（半消息 + 回查接口） | 中 | 好 | 已用 RocketMQ 的业务交易 |
| 最大努力通知 | 弱一致 | 低 | 低 | 好 | 容忍失败的通知场景（支付结果通知商户） |

逐个要点：

- 2PC/XA：准备阶段锁资源到提交才释放，协调者宕机则参与者阻塞；数据库长事务是性能与连接数的灾难。XA 由数据库驱动实现，业务无感但牺牲可用性，只适合并发极低的场景。
- TCC：把业务操作拆成 Try（预留资源，如冻结库存）、Confirm（确认执行）、Cancel（释放预留）。三个问题必须解决：空回滚（Try 没执行就收到 Cancel，要直接返回成功）、悬挂（Cancel 先于 Try 到达，要拒绝迟到的 Try）、幂等（Confirm/Cancel 重复调用）。不解决这三件事，TCC 在生产上一定出事。
- Saga：把长事务拆成有序的本地事务序列，每个本地事务配一个补偿；失败时按逆序回滚（向后恢复）或继续向前重试（向前恢复）。编排式（Orchestration，一个协调器驱动）比协同式（Choreography，事件驱动）更可控、可观测，现代实现（Seata Saga 状态机、Camunda/Zeebe）以编排为主。Saga 不保证隔离性，中途状态对外可见，需要用业务设计规避（如「扣款中」状态）。
- 本地消息表：把「业务写入」和「消息写入」放同一本地事务，再用定时任务扫描未发消息投递。优点是不挑 MQ、实现直白；缺点是消息表与业务表耦合、扫描任务有延迟、消息量大有扫描压力。
- 事务消息：RocketMQ 半消息机制，生产者先发半消息（对消费者不可见），本地事务执行成功后 commit、失败 rollback，Broker 未收到确认时回查本地事务状态。比本地消息表轻，但绑定 RocketMQ。实现原理详见 [消息队列.md](消息队列.md) Q07。
- 最大努力通知：主动方反复重试通知被动方，适用于「通知不到就算了」的场景（如支付结果推送商户），本质是可靠通知而非事务。

**为什么这样设计**：没有一种方案同时满足强一致、高性能、低侵入——这是分布式事务的根本权衡。2PC 用同步和阻塞换强一致；柔性事务用「业务可补偿」换异步和性能，前提是每个参与方都要提供补偿接口并处理幂等。所以选型不是「哪个最好」，而是「这个业务能不能被补偿」：资金类多数选 TCC 留足人工介入点，长流程选 Saga，已重度使用 RocketMQ 的选事务消息，遗留单体跨库先用 XA 顶住再逐步拆分。

**面试官可能继续追问**：

- **TCC 的空回滚和悬挂具体怎么防？** —— Try 执行时先插入事务控制记录（如 try_record 表），Cancel 到达时查记录：没有 Try 记录就写入「已取消」标记并直接返回；Try 执行时若发现「已取消」标记则拒绝执行（防悬挂）。Seata 的事务控制表就是干这个的。
- **事务消息的 Broker 回查会不会把业务库打挂？** —— 回查有次数和退避策略（默认 15 次左右），且回查接口必须轻量（只查本地事务状态，不执行业务）。回查不过要配告警，说明本地事务结果本身有问题。
- **Seata 的 AT 模式是什么？** —— AT 是 Seata 对 2PC 的改良：一阶段把「前后镜像」存 undo_log 并本地提交，二阶段用镜像生成反向 SQL 补偿或删除 undo_log。对业务零侵入，但全局锁期间持有行锁、高并发下有性能争议，属于「无侵入但有代价」的路线。

**实际工程场景**：WMS 的出库流程天然是长事务：扣库存、生成出库单、通知 WCS/TMS、回写 ERP，任何一环失败都要整体可回退。工程上通常不用一个全局事务覆盖全链路，而是按业务边界拆成多个本地事务 + 事务消息/MQ 事件驱动，每个环节配补偿（如 TMS 通知失败则重试，最终人工兜底），并保证每个消费端幂等（见 Q12 与 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md)）。核心原则：能补偿的业务用柔性事务，不能补偿的（已收款）才值得上 TCC/2PC，且必须留对账兜底。

**容易答错的地方**：

- 「事务消息一定比本地消息表好」——要看是否已用 RocketMQ、团队运维能力、以及是否愿意绑定具体 MQ；本地消息表通用且不依赖 MQ 特性，换 MQ 时代价小。
- 「TCC 的 Try 就是锁资源」——Try 是预留（冻结），不阻塞别人读；隔离性靠业务设计而非技术机制，这和 2PC 的行锁是两回事。
- 「Saga 就是逆序回滚」——Saga 是补偿而非严格回滚，补偿本身也是业务操作，也可能失败；向前恢复（继续重试）在很多场景比回滚更合理。
- 「用了分布式事务框架就不需要幂等了」——Confirm/Cancel、补偿、消息消费都可能重复触达，幂等是柔性事务的前置条件。

> 权威内容：分布式事务当前尚未在仓库建设，可参考 Seata 官方文档的 AT/TCC/Saga 模式章节与 Saga 论文《Sagas》。

### Q05：Raft 共识算法的原理是什么？为什么工程上选 Raft 而不是 Paxos？ `P1` `中频`

**30 秒回答**：Raft 是把共识拆成三个子问题的算法：Leader 选举、日志复制、安全性约束。节点分 Follower/Candidate/Leader 三态，用 term（任期）和随机选举超时避免选票分裂；Leader 把日志条目复制到多数派即视为已提交；通过「已提交条目不被覆盖」等约束保证正确性。etcd、Consul、RocketMQ 5.x 的 DLedger（Raft 变体）都用它。

**深入理解**：

- 三态与任期：Follower 被动收心跳；Candidate 发起选举；Leader 任期内心跳保位。term 单调递增，每个节点观察到更大 term 就退位并跟进，相当于逻辑时钟，用来废弃过期 Leader 的旧消息。
- Leader 选举：Follower 在随机超时（如 150~300ms）内没收到心跳就升级 Candidate，term+1、先投自己再拉票；拿到多数票当选。随机化是关键——固定超时会让多个节点同时参选、选票分裂、反复重选；随机化让某个节点大概率先醒。
- 日志复制：客户端请求写 Leader，Leader 追加日志（未提交），并行发给 Follower，多数派落盘后提交并应用，随后心跳把提交位置带给 Follower。日志项是 (term, index, command)，index 连续。
- 安全性约束（面试区分度的核心）：① 选举限制——Candidate 的日志必须至少和多数派一样新（比较 last term 再比 index），否则选出的 Leader 缺已提交条目；② 已提交的条目在后续 Leader 的日志中同 index 位置一定是它（Leader 不覆盖已提交项，只追加）；③ 状态机按 index 顺序应用。
- 与 Paxos 对比：Paxos（Basic Paxos/Multi-Paxos）理论完备但难以理解，论文没给工程细节（谁当 Leader、日志怎么压缩都没说清），各厂实现差异大；Raft 用「强 Leader + 随机超时 + 清晰的状态机描述」换可理解性和可实施性，工程上 bug 更少。Raft 不是理论上更优，而是工程上更可控。
- 应用：etcd（Kubernetes 的存储）、Consul 用 Raft；ZooKeeper 用的是 ZAB（ZooKeeper Atomic Broadcast）——原子广播协议，与 Raft 同属「Leader + 多数派」家族但细节不同（ZAB 强调崩溃恢复阶段的全局有序）；Kafka 2.8 起 KRaft 模式用类 Raft 的 KRaft 协议替代 ZooKeeper 管理元数据，注意 KRaft 不是标准 Raft，是 Kafka 基于 Raft 思想定制的实现。

**为什么这样设计**：Raft 的核心设计取舍是「用强 Leader 换取简单」：所有写走 Leader，读默认也走 Leader（线性一致读），避免了 Paxos 多主/无主的复杂对等协商；随机选举超时把「活锁」问题概率化解决；日志项带 term 让冲突检测变成简单的比较。它放弃了理论上的最优性，换来工业界可正确实现的共识。

**面试官可能继续追问**：

- **Raft 读一定要走 Leader 吗？** —— 线性一致读必须走 Leader（或 Leader 确认自己仍是 Leader 后由 Follower 读，etcd 的 ReadIndex 方案）。Follower 直接读可能读到旧值，属于 stale read，某些业务可接受则无需强一致读。
- **少数派分区里的旧 Leader 会怎样？** —— 它无法凑齐多数派提交新日志，term 也不会增长；多数派分区选出新 Leader 后，旧 Leader 收到更高 term 的消息自动退位。它提交不了新数据，所以不会造成数据分叉。
- **Raft 和 ZAB 最大的区别？** —— 目标不同：ZAB 是原子广播（保证全局顺序和最终一致），Raft 是复制状态机共识；Raft 有明确的「已提交」概念和选举日志新度检查，ZAB 靠崩溃恢复阶段的历史同步。工程选型上 etcd/Consul 用 Raft，ZK 生态用 ZAB。

**实际工程场景**：业务系统一般直接用 etcd（K8s 生态、配置中心、服务发现的强一致存储）而不是自己实现 Raft。面试里回答「了解 Raft 原理，选型时知道 etcd 用 Raft、ZK 用 ZAB、KRaft 是 Kafka 定制协议」比声称「读过 Raft 源码」更务实。真正需要关注 Raft 的场景：自研元数据存储、评估 etcd 写性能上限（约万级 QPS，随副本数下降）、以及排查 etcd 集群选主导致的抖动。

**容易答错的地方**：

- 「Raft 就是 Multi-Paxos」——思想同源但 Raft 是独立设计，有强 Leader、随机超时、日志 term 等独特机制，实现不通用。
- 「多数派写入 = 强一致」——多数派只是提交条件；读不强制走 Leader 时仍可能读到旧值。
- 「Kafka 2.8 后完全去掉了 ZooKeeper」——KRaft 从 2.8 开始预览、3.x 才生产可用，迁移是渐进过程，不同版本集群状态差异很大，回答时要带版本。
- 「随机超时是为了负载均衡」——是为了降低选票分裂概率，让某个节点率先超时参选。

> 权威内容：Raft 共识算法当前尚未在仓库建设，可参考 Raft 论文 《In Search of an Understandable Consensus Algorithm》与 etcd 官方文档。

### Q06：一致性哈希的原理是什么？解决什么问题？ `P1` `中频`

**30 秒回答**：一致性哈希把数据和节点都映射到一个 0~2^32-1 的哈希环上，数据沿环顺时针找到的第一个节点就是它的归属；节点上下线只影响环上相邻区段的数据，迁移量约 1/N，而取模哈希在节点数变化时会近乎全量重哈希。虚拟节点（每台机器在环上放多个副本点）用来解决数据倾斜。

**深入理解**：

- 哈希环：key 哈希后落在环上某点，顺时针遇到第一个节点即命中。2^32 取模是常见实现（如 Ketama）。
- 节点变动的影响：加一个节点只承担它前一个节点（顺时针方向）到它之间的那段数据；删一个节点它的数据全部转移给后一个节点。N 个节点变动一个，期望迁移 1/N 的数据；取模哈希则是约 (N-1)/N 的数据错位、近乎全量。
- 数据倾斜问题：节点少时，哈希点在环上分布不均，有的节点管一大段（热点）、有的管一小段。虚拟节点解决：每台物理机放 150~200 个虚拟节点，统计意义上分布均匀，代价是元数据（虚拟节点表）变大、路由多一层映射。
- 与取模的对比：

| 维度 | 取模哈希 | 一致性哈希 |
| --- | --- | --- |
| 节点扩容 | 几乎全量迁移 | 约 1/N 迁移 |
| 实现复杂度 | 一条 % | 环 + 虚拟节点 + 路由表 |
| 数据均衡 | 依赖 key 分布 | 虚拟节点后接近均匀 |
| 适用场景 | 节点固定、可容忍重建 | 节点频繁变化、缓存分片 |

- Redis Cluster 是变体：预定义 16384 个槽位，key 用 CRC16(key) % 16384 算槽，槽再分配到节点。它放弃了「节点决定区间」改为「槽位分配」，好处是可以按槽粒度手动做再平衡（addslots/migrateslots），比纯哈希环更可控。
- 注意：一致性哈希只解决「分布与迁移」，不解决副本与容错——缓存场景每个节点仍可配主从/多副本；数据库分片场景每个分片本身可能是集群。

**为什么这样设计**：取模哈希简单但在弹性伸缩时缓存会瞬间击穿 DB（大量 key 同时 miss），这是缓存系统不可接受的；一致性哈希把「节点数」从哈希函数里解耦，节点变动只局部迁移，缓存命中率不会断崖下跌。虚拟节点是工程折中：用空间（元数据）换均衡，同时让不同规格的机器可以配置不同虚拟节点数（权重）。

**面试官可能继续追问**：

- **加了虚拟节点还会倾斜吗？** —— 概率上接近均匀，但 key 分布极不均匀（如 key 都带同前缀）时仍可能倾斜，需要按业务 key 特征加盐或调权重。
- **一致性哈希怎么支持副本？** —— 常见做法是沿环顺时针找接下来的 k 个不同物理节点（跳过同一物理机的虚拟节点）作为副本位置，这样主副本故障时相邻节点顶上，迁移仍局部。
- **Redis Cluster 为什么不直接用一致性哈希？** —— 槽位是显式分配的，运维可以精确指定「哪些槽搬到哪个节点」，做再平衡和运维干预比环上自动定位更可控；代价是要维护 slot→node 的映射并在客户端缓存。

**实际工程场景**：WMS 的本地缓存（如库位维度热点数据）分片、以及自研缓存中间件选型时会用到一致性哈希思想。更常见的现代实践：Memcached 客户端（Ketama）、Redis Cluster 槽位、以及 Dubbo 的一致性哈希负载均衡（把相同参数的调用打到同一 provider，利用本地缓存）。评估点：节点是否频繁变化（不变则取模够用）、是否容忍迁移期缓存命中率下降、运维能否干预再平衡。

**容易答错的地方**：

- 「一致性哈希完全均匀」——不加虚拟节点、节点少时倾斜明显；虚拟节点是必需组件不是可选优化。
- 「扩容时零影响」——迁移过程中被迁移的 key 仍会 miss，只是 miss 范围从全量降到 1/N；缓存场景要配预热或双读。
- 「Redis Cluster 就是一致性哈希」——是槽位变体，语义接近但机制（16384 槽、CRC16）与运维接口都不同，面试要分开说。

> 权威内容：一致性哈希当前尚未在仓库建设，可参考 Karger 等人的论文《Consistent Hashing and Random Trees》与 Redis Cluster 官方规范文档。

### Q07：服务注册与发现怎么设计？ `P1` `中频`

**30 秒回答**：注册中心干四件事：服务注册（上线时登记地址与元数据）、服务发现（调用方按名字拿实例列表）、健康检查（剔除不可用实例）、变更通知（列表变化触达调用方）。核心取舍是 CP（强一致列表，如 ZooKeeper、Nacos 持久实例）还是 AP（高可用列表，如 Eureka、Nacos 临时实例），以及推送（服务端推）还是拉取（客户端定时拉）的结合方式。

**深入理解**：

- 注册与心跳：服务提供者启动时注册，运行期间用心跳/TTL 保活。Eureka 用心跳续约（默认 30s 周期），服务端超时未续约就剔除（默认 90s）；ZK 用临时节点，会话断连节点即删；Nacos 临时实例用心跳 + 超时剔除，持久实例靠主动健康检查。
- 发现模式：
  - 客户端发现（Eureka/Ribbon）：客户端缓存注册表并定期全量/增量拉取（Eureka 默认 30s 拉一次），客户端自己做负载均衡。服务端压力小，客户端有缓存所以注册中心短暂宕机不影响已启动服务互相调用。
  - 服务端发现（K8s Service + kube-proxy/iptables、Service Mesh sidecar）：客户端访问虚拟 IP，由平台/代理转发到后端实例，客户端无感知。
- CP vs AP 的取舍（呼应 Q03）：ZK 的 CP 模型在 Leader 切换期间注册不可用，且写吞吐受限，大规模服务发现下反而脆弱；Eureka 的 AP 设计（peer 异步复制、自我保护模式——15 分钟内心跳恢复率低于阈值就暂停剔除，防网络抖动误杀）就是为可用性而生。Nacos 双模式：临时实例 AP（Distro 协议、最终一致）、持久实例 CP（Raft）。
- 临时 vs 持久节点：ZK 临时节点绑会话，进程崩溃即消失，适合「活着才在」的服务实例；持久节点跨会话存在，适合配置、元数据类数据（Nacos 配置就是持久化 + 长轮询推送）。
- 自我保护与误杀是运维重点：网络分区时 AP 注册中心选择「保留可疑实例」（保可用）还是「剔除」（保新鲜），是可用性与正确性的取舍；调用端必须配重试 + 熔断兜底，因为拿到已死实例的 IP 是常态。

**为什么这样设计**：注册中心的本质矛盾是「列表要新鲜」还是「随时能拿到列表」。CP 选择前者（宁可暂时拿不到），AP 选择后者（宁可拿到旧的）。为什么互联网多用 AP 注册中心：调用方对「偶尔拿到过期 IP」有重试和熔断兜底，但对「注册中心挂了导致服务全瘫痪」零容忍；所以宁可旧列表 + 客户端健康检查，不要强一致 + 单点脆弱。这也是 Eureka 1.x 设计文档里反复强调的思路。

**面试官可能继续追问**：

- **客户端缓存过期但服务端已更新怎么办？** —— 客户端定期拉取（Eureka 30s）+ 调用失败重试下一个实例；长轮询/推送（Nacos）可以把延迟降到秒级但服务端要维持连接。核心是「缓存 + 重试」组合，而不是追求实时。
- **健康检查有哪几层？** —— 注册中心层（心跳/TTL/主动探测，剔除实例）、客户端层（调用失败计数熔断）、基础设施层（K8s readiness probe、SLB）。三层都要有，任何一层单独都不够。
- **服务上线瞬间流量打爆怎么办？** —— 启动预热：注册时带权重 0 或小权重，健康检查通过后按步长提升；或客户端首次调用做小流量试探。注册中心本身不解决冷启动，要业务配合。

**实际工程场景**：WMS 内部服务规模中等，用 Nacos/Eureka 均可；关注三点：① 实例元数据要带仓库/区域标签，发现时按标签过滤（同仓优先）；② 剔除延迟要敢配——网络抖动时误杀的代价（重启风暴）比多调几次失败实例更高，配合客户端重试；③ 跨机房部署要评估注册中心同步链路，AP 模式 peer 间最终一致，机房级故障时本机房优先自治。

**容易答错的地方**：

- 「注册中心是强一致系统所以用 ZK 最好」——服务发现是典型读多写少、可用性敏感场景，ZK 的 CP 模型在这里是劣势不是优势。
- 「有了注册中心调用方一定拿到最新列表」——拉取模式有秒级缓存延迟，推送模式有连接重建窗口；拿到过期 IP 是设计内的常态，靠重试兜底。
- 「心跳越快越好」——心跳周期直接决定注册中心写压力，数千实例时 1s 心跳就是数千 QPS；周期要和剔除时间折中。
- 「Eureka 2.x 还在广泛使用」——Eureka 2.x 开源计划已停止，主流是 1.x + 自研或迁移 Nacos/Consul，版本情况要讲清楚。

> 权威内容：服务注册与发现当前尚未在仓库建设，可参考 Nacos 官方文档的概念篇与 Eureka 1.x 设计文档。

### Q08：分布式限流与熔断怎么做？ `P1` `中频`

**30 秒回答**：限流是「入口掐量」保系统不挂，分单机限流（Guava RateLimiter、Sentinel 的匀速队列/令牌桶）和集群限流（Redis + Lua 集中计数、或单机配额均分）；熔断是「下游生病时先断开」防级联故障，状态机 Closed→Open→Half-Open；降级是「资源不够时保核心」。三件套常一起用：限流控入口、熔断控依赖、降级控体验。

**深入理解**：

- 单机限流算法：计数器（固定窗口，有临界突刺问题）、滑动窗口、漏桶（恒定速率，Redis-Cell 或 Guava）、令牌桶（允许突发，RateLimiter）。分布式下限流是近似值——要么集中（Redis + Lua 精确但多一次网络和单点），要么均分（总配额 / 实例数，无中心依赖但实例数变化时重新分派、不精确）。
- 集群限流两种路线对比：

| 路线 | 精确性 | 依赖 | 适用 |
| --- | --- | --- | --- |
| Redis + Lua 集中计数 | 精确 | Redis 可用性与热点 key | 严格配额（API 按租户计费） |
| 单机配额均分 | 近似（实例变动时偏差） | 实例数感知（注册中心） | 大多数业务限流 |

- 熔断状态机（Sentinel / Resilience4j / Hystrix 同构）：Closed 正常放行，统计错误率/慢调用比例；达到阈值进 Open，直接走降级逻辑（快速失败）；冷却一段时间进 Half-Open，放少量探测请求，成功则回 Closed，失败则回 Open。关键参数：慢调用阈值、错误率阈值、最小请求数（防低流量误判）、半开探测数。
- 降级策略：返回兜底数据（缓存旧值、默认列表）、关闭非核心功能（推荐位、报表）、排队或异步化。降级开关要能按粒度（接口/租户/机房）动态配置，而不是改代码重启。
- 与网关的分工：入口限流（网关层按 IP/租户/接口）、依赖熔断（业务层按下游服务）、兜底降级（返回可用的简化响应）。三层粒度不同，不能互相替代。

**为什么这样设计**：限流放在最靠近流量的地方（网关/接入层）最省资源，但按业务维度（租户、用户价值）限流需要业务信息，所以实际是「网关粗限流 + 业务细限流」两层。熔断为什么不直接重试到底：下游故障时重试会放大流量（重试风暴），熔断先「止损」等下游恢复，比重试更符合故障期的系统利益。集群限流不默认用 Redis：每个请求多一次 Redis 往返，且 Redis 成为新的故障点——配额均分用注册中心的实例数信息就能近似实现，多数业务够用。

**面试官可能继续追问**：

- **Redis + Lua 限流的热点 key 怎么优化？** —— 按接口/租户拆分 key 打散、本地预扣 + 周期性向 Redis 同步的混合模式（牺牲短期精确性换性能）、或用 Redis-Cell 模块的 GCRA 算法（一次命令完成限流判断）。
- **实例数变化时配额均分怎么处理？** —— 新实例上线拿平均配额（或先给保守配额）、实例下线多出的配额回收；可以引入「配额中心」定期重算分发给各实例，本质是把精确性和集中度做一个折中档位。
- **熔断打开期间的健康探测怎么设计？** —— 半开状态的探测请求要独立标记（带特殊头），且半开放量要小（如 10%），避免下游刚恢复就被探测流量再打挂；连续失败要重新 Open 且冷却时间指数退避。

**实际工程场景**：WMS 的出库接口是典型要保护的核心链路：网关层按仓库 ID 限流防突发波次压垮库存服务，业务层对 ERP、TMS 等下游调用配熔断（下游超时先返回「处理中」让客户端轮询，而不是阻塞重试），报表类非核心接口配降级开关。选型上 Sentinel（阿里系、规则动态化、控制台友好）和 Resilience4j（轻量、函数式、适合 Spring Boot 原生）都常用；关键不是用哪个，而是阈值要按真实压测数据定、规则要能热更新、熔断动作要有监控告警。Redis 相关实现细节见 [Redis.md](Redis.md)，秒杀场景的完整分层限流见 [场景设计题](../04-场景设计题/README.md) 与 [秒杀与库存扣减](../04-场景设计题/秒杀与库存扣减.md)。

**容易答错的地方**：

- 「限流阈值拍脑袋定」——阈值要来自压测和线上观测（单机容量 × 安全系数），拍脑袋的值要么形同虚设要么误杀正常流量。
- 「熔断是异常处理，try-catch 就行」——熔断是状态机，要点是自动恢复探测和降级联动，catch 住异常只是它的一个动作。
- 「集群限流一定要 Redis」——均分模式无中心依赖，可用性更好；Redis 模式更精确但引入单点和热点 key 风险，要看业务能不能接受近似。
- 「熔断只针对下游服务」——慢 SQL、缓存节点、第三方接口都可以是熔断对象，判据是「调用可能失败或拖垮我」的任何依赖。

> 权威内容：分布式限流与熔断尚未在仓库独立成篇，可参考 [场景设计题](../04-场景设计题/README.md) 中的分层限流设计与仓库 [Redis.md](Redis.md)；Sentinel 官方文档提供了状态机与规则的完整说明。

### Q09：分布式 Session 怎么做？ `P1` `中频`

**30 秒回答**：四种路线——sticky session（负载均衡按会话粘到同一节点，简单但故障丢会话、扩缩容不均）、session replication（节点间同步复制，一致但广播流量大、节点多时爆炸）、Redis 集中式（推荐，会话外置、故障恢复快、水平扩展自由）、JWT 无状态（token 自带信息、服务端零存储，但无法主动失效、体积大）。中小规模选 Redis 集中式，微服务/开放平台场景选 JWT，两者也可混用（JWT 做身份 + Redis 存会话状态）。

**深入理解**：

- sticky session：Nginx 的 ip_hash 或按 cookie 粘滞。问题：节点宕机该节点会话全丢、扩缩容时分布不均、滚动发布需要会话 draining。
- session replication：Tomcat cluster 的 DeltaManager 全量/增量广播。节点数 N 时广播量约 N²，只适合小集群；本质是用网络和内存换无单点。
- Redis 集中式：登录态存 Redis（Hash 结构：userId→角色、权限、登录时间），TTL 续期；水平扩展无状态。要处理：Redis 故障时的降级（本地缓存兜底或重登）、序列化、key 设计（token→userId 索引，支持踢人下线）。续期策略：滑动过期（每次访问续）还是固定过期，安全敏感场景要短 TTL + 主动续。
- JWT 无状态：header.payload.signature，服务端验签即可，无需存储。代价：① 签发后无法主动作废（登出、改密、踢人失效），补救是黑名单（Redis 存 jti + 过期时间）或短有效期 + refresh token 轮换；② payload 只适合放非敏感标识，体积随声明增长；③ 无法在服务端「看到」在线用户（审计、强制作业困难）。
- 登录态一致性细节：Redis 方案下多点登录、踢人、权限变更的生效是即时的（改 Redis 即生效）；JWT 方案权限变更要等 token 过期，所以权限这类易变数据不应放 JWT。

**为什么这样设计**：Session 的本质是「把有状态服务变成无状态服务」的程度选择。粘滞和复制都是让节点间「共享」会话状态——前者靠路由保证同一用户总到同一台（空间上不共享），后者靠复制让每台都有（时间上最终一致）；Redis/JWT 是干脆把状态挪出节点——一个集中存储、一个编码进请求。集中存储保留了「可变、可控」的能力，编码进请求换来零存储但放弃可控性，这就是「JWT 登出怎么办」成为经典追问的原因。

**面试官可能继续追问**：

- **JWT 登出怎么实现？** —— 短有效期 + refresh token 轮换是主流；强制登出用 Redis 黑名单存 jti 直到 token 自然过期（等于部分退回有状态）。想完全无状态又支持登出，没有银弹。
- **Redis 存 Session，Redis 挂了怎么办？** —— 主从 + 哨兵/集群保可用；极端情况用户重登（登录态丢失的代价远小于系统不可用）；更高级用本地缓存一级 + Redis 二级，允许短暂脏读。
- **微服务架构 Session 放哪？** —— 网关/认证服务统一鉴权后，把用户信息放请求头透传给下游，下游无状态；权限数据建议每次从权限服务实时取或短缓存，不要长期放在 token 里。

**实际工程场景**：WMS 后台（PDA、Web 端）用户量中等、权限按仓库/角色划分，通常 Redis 集中式：token 为随机串（不可预测），Redis 存 userId + 仓库列表 + 角色，TTL 30 分钟滑动续期；支持「踢下线」（删 Redis key）和「单点/多点登录策略」。对外 API（对接第三方物流、ERP）用 API Key/签名而不是 Session。混架构很常见：内部用户 Session + 外部调用 OAuth2/JWT，面试时说清「按调用方类型选」比二选一更体现经验。

**容易答错的地方**：

- 「JWT 无状态所以更安全」——JWT 只是自包含，签名保证不被篡改，但无法作废是安全劣势；敏感系统恰恰需要可撤销的会话。
- 「session 放 Redis 就是分布式 Session 的全部」——还要答序列化兼容、TTL 续期策略、Redis 故障降级、key 安全（token 不可预测、防会话固定攻击）。
- 「sticky session 很 low」——在无会话状态改造之前它是成本最低的方案，滚动发布时 draining 处理好即可；面试贬低它显得没做过生产。

> 权威内容：分布式 Session 当前尚未在仓库建设，可参考 Tomcat 官方文档的 Clustering/Session Replication 章节与 OWASP Session Management Cheat Sheet。

### Q10：分布式任务调度怎么保证不重不漏？ `P1` `中频`

**30 秒回答**：单机定时任务（ScheduledExecutorService、Spring @Scheduled、Quartz）的问题是一多实例就重复执行、一单节点就单点；分布式调度的核心是「同一时刻一个任务只在一个节点上跑」——常见做法是抢占式调度（XXL-Job、ElasticJob 都基于此）：调度中心触发、多实例抢锁/竞争路由，抢到的执行。同时要处理分片（大任务拆片并行）、失败重试与幂等、监控告警。

**深入理解**：

- Quartz 集群模式：用数据库表（LOCKS 表）做行锁抢占，多个节点持同一份 Job 定义，同一 trigger 只有一个节点抢到锁并触发。是 JDBC JobStore + 行锁，不是无中心化设计，节点多时 DB 行锁有竞争。
- XXL-Job：调度中心（中心化）按 cron 触发，路由策略（第一个、轮询、随机、一致性哈希、故障转移）选执行器节点；执行器回调执行结果。中心化简单直观，调度中心要保可用。
- ElasticJob：基于 Quartz 与 ZK（3.x 支持 etcd）做弹性分片：任务分片项（如 0~9）注册到 ZK，节点上下线时分片自动重分配，每节点领一片执行。适合数据分片型任务（分库分表各跑一片）。
- 分片广播：把任务广播到所有实例各领参数（如分页号）并行处理，适合「每个节点处理本地数据」的场景；失败一个分片可单独重试。
- 抢占与单点问题：抢占式（竞争锁）简单但触发时刻有竞争开销；主从式（一主多备、Leader 故障时备机顶上）切换快但依赖选主。两者都要保证：切换期间任务最多延迟不错拍，触发与执行要留幂等。
- 失败重试与幂等：任务天然 at-least-once（触发后执行器失联会重发），所以任务体必须幂等；失败要能按策略重试（固定次数/退避/进死信人工处理），并配超时控制防僵尸任务。
- 监控告警：任务成功率、执行时长趋势、漏触发告警。漏触发比失败更危险——失败看得见，漏触发（调度中心挂了、cron 写错）悄无声息。

**为什么这样设计**：定时任务的诉求是「到点执行一次」，多实例下这天然是分布式互斥问题（见 Q01），所以所有分布式调度框架最后都落在「竞争 + 路由」上。区别只在于竞争用什么（DB 行锁、Redis、ZK 选举）、路由怎么算（固定、轮询、分片）。分片存在的意义是单节点执行太慢的大任务（如全量对账）要并行化，代价是分片边界的数据倾斜和分片间顺序无法保证——所以顺序敏感的任务不能分片。

**面试官可能继续追问**：

- **任务执行时间超过触发间隔怎么办？** —— 阻塞策略：单机串行（丢弃后续/排队）、并行（多线程，注意资源）、错过即补（misfire）。调度框架（Quartz misfire 指令、XXL-Job 阻塞处理）都提供配置，选错会把定时任务变成压力源。
- **怎么保证任务不漏不重？** —— 不漏靠调度中心高可用 + 触发记录持久化 + 漏触发检测（比对应触发与实际执行的报表）；不重靠执行器幂等 + 「执行记录」唯一键（任务 ID + 业务日期 + 分片）。对账类任务用「以业务数据为准 + 任务只是触发器」的思路最稳。
- **XXL-Job 调度中心挂了会怎样？** —— 已触发的任务继续执行完（执行器独立），但新触发暂停，恢复后错过的一次按 misfire 策略决定补不补。所以调度中心要做 HA（多实例 + DB），执行器要能脱离调度中心运行一会。

**实际工程场景**：WMS 的定时任务分几类：① 数据同步（ERP 库存同步、运单状态拉取）——按来源分片并行、失败重试、幂等靠「同步批次号」；② 对账（库存对账、收发存）——以业务库为准、任务只做比对和出差异报表，允许事后补跑；③ 清理（过期会话、临时数据）——低优先级、错过即补。实践要点：所有任务体幂等、执行记录落库（任务 ID + 业务日期唯一键）、按「关键任务」和「可补跑任务」分等级配告警，不用一个调度系统既跑秒级任务又跑日终批处理（延迟要求不同应分离）。

**容易答错的地方**：

- 「@Scheduled 多实例部署就重复执行」——分情况：无状态重复执行有害（重复发消息），幂等的重复执行无害；不要一上来就否定单机调度。
- 「分片越多越快」——分片是数据/执行维度切分，分片间无顺序保证；倾斜的分片（如某仓数据量大 10 倍）决定总时长，分片数要按数据分布设计。
- 「任务失败重试就一定幂等」——重试是框架能力，幂等是任务体自己的事；「重试 + 非幂等」等于重复扣款/重复发货。
- 「抢占式调度有单点」——竞争是去中心的，单点只在调度触发/元数据存储上（XXL-Job 的调度中心 DB），要分开说。

> 权威内容：分布式任务调度当前尚未在仓库建设，可参考 XXL-Job 官方文档与 ElasticJob（ShardingSphere）官方文档。

### Q11：分布式链路追踪怎么落地？ `P1` `中频`

**30 秒回答**：链路追踪用 traceId（一次请求全局唯一）+ spanId（单次调用片段）把跨服务、跨 MQ、跨线程的调用串成一条链。落地三件事：① 传播（通过 HTTP header、MQ 消息属性、线程池 MDC 透传上下文）；② 采集（agent 字节码增强无侵入埋点，如 SkyWalking Java agent、Pinpoint）；③ 分析（采样、存储、查询、依赖拓扑）。核心价值是排查线上问题时「一条命令看全链路」而不是登五台机器翻五套日志。

**深入理解**：

- 上下文模型（OpenTracing/OpenTelemetry 的 W3C traceparent）：trace 是完整调用链，span 是有父子关系的片段（spanId + parentSpanId + traceId + 操作名 + 起止时间 + 标签/日志）。跨进程传播靠上游把 context 注入（HTTP header / MQ properties / gRPC metadata），下游提取并成为当前 context。
- MDC 透传：日志框架（logback/log4j2）的 MDC 把 traceId 放进日志上下文，业务日志自动带 traceId，这是「链路」和「日志」互查的关键。要点：线程池/异步场景要手动传递 MDC（装饰 TaskDecorator、TransmittableThreadLocal），漏传是最常见坑。
- MQ 场景：生产端把 trace context 写进消息属性，消费端提取并恢复 span——这样「订单服务 → MQ → 库存服务」在链路里是一条链而不是两段孤岛。SkyWalking 对 RocketMQ/Kafka 的插件自动处理。
- agent 埋点方式对比：字节码增强（SkyWalking、Pinpoint，零业务侵入但要关注启动耗时与兼容性）、OTel Java agent（标准化、手动埋点 SDK 辅之）。版本兼容是主要风险：JDK 大版本、框架升级后 agent 可能失效或误报。
- 采样：全量 trace 存储成本高（每请求多个 span），采样策略：头部采样（请求入口按比例决定整条链采不采，省资源但可能错过「根因在链路后段」的问题）、尾部采样（链路结束后按「有错误/超时」再决定，捕获率高但缓冲区成本高）。生产常见组合：低比例头部采样保常态 + 100% 采集错误链路。
- 与日志/metrics 的关系（可观测性三支柱）：metrics 告警发现问题、tracing 定位问题在哪个服务哪个调用、logging 看细节。三者用 traceId 关联，缺一不可。

**为什么这样设计**：无侵入埋点用字节码增强而不是业务代码里手写，是因为改造成百上千个服务不现实，且埋点代码会污染业务；采样是因为全量 trace 的写入量和存储成本随 QPS 线性增长，而 99% 的 trace 是正常的——只存「有问题的」是成本与效果的折中。traceId 全局唯一而不重用 span 序号，是为了让日志、指标、告警能低代价关联。

**面试官可能继续追问**：

- **traceId 怎么保证全局唯一、跨服务不乱？** —— 入口生成（64/128 位随机或 IP+时间+随机），后续服务只透传不重新生成；跨 MQ 也要带过去。乱序/串链的根源通常是异步线程没透传或重试生成了新 traceId。
- **为什么不用日志的 requestId 自己拼？** —— 可以拼「半个链路」（如果每个服务都乖乖传），但缺少 span 父子关系、耗时分解、依赖拓扑这些结构化能力，自拼方案在异步和扇出场景很快就会退化。可以聊「轻量自建 vs 上 APM」的权衡。
- **SkyWalking 对性能影响多大？** —— agent 增强的调用点才有开销（通常个位数百分比），热点在序列化和上报；采样和批量上报可以把影响压到可接受。要关注的是启动耗时增加（字节码转换）和与老框架的兼容。

**实际工程场景**：WMS 的链路是「PDA/Web → 网关 → 订单/库存/出库服务 → MQ → 作业执行 → ERP/TMS 第三方」，排查「出库单卡住」的问题时链路能直接显示卡在哪个 span（如 ERP 接口 8s 超时）。落地建议：① 入口（网关）强制生成/透传 traceId，日志 pattern 带 traceId；② 异步线程池统一装饰传递 MDC；③ MQ 生产/消费埋点 context；④ 采样 5%~10% + 错误全采；⑤ 告警联动：慢 span 阈值告警直接带 traceId 链接。SkyWalking 因为 Java 生态友好、无侵入、有 UI 是常见选择；Jaeger/Pinpoint 也是常见备选，选型看团队规模与协议偏好（OTel 是趋势）。MQ 侧的指标监控见 [消息队列.md](消息队列.md) Q09。

**容易答错的地方**：

- 「链路追踪只用于查错误」——慢调用分析、依赖瓶颈、容量规划同样靠 span 耗时分解，这是它更大的日常价值。
- 「加了 agent 就一劳永逸」——异步、线程池、MQ 边界是最容易断链的三处，要验证断链率；框架/中间件升级后要回归验证埋点。
- 「采样率越高越好」——头部高采样率存储成本线性涨，且不提高捕获问题的能力；错误 100% + 常态低比例才是性价比解。
- 「traceId 放 header 就跨了服务」——还要有 spanId 和采样标志的完整 context，且各协议（HTTP/MQ/gRPC）注入方式不同，漏一种就断链。

> 权威内容：分布式链路追踪当前尚未在仓库建设，可参考 OpenTelemetry 官方文档与 SkyWalking 官方文档。

### Q12：分布式系统怎么做幂等与防重？ `P0` `高频`

**30 秒回答**：分布式下「重复」不可避免（网络重试、MQ at-least-once、用户双击、定时任务重发），所以通用防重框架是四类手段的组合：唯一键（DB 唯一索引、Redis setNx）、Token 机制（先领 token 后提交）、状态机（合法迁移才放行）、去重表（与业务同事务落记录）。选型看重复的来源：客户端重复用 Token，服务重试用状态机/唯一键，MQ 消费用去重表 + 幂等。

**深入理解**：先划清边界（避免和相邻内容重复）：本题讲分布式层面的通用防重框架；MQ 消费幂等的具体手段与 ack 时机见 [消息队列.md](消息队列.md) Q02；接口级幂等的完整设计（含并发重复 vs 延迟重复、代码示例）见 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md)。

- 唯一键：DB 唯一索引（插入冲突即视为已处理，最可靠但依赖 DB）、业务唯一键（如「订单号 + 操作类型」做唯一索引，防同一订单重复发货）。关键：去重记录与业务数据必须同本地事务，否则出现「去重成功、业务失败」的悬挂记录。
- Token 机制：客户端提交前先请求服务端领一次性 token（Redis 生成并存储），提交时带 token，服务端用 Lua 比对 + 删除原子校验。防的是「用户双击/前端重发」这类客户端重复，是幂等链路的入口闸。
- 状态机：只允许合法状态迁移（已支付→已发货），重复/乱序消息自然被拒（条件更新 update ... set status=目标 where status=来源，affected_rows>0 才成立）。适合流程型业务，是最「业务化」也最稳的幂等。
- 去重表：MQ 消费、回调通知场景，消息 ID/业务键插入去重表（同事务），已存在则跳过。注意 TTL：去重表不能无限长，按业务窗口清理（如保留 7 天），清理窗口要大于最大重试/重复延迟。
- 组合拳：典型链路是入口 Token → 业务唯一键 → 状态机条件更新 → 去重表兜底。多层防线不是冗余，是因为每层防的重复来源不同、失效模式不同。

**为什么这样设计**：幂等的本质是「把不可靠的重复调用收敛到确定的结果」，而分布式系统里没有单一层能覆盖所有重复来源——客户端重发、LB 重试、MQ 重投、定时任务重跑各有通道，所以防线必须分层：每层只解决自己那类重复，且每层都要有明确的失效模式（DB 唯一索引怕热行、Redis 怕过期和故障、状态机怕乱序跨度过大）。另一个设计原则：幂等判断要靠近「副作用发生地」——在真正写库的那一步做条件更新，比在入口拦一道更可靠。

**面试官可能继续追问**：

- **幂等键怎么选？** —— 按「重复的语义单元」选：MQ 消费用消息 ID（但消息 ID 可能被生产端重复生成，更稳的是业务唯一键如「单据号 + 动作」）；支付回调用「商户单号 + 渠道流水号」。核心：幂等键必须对应业务上「一次」的定义。
- **Redis 去重和 DB 唯一索引怎么配合？** —— 常见两级：Redis setNx 挡掉绝大部分重复（快、减 DB 压力），DB 唯一索引兜底防 Redis 失效窗口（过期、故障、集群切换）下的重复。Redis 是性能层，DB 是正确性层。
- **去重表数据量爆炸怎么办？** —— 按时间/业务分表分区、冷数据归档；去重窗口按「最大可能的重复延迟」定（如 MQ 重试上限 + 人工重发间隔），不是越长越好。

**实际工程场景**：WMS 里重复来源很多：PDA 弱网重发提交、MQ 重投、ERP 回调重试。常见组合：出库提交接口用 Token 防 PDA 重点；库存扣减用「单据号」唯一索引 + 状态机条件更新；MQ 消费（如理货完成回写出库单）用去重表（消息 ID）+ 幂等更新。上线新接口的自查清单：重复调用的后果是什么、副作用发生在哪一步、那一步有没有唯一约束。具体方案细节见 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md) 与 [消息队列.md](消息队列.md) Q02。

**容易答错的地方**：

- 「幂等就是加个 Redis setNx」——Redis 是优化层，key 过期后窗口内的重复、Redis 故障期间的重复都会漏；DB 唯一索引/状态机才是正确性层。
- 「去重表越全越好」——全量去重表存储无限增长，且插入本身成为热点；按重复窗口保留 + 冷热分离才是工程解。
- 「幂等只对写接口」——读接口天然幂等不用管，但要防「副作用型读」（如读一次触发一次刷新任务）。
- 「有了幂等就可以随便重试」——重试放大流量，熔断限流（Q08）和幂等是配套的：幂等保证「重试安全」，限流保证「重试不压垮系统」。

> 权威内容：接口幂等的完整设计见 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md)；MQ 消费幂等见 [消息队列.md](消息队列.md) Q02；OWASP 与各框架文档有 Token 机制的通用实现参考。

## 面试前速记

- 分布式锁四步原子性：加锁 + 过期一条 SET NX PX，释放 Lua 比对；Redisson 看门狗只在 leaseTime<0 时生效；主从切换有丢锁窗口，强一致用 etcd/ZK 临时节点。
- 分布式 ID：号段（中心化、递增、重启浪费号段）对雪花（本地、趋势递增、怕时钟回拨）；时间戳放高位是为避免 B+ 树页分裂。
- CAP：P 是前提，只在网络分区时 CP/AP 二选一；BASE 是最终一致的工程化；Nacos 临时实例 AP、持久实例 CP。
- 分布式事务：2PC/XA 强一致但阻塞；TCC 高性能高侵入（防空回滚/悬挂/幂等）；Saga 补偿长流程；本地消息表通用；事务消息绑定 RocketMQ。
- Raft：term + 随机超时选主，多数派提交，已提交不被覆盖；工程选它因为可理解可实现；KRaft 是 Kafka 定制版不是标准 Raft，3.x 才生产可用。
- 一致性哈希：节点变动只迁约 1/N，虚拟节点防倾斜；Redis Cluster 是 16384 槽位变体，可按槽做再平衡。
- 注册中心：CP（ZK）列表新鲜但可能不可用，AP（Eureka）保可用靠客户端重试兜底；心跳周期与剔除时间要折中。
- 限流熔断降级：集群限流 Redis+Lua 精确对均分近似；熔断 Closed→Open→Half-Open 状态机；阈值要压测数据定，不能拍脑袋。
- Session：Redis 集中式（推荐、可控可踢人）对 JWT（无状态、难作废）；混用常见，按调用方类型选。
- 任务调度：抢占式路由保「只跑一次」，分片并行、任务体必须幂等；漏触发比失败更危险，要配检测报表。
- 链路追踪：traceId 透传三处易断链（HTTP header、MQ 属性、线程池 MDC）；agent 无侵入埋点；错误 100% + 常态低比例采样。
- 幂等分层：Token 防客户端重发、唯一键/状态机保正确、去重表兜 MQ；Redis 是性能层，DB 是正确性层。
