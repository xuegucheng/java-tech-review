# Q13. 最左前缀原则？

> 数据库基础 · P0 · 高频

**30 秒回答**：联合索引 (a,b,c) 的查找从最左边的列开始，跳不过前导列直接用后面的列；而且一旦某一列用了范围条件，它之后的列就只能过滤、不能再用于定位——顺序上要把等值列放前、范围列放后。

**深入理解**：B+ 树按索引列的有序性逐层排序，(a,b,c) 的全局有序性是「先按 a、a 相同按 b、b 相同按 c」。所以 `where a=1 and b=2` 能定位到很窄的范围，`where b=2` 则完全无法利用这个顺序，只能全索引扫描或全表扫描。范围截断的机制：`where a=1 and b>2 and c=3` 中，b 是范围，存储引擎在定位到 (1,2) 之后只能顺序扫，无法再用 c 跳定位，c 只能对扫到的行做过滤（配合 ICP）。MySQL 8.0.13 引入 Skip Scan：当前导列 a 的基数很低（如只有几个取值）时，优化器可以把 a 的每个取值分别与 b、c 组合探测，等价于跳过 a——这削弱了「必须带最左列」的绝对性，但仍以 explain 实测为准。

**面试官可能继续追问**：
- **联合索引 (a,b,c)，where a=1 and c=3 用到索引了吗？** —— 用到了 a，c 用不到定位；因为中间断了 b，c 在全局顺序上并不连续，只能作为回表/ICP 的过滤条件。
- **索引列顺序怎么定？** —— 等值条件列优先（区分度高的放最前收益更大需实测），范围列放最后；同时兼顾查询频次——为最高频的查询形态定顺序，其余形态靠冗余索引补。

**实际工程场景**：WMS 按「仓库 + 状态 + 创建时间」查出库单，索引就按 (warehouse_id, status, create_time) 建：warehouse_id 和 status 几乎总是等值条件，create_time 是范围。反过来按「创建时间在前」建，等值列被范围列截断，扫描量会大一个量级——这是最典型的顺序错误。

**容易答错的地方**：把「最左前缀」背成「查询必须按索引列顺序写」。条件书写顺序无所谓，优化器会自动重排；关键是「索引列的存在性与截断位置」，而不是 SQL 里谁先谁后。

> 权威内容：MySQL 联合索引与最左前缀当前尚未在仓库建设，可参考 MySQL 官方文档「Multiple-Column Indexes」「Skip Scan」章节。
