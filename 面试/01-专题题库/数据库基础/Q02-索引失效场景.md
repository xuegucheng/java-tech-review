# Q02. 索引失效有哪些场景？

> 数据库基础 · P0 · 高频

**30 秒回答**：索引失效不是一条条语法规则，而是优化器判断走索引的代价高于全表扫描，最常见的触发点是索引列被函数或运算包裹、隐式类型转换、以通配符开头的模糊匹配，以及联合索引不满足最左前缀。

**深入理解**：场景可以分几类。列上做函数或运算，如 `where date(create_time)='2026-01-01'`、`where id+1=10`，破坏了索引的有序性，只能逐行计算；`varchar` 列与数字比较（`where name = 123`）会把整列转成数字，索引不可用，反过来整型列与字符串常量比较是把常量转成整型，索引仍然可用，方向不要答反。`like '%abc'` 无法定位扫描起点，`like 'abc%'` 可以。联合索引 (a,b,c) 跳过 a 直接用 b、c 不满足最左前缀；范围条件之后的列在存储引擎层无法继续用于定位，只能靠索引下推在索引层过滤（ICP，MySQL 5.6 引入）。`or` 两侧只要有一侧不是索引列，通常整体退化为全表扫。选择性极差的列（如性别）走索引反而更慢。MySQL 8.0.13 起新增 Skip Scan，会在前导列基数很低时跳过它直接用后续列，所以最终要以 `explain` 实测为准。

**面试官可能继续追问**：
- **为什么对索引列用函数会让索引失效？** —— 索引里存的是列的原始值并按它排序，函数运算后的值不再保持这个顺序，优化器无法用有序结构定位，只能逐行算完再比。
- **`like '%abc'` 有没有办法走索引？** —— 有，但要么改数据模型（如把反转串单独建索引处理后缀匹配），要么交给搜索引擎的倒排索引；MySQL 本身的 B+ 树定位不了前缀通配的扫描起点。

**实际工程场景**：WMS 出入库流水按天查询，如果写 `where date(create_time) = '2026-05-01'`，即使 create_time 有索引也会全表扫；正确写法是改成范围条件 `create_time >= '2026-05-01 00:00:00' and create_time < '2026-05-02 00:00:00'`，把函数从列上拿走。

**容易答错的地方**：把隐式转换的方向答反——字符串列与数字比较时「列被转换」，索引失效；数字列与字符串比较时「常量被转换」，索引可用。判断口诀是「列这边的转换都致命」。

> 权威内容：MySQL 索引失效与优化器选择当前尚未在仓库建设，可参考 MySQL 官方文档「Optimization」中的 Range Optimization 与 Index Condition Pushdown 章节。
