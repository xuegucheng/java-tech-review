## 专题定位

- 网络题的特点是「结论人人会背、追问立刻见深度」：每个结论都要能说出「不这样做会发生什么具体故障」，否则只能停在第一层。
- 面试官主要验证：是否理解每个机制解决的具体问题（而不是只会报名字）、能否把机制和线上故障对上（重传、502/504、TIME_WAIT 堆积）、是否分得清流量控制与拥塞控制这类易混概念。
- 5 年以上工程师要答到：TCP 可靠传输的全套机制及相互关系、HTTP 语义（状态码/方法/缓存/会话）的工程取舍、TLS 与认证方案（Session vs JWT）的版本差异与代价。
- 现行标准要知道版本：TCP 是 RFC 9293（取代 RFC 793，握手流程本身未变），HTTP/1.1 是 RFC 9110/9112，HTTP/2 是 RFC 9113，HTTP/3 是 RFC 9114（跑在 QUIC 上），TLS 1.3 是 RFC 8446。

## 题目正文

### Q01：TCP 为什么三次握手？两次为什么不行？ `P0` `高频`

**30 秒回答**：三次握手是双方各自确认「自己的发送能力和对方的接收能力都正常」并同步初始序列号的最小次数，两次只能完成单向确认，无法让客户端确认服务端的发送能力。

**深入理解**：过程是客户端发 SYN(seq=x)，服务端回 SYN+ACK(seq=y, ack=x+1)，客户端回 ACK(ack=y+1)。两次挥手的问题在于：第二次之后服务端已能确认客户端发送正常、自己也收到了 SYN，但客户端收不到任何确认自己 SYN 被收到的消息，也无法验证服务端发送通道是否可用。此外 MSS、窗口扩大因子、SACK permitted 等选项只在 SYN 段携带，一次往返交换不完。两次握手还有一个现实后果：网络中滞留的旧 SYN 重传到达时，服务端会直接建立一条对端并不认账的半开连接并占用资源。现行标准是 RFC 9293，它取代 RFC 793，握手流程本身上没有变化。

**为什么这样设计**：不选两次，是因为两次无法让客户端确认服务端的发送能力，也不足以完成双向的序列号同步；不选四次，是因为服务端的 SYN 与 ACK 可以合并在一个报文里发出，三次已经覆盖双向确认，再加一次往返只增加延迟、不带来任何新信息。

**面试官可能继续追问**：
- **第三次握手可以携带数据吗？** —— 可以。此时客户端已确认服务端收发正常，但**服务端在第三次握手完成前不能发数据**——它发出去也没人确认，且第三次握手的 ACK 可能丢，丢了的连接服务端却不自知。
- **SYN 洪水攻击和握手有什么关系？** —— 攻击者只发 SYN 不收 ACK，服务端的半连接队列被占满，正常握手全部失败。对策是 SYN cookie（不存状态、把状态编码进序列号）和增大半连接队列，属于内核参数与防火墙层。
- **初始序列号为什么是随机的？** —— 防止网络中滞留的旧连接报文被新连接按序号误收，也让攻击者难以预测序号做注入。ISN 由内核按时间等算法生成，不是应用可控的。

**实际工程场景**：排查「连接建立慢」要看 SYN 重传（`netstat -s` 看 `TCPSynRetrans`）与半连接队列溢出；负载均衡/代理每跳都可能引入一次握手，链路越长握手开销越可观，连接复用（keep-alive、连接池）就是为摊掉它。

**容易答错的地方**：把「三次」解释成「三次数据传输」而不是「双向能力确认 + 序号同步」的最小次数；说握手过程随 RFC 9293 发生了大变化（取代的是文档编号，流程未变）；忽略旧 SYN 重传造成半开连接这个现实理由。

> 权威内容：TCP 三次握手细节当前尚未在仓库建设，可参考 RFC 9293 与《TCP/IP 详解 卷 1》。

### Q02：四次挥手为什么要 TIME_WAIT？ `P0` `高频`

**30 秒回答**：TIME_WAIT 是主动关闭方发出最后一个 ACK 后保持 2MSL 的状态，用来保证对端能收到确认，并让本次连接方向的旧报文在网络中彻底消亡。

**深入理解**：挥手过程是 FIN → ACK → FIN → ACK。被动关闭方收到 FIN 时可能仍有数据未发完，所以它的 ACK 和自己的 FIN 不能合并，需要四次。TIME_WAIT 要解决两件事：一是若最后一个 ACK 丢失，对端会重传 FIN，只有主动方还在 TIME_WAIT 才能重发 ACK，否则对端收到 RST 无法正常关闭；二是让本方向上所有报文在网络中消亡，避免被四元组相同的新连接误收。Linux 上该状态实际固定为 60 秒（内核用常量而非直接取 MSL 的两倍），Windows 上则取 2MSL。代价是短连接场景下主动方会堆积大量 TIME_WAIT，占用端口和内核内存，可用连接池复用或调整内核参数缓解。

**为什么这样设计**：不省掉 TIME_WAIT，是因为「ACK 可能丢」和「旧报文可能串扰新连接」这两件事没有别的机制兜底；而把等待放在主动关闭方，是因为只有它知道连接何时真正结束，也只有它是最后一个可能重发 ACK 的一方。

**面试官可能继续追问**：
- **为什么被动关闭方不需要 TIME_WAIT？** —— 它发完 FIN 就进入 LAST_ACK，收到最后一个 ACK 即关闭；它不需要重发自己的 FIN（对端会重传 FIN 给它），也不存在「它先关闭但旧报文还在」的时序问题。
- **TIME_WAIT 太多有什么具体危害？** —— 每个 TIME_WAIT 占用一个四元组和内核内存；作为客户端高频短连接时可能耗尽本地临时端口，报 `cannot assign requested address`；服务端主动关连接的场景还会占满连接跟踪表。
- **怎么缓解？** —— 优先改行为：连接池复用、让客户端主动关闭（把 TIME_WAIT 堆在客户端侧，客户端基数大）；其次才是内核参数（`tcp_tw_reuse` 只对客户端安全、`tcp_max_tw_buckets` 调大上限）。不要动 `tcp_tw_recycle`，它已因 NAT 环境下的严重问题被移除。

**实际工程场景**：压测或短连接风暴后看到 `ss -s` 里大量 `timewait` 是常态，先分清是客户端还是服务端在主动关，再决定是加连接池还是挪关闭方。数据库连接池、HTTP 客户端池（OkHttp、HttpClient）的核心收益之一就是消灭这类 TIME_WAIT。

**容易答错的地方**：说 TIME_WAIT 是 2MSL 所以 Linux 上就是 2×30 秒（Linux 实际固定 60 秒常量）；以为双方都要 TIME_WAIT（只有主动关闭方）；以为 `tcp_tw_reuse` 可以随手开（仅对出向连接安全，且依赖时间戳）。

> 权威内容：TCP 连接终止与 TIME_WAIT 当前尚未在仓库建设，可参考 RFC 9293 与《TCP/IP 详解 卷 1》。

### Q03：HTTP 和 HTTPS 的区别？TLS 握手过程是怎样的？ `P0` `高频`

**30 秒回答**：HTTPS 是 HTTP 报文交给 TLS 加密后再承载在 TCP 之上，解决窃听、篡改和身份伪造；TLS 握手先用非对称方式协商出一个共享的对称密钥，再用这个密钥加密应用数据，默认端口从 80 变为 443。

**深入理解**：TLS 1.2 的完整握手需要两次往返：ClientHello（客户端随机数、支持的版本与密码套件、SNI）→ ServerHello + 证书 + ServerKeyExchange + ServerHelloDone → 客户端验证证书链、生成 PreMasterSecret 并用服务端公钥加密发送（RSA 密钥交换，TLS 1.3 已移除）→ 双方由两个随机数加 PreMasterSecret 导出会话密钥 → ChangeCipherSpec 与 Finished 双向确认。TLS 1.3 把握手压缩到一次往返，并支持 0-RTT 会话恢复，同时移除了 RSA 密钥交换、CBC 模式和 RC4，只保留具备前向安全性的 (EC)DHE，并把密钥交换、证书等握手消息整体加密。代价方面，握手本身多出一到两次往返，证书链验证与密钥运算都要消耗 CPU，因此实践中依赖连接复用和 session ticket 来摊薄。

**为什么这样设计**：业务数据不用非对称加密，是因为 RSA 与椭圆曲线运算比对称加密慢几个数量级，也不适合处理大块数据；非对称只用一次，负责把对称密钥安全地交给对端，之后的数据阶段用 AES 或 ChaCha20 兼顾速度与安全。TLS 1.3 移除 RSA 密钥交换，正是因为它不具备前向安全性——服务端私钥一旦泄露，历史流量就可被解密。

**面试官可能继续追问**：
- **证书链验证具体验什么？** —— 逐级验签直到信任锚（根 CA），再核对域名（SAN/CN）、有效期、吊销状态（CRL/OCSP）。任何一环不过，浏览器报证书错误，常见根因是域名不匹配、缺中间证书、过期。
- **前向安全性是什么？** —— 每个会话用临时密钥交换（ECDHE）导出独立密钥，会话结束即丢弃；即使服务端长期私钥日后泄露，已录制的历史流量也无法解密。RSA 密钥交换做不到这一点。
- **0-RTT 有什么代价？** —— 恢复会话时跳过握手直接发数据，省一个 RTT，但 0-RTT 数据**不保证前向安全、且可被重放**——只能用于幂等请求，支付类接口必须禁用。
- **HTTP/2、HTTP/3 和 TLS 什么关系？** —— HTTP/2（RFC 9113）仍跑在 TLS 之上；HTTP/3（RFC 9114）改用基于 UDP 的 QUIC，TLS 1.3 被直接吸收进 QUIC 握手，连 TCP 队头阻塞也一起绕开了。

**实际工程场景**：服务端性能预算里，TLS 握手 CPU 通常靠 ECDSA 证书 + 会话复用/session ticket 摊薄；内网服务间通信也建议默认 mTLS 或至少 TLS——「内网即可信」的假设在零信任趋势下已不成立。配置上要关掉 TLS 1.0/1.1，优先 TLS 1.2/1.3。

**容易答错的地方**：说「HTTPS 用非对称加密传输数据」（只有密钥交换用，数据用对称）；不知道 TLS 1.3 已移除 RSA 密钥交换；混淆「加密」（机密性）与「证书」（身份认证）解决的是不同问题；说握手只要一次往返（那是 TLS 1.3，1.2 是两次）。

> 权威内容：HTTP 与 TLS 的协议细节当前尚未在仓库建设，可参考 RFC 9110、RFC 8446、RFC 5246 与《图解 HTTP》。

### Q04：一次完整的 HTTP 请求发生了什么？ `P1` `中频`

**30 秒回答**：先用 DNS 把域名解析成 IP，再建立 TCP 连接（HTTPS 还要加密握手），客户端发出请求报文，服务端处理后返回响应，连接按需复用或关闭，浏览器最后解析并渲染。

**深入理解**：解析顺序通常是浏览器自身缓存、hosts 文件、系统 DNS 缓存、本地 DNS 服务器，再由本地 DNS 依次向根、顶级域和权威服务器递归查询，拿到 A 或 AAAA 记录。随后三次握手建立 TCP，若是 HTTPS 则插入 TLS 握手。HTTP/1.1 默认持久连接，支持流水线但响应必须按请求顺序返回，一旦队首阻塞后面全部等待；HTTP/2 在同一连接上做多路复用，改用二进制分帧并用 HPACK 压缩头部；HTTP/3 直接跑在基于 UDP 的 QUIC 上，从传输层避免队头阻塞。真实链路中通常还有 Nginx 等反向代理，内部再转发一跳。响应到达浏览器后，解析 HTML 构建 DOM、解析 CSS 构建 CSSOM，再触发渲染和后续静态资源请求。

**为什么这样设计**：把「定位—连接—请求—响应—渲染」拆成分层协议，每层只解决一个问题，替换任意一层不影响其他层——DNS 换协议、TCP 换 QUIC、HTTP 换版本都是这条演进路线。分层也意味着每层都引入自己的成本（解析缓存、握手 RTT、代理跳数），全链路优化就是逐层砍这些成本。

**面试官可能继续追问**：
- **DNS 解析为什么可能很慢？怎么优化？** —— 递归链每一跳都是 RTT，跨运营商更糟。对策：DNS prefetch、HTTPDNS 绕过 LocalDNS 的调度混乱、合理的 TTL 与缓存预热。
- **HTTP/2 的一路请求卡住会影响别的请求吗？** —— 不会像 HTTP/1.1 那样队头阻塞（多路复用按帧交错），但底层的 TCP 层丢包仍会阻塞所有流——这正是 HTTP/3 换掉 TCP 的动机。
- **为什么说首屏优化绕不开「减少 RTT」？** —— DNS、TCP、TLS 各占 RTT，HTTP/1.1 还有串行请求；早期优化（减少域名数、合并请求、spdy/HTTP2、TLS 1.3、0-RTT）全部围绕压缩 RTT 次数做文章。

**实际工程场景**：做接入层排障时，把「用户慢」拆成 DNS、握手、首包、传输、渲染五段分别量（浏览器 Performance 面板、网关 access log），而不是笼统说「网络慢」。接 CDN 后要意识到链路多了一跳，回源行为与缓存命中率决定这一跳的价值。

**容易答错的地方**：漏掉 DNS 与 TLS 握手（把它们当成「网络层细节」）；说 HTTP/2 完全解决队头阻塞（解决的是 HTTP 层，TCP 层还在）；以为渲染在拿到全部响应后才开始（流式解析，资源是边下边发起的）。

> 权威内容：HTTP 请求全流程当前尚未在仓库建设，可参考 RFC 9110、RFC 9113 与《HTTP 权威指南》。

### Q05：TCP 粘包是怎么产生的？怎么解决？ `P1` `低频`

**30 秒回答**：TCP 是面向字节流的，只保证字节顺序不保留应用层每次写入的边界，接收方一次读取可能拿到多段报文或半段报文，这就是粘包与半包。

**深入理解**：粘包不是协议缺陷，而是字节流语义的必然结果，根因有三处：应用层连续写入多份数据、Nagle 算法把小的待发数据合并成一个段、接收缓冲区里已积累多个报文而应用一次就读走。解决思路只有一条——在应用层自己划边界，主流三种：定长消息、分隔符（如换行）、长度字段（先读固定长度的头，再按长度读体）。这与 UDP 不同，UDP 保留报文边界，一次 send 对应一次 receive，但会丢包和乱序。实践中长度字段最稳，实现时必须同时处理半包（读不满先暂存等下次）和长度非法（校验上限，防止被恶意长度撑爆内存）。

**为什么这样设计**：字节流语义是 TCP 对可靠传输的抽象——它只承诺「字节按序到达」，边界是应用层概念，塞进传输层会让协议背负业务假设。所以责任划分是清晰的：传输层管顺序和可靠，应用层管边界。UDP 保留边界是因为它「尽量交付单个报文」，语义不同，代价是丢包与乱序没人管。

**面试官可能继续追问**：
- **Nagle 算法是什么，什么时候该关？** —— 小写入先攒着，等收到 ACK 或多个小包合并后再发，减少小包数量。请求-响应型、延迟敏感的协议要关（`TCP_NODELAY`），否则「写一次等一次」的交互模式会被 Nagle 叠加 ACK 延迟拖出 40ms 级毛刺。
- **怎么防恶意长度字段？** —— 读到长度先和配置上限比，超限直接断链或报错；缓冲区按上限预分配或用有界缓冲，绝不按对端给的数字直接 malloc。
- **为什么游戏/音视频有时选 UDP？** —— 它们宁愿丢旧包也不要延迟，自己按时间戳丢弃过期帧；用 TCP 会因重传把过期数据硬塞进来，反而更卡。

**实际工程场景**：所有自研 RPC、消息推送、IoT 协议都要处理这题。成熟框架（Netty 的 `LengthFieldBasedFrameDecoder`、gRPC 的 HTTP/2 帧）已内置边界处理，自己写 socket 服务时必须手工实现，且半包暂存逻辑是 bug 高发区。

**容易答错的地方**：把粘包说成 TCP 的缺陷或 bug；只说「用分隔符」不提长度字段方案与半包处理；以为 TCP 有「消息」概念（那是字节流）；忽略长度上限校验这个安全问题。

> 权威内容：TCP 字节流与粘包处理当前尚未在仓库建设，可参考 RFC 9293 与《UNIX 网络编程 卷 1》。

### Q06：TCP 怎么保证可靠传输？ `P0` `高频`

**30 秒回答**：核心是序列号加确认应答——每个字节编号，接收方累计确认，发送方对「未确认的数据」负责：超时未确认就重传，收到三个重复 ACK 就快速重传；再用滑动窗口实现流量控制防止压垮接收方，用拥塞控制防止压垮网络。

**深入理解**：拆开讲每个机制解决的具体问题：

| 机制 | 解决什么问题 | 关键点 |
| --- | --- | --- |
| 序列号 + 累积确认 | 乱序与丢失检测 | 每个字节有序号，ACK = n 表示「n 之前的数据都正确收到」；SACK 选项可报告不连续的块，减少不必要重传 |
| 超时重传 | ACK 丢失或数据丢失 | RTO 基于实测 RTT 动态计算（SRTT + RTTVAR，Karn 算法排除重传样本），超时后 RTO 指数退避；重传是兜底路径 |
| 快速重传 | 超时等待太慢 | 连续 3 个重复 ACK 说明后续段到了而中间段丢了，不等 RTO 立即重传 |
| 滑动窗口 | 接收方处理不过来 | 发送方只发「在窗口内」的数据；接收方通过 ACK 的窗口字段通告剩余容量，窗口为 0 时发送方停发，靠窗口探测器恢复 |
| 流量控制（rwnd） | 保护接收方 | 接收窗口由**接收端**决定，防止发送方把接收缓冲区冲爆 |
| 拥塞控制（cwnd） | 保护网络 | 拥塞窗口由**发送端**根据丢包/时延推断：慢启动指数增长 → 达到 ssthresh 后拥塞避免线性增长；超时判丢包则 ssthresh 减半重新慢启动；3 个重复 ACK 走快重传 + 快恢复（cwnd 减半后线性增长，不回到起点） |

发送方的实际发送量取 `min(rwnd, cwnd)`——两个窗口一个保护接收方、一个保护网络，任何一边收紧都生效。

**为什么这样设计**：可靠不等于「每条都单独确认」——累积确认加 SACK 在开销与信息量之间折中；重传分两条路径（超时 / 重复 ACK）分别覆盖「严重拥塞」和「轻微丢包」，避免一律等超时把时延放大；快恢复不回到慢启动，是因为丢包不代表网络已瘫，回到起点等于白白放弃带宽。

**面试官可能继续追问**：
- **流量控制和拥塞控制的区别？** —— 前者保护接收方（rwnd 由对端通告，解决「发太快收不过来」），后者保护网络（cwnd 自己算，解决「发太快中间设备扛不住」）。前者是对端明确告诉你的，后者是猜的。
- **为什么 RTO 必须动态？** —— 固定 RTO 要么太短（把正常的延迟抖动误判成丢包，触发虚假重传）、要么太长（真丢包后干等）。Jacobson 算法用平滑 RTT 加 RTT 偏差动态估算，是对「网络时延不确定」的适应。
- **快速重传为什么是 3 个重复 ACK？** —— 工程经验值：容忍一定的乱序重排（乱序也会产生重复 ACK）的同时，保证及时性。取 2 太容易被乱序触发，取更大则等得更久。

**实际工程场景**：排查吞吐上不去，先分清是接收方窗口（对端应用读得慢，`ss -i` 看 rcv_space）还是拥塞窗口（链路丢包，看重传率 `Retrans`）；跨公网高 RTT 场景的实际吞吐受带宽时延积（BDP = 带宽 × RTT）限制，这就是为什么跨国传输难跑满带宽。内核参数（缓冲大小、BBR）调优也建立在这两个窗口模型上。

**容易答错的地方**：混淆流量控制与拥塞控制（或只说一个）；说 TCP 保证「不丢包」而不提是靠重传兜底；以为 ACK 是对每条报文单独确认（默认是累积确认）；以为重传后 RTO 不变（会翻倍退避）。

> 权威内容：TCP 可靠传输机制当前尚未在仓库建设，可参考 RFC 9293 与《TCP/IP 详解 卷 1》。

### Q07：TCP 和 UDP 的区别？ `P0` `高频`

**30 秒回答**：TCP 是面向连接的可靠字节流：有握手、序号确认、重传、流量与拥塞控制，代价是额外 RTT、状态和 20 字节头部；UDP 是无连接的报文：尽力交付、保留报文边界、不保证可靠与有序，头部只有 8 字节。要可靠又要低时延，现代方案是 QUIC——在用户态把可靠性、加密、多路复用重做一遍。

**深入理解**：

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接，三次握手维护状态 | 无连接，每报文独立路由 |
| 可靠性 | 序号 + ACK + 重传，丢不丢由内核管 | 尽力交付，丢、重、乱都不管 |
| 数据形态 | 字节流，无报文边界（粘包见 Q05） | 保留报文边界，一次 send 对应一次 recv |
| 头部开销 | 20 字节起，选项可到 60 | 固定 8 字节（源/目的端口、长度、校验和） |
| 拥塞/流量控制 | 有（rwnd + cwnd） | 无，发多快全凭应用 |
| 传输模式 | 仅单播（点对点四元组） | 单播、广播、多播 |
| 典型场景 | 文件、HTTP、数据库、RPC | 音视频通话、DNS、游戏、QUIC |

UDP 的适用逻辑不是「快」而是「重传没意义」：视频/语音帧等到了也过期，丢了不如直接跳过；DNS 一问一答，自己控制重传比内核的超时策略更懂场景。TCP 不适合广播/多播是结构性的：它的 ACK、序号、窗口都假设单一对端，广播场景里接收方能力异构，一个慢接收端就会通过拥塞控制拖垮整个组，且每个接收方都要回 ACK 会造成 ACK 风暴。

**为什么这样设计**：传输层提供两个极端而不是中间态，是因为「可靠性做在哪」没有统一答案——TCP 把它做进内核，应用无感但失去控制；UDP 把控制权还给应用，代价是每个应用都要自己造轮子。QUIC（HTTP/3 的底座）证明的正是第三条路：在用户态实现可靠 + 加密 + 多路复用，还不受操作系统升级拖累。

**面试官可能继续追问**：
- **UDP 怎么做可靠？** —— 应用层自己补：序号、ACK、重传、拥塞（如 KCP 以带宽换时延，QUIC 把 TCP 的机制搬到用户态并整合 TLS 1.3）。
- **UDP 一定比 TCP 快吗？** —— 不一定。免握手只在「少量报文」时占优；长连接持续传输时，TCP 的拥塞控制与批量确认反而可能跑出更高吞吐。比较要带场景。
- **TCP 为什么不能做广播？** —— 点对点语义：确认、序号、窗口、拥塞控制全部围绕单一对端设计，多接收方时 ACK 风暴与异构接收能力无解。广播/多播天然属于 UDP。

**实际工程场景**：内网服务间通信默认 TCP（可靠性免费且生态成熟）；延迟敏感且能容忍丢包的实时流用 UDP 自研或基于 WebRTC/QUIC；物联网、游戏网关是 UDP 的典型战场。用 UDP 自研可靠协议前先评估 QUIC/KCP 等现成方案，别从零写重传。

**容易答错的地方**：说 UDP 一定比 TCP 快（要分场景）；说 TCP 支持广播/多播；说 UDP 没有校验和（有，且 IPv6 下强制）；只说「UDP 不可靠」不说它保留了报文边界这个关键差异。

> 权威内容：TCP 与 UDP 对比当前尚未在仓库建设，可参考 RFC 9293、RFC 768 与《TCP/IP 详解 卷 1》。

### Q08：HTTP 常见状态码有哪些？ `P1` `中频`

**30 秒回答**：1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误；高频的是 200/204/206、301/302/307/308、304、400/401/403/404/405/429、500/502/503/504——记的时候按「谁的错、下一步干什么」分类记，比死背数字牢。

**深入理解**：逐个说含义：

| 状态码 | 含义与要点 |
| --- | --- |
| 200 OK | 请求成功，响应体带资源 |
| 204 No Content | 成功但无响应体（PUT/DELETE 常用；与 200 的区别是没 body） |
| 206 Partial Content | 范围请求成功（断点续传、视频拖放） |
| 301 Moved Permanently | 永久重定向；历史上多数实现把方法改成 GET |
| 302 Found | 临时重定向；方法处理历史上不统一，是历史包袱最大的一档 |
| 307 Temporary Redirect | 临时重定向，**严格保持原方法与请求体** |
| 308 Permanent Redirect | 永久重定向且保持方法，是 301 的「保方法」版 |
| 304 Not Modified | 协商缓存命中（`If-None-Match`/`If-Modified-Since` 比对未变），无响应体 |
| 400 Bad Request | 请求本身有问题（语法、参数、JSON 解析失败） |
| 401 Unauthorized | **未认证**，需带 `WWW-Authenticate` 头说明认证方式 |
| 403 Forbidden | 已认证但**无权限**；与 401 是「没登录」和「登录了也没用」的区别 |
| 404 Not Found | 资源不存在（或存在但不愿暴露，与 403 的选择是安全策略） |
| 405 Method Not Allowed | 方法不支持，应带 `Allow` 头列出支持的方法 |
| 429 Too Many Requests | 限流；可带 `Retry-After` 告知退避时长 |
| 500 Internal Server Error | 服务端未捕获异常，最笼统的「我炸了」 |
| 502 Bad Gateway | 代理/网关从上游收到**无效响应**（上游挂了、协议错误、连接被拒） |
| 503 Service Unavailable | 服务主动不可用（过载、熔断、维护），常带 `Retry-After` |
| 504 Gateway Timeout | 代理**等上游超时**，上游根本没在时限内响应 |

502 与 504 的区别是高频追问：502 是「上游回了但内容不对/连不上」，504 是「上游连上了但迟迟不回」。301/302/307/308 的分界同样是高频：方法是否保持——307/308 保持，301/302 历史上不保持（302 的不统一正是 307 被引入的原因）。语义上这些状态码从 HTTP/1.1（RFC 7231）到 HTTP/2（RFC 9113）、HTTP/3（RFC 9114）一脉相承，现行定义在 RFC 9110 第 15 节。

**为什么这样设计**：状态码把「谁该负责、下一步做什么」编码进协议：4xx 让客户端改请求（改不动才是 5xx），5xx 让客户端重试或降级。缓存层、重试框架、CDN、爬虫全都依赖这套语义做决策——所以「什么都返回 200 + body 里塞错误码」等于放弃了整个生态的自动化能力。

**面试官可能继续追问**：
- **301 和 302 对 SEO 有什么不同？** —— 301 传递权重、表示站点永久迁移；302 不传递（历史上被大量滥用于临时跳转）。换域名、HTTP 跳 HTTPS 用 301，活动临时页用 302。
- **304 是怎么产生的？** —— 协商缓存：请求带 `If-None-Match`（ETag）或 `If-Modified-Since`，服务端比对资源未变则回 304 无 body，浏览器用本地副本。配合 `Cache-Control`/`Expires` 构成强缓存 + 协商缓存两级。
- **重试策略应该怎么定？** —— 只对幂等请求重试；对 429/503 按 `Retry-After` 退避，对 502/504 换上游节点重试，对 400/401/403 重试无意义（问题在请求本身）。

**实际工程场景**：网关层要做统一错误映射——把内部异常、超时、上游不可用分别翻译成 500/504/502，并留 traceId；健康检查端点返回 200；限流中间件返回 429 + `Retry-After`。监控按 5xx 细分 500/502/504 才能区分「应用 bug」和「链路/上游问题」。

**容易答错的地方**：把 401 理解成「没权限」（是未认证）；把 502 当服务端代码错误（那是 500；502 是网关到上游这一段）；以为所有 3xx 都保持方法（307/308 才保持）；所有接口一律 200 + 错误码在 body（放弃协议语义）。

> 权威内容：HTTP 状态码语义当前尚未在仓库建设，可参考 RFC 9110 第 15 节与《图解 HTTP》。

### Q09：Cookie、Session、Token、JWT 是什么关系？ `P0` `高频`

**30 秒回答**：Cookie 是浏览器的存储与传输机制，Session 是服务端状态——经典组合是 Session ID 存 Cookie、数据存服务端，属有状态方案；Token/JWT 是无状态方案，凭据自描述、签名可验证，服务端不存会话。JWT 的代价是无法主动失效，靠短过期加刷新令牌兜底。

**深入理解**：Cookie 由 `Set-Cookie` 种下、请求自动带回；关键属性：`HttpOnly`（禁 JS 读取，防 XSS 偷窃）、`Secure`（仅 HTTPS 传输）、`SameSite`（Lax/Strict/None，防 CSRF，Chrome 80 起默认 Lax，`None` 必须配 `Secure`）、`Domain`/`Path`/过期时间；单条约 4KB。Session 的分布式三方案：sticky（同会话路由到同节点，节点故障即丢会话）、复制（节点间广播同步，节点多时流量放大、内存翻倍）、Redis 集中式（主流，代价是每请求多一跳网络 IO 和单点依赖）。Token 两种形态：不透明随机串（服务端查存储，可随时吊销，本质是换了载体的 Session ID）和 JWT（`Header.Payload.Signature` 三段 Base64Url，HS256 对称签名或 RS256/ES256 非对称；签名保证**未被篡改**，但 payload 只是编码不是加密，敏感信息不能放）。JWT 的结构性问题：签发后到过期前始终有效，注销、改密、踢下线都做不到；应对是组合拳——access token 短有效期（分钟级）+ refresh token 长寿命可轮换、黑名单（按 `jti` 注销）、版本号机制（用户改密后旧 token 全部失效）。

**为什么这样设计**：有状态方案把「状态存哪」变成架构问题（ sticky 赌路由、复制赌规模、Redis 赌延迟），无状态方案把「状态谁验」变成算法问题——JWT 用签名验证换水平扩展能力，代价是交出控制权（无法失效）。这个交易在所有无状态认证里都存在，JWT 只是把它做得最彻底。

**面试官可能继续追问**：
- **JWT 安全吗？** —— 防篡改（有签名）但不防窃听（不加密，必须 HTTPS）、不防重放（无 `jti`/`nonce` 时同一 token 可反复用）、算法要钉死（`alg: none` 攻击就是篡改头部把签名关掉）。服务端必须显式指定期望算法。
- **退出登录怎么让 JWT 失效？** —— 短过期是主策略；要求即时生效就得引入服务端状态：黑名单存 `jti` 到过期时间，或按用户维护 token 版本号。这等于把无状态又改回有状态，所以要按业务对「即时失效」的真实需求取舍。
- **CSRF 和 XSS 分别防什么？** —— CSRF 是盗用浏览器自动带的凭证（`SameSite` + 双重提交 token），XSS 是偷页面里的敏感数据（`HttpOnly` + CSP）。核心 Cookie 认证两者都要防；Bearer Token 放 `Authorization` 头天然免疫 CSRF，但仍是 XSS 的盗窃目标。

**实际工程场景**：单体或少量节点用 Session + Redis 集中式最稳（可控、可踢人）；微服务间传递身份用 JWT（免查存储、声明自带），但只放必要声明、控制体积（每个请求都带）、access token 短命 + refresh 轮换；纯前端 SPA 现在更推荐 BFF 模式下 Cookie 存 Session，把 token 藏后端，XSS 面更小。多端（App + Web）登录态建议独立 token 体系分开治理。

**容易答错的地方**：说 JWT 是加密的（默认只签名，payload 可解）；说 JWT 完全不需要服务端存储（黑名单/刷新令牌就是存储）；把 401 与 token 过期处理混为一谈（过期是重新刷新的信号，不是权限不足）；以为 `SameSite=Lax` 万能（跨站 POST 场景要配合 token）。

> 权威内容：会话与令牌机制当前尚未在仓库建设，可参考 RFC 6265（Cookie）、RFC 7519（JWT）与 OWASP Session Management Cheat Sheet。

### Q10：GET 和 POST 的区别？ `P1` `中频`

**30 秒回答**：语义上 GET 是「取资源」——安全、幂等、可缓存；POST 是「提交处理」——不安全、不幂等、默认不缓存。技术上 GET 也能带 body、POST 也不比 GET 更安全，差异主要是语义和基础设施对语义的待遇（缓存、重试、长度、编码），不是安全边界。

**深入理解**：

| 维度 | GET | POST |
| --- | --- | --- |
| 语义 | 获取资源，不应改变状态 | 提交数据、触发处理 |
| 安全/幂等 | 安全 + 幂等 | 不安全 + 不幂等 |
| 缓存 | 响应可被浏览器/代理/CDN 缓存 | 默认不缓存 |
| 参数位置 | URL query，长度受限（浏览器约 2KB～8KB，服务端如 Nginx 的 `large_client_header_buffers` 也限） | 请求体，基本不限 |
| 编码 | `application/x-www-form-urlencoded` 拼在 URL 后 | form 编码、JSON、multipart 均可 |
| 浏览器行为 | 可收藏、刷新无害重放 | 刷新弹「是否重新提交」 |
| 隐私面 | 参数进 URL → 进 Referer、日志、浏览历史 | 参数在 body，不进 URL |

纠正常见误解：GET **可以**带 body（RFC 9110 不禁止，只是没有定义好的语义，多数基础设施会忽略它）；POST 不是「更安全」——两者都不加密，安全靠 HTTPS，POST 只是不把参数落在 URL 和日志里；POST 也不天然幂等（重复提交可能创建多笔订单，这正是幂等键存在的理由）。REST 语义对应：GET 列表/详情、POST 创建（服务端生成 ID）、PUT 全量替换（幂等）、PATCH 部分更新、DELETE 删除（幂等）。

**为什么这样设计**：HTTP 把方法语义做成协议级契约，缓存、重试、爬虫、CDN、预取全部依赖它做正确决策——用 POST 做查询等于放弃所有缓存层，用 GET 做写入等于让预取器帮你重复触发副作用。幂等性尤其值钱：它是自动重试、断路器恢复、消息去重的前提。

**面试官可能继续追问**：
- **PUT 和 POST 创建资源的区别？** —— PUT 幂等：同一 URL 重复放同一份数据结果一样，适合指定 ID 创建与全量替换；POST 不幂等：重复提交创建多份，适合服务端生成 ID。选错会让重试把数据写坏。
- **为什么一般不用 DELETE 传 body？** —— 语义上 DELETE 按 URI 定位资源，请求体没有定义良好的含义；协议允许带但生态不支持，删除条件应放 query。
- **OPTIONS 和 HEAD 用在哪？** —— OPTIONS 是 CORS 预检（带 `Origin`/`Access-Control-Request-Method` 询问服务端许可）；HEAD 是「GET 但不返回 body」，用于探活和拿元信息（`Content-Length`、ETag）。

**实际工程场景**：查询一律 GET（吃缓存、可分享、可预取）；写操作 POST/PUT/PATCH；网关和重试框架按幂等性决定哪些方法可自动重试。涉及金额、库存的写接口即使语义是 POST，也要在业务层加幂等键——协议幂等和业务幂等是两回事。

**容易答错的地方**：说 GET 不能带 body（能，只是没语义）；说 POST 比 GET 安全（都不加密）；说 POST 幂等（不幂等才是它要幂等键的原因）；把 REST 设计成「URL 里带动词」（`/getUser`、`/deleteOrder` 是反模式，资源名词 + 方法表达动作）。

> 权威内容：HTTP 方法语义当前尚未在仓库建设，可参考 RFC 9110 第 9 节与《HTTP 权威指南》。

## 面试前速记

- 三次握手的本质：双向能力确认 + 初始序列号同步；两次无法让客户端确认服务端发送能力，还会被旧 SYN 重传造出半开连接。
- TIME_WAIT 两个理由：最后一个 ACK 可能丢（要能重发）、旧报文要在网络里消亡（防四元组复用后串扰）；只有主动关闭方有，Linux 固定 60 秒。
- TLS 1.2 握手两次 RTT、1.3 一次且支持 0-RTT；1.3 移除 RSA 密钥交换（无前向安全），只留 (EC)DHE；非对称只用于换密钥，数据用对称加密。
- 可靠传输 = 序号 + 累积确认（SACK 报告空洞）+ 超时重传（RTO 动态、指数退避）+ 快重传（3 个重复 ACK）+ 流量控制（rwnd，保护接收方）+ 拥塞控制（cwnd 慢启动/拥塞避免/快恢复，保护网络）；实际发送量取 min(rwnd, cwnd)。
- TCP 是字节流无边界，UDP 保留报文边界；UDP 的优势场景是「重传没意义」而不是「更快」；TCP 点对点语义决定了它不能做广播/多播。
- 状态码按「谁的错、下一步干什么」记：401 未认证 vs 403 无权限；502 是上游回了无效响应，504 是等上游超时；307/308 保持方法，301/302 历史上不保持。
- 缓存两级：强缓存（`Cache-Control`/`Expires`）命中不发请求，协商缓存（ETag/`If-None-Match`）命中回 304 无 body。
- Cookie 四属性：HttpOnly（防 XSS）、Secure（仅 HTTPS）、SameSite（防 CSRF，Lax 是默认）、Domain/Path；Session 分布式三方案：sticky、复制、Redis 集中。
- JWT = Header.Payload.Signature，签名防篡改、payload 不加密；无法主动失效 → access 短命 + refresh 轮换 + 黑名单 + 版本号。
- GET 可带 body 但无语义，POST 不比 GET 安全（都不加密，靠 HTTPS）；POST 不幂等，写接口业务层要幂等键。
- REST 语义：GET 读、POST 创建、PUT 全量替换、PATCH 部分更新、DELETE 删；幂等性是自动重试的前提。
- 版本坐标：TCP 现行标准 RFC 9293；HTTP/1.1 = RFC 9110/9112，HTTP/2 = RFC 9113，HTTP/3 = RFC 9114（QUIC）；TLS 1.3 = RFC 8446。
