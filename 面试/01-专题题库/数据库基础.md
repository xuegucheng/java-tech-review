### Q01：InnoDB 索引为什么用 B+ 树而不用 B 树或哈希？ `P0` `高频`

**30 秒回答**：因为 B+ 树的非叶子节点不存数据、叶子节点之间还有序连成链表，在同样的磁盘 IO 次数下能支持范围查询和排序，而 B 树和哈希索引做不到。

**深入理解**：B+ 树非叶子节点只放键和指针，同样大小的页能容纳更多键，扇出更大、树更矮，典型千万行表也就 2～4 层，一次查询的随机 IO 次数可预期。数据全部集中在叶子层，叶子按索引列有序并用指针串成双向链表，所以 `between`、`order by`、`limit` 这类范围与顺序扫描只需定位起点再顺序读。B 树每个节点都带数据，单页能放的键更少、树更高，而且范围查询需要跨层中序遍历并回溯父节点，随机 IO 更多。哈希索引只支持等值查找，不支持范围、排序和最左前缀，冲突时还要扫链表，因此 InnoDB 没有把它做成用户可选的索引类型，而是提供自适应哈希索引（AHI），由引擎针对热点等值查询自动建立，无法手工创建。

**为什么这样设计**：磁盘数据库的查询代价由随机 IO 次数主导，选索引结构本质是「用更矮的树换更少的页读取」；如果数据全在内存、随机访问几乎免费（比如 Redis），跳表或哈希才是更合适的结构。所以 B+ 树是磁盘这个前提下的最优解，而不是普适最优解。

**面试官可能继续追问**：
- **MySQL 一棵 B+ 树能存多少行数据？** —— 按默认页大小 16KB、主键 bigint（8 字节）+ 指针（约 6 字节）估算，单节点可存约 1000+ 个键，两层即可容纳千万级，三层可达数十亿级，所以千万级表的树高通常是 2～3。
- **自适应哈希索引（AHI）为什么不能手工创建？** —— 它是引擎根据查询模式在内存中自动建立的，判断依据是「该等值查询是否足够热」，交给引擎动态决策比让 DBA 手工配置更可靠，也无法通过 DDL 干预。

**实际工程场景**：建索引时优先用有序自增主键，让新记录落在 B+ 树最右侧、避免页分裂；用 UUID 作主键时插入位置随机，页分裂与磁盘随机写会显著推高写入放大——这是日志表、流水表最常见的隐性瓶颈。

**容易答错的地方**：把「B+ 树矮」说成唯一理由。更关键的是范围查询与排序：B 树数据分散在各层，范围扫描要跨层回溯；B+ 树叶子层有序且链表相连，一次定位后顺序读即可。

> 权威内容：MySQL 索引与 B+ 树当前尚未在仓库建设，可参考 MySQL 官方文档「InnoDB Indexes」章节与《高性能 MySQL》索引章节。

### Q03：千万级数据分页怎么优化？ `P0` `高频`

**30 秒回答**：深分页慢是因为 `limit 1000000, 20` 仍然要让数据库扫过并丢弃前 100 万行，优化的核心是让数据库根本不去碰这些行。

**深入理解**：三种常用手段。延迟关联：先用覆盖索引只取主键，`select id from t order by id limit 1000000, 20`，再拿这 20 个主键回表取其余字段，把 100 万次回表降到 20 次。游标分页（keyset）：把 offset 换成条件 `where id > 上一页最后一个 id order by id limit 20`，每页代价恒定，代价是只能顺序翻页、不能跳页，并要求排序字段稳定唯一（通常就是主键）。业务侧限制可翻页深度，或改用搜索引擎的 `search_after`，把大偏移量交给倒排索引。另外要确认 `order by` 的列本身有索引，否则即使分页写法对了仍会多出一次 filesort；覆盖索引能让第一步完全在索引内完成。

**面试官可能继续追问**：
- **延迟关联为什么快？** —— 覆盖索引扫描不碰数据行，第一步拿 20 个主键的代价远小于 100 万次回表；回表次数从「偏移量 + 页大小」降到「页大小」。
- **游标分页的排序字段不唯一会怎样？** —— 边界上可能漏记录或重复记录，必须补一个唯一字段做次级排序，比如 `order by create_time, id`。

**实际工程场景**：管理后台的流水列表天然要深翻页，用延迟关联扛住；面向 C 端的分页（订单列表、消息列表）改成游标分页，产品上表现为「加载更多」而不是「跳到第 N 页」——这个产品约束值得提前说，面试里讲出「深翻页需求本身该不该存在」是加分项。

**容易答错的地方**：只说「加索引」。深分页慢的根源是偏移量导致的大量扫描与丢弃，索引只能保证定位快，不能消除扫描行数；没有覆盖索引时 `limit` 第一步本身就在反复回表。

> 权威内容：MySQL 深分页与 LIMIT 优化当前尚未在仓库建设，可参考 MySQL 官方文档「LIMIT Optimization」章节。

### Q04：MVCC 是怎么实现的？解决什么问题？ `P0` `高频`

**30 秒回答**：MVCC 靠每行的隐藏版本字段、undo log 版本链和 ReadView 实现，让普通查询读取历史版本而不加锁，解决的是读写互相阻塞的问题。

**深入理解**：InnoDB 每行都有隐藏列 `DB_TRX_ID`（最后修改该行的事务 id）和 `DB_ROLL_PTR`（指向 undo log 中的旧版本），每次修改会生成 undo 记录并把这些版本串成链。快照读时生成 ReadView，它记录当前未提交的活跃事务 id 集合以及可见性判断需要的上下界，然后沿版本链从新到旧找到第一个对当前事务可见的版本。可重复读（RR，InnoDB 默认）只在事务第一次快照读时生成 ReadView 并一直复用，所以同一事务内多次读结果一致；读已提交（RC）每次 select 都重新生成，所以能看到别的事务刚提交的数据。要注意当前读（`select ... for update`、`update`、`delete`）不走 MVCC，它读最新版本并加锁。

**为什么这样设计**：用「读旧版本」换来读操作完全不加锁，代价是旧版本不能立即回收，需要 purge 线程清理 undo；长事务会让版本链不断变长、undo 表空间膨胀，既拖慢查询也拖慢回滚。所以长事务在这个设计下有明确代价，不是代码风格问题。

**面试官可能继续追问**：
- **ReadView 里有哪些字段？** —— `m_ids`（生成快照时活跃的事务 id 列表）、`min_trx_id` 与 `max_trx_id`（列表的最小值与下一个待分配 id）、`creator_trx_id`（自己的事务 id）。判断规则：比自己新的不可见，比自己旧且已提交的可见，落在活跃区间里的看是否在 `m_ids` 中。
- **为什么 RR 下能解决幻读？** —— 快照读靠 ReadView 复用，同一事务内多次读看到同一份数据；当前读则靠 Next-Key Lock（间隙锁）阻止别的事务在查询范围内插入，两者合起来才堵住幻读。

**实际工程场景**：长事务是线上 undo 膨胀的头号来源——一个忘提交的事务挂着，版本链就一直长。监控上要盯 `information_schema.innodb_trx` 里运行超过阈值的事务；批量任务要拆成小事务、用完即提交。

**容易答错的地方**：说「MVCC 解决了幻读」。严格说快照读解决的是不可重复读，RR 下的幻读要靠间隙锁；RC 下 MVCC 挡不住幻读，当前读也基本没有间隙锁。

> 权威内容：InnoDB MVCC 与多版本并发控制当前尚未在仓库建设，可参考 MySQL 官方文档「InnoDB Multi-Versioning」章节与《MySQL 是怎样运行的》事务章节。

### Q05：事务隔离级别和 MVCC 是什么关系？ `P0` `高频`

**30 秒回答**：MVCC 是实现「读已提交」和「可重复读」这两个隔离级别的手段，隔离级别决定 ReadView 的生成时机；而写写冲突不归 MVCC 管，靠锁解决。

**深入理解**：SQL 标准定义 RU、RC、RR、Serializable 四级，InnoDB 默认 RR。对应关系是：RC 下每条快照读都新建 ReadView，因此可能出现不可重复读；RR 下只在第一次快照读时生成并复用，因此可重复读；RR 还通过 Next-Key Lock 让当前读也基本避免幻读，而 RC 下间隙锁基本不失效，并发更高但更依赖 binlog 的 row 格式。快照读走 MVCC，当前读走锁，两者分工。RU 在 InnoDB 中几乎没有实际使用场景，Serializable 会给普通查询也加共享锁，用并发换正确性。

**为什么这样设计**：因为 MVCC 只能决定「某个版本该不该被读到」，它无法阻止两个事务同时修改同一行造成丢失更新，这类写写冲突必须由锁裁决；把可见性交给版本、把冲突交给锁，读多写少的业务才不会被读写互斥拖慢。

**面试官可能继续追问**：
- **Serializable 下普通 select 会加锁吗？** —— 会加共享锁，所以 Serializable 的读也要等写结束，并发度接近单线程，生产几乎不用。
- **隔离级别越高越好吗？** —— 不是。每升一级都在加锁范围或版本链长度上付出代价，选型看业务能接受的不一致窗口，互联网默认 RC 或 RR，金融强一致场景才会考虑 Serializable 加显式锁。

**实际工程场景**：库存扣减这类写写冲突场景，靠的是 `update ... where count >= 1` 的行锁与影响行数判断，和隔离级别关系不大；把「加了最高隔离级别就万事大吉」当结论，会在锁竞争上吃大亏。

**容易答错的地方**：把「幻读」和「不可重复读」混为一谈。前者是「同样的范围条件两次查出的行集合不同」（多了或少了几行），后者是「同一行两次读出的值不同」；RC 就已经解决了后者，但不解决前者。

> 权威内容：MySQL 事务隔离级别当前尚未在仓库建设，可参考 MySQL 官方文档「Transaction Isolation Levels」章节。

### Q07：MySQL 死锁怎么排查？ `P1` `重点`

**30 秒回答**：先用 `show engine innodb status` 的 `LATEST DETECTED DEADLOCK` 段（或开启 `innodb_print_all_deadlocks` 把每次死锁写进错误日志）看两个事务各持有什么锁、在等什么锁，再回到 SQL 和表结构找加锁顺序不一致的地方。

**深入理解**：死锁段里重点看四件事：两个事务的 SQL、各自持有的锁与等待的锁（如 `X locks rec but not gap` 这类记录）、涉及的索引，以及最终被回滚的是哪个事务。最常见的原因是更新条件没走索引，扫描到的行都被锁住，把行锁放大成大范围锁，此时两个事务极易形成环路；其次是加锁顺序不一致，事务 A 先改 a 再改 b、事务 B 先改 b 再改 a。InnoDB 会自动检测死锁并回滚「代价较小」的那个事务，所以业务侧必须能重试。线上定位锁等待可以用 `performance_schema.data_locks` 与 `data_lock_waits`；MySQL 8.0 已移除 `information_schema.INNODB_LOCKS`、`INNODB_LOCK_WAITS`，只有 5.7 及以前才用它们。解决方向是统一加锁顺序、按主键顺序批量更新、拆小事务缩短持锁时间、让更新条件走唯一索引以减少间隙锁，必要时把隔离级别降到 RC 减少 gap lock。

**为什么这样设计**：因为死锁不是缺陷而是并发加锁的必然产物，InnoDB 的策略是「检测到就回滚代价小的一方」，所以工程目标不是消灭死锁，而是保证死锁后业务可重试、并尽量不让单条语句的锁范围扩大。

**面试官可能继续追问**：
- **为什么更新条件不走索引时锁范围会放大？** —— 每条被扫描到的行都会加锁，全表扫就意味着把整表行都锁了，而且还会带上间隙锁，两个这样的语句几乎必然成环。
- **业务侧收到死锁报错怎么办？** —— 按「可重试错误」处理：捕获后有限次重试（带退避），同时报警观察频率；只重试不改代码，等于放任根因。

**实际工程场景**：WMS 库存扣减如果写成 `update stock set count = count - 1 where sku_id = ?`（sku_id 是普通索引）且并发理货任务同时在改同一批记录，就可能出现死锁；治理手段是让扣减走唯一索引或主键、批量任务按主键升序执行、缩短事务到「扣减 + 记流水」两步。

**容易答错的地方**：把死锁和单纯的锁等待混为一谈。锁等待是暂时的、会随对方提交解除；死锁是环形等待，永远无法自行解开，必须靠检测与回滚。另外 5.7 的 `INNODB_LOCK_WAITS` 在 8.0 已移除，答错版本会被追问。

> 权威内容：MySQL 死锁与 InnoDB 锁诊断当前尚未在仓库建设，可参考 MySQL 官方文档「Deadlocks」「InnoDB Locking」章节与《高性能 MySQL》锁章节。

### Q08：事务的 ACID 分别怎么实现的？ `P0` `高频`

**30 秒回答**：原子性靠 undo log 回滚，持久性靠 redo log 加 WAL（写前日志），隔离性靠 MVCC 加锁，一致性是前三者共同服务的目标而不是单独手段——每个特性都有明确的底层组件对应。

**深入理解**：原子性：事务修改前先写 undo log（旧值镜像），崩溃或显式回滚时按 undo 逆序恢复；undo 同时是 MVCC 版本链的载体，一份日志两用。持久性：redo log 记录「页将要被改成什么」，提交时先写 redo 再改缓冲池，只要 redo 落盘（`innodb_flush_log_at_trx_commit=1`，默认）已提交的数据就不会丢，脏页何时刷回磁盘则不影响已提交事务——这就是 WAL。隔离性：读写之间用 MVCC 做快照读，写写之间用锁（行锁/间隙锁）互斥。一致性：唯一索引、外键约束、非空约束、以及业务层的状态机，加上前三者不违约，才共同构成一致性。`innodb_flush_log_at_trx_commit` 三个取值要能说清：1 表示每次提交都刷盘（最安全），2 表示只写入操作系统缓存（MySQL 崩溃不丢、宕机丢），0 表示每秒刷一次（性能最好、丢一秒）。

**面试官可能继续追问**：
- **redo log 已经落盘了，脏页还没刷盘，宕机会怎样？** —— 恢复时用 redo log 重放已提交的修改，未提交的用 undo 回滚，数据不丢也不乱；这正是 WAL 存在的意义。
- **`sync_binlog` 和 `innodb_flush_log_at_trx_commit` 的区别？** —— 前者管 binlog 落盘（影响主从一致），后者管 redo log 落盘（影响本地持久性），两个参数共同决定「提交后能承受哪种故障」。

**实际工程场景**：配置化刷盘策略是常见取舍点——对资损敏感的账务表用 `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`；可容忍秒级丢失的流水表可放宽到 2 换取写入吞吐。这个取舍要在面试里主动说，说明你知道每个参数对应哪种故障场景。

**容易答错的地方**：把一致性说成「靠数据库保证」。一致性是业务与约束共同定义的目标；数据库提供工具（日志、锁、约束），最终一致性由正确使用这些工具的代码保证。

> 权威内容：MySQL 事务与日志当前尚未在仓库建设，可参考 MySQL 官方文档「InnoDB Redo Log」「Undo Log」「The Binary Log」章节。

### Q10：两阶段提交是怎么回事？ `P1` `重点`

**30 秒回答**：事务提交时 InnoDB 先写 redo log 的 prepare 记录，再写 binlog，最后才写 redo log 的 commit 记录——用这两个「半提交点」保证 redo log 和 binlog 的逻辑一致，崩溃后能按两者状态决定提交还是回滚。

**深入理解**：为什么需要它：redo log 和 binlog 是两个独立的日志系统，如果「写 redo」和「写 binlog」之间发生崩溃，会出现「redo 有这笔、binlog 没有」或反之——前者导致从库少数据，后者导致主库恢复后凭空多数据。两阶段提交的崩溃恢复判定：prepare 之后、binlog 之前崩溃 → 该事务未写 binlog，回滚；binlog 写完后、commit 之前崩溃 → binlog 完整，提交。组提交（group commit）进一步把多个事务的刷盘合并，缓解两阶段带来的写入放大——这是为什么开启 binlog 后 DBA 仍能通过调 `binlog_group_commit_sync_delay` 等参数把写入性能拉回来。

**面试官可能继续追问**：
- **两阶段提交和分布式事务的 2PC 是一回事吗？** —— 不是。这里是单机两个日志文件之间的一致性协议，参与者是同一实例的两种日志；分布式 2PC 涉及跨节点协调，代价和复杂度完全另一个量级。
- **关掉 binlog 还需要两阶段提交吗？** —— 不需要，没有 binlog 就少了「另一个日志系统」，InnoDB 会走单阶段提交，写入更快，但也就无法主从复制和基于 binlog 的恢复了。

**实际工程场景**：开启 binlog 的主库写入吞吐通常有明显下降（多一次落盘），优化方向不是关 binlog，而是组提交 + 合理的刷盘参数；面试里能说出这层取舍，比背「两阶段保证一致性」更完整。

**容易答错的地方**：把两阶段提交说成「保证分布式事务一致性的手段」。这里的 2PC 是 MySQL 内部 redo/binlog 的一致性协议，和业务层的分布式事务方案（TCC、Saga）不是一回事。

> 权威内容：MySQL 两阶段提交当前尚未在仓库建设，可参考 MySQL 官方文档「Redo Log Commit」与《MySQL 技术内幕》相关章节。

### Q11：聚簇索引和二级索引？ `P0` `高频`

**30 秒回答**：聚簇索引的叶子节点存的是整行数据，二级索引的叶子节点存的是主键值；所以通过二级索引查数据要先在二级树找到主键、再回聚簇索引查整行，这叫回表，代价是两次 B+ 树查找。

**深入理解**：InnoDB 中聚簇索引就是主键索引，表数据按主键组织存储。因此 InnoDB 表必须有主键：显式声明最好；没声明则选第一个「非空的唯一索引」顶替；连唯一索引都没有，就隐式生成一个 6 字节的 `_row_id` 作为聚簇索引——它不可见、不可查，还占地方。二级索引（辅助索引）的叶子存「索引列 + 主键」，覆盖索引（见 Q12）就是让查询所需列全部落在索引里从而免掉回表。主键选择直接影响写入性能：自增主键让新行总是追加到 B+ 树最右，几乎无页分裂；UUID/雪花 ID 看似无序（对 B+ 树而言雪花的高位时间戳保证了趋势递增，实际尚可），但纯 UUID 会让插入位置随机、频繁页分裂、缓冲池命中率下降。

**面试官可能继续追问**：
- **为什么二级索引里存主键而不是行指针？** —— 行在页内的位置会随更新、页分裂而变化，存物理地址就要跟着改所有二级索引；主键值是逻辑稳定的，更新非主键列不影响二级索引。
- **没有主键的表会发生什么？** —— 选唯一索引或生成隐式 row_id，后者导致所有二级索引都变相变大（每个条目多带 6 字节），且 count(*) 之类的操作无法利用最紧凑的结构。

**实际工程场景**：WMS 单据表设计时坚持「自增或雪花主键 + 业务唯一键建唯一索引」：主键管存储效率，业务唯一键管幂等与检索。曾遇到的历史库用 UUID 主键，插入吞吐上不去，根因就是页分裂——这类案例面试里可以直接引用。

**容易答错的地方**：说「一张表可以有多个聚簇索引」。聚簇索引只有一个，就是主键索引；二级索引可以有多个，但都必须携带主键值。

> 权威内容：MySQL 索引结构当前尚未在仓库建设，可参考 MySQL 官方文档「Clustered and Secondary Indexes」章节。

### Q12：覆盖索引和回表？ `P0` `高频`

**30 秒回答**：覆盖索引指查询需要的所有列都能在同一个二级索引里取到，从而免掉回聚簇索引查整行这一步；explain 的 Extra 出现 `Using index` 就是覆盖索引生效的标志。

**深入理解**：普通二级索引查询是两步：二级 B+ 树定位主键 → 聚簇 B+ 树取行。当 select 列表、where 条件、order by 涉及的列全部包含在某个联合索引中时，第一步拿到的数据已经够用，第二步消失。因此设计联合索引时，把高频查询的「等值条件列 + 需要返回的列」按最左前缀顺序编排，是最常见的覆盖索引手法。反例是把 `select *` 当常态——星号展开后任何联合索引都不可能覆盖，回表无法避免。索引下推（ICP，MySQL 5.6+）是覆盖之外的减负手段：把 where 中能用索引列过滤的条件下推到存储引擎层，先过滤再回表，减少回表次数，explain Extra 显示 `Using index condition`。

**面试官可能继续追问**：
- **覆盖索引是不是越多越好？** —— 不是。覆盖索引靠「加宽联合索引」实现，索引越宽写入维护成本越高、单页容纳条目越少；只为少数核心查询做覆盖，其他查询用回表换更瘦的索引。
- **count(*) 为什么有时走覆盖索引特别快？** —— 如果存在一列 NOT NULL 的索引，优化器会选最小的那棵索引树遍历计数，避免回表；这也解释了「count 哪个字段快」这类问题的答案。

**实际工程场景**：WMS 出库单列表页查询「单号 + 状态 + 创建时间」，把 (status, create_time, order_no) 建成联合索引后，列表查询完全覆盖，深分页也顺带解决——一次索引设计同时干掉回表和 filesort 两个问题，这是覆盖索引最值的场景。

**容易答错的地方**：把「不回表」理解成「不读索引」。覆盖索引只是省掉第二次 B+ 树查找，第一次索引扫描照常发生；索引本身太大时扫描成本依然可观。

> 权威内容：MySQL 覆盖索引与索引下推当前尚未在仓库建设，可参考 MySQL 官方文档「Covering Indexes」「Index Condition Pushdown」章节。

### Q14：行锁、间隙锁、Next-Key Lock？ `P0` `源码`

**30 秒回答**：InnoDB 的行锁加在索引记录上：Record Lock 锁单行，Gap Lock 锁行之间的间隙（阻止插入），Next-Key Lock 是两者合起来锁一个「记录 + 它前面的间隙」；RR 下范围查询会加上间隙锁防幻读，RC 下间隙锁基本不生效。

**深入理解**：三种锁的粒度要能画出来：索引上相邻两条记录之间是 gap，Next-Key = record + 它前面的 gap。加锁规则的核心结论：唯一索引/主键等值查询且命中时，退化成只锁这一行（gap 不需要，别人插进来也是不同的键）；范围查询、非唯一索引等值查询会加间隙锁，把「可能被插入的位置」一并锁住。插入意向锁（Insert Intention Lock）是一种特殊的 gap 锁，表示「我想在这儿插入」，多个事务可以在同一 gap 上并存插入意向锁，真正互斥的是「插入位置与已有锁冲突」时。锁加在索引上意味着：更新条件不走索引时，InnoDB 会把所有扫描到的行加上锁，行锁退化成表级效果，这是死锁与吞吐崩跌的共同根源。

**面试官可能继续追问**：
- **为什么 RR 要加间隙锁而 RC 不加？** —— RR 要防幻读，快照读靠 ReadView 防了「读到新行」，但当前读（for update）必须阻止别人真的插进来，间隙锁就是这个物理阻止；RC 接受幻读，就不需要这层锁，代价是并发更高、一致性更弱。
- ** gap lock 能完全关掉吗？** —— 可以把隔离级别降到 RC（实际最常用），或改语句形态（走唯一索引等值）；没有单独「关闭 gap lock」的开关，它是 RR 语义的一部分。

**实际工程场景**：并发理货场景下两个事务同时 `update stock set ... where sku_id = ? and warehouse_id = ?`，如果 (sku_id, warehouse_id) 不是唯一索引，等值查询会加间隙锁，再叠加插入意向锁就容易死环；治理手段是把更新收敛到唯一索引、批量任务按主键升序、必要时 RC 降级。

**容易答错的地方**：说「行锁就是锁住一行数据」。准确说是锁住索引记录——条件没走索引时，锁的范围是「扫过的所有记录 + 相关间隙」，这也是为什么慢查询和死锁常常同时出现。

> 权威内容：InnoDB 锁与 Next-Key Lock 当前尚未在仓库建设，可参考 MySQL 官方文档「InnoDB Locking」章节与《MySQL 是怎样运行的》锁章节。

### Q15：读已提交和可重复读怎么选？ `P1` `重点`

**30 秒回答**：RR 每事务一份 ReadView、可重复读但版本链更长、间隙锁更多；RC 每条语句一份 ReadView、能看到别人已提交的修改、并发更高；国内互联网默认 RC 居多，金融账务类倾向 RR，选型看业务能接受的不一致窗口。

**深入理解**：RC 的具体代价与好处：语句级快照意味着「同一事务内两次相同查询结果可能不同」，业务代码若依赖事务内读一致性会出错；好处是锁持有时间短（语句结束即释放）、死锁概率低、undo 版本链短。RR 的代价：长事务会让版本链持续变长，purge 追不上时 undo 膨胀；间隙锁在范围查询下把并发写入堵死。一个常被忽视的点：RC 下 binlog 必须用 row 格式——statement 格式下同一事务的多条语句在从库重放顺序与主库执行顺序不一致，会导致数据分歧。半一致性读（semi-consistent read）是 RC 下的优化：update 遇到已锁定的行时先读最新已提交版本判断是否还满足 where，不满足就跳过，减少锁等待。

**面试官可能继续追问**：
- **为什么互联网公司偏爱 RC？** —— 业务普遍接受「事务内最终一致」而非「事务内时刻一致」，RC 的锁窗口小、死锁少、undo 压力小，对高并发写入更友好；代价由业务层的幂等与状态机兜住。
- **RR 改 RC 要注意什么？** —— 代码里依赖「同一事务重复读同一行结果相同」的逻辑会暴露（如先查后改的悲观判断失效）；同时必须确认 binlog 为 row 格式。

**实际工程场景**：WMS 的库存查询与扣减分离在两个事务里，用 RC + 条件更新（`where count >= n`）保证最终正确性，比 RR 的间隙锁更适合高并发扣减；而账务类流水要求「一个事务内余额读两次必须一致」，就该用 RR。

**容易答错的地方**：认为「RR 全面优于 RC」。RR 隔离性更强但并发与维护代价都更高；也存在「RC 全面优于 RR」的反向误读——选型标准从来是业务一致性需求，不是级别数字大小。

> 权威内容：MySQL 隔离级别选型当前尚未在仓库建设，可参考 MySQL 官方文档「Transaction Isolation Levels」「Consistent Nonlocking Reads」章节。

## 面试前速记

- B+ 树胜在「非叶子不存数据 + 叶子有序链表」：树更矮、范围扫描顺序读；哈希只配等值。
- 索引失效的本质是「优化器估算走索引更贵」；对列做函数/运算、隐式转换（列这边转才致命）、`%x` 前导通配、跳过最左列，是四大高发场景。
- 深分页优化的核心是「别让数据库碰前面的行」：延迟关联（覆盖索引取主键）或游标分页（`id > 上一页最大 id`）。
- MVCC = 隐藏列（`DB_TRX_ID`/`DB_ROLL_PTR`）+ undo 版本链 + ReadView；RR 首次读生成、RC 每次读生成；当前读不走 MVCC 走锁。
- ACID 的落点：原子性 undo、持久性 redo+WAL、隔离性 MVCC+锁、一致性是目标。
- 三大日志：redo 循环写管崩溃恢复，undo 管回滚与版本链，binlog 追加写管主从与恢复；两阶段提交保 redo 与 binlog 一致。
- 聚簇索引叶子存整行，二级索引叶子存主键；二级索引查数据要回表；InnoDB 必须有主键。
- 覆盖索引 = 查询列全在索引里，`Extra=Using index`；`select *` 永远无法覆盖。
- 最左前缀：跳不过前导列，范围列之后的列只能过滤；等值在前、范围在后；8.0.13 起有 Skip Scan 例外。
- 锁加在索引上：更新不走索引 = 锁范围放大；RR 范围查询加间隙锁，RC 基本不加。
- RC vs RR：RC 锁窗口小、并发高、事务内读不一致；RR 可重复读但版本链长、间隙锁多；RC 下 binlog 必须 row 格式。
- 主从复制 = binlog → relay log → SQL 线程重放；半同步不丢 ACK 前的数据但不保证已应用；判断延迟看 GTID 差。
