# Redis

> 一句话定位：Redis 在面试里考的是「内存模型 + 缓存架构 + 高可用」的全链路——数据结构、为什么快、持久化、缓存异常、一致性、分布式锁、集群分层都会问；与数据库专题的分界线在于：数据库考存储引擎与 SQL，Redis 考缓存与中间件侧的设计取舍。

## 专题定位

- Redis 是覆盖面最宽的中间件考点：从底层数据结构一路问到集群，任何一层答浅都会直接暴露真实深度，5 年以上基本默认你「用过、踩过坑、能按根因选方案」。
- 面试官主要验证三件事：能否按根因选方案（穿透/击穿/雪崩不混答）；能否量化代价（一致性窗口、锁失效条件、淘汰策略的副作用）；有没有线上排查手感（大 key、热 key、fork 卡顿、命中率）。
- 本专题只给面试口径的答案，机制解释以官方文档与《Redis 设计与实现》为准；场景设计框架（容量估算、分层）在 [04-场景设计题](../04-场景设计题/缓存一致性与幂等.md)，这里不重复。
- 每条结论都要能带出「所以会怎样」：比如选了 `allkeys-lru`，就要能说出缓存污染与命中率下降；说「单线程」，就要补一句指的是命令执行单线程、6.0 起网络 IO 已可多线程。

### Q01：缓存穿透、击穿、雪崩有什么区别，分别怎么解决？ `P0` `高频`

**30 秒回答**：三者都是请求绕过或压垮缓存后直达数据库，区别在于查的是什么：穿透查的是从来不存在的数据，击穿是一个热点 key 过期瞬间大量并发回源，雪崩是大量 key 同时失效或缓存整体不可用。穿透用布隆过滤器和空值缓存拦截，击穿用互斥锁或逻辑过期控制回源并发，雪崩用 TTL 随机抖动加多级缓存和限流兜底。

**深入理解**：三者的根因完全不同，解法不能混用。

| 问题 | 根因 | 缓存状态 | 解法 |
| --- | --- | --- | --- |
| 穿透 | 查询根本不存在的数据 | 缓存里从未有过信息 | 布隆过滤器入口拦截；缓存空值 + 短 TTL；参数合法性校验 |
| 击穿 | 单个热点 key 失效 | 有过，刚丢了 | 互斥锁/singleflight 回源；逻辑过期（value 带过期时间，永不过期）；热点 key 异步刷新 |
| 雪崩 | 大面积同时失效或缓存宕机 | 有过，成片丢了 | TTL 加随机抖动；多级缓存；限流降级兜底 |

- **穿透的代价要说清**：布隆过滤器有假阳性（不在集合的可能被判为在），只能挡「一定不存在」的流量，且不支持删除；缓存空值会占内存，TTL 设长了脏数据占位、设短了仍会打穿，通常 30～60 秒量级配合业务容忍度。
- **击穿的互斥方案**：回源路径加 `SET lock NX PX`，只有一个请求打到数据库，其余等待后重读缓存。代价是等待方多一次 RT，锁本身成为新单点；singleflight 用本地合并可以省掉这次 Redis 往返，但只在单进程内有效。
- **雪崩的本质是「失效时间过于整齐」**：批量写入缓存时用一个固定 TTL，到期日就是集中回源日；写缓存时给 TTL 加 10%～20% 随机量即可打散。缓存整体不可用（宕机、网络分区）时，限流降级是最后一道闸，Hystrix/Sentinel 类组件按数据库容量配置配额。
- 「缓存与数据库一致性」是另一个问题，不要和这三个混在一起答，见 Q08。

**为什么这样设计**：因为三者的根因不同——穿透是缓存里「从未有过信息」，击穿和雪崩是「有过但状态丢了」；按根因选方案，才不会答成「统一给 TTL 加随机值」这种解决不了穿透的答案。

**面试官可能继续追问**：
- **布隆过滤器误判了怎么办？** —— 误判方向是「说存在其实不存在」，所以只能用来否定，不能用来确认；真的热点数据被误判拦截时，要么调大位数组和哈希函数数量降误判率，要么对少量被拦截的 key 做二次校验放行。
- **互斥锁回源，拿到锁的请求挂了怎么办？** —— 所以锁必须带 TTL，且 TTL 要覆盖「查库 + 回填」的耗时；更稳的做法是锁 TTL 短、业务执行续期（看门狗思路，见 Q09/Q10），或者干脆接受这次回源失败，靠 TTL 过期后自然恢复。
- **空值缓存和布隆过滤器同时上会不会重复？** —— 两者是纵深防御不是替代：布隆在入口挡掉「明显不存在」的流量，空值缓存兜住漏过来和已删除的数据；数据量小、攻击流量可识别时，参数校验比两者都便宜。

**实际工程场景**：WMS 的出库查询按出库单号查询，外部或异常调用方会批量构造不存在的单号——入口先做单号格式/长度校验，再上布隆过滤器（单号属于「可枚举全集」的场景很适合），极端情况下缓存短 TTL 空值。库存扣减的 SKU 维度缓存是典型热点，大促前给 TTL 加随机抖动，并对 Top SKU 用逻辑过期加异步刷新，避免整点集中回源把库存库打满。

**容易答错的地方**：
- 把三个问题答成一种「加随机 TTL」的组合拳，随机化对穿透完全无效。
- 布隆过滤器的误判方向说反，或者说「布隆过滤器可以删除元素」（计数布隆才行，标准布隆不行）。
- 击穿说成「缓存过期导致雪崩」——单个热点 key 失效是击穿，成片失效才是雪崩。
- 以为互斥锁方案没有代价，答不出等待方的 RT 和锁单点问题。

> 权威内容：Redis 缓存异常与高可用当前尚未在仓库建设，可参考 Redis 官方文档「Client-side caching」「Redis cluster」章节与《Redis 设计与实现》。

### Q02：Redis 的持久化机制，RDB 和 AOF 怎么选？ `P0` `高频`

**30 秒回答**：RDB 是某一时刻的全量快照，文件小、恢复快但可能丢较多数据；AOF 追加写命令，丢数据少但文件大、恢复慢；生产上通常两者都开，用 AOF 保证少丢数据、用 RDB 做快速恢复和备份。

**深入理解**：

- **RDB**：由 `save`（同步，阻塞主线程，生产禁用）或 `bgsave` 触发，也可以配置 save 策略（如 `save 900 1`，即 900 秒内至少 1 个 key 变化就快照）。`bgsave` fork 子进程写入，依赖写时复制，父子进程共享内存页，父进程只在新写入时复制旧页，所以大部分情况内存不会翻倍；但实例很大时 fork 本身就会造成百毫秒级卡顿，两次快照之间的数据会丢失。
- **AOF**：追加记录写命令，三种刷盘策略：`always` 每条命令都落盘（最安全也最慢）、`everysec` 每秒一次（默认，最多丢 1 秒数据）、`no` 交给操作系统决定。AOF 文件会随命令堆积膨胀，靠重写（`bgrewriteaof` 或满足自动重写阈值时触发）压缩——重写同样 fork，重写期间的新命令写入 AOF 重写缓冲区，重写完成后原子替换。
- **混合持久化（Redis 4.0 起，`aof-use-rdb-preamble yes`）**：重写后的 AOF 文件头部是全量 RDB、后面追加增量 AOF 命令，加载时直接读 RDB 段，兼顾恢复速度与丢数据量；Redis 7.0 起默认开启。注意这个文件旧版本 Redis 读不了。
- **Multi-part AOF（Redis 7.0 起）**：AOF 从单文件变为 manifest 管理的多文件结构（一个 base 全量文件 + 多个 incr 增量文件），重写只生成新 base，目录结构变化是升级时要注意的兼容点。
- 恢复优先级：AOF 开启时优先用 AOF 恢复（丢数据少），没有 AOF 才找 RDB。

**为什么这样设计**：内存数据库的持久化存在一对天然矛盾——快照的写入量随数据规模增长，日志的写入量随时间增长，任何一方都无法单独覆盖两种需求；混合持久化是承认两者各有边界之后的折中，而不是其中一个方案被淘汰。

**面试官可能继续追问**：
- **AOF `everysec` 到底丢多少？** —— 最多丢 1 秒，且丢的是「fsync 成功之后到宕机」的写入；回答时必须说清「选了 AOF 默认也最多丢 1 秒」，只说「AOF 不丢数据」会被判定为背概念。
- **fork 卡顿怎么规避？** —— 控制单实例内存量（这是最有效的手段，也是后面迁 Cluster 的动机之一）；fork 时机避开流量高峰；关闭内核透明大页 THP（`echo never > /sys/kernel/mm/transparent_hugepage/enabled`），THP 会让 COW 的复制粒度从 4KB 变成 2MB，显著放大写时复制的延迟。
- **RDB 和 AOF 同时开会互相影响吗？** —— 会抢同一个 fork 名额和磁盘 IO；bgsave 与 bgrewriteaof 不会同时执行，但 AOF rewrite 期间如果触发 bgsave 会排队等待，大实例上表现为周期性延迟毛刺（Q15 的排查案例）。

**实际工程场景**：WMS 缓存集群的常规配置是 RDB + AOF 双开：AOF `everysec` 承接实时性，RDB 每小时一份作为备份与快速恢复载体，并定期把 RDB 传到对象存储做异地容灾。恢复演练要定期做——只配不恢复，等于没有备份。

**容易答错的地方**：
- 说 `save` 和 `bgsave` 只是「一个快一个慢」，答不出 bgsave 依赖 fork + 写时复制、大实例 fork 卡顿。
- 不知道混合持久化是哪一版引入的（4.0），也说不清「重写后的文件头是 RDB」。
- 以为 AOF `always` 就绝对不丢——fsync 成功前的操作系统页缓存数据仍可能随宕机丢失，只是窗口比 everysec 小。
- 忽略 Redis 7.0 AOF 多文件结构，说「AOF 就是一个 appendonly.aof 文件」。

> 权威内容：Redis 持久化机制当前尚未在仓库建设，可参考 Redis 官方文档「Redis Persistence」章节。

### Q03：Redis 大 key 怎么发现和处理？ `P1` `中频`

**30 秒回答**：大 key 指单个 value 过大的 key，经验上 String 超过 10KB、或集合类型元素数达到几千个，危害是阻塞 Redis 单线程、拖慢主从同步与集群迁移、并造成内存分布不均；发现用 `--bigkeys`、`--memkeys` 和 `MEMORY USAGE`，处理靠拆分，删除用 `UNLINK` 异步回收。

**深入理解**：

- **发现手段**：
  - `redis-cli --bigkeys`：基于 SCAN 采样统计各类型最大的 key，对线上相对安全（可加 `-i` 控制采样间隔）但不是精确值。
  - `redis-cli --memkeys`（Redis 6.0 起）：按内存占用排序，同样采样。
  - `MEMORY USAGE key`：精确看单个 key 的占用，适合定点确认。
  - 离线侧用 rdb-tools 一类工具分析 RDB 文件做全量统计，最准但有时延。
- **危害的机理**：Redis 命令执行是单线程，一个 `HGETALL` 拉 10 万字段的 hash，序列化输出会长时间占住主线程；大 key 还会让主从同步的 RDB 传输和 Cluster 的槽迁移变慢，并在分片间造成内存倾斜。
- **处理思路是拆分**：大 hash 按字段范围（如用户 ID 尾号）拆成多个 key、改用 hash 的 field 粒度读写代替整块读取；大 list/set 按业务维度分片（如按天、按仓库分桶）。
- **删除要异步**：用 `UNLINK` 代替 `DEL` 走异步回收（Redis 4.0 起），过期回收也可开启 `lazyfree-lazy-expire`，避免一次性释放大对象阻塞主线程。注意 `UNLINK` 只异步释放内存，命令本身仍然同步执行，超大 key 的 `DEL` 序列化输出才是阻塞源。

**为什么这样设计**：删除是运维里最高频触发大 key 危害的动作，而「同步释放」和「异步释放」对调用方无差别——把释放挪到后台线程（`lazyfree`），等于用一点内存延迟回收换主线程不阻塞，是典型的用时间换可用性。

**面试官可能继续追问**：
- **大 key 删除时阻塞了怎么办，已经晚了怎么救？** —— 预防优先：上线前用 `--bigkeys` 扫一遍；已经存在的，用 SCAN 遍历后 `UNLINK` 分批删，避开高峰；如果是集合类型，还可以 `SRANDMEMBER`/`SPOP` 少量多次删，把阻塞摊到多个命令里。
- **大 key 怎么影响主从同步？** —— 全量同步时大 key 进入 RDB 让传输和加载变长，从库长时间处于同步中状态；增量阶段主库传播 DEL 大 key 只是发命令，影响不大，但真正阻塞主库的是删除时的内存释放和集合命令的 O(N) 输出。
- **拆成多个 key 之后事务/Lua 怎么办？** —— 拆分后的多个 key 在 Cluster 下大概率不在同一 slot，跨 slot 的 Lua 和事务直接报错（见 Q14）；要么用 hash tag 强制同槽，要么接受业务上放弃跨 key 原子性。

**实际工程场景**：WMS 的出库查询结果如果按「一个 hash 存整个出库单头 + 明细行」设计，明细行几百条时单 key 轻松上几十 KB，且每次查询整块拉回——更合理的做法是头与明细分开、明细按行号分桶，查询用 `HMGET` 取必要字段。库存扣减用的 hash 同理，只把要原子扣减的字段放进同一个 key，避免把整个商品对象塞进去。

**容易答错的地方**：
- 只把「value 字节数大」当大 key，忽略「元素个数多」的类型（几百万元素的 set 即使总字节不大也是大 key）。
- 把大 key 和热 key 混为一谈：大 key 是体积问题，热 key 是频次问题，解法相反（拆分 vs 分散流量），见 Q13。
- 说 `UNLINK` 完全不阻塞——异步释放在 4.0 后是后台线程做，但命令执行和从库 DEL 传播仍是同步路径。
- 拿 `KEYS` 去线上找大 key，直接阻塞。

> 权威内容：Redis 大 key 与内存治理当前尚未在仓库建设，可参考 Redis 官方文档「MEMORY USAGE」「redis-cli」以及「Latency troubleshooting」章节。

### Q04：Redis 的五种数据结构及使用场景？ `P0` `高频`

**30 秒回答**：String 做缓存和计数器，Hash 存对象、支持字段级读写，List 做简单队列和最新列表，Set 做去重和交集并集，ZSet 做排行榜和范围查询；底层编码各有演化——String 有 int/embstr/raw 三态，Hash 小对象用 listpack 大了转 hashtable，List 是 quicklist，Set 小整数集用 intset，ZSet 是 skiplist 加 hashtable。

**深入理解**：

| 类型 | 典型场景 | 底层编码与转换条件 |
| --- | --- | --- |
| String | 缓存对象、计数器、分布式锁 value | int（纯整数）→ embstr（≤44 字节）→ raw；embstr 是只读的，任何修改转 raw |
| Hash | 存商品/用户对象、字段级读写 | 小对象用 listpack（默认 ≤128 个 field 且每个 ≤64 字节），超出转 hashtable |
| List | 最新 N 条、简单消息队列 | quicklist：多个 listpack/ziplist 节点串成的双向链表 |
| Set | 标签去重、共同关注、抽奖 | intset（全整数且 ≤512 个）→ hashtable；7.2 起小的非整数集合也可用 listpack |
| ZSet | 排行榜、延迟队列、范围检索 | listpack（≤128 个元素且每个 ≤64 字节）→ skiplist + hashtable 双结构 |

- **ZSet 为什么用跳表不用红黑树**：一是范围查询友好，跳表按 score 有序且底层是链表，取一段区间就是遍历一层链表，O(logN+M)；红黑树也能中序遍历，但代码量和常数都更大。二是实现简单、维护局部化：插入只改相邻层指针，不需要旋转和重新着色，出 bug 时好调试。三是内存上跳表期望每个节点约 1.33 个指针（Redis 用 p=1/4 的层级概率），比红黑树每个节点的双孩子加父指针加颜色位更省。代价是最坏情况概率性地退化，工程上可接受。skiplist 之外 Redis 还同时维护一个 hashtable，保证按 member 查找是 O(1)。
- **ZSet 的排序规则**：先按 score 排，score 相同按 member 字典序排。
- **Hash 存对象 vs String 序列化**：Hash 的优势是字段级读写——改一个字段不用读出整个对象再整块写回，网络传输量小，小对象 listpack 编码内存紧凑；劣势是跨语言客户端要约定一致的字段结构、大 hash 有 bigkey 风险（见 Q03）、早期版本无法给单个 field 设 TTL（Redis 7.4 引入 `HEXPIRE` 等 field 级过期命令补齐）。String 存 JSON 的优势是通用简单、任何语言直接读，劣势是整读整写、大 value 同样有 bigkey 风险。结论：字段会被分散更新的对象用 Hash，只整体读、偶尔写、且要跨语言传递的用 String。
- **渐进式 rehash**：dict 维护两张哈希表，扩容时按每次访问/后台任务推进迁移，查询同时查两张表，避免一次性 rehash 阻塞主线程——这是「Redis 看起来是 O(1) 却不卡」的隐藏前提。

**为什么这样设计**：一套数据结构给多种编码，是因为小对象和大对象的瓶颈完全不同——小对象要省内存和 CPU（紧凑编码），大对象要 O(1) 查找（哈希表）和 O(logN) 范围（跳表）；在类型内部按数据形态自动切换编码，等于把「该用什么结构」这个选择推迟到数据真正变大的时候，调用方无感。

**面试官可能继续追问**：
- **listpack 和 ziplist 什么关系？** —— ziplist 是旧实现，Redis 5.0 引入 listpack 作为其替代，7.2 起所有类型统一用 listpack、ziplist 彻底移除；答「ziplist 是压缩的」是错的，它是紧凑编码不是压缩。
- **listpack 编码的 Hash 什么时候变成 hashtable？** —— 任一 field 超过 `hash-max-listpack-value`（默认 64 字节）或总数超过 `hash-max-listpack-entries`（默认 128）就转；5.0 之前这两个参数叫 `hash-max-ziplist-entries/values`，改名是版本差异。
- **Set 是有序的吗？** —— 无序，底层 hashtable 按哈希值散列，迭代顺序不保证；要有序必须用 ZSet。intset 编码下元素按整数有序存放只是实现细节，不要当成特性依赖。

**实际工程场景**：WMS 的库存扣减缓存用 String 存「可用库存数」配 Lua 做查-扣原子操作（简单标量，不需要 Hash 的对象语义）；商品基础信息用 Hash，因为商品改价只改 price 字段，字段级更新避免整块回写；出库单状态机流转适合 ZSet——score 存期望处理时间戳，做延迟扫描队列，到期取 `ZRANGEBYSCORE` 区间即可。

**容易答错的地方**：
- 说 embstr 阈值是 39/44 字节但不解释它是「只读编码、修改即转 raw」。
- 把 quicklist 说成「ziplist 的链表」，不提 5.0 之后节点内已是 listpack、7.2 才彻底移除 ziplist。
- ZSet vs 红黑树的问题答不到「范围查询 + 实现简单 + 内存」三点中的至少两点。
- 不知道 7.4 才有 hash field 级过期，或反过来把 `HEXPIRE` 说成很早就有。

### Q05：Redis 为什么快？ `P0` `高频`

**30 秒回答**：Redis 快是多个因素叠加的结果：数据全在内存，单线程执行命令避免了上下文切换和锁竞争，IO 多路复用让它一个线程就能处理海量连接，底层是哈希表、跳表这类 O(1)/O(logN) 的高效结构，加上 RESP 协议简单、渐进式 rehash 不造成停顿；这里说的单线程指的是命令执行单线程，Redis 6.0 起网络读写已经可以多线程。

**深入理解**：

- **纯内存**：内存随机访问是百纳秒级，磁盘寻道是毫秒级，差四个数量级；这是快的第一因，也是它的边界——数据规模受物理内存约束，所以后面才有持久化和集群分片。
- **单线程执行命令**：命令在主线程顺序执行，没有锁、没有上下文切换、没有多核缓存一致性开销；同时天然保证了单条命令的原子性。代价是任何 O(N) 命令（`KEYS`、`SMEMBERS` 大集合）都会阻塞所有请求——所以 Redis 的「快」是有前提的，慢命令治理才是线上稳定性关键（见 Q15）。
- **IO 多路复用**：基于 epoll（Linux）的事件循环，一个线程管理成千上万连接，只处理就绪的事件，没有忙等；这才是 Redis 能扛高并发连接的根本，不是「单线程所以快」。
- **高效数据结构**：哈希表 O(1)、跳表 O(logN)、listpack 紧凑连续内存对 CPU 缓存友好；这些结构的选取原则在 Q04。
- **渐进式 rehash**：扩容不一次性搬完，把耗时摊到多个事件循环周期，查询时同时查新旧两张表，避免停顿。
- **RESP 协议**：简单文本协议，解析成本接近零；配合 pipeline，客户端一次发多条命令、一次读多个回复，把 RTT 摊销到接近零，这也是「Redis 能抗几十万 QPS」测试数据的常见前提。

**为什么这样设计**：不用多线程执行命令，是因为 Redis 的定位是「所有数据在内存、单条命令很快」——瓶颈在网络 IO 不在 CPU 计算，给命令执行加锁的收益小于开销，还会破坏单命令原子性这个被无数业务依赖的性质。所以 6.0 引入多线程时只动网络层，命令执行和淘汰等核心逻辑始终留在单线程（见 Q06）。

**面试官可能继续追问**：
- **那单线程怎么利用多核？** —— 一个实例用不满多核，就用多个实例（分片）或者同机多进程部署；7.x 的任务也是往这个方向走，而不是把命令执行改成多线程。
- **为什么 pipeline 快？** —— 省的是 RTT 不是执行时间，命令本身还是排队单线程执行；所以 pipeline 适合批量小命令，不适合把一条慢命令包进去。
- **渐进式 rehash 期间查询一个正在迁移的 key 会漏吗？** —— 不会，迁移期间查询同时查 ht[0] 和 ht[1]，写入只进新表；真正要注意的是 rehash 期间的内存双表占用。

**实际工程场景**：WMS 的出库查询如果要批量查 200 个出库单，串行 RTT 累加是主要耗时，用 pipeline 一次发出可以把接口耗时从几十毫秒压到几毫秒；但如果单个查询本身就是 `HGETALL` 一个大 hash，pipeline 只是让阻塞来得更密集——先治慢命令，再谈批量化。

**容易答错的地方**：
- 只答「纯内存 + 单线程」两点，漏掉 IO 多路复用这个并发根基。
- 说「Redis 是单线程的所以一定不会慢」——单线程恰恰意味着一个慢命令阻塞所有请求。
- 不知道 6.0 起网络 IO 可多线程、命令执行仍单线程，把这当矛盾。
- 把 RESP 说成二进制协议（那是 3.0 实验性引入、后来放弃的方向）。

> 权威内容：Redis 性能原理当前尚未在仓库建设，可参考 Redis 官方文档「Data types」「Pipelining」章节与《Redis 设计与实现》。

### Q06：Redis 的单线程模型和 IO 多路复用？ `P0` `高频`

**30 秒回答**：Redis 服务端是基于 epoll 的 Reactor 模型：主线程跑一个事件循环，用 epoll_wait 拿到就绪的文件事件，分派给对应处理器——连接可读就 accept，客户端可读就读入命令缓冲并解析执行，可写就把输出缓冲写回。所谓单线程指的是这条「事件循环 + 命令执行」的主线只有一条；Redis 6.0 起网络读写可以交给多个 IO 线程，命令执行仍然单线程，且默认关闭。

**深入理解**：

- **文件事件与分派器**：`ae.c` 的事件循环是核心——注册在 epoll 上的 socket 产生事件后，`aeProcessEvents` 派发到文件事件处理器：accept、read、write、以及「命令就绪后执行」。命令执行的结果先写入客户端输出缓冲，再注册写事件发送，所以一次请求通常是「一次读事件 + 一次写事件」。
- **beforeSleep/afterSleep**：每轮循环休眠前会尝试非阻塞地把输出缓冲刷给客户端、关闭超时连接，这是「输出缓冲不无限堆积」的机制。
- **为什么命令执行不用多线程**：核心是为了原子性和顺序性——所有命令在一个线程上顺序执行，天然无需加锁，单命令语义就是原子的；多线程执行命令需要细粒度锁，收益不抵复杂度。Redis 的并发模型选择本质是「用单线程的确定性换掉锁的开销」。
- **Redis 6.0 的多线程 IO**：主线程负责把就绪的连接轮转分给多个 IO 线程，由 IO 线程完成「读 socket + RESP 解析」和「写 socket」，解析后的命令交回主线程执行。默认 `io-threads 1`（等于关闭），开启要同时设置 `io-threads` 和 `io-threads-do-reads yes`（6.0）；Redis 7.0 起 `io-threads-do-reads` 移除，只需 `io-threads` 大于 1 即同时开启读写多线程。多线程只摊薄网络拷贝和协议解析的 CPU，对大 key 查询这类执行慢的命令毫无帮助。
- **QPS 的量级概念**：普通云主机上单实例常见 8～10 万 QPS 的读能力，瓶颈通常在网络和内存带宽，不是 CPU 单核——这是判断「要不要提前分片」的经验线。

**为什么这样设计**：Redis 没有采用 Netty 那种主从 Reactor 分工，而是把 accept、read、write、execute 全放在一个循环里，是因为命令执行必须在同一线程；多线程只放在纯 IO 搬运上，是 6.0 在保持核心模型不变的前提下，对多核机器的针对性优化——这是典型的「能不碰正确性就不碰」。

**面试官可能继续追问**：
- **IO 多线程开启后，同一连接的读写还是同一个线程吗？** —— 不是强绑定，按就绪顺序轮转分配，协议解析结果是顺序交回主线程的，命令执行顺序不受影响。
- **多线程 IO 能解决慢查询阻塞吗？** —— 不能，阻塞来自命令执行，那一段永远是单线程；它只缓解「网络拷贝和协议解析吃掉单核」的场景，通常是带宽打满、CPU 单核瓶颈时才有明显收益。
- **一个客户端连接在事件循环里怎么防止被饿死？** —— 输出缓冲有软硬上限（`client-output-buffer-limit`），超限就断开或限制该客户端；单个连接不会无限占用主线程。

**实际工程场景**：WMS 的出库查询高峰如果监控发现 Redis CPU 单核打满但 QPS 并未到瓶颈、且大 key 已治理干净，可以尝试开 `io-threads 4` 做针对性优化——但先确认瓶颈真的在网络层，多数团队最后发现瓶颈在业务侧慢命令。这是排查顺序问题：先慢日志，再谈多线程。

**容易答错的地方**：
- 说「Redis 6.0 就全面多线程了」——只有 IO 层，命令执行、过期、淘汰仍在单线程。
- 不知道 `io-threads` 默认关闭，或分不清 6.0 的 `io-threads-do-reads` 与 7.0 的简化。
- 把 epoll 说成「多路复用就是多线程」——epoll 是单线程内管理多连接的机制，和多线程执行命令是两回事。
- 答「为什么不用多线程」只说「因为快」，给不出原子性和锁开销的论证。

> 权威内容：Redis 单线程模型与 IO 多路复用当前尚未在仓库建设，可参考《Redis 设计与实现》事件章节与 Redis 源码 `ae.c`。

### Q07：Redis 的过期删除和内存淘汰策略？ `P0` `高频`

**30 秒回答**：过期删除靠惰性加定期两种策略配合：惰性是访问 key 时顺手检查，定期是后台每秒抽样检查；当内存到达 maxmemory 还不够时，才按 maxmemory-policy 淘汰——共 8 种，allkeys-lru/volatile-lru/allkeys-lfu/volatile-lfu/allkeys-random/volatile-random/volatile-ttl 和 noeviction。注意 Redis 的 LRU 是采样近似实现，LFU 从 4.0 才开始支持。

**深入理解**：

- **过期的存储**：每个 key 的过期时间戳存在 `redisDb.expires` 字典里，key 本体还在主字典；过期不是「到点消失」，而是「检查到过期时逻辑删除」。
- **三种删除策略的配合**（定时删除不在 Redis 主链路里，用定时器逐个到点删的代价是 CPU 和海量定时器，Redis 不做）：
  - **惰性删除**：每次访问前 `expireIfNeeded` 检查，过期就删；expires 为空的库直接跳过检查。保证「被访问到的坏数据一定被清掉」。
  - **定期删除**：`serverCron` 里 `activeExpireCycle` 每秒跑 `hz`（默认 10）次，每个库随机抽固定数量 key 检查，超比例过期就加速循环，但有 CPU 时间预算。保证「没人访问的 key 也能被清掉」。
  - **内存淘汰**：前两者是「过期才删」，但如果 key 永不过期、或删除速度跟不上写入速度，内存仍会满，这时按策略主动淘汰。
- **8 种 maxmemory-policy**：

| 策略 | 淘汰范围 | 说明 |
| --- | --- | --- |
| noeviction | 不淘汰 | 写命令直接报错，默认值 |
| allkeys-lru | 所有 key | 最常用，纯缓存场景 |
| volatile-lru | 只淘汰有 TTL 的 key | 混合存储慎用 |
| allkeys-lfu | 所有 key | 按访问频率淘汰，抗缓存污染 |
| volatile-lfu | 只淘汰有 TTL 的 key | 同上，范围受限 |
| allkeys-random | 所有 key | 随机，极少用 |
| volatile-random | 只淘汰有 TTL 的 key | 同上 |
| volatile-ttl | 只淘汰有 TTL 的 key | 淘汰剩余生存时间最短的 |

- **LRU 是近似的**：不为每个 key 维护全局 LRU 链表（内存和锁开销大），而是 `maxmemory-samples`（默认 5）随机采样几个 key，淘汰其中 idle 最久的。采样越小越省 CPU、近似越粗。
- **LFU**：每个 key 带 8 位 counter，访问按 `lfu-log-factor` 概率递增，counter 还按 `lfu-decay-time`（分钟）衰减，让「最近没人访问的热 key」降温，避免一次批量扫描把冷数据顶成热数据。4.0 引入。
- **删除的异步化**：`lazyfree-lazy-expire yes` 让过期删除走后台线程释放内存，大对象不阻塞主线程（4.0 起）。

**为什么这样设计**：不用「精确到点的定时删除」，是因为海量 key 各带一个定时器的 CPU 和内存代价比「惰性 + 抽样」高一两个数量级；不用精确 LRU 链表，是因为维护全局有序链表的写放大在纯内存高频写入场景不可接受。采样近似本质上是用正确率的可度量损失，换确定性的性能收益。

**面试官可能继续追问**：
- **大量 key 同一秒过期，定期删除来得及吗？** —— 来不及，activeExpireCycle 有 CPU 预算，会被动放缓；这正是雪崩的一种成因，解法是 TTL 加随机抖动（Q01），不是靠删除策略。
- **volatile-lru 为什么危险？** —— 只淘汰带 TTL 的 key，如果实例里混存了不过期的持久数据，内存满时它们永远不被淘汰，写请求直接报 OOM；做纯缓存就用 allkeys 系列。
- **缓存该选 LRU 还是 LFU？** —— 有明显冷热分层、且存在周期性全量扫描场景的选 LFU；访问模式均匀、只想要个默认策略的选 allkeys-lru；任何策略都不解决「该缓存什么」的问题，那是命中率设计问题。

**实际工程场景**：WMS 缓存集群如果混存「库存快照（带 TTL）+ 字典数据（长期）」，选 `volatile-lru` 就要接受字典数据挤爆内存的风险；更稳的做法是物理隔离——字典和业务缓存分开实例，各自用 noeviction/allkeys-lru。maxmemory 通常配到物理内存的 60%～70%，给 fork 和碎片留余量。

**容易答错的地方**：
- 说 Redis 有过期定时器、到点立即删除——只有惰性和定期抽样，从不过期到被删之间通常有秒级延迟。
- 分不清「过期删除」和「内存淘汰」是两个机制：前者因为 TTL 到了，后者因为内存满了。
- 不知道 LFU 是 4.0 才有的，或把 LRU 的采样近似说成精确 LRU。
- 默认策略说错：noeviction 才是默认，不是 allkeys-lru。

> 权威内容：Redis 过期与淘汰当前尚未在仓库建设，可参考 Redis 官方文档「Redis as an LRU cache」「Eviction policies」章节。

### Q08：缓存和数据库怎么保持一致？ `P0` `高频`

**30 秒回答**：主流做法是 Cache Aside 模式——读的时候先读缓存、未命中回填，写的时候先更新数据库、再删除缓存；删除而不是更新，是因为更新缓存在并发下可能和数据库顺序相反，缓存会长期留旧值，而删除是幂等的。这套方案是最终一致，不一致窗口在「更新数据库成功」到「删除缓存成功」之间，通常毫秒级；要更稳可以订阅 binlog 异步删缓存。

**深入理解**：

| 策略 | 流程 | 问题 | 结论 |
| --- | --- | --- | --- |
| 先更新 DB，再更新缓存 | DB → Cache | 两个写请求的更新顺序可能反了，缓存留旧值 | 不推荐 |
| 先删缓存，再更新 DB | Cache → DB | 删除后、更新前有读请求，把旧值写回缓存 | 不推荐 |
| 先更新 DB，再删缓存 | DB → Cache | 仍有极小概率不一致，但窗口最小 | 推荐（Cache Aside） |
| 订阅 binlog 删缓存 | DB → binlog → Cache | 有延迟，顺序由 DB 保证 | 顺序敏感场景用 |

- **为什么是删不是更新**：更新缓存要求「把计算结果写进缓存」，并发下两个写的完成顺序可能与 DB 顺序相反；删除是幂等的，无论执行几次结果一致，且下次读自然回填最新值。前提是「缓存数据能从 DB 重算」——不能重算的数据（聚合结果、跨库 Join）才需要权衡更新策略。
- **为什么先更新 DB 再删缓存**：反过来做的话，「删缓存」到「更新 DB」之间有读请求命中 miss，会把旧值回填并长期驻留；正序只留「DB 更新成功到缓存删除成功」的极小窗口，且要恰好这期间有读才不一致。
- **延迟双删**：先删缓存 → 更新 DB → 休眠一个大于「读库 + 回填」的时长 → 再删一次。它是补偿手段不是根治：休眠时长难定、第二次删除可能失败、极端并发下仍有窗口；面试里要主动说这些代价，别当成银弹。
- **订阅 binlog**：Canal/Maxwell 伪装成 MySQL 从库拉 binlog，投递到 MQ，消费端按 key 删缓存。优点是业务代码零侵入、顺序由 binlog 单队列保证；代价是多一套组件、有毫秒到秒级延迟、消费失败要兜底重试、消息乱序（多分区消费）反而制造不一致。
- **读写穿透**（Read/Write Through）简述：把缓存当作主存储，由缓存层负责同步 DB，业务无感；实现上要么用带持久化的缓存产品，要么在访问层封装，工程上多数团队仍是 Cache Aside。
- **不一致窗口怎么量化**：Cache Aside 正常是毫秒级（一次删除的耗时）；binlog 方案是「binlog 产生到消费完成」的延迟，通常百毫秒到秒级。任何异步方案都做不到强一致，要强一致要么串行化（写和回填都用同一把分布式锁，退化为低吞吐），要么这个数据不缓存。

**为什么这样设计**：先更新 DB 再删缓存能在不引入任何分布式事务的前提下把不一致窗口压到最小，是因为它把「并发写之间的顺序」交给了数据库保证（数据库是顺序执行点），缓存只做被动的失效；而所有「更新缓存」的方案都要自己维护一个顺序，这个顺序和数据库没有任何天然同步机制。

**面试官可能继续追问**：
- **删除缓存失败了怎么办？** —— 三个方向：删除失败重试（消息队列补偿）；靠 TTL 自然过期兜底（接受分钟级不一致）；订阅 binlog 让删除动作本身也被数据库事件驱动。生产中通常是「重试 + 短 TTL」组合。
- **延时双删睡多久？** —— 覆盖「一次读库耗时 + 一次回填耗时」再加余量，通常几百毫秒到 1 秒；但这会拖慢写接口，所以更常见的是写完直接返回、补偿逻辑异步做。
- **什么数据根本不该加缓存？** —— 写多读少的（每次写都要删缓存，命中率还低）、强一致要求的（余额、库存预占）、能从 DB 一次索引查询低成本拿到的。「Redis 一定比 MySQL 快所以要加缓存」是错误示范：单行主键查询在索引命中时就是百微秒级，加缓存后多一次网络往返，还要承担一致性成本和容量治理；缓存的价值在热点聚合、跨库 Join、复杂计算复用、跨服务共享状态，判断依据是访问模式和命中率，不是「Redis 更快」。
- **binlog 方案消息乱序了怎么办？** —— 按 key 分区保证同一 key 的顺序，或消费时比对版本号/时间戳丢弃旧消息；否则后到的旧删除会覆盖新回填。

**实际工程场景**：WMS 的库存数量是高频读写数据，天然不适合做「DB 更新 + 缓存同步」——每次扣减都要删缓存，写放大明显，且扣减本身有事务语义；实践中库存扣减直接走数据库行锁/乐观锁，缓存只服务「商品信息、仓库字典」这类读多写少的数据。慢 SQL 旁路缓存的思路同理：先看慢 SQL 的调用频次和结果可重算性，再决定缓存粒度，不要为了缓存而缓存。

**容易答错的地方**：
- 把 Cache Aside、Read/Write Through、延迟双删、binlog 混成一套「标准方案」，答不出各自窗口和代价。
- 只讲「怎么保证一致」，不讲「只能最终一致、窗口多大、怎么量化」——5 年以上必须能谈代价。
- 说「先删缓存再更新 DB 也行，只要加了延迟双删」——延迟双删是补丁不是等价方案，窗口和复杂度都在。
- 用「Redis 一定比 MySQL 快」作为加缓存的理由（红线：这是错误示范）。

> 权威内容：缓存一致性的场景设计框架见 [缓存一致性与幂等](../04-场景设计题/缓存一致性与幂等.md)；Redis 侧机制当前尚未在仓库建设，可参考 Redis 官方文档「Client-side caching」章节。

### Q09：Redis 分布式锁怎么实现？ `P0` `高频`

**30 秒回答**：最小实现是 `SET lock_key unique_value NX PX 30000`——一条命令同时完成加锁和设置过期，value 存唯一标识；释放时用 Lua 脚本先比对 value 再删除，避免误删别人的锁；业务执行时间不确定时用看门狗续期。它的失效条件也要主动说：主从异步复制下，主节点加锁成功未同步就宕机，从节点升主后锁会消失，两个客户端可能同时持锁。

**深入理解**：

- **加锁为什么必须一条命令**：早期的 `SETNX` + `EXPIRE` 两条命令，中间宕机会死锁；Redis 2.6.12 起 SET 支持 NX/EX/PX 组合参数，才真正做到原子加锁带过期。
- **value 为什么存唯一标识**：锁可能因业务超时而自动过期，此时别的客户端可能已拿到同一把锁；释放时不校验直接 DEL，删掉的就是别人的锁。唯一标识（UUID + 进程/线程信息）让释放操作能识别「这是不是我的锁」。
- **释放的 Lua 脚本**：`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`——get 和 del 之间可能被插入别的命令，交给 Lua 在单线程里整体执行才原子。
- **续期**：锁 TTL 必须大于业务最长时间，估不准就看门狗（Redisson 默认 30 秒过期、每 10 秒续，见 Q10）或业务侧定期续期脚本；续不到就主动让出锁，不能闷头继续执行。
- **主从切换丢锁**：锁加在主节点，复制是异步的，主从切换瞬间锁可能「物理上还在旧主、逻辑上已失效」，新主上另一个客户端可以加锁成功——出现两个持有者。Redlock（多数派独立节点）是缓解方案但有争议（见 Q10）；对正确性敏感的场景应选 etcd/ZooKeeper 的临时节点，或干脆不用分布式锁、用数据库唯一索引/乐观锁。
- **业务侧必须兜底**：分布式锁是性能优化（把并发挡在外面），不是正确性保证；真正不能重复执行的操作要有幂等第二道闸（唯一索引、状态机、版本号）。

**为什么这样设计**：把「加锁、过期、校验、释放」都收敛到 Redis 单线程执行的命令和 Lua 脚本里，是为了不引入分布式事务就拿到原子性——任何「先 GET 再 SET」的客户端侧判断在高并发下都有窗口；这也是为什么 value 校验逻辑必须写在 Lua 里而不是业务代码里。

**面试官可能继续追问**：
- **锁的 TTL 设多久合适？** —— 覆盖业务 P99 耗时再加 2～3 倍余量；估不准就传较短 TTL 加看门狗续期。设太长，宕机后死等；设太短，业务没跑完锁就没了。
- **看门狗续期本身失败了怎么办？** —— 续期失败说明 Redis 可能已出问题，此时应当终止业务执行而不是继续；Redisson 的看门狗续期失败会让锁失效，业务继续跑就进入了「无锁执行」的危险区，所以调用方要能感知锁状态。
- **Redlock 能解决主从丢锁吗？** —— 部分缓解：向 N 个独立 master 加锁、多数派成功才算拿到，单点切换丢锁概率大幅降低；但 Martin Kleppmann 指出它依赖时钟假设，GC pause 和时钟漂移下仍有窗口，且运维成本高。多数团队的答案是「Redisson 单锁 + 业务幂等」，强一致选 etcd/ZK。
- **和 分布式.md 的分布式锁题什么关系？** —— 那边讲方案选型（Redis vs ZK vs DB、Redlock 争议、失效场景推演），这里聚焦 Redis 侧的实现细节：命令原子性、value 校验、续期、脚本边界。

**实际工程场景**：WMS 的库存扣减如果要做「应用层防重」，可以用 `SET stock_lock:{skuId} {uuid} NX PX` 挡住并发重复扣减，但扣减本身仍要落在数据库的乐观锁/行锁上——锁只减少无效并发，数据正确性最终由数据库保证。出库单的「撤回再提交」状态机同理，锁 + 状态流转条件双保险。

**容易答错的地方**：
- 用 `SETNX` + `EXPIRE` 两条命令加锁（非原子，宕机即死锁）。
- 释放时直接 `DEL` 不校验 value，答不出「会误删别人的锁」。
- 说「Redis 分布式锁是强一致的」——异步复制 + 故障切换决定了它有丢锁窗口。
- 不知道看门狗机制，或把看门狗说成「Redis 自带功能」（它是 Redisson 客户端的实现，不是 Redis 服务端能力）。

> 权威内容：分布式锁的方案选型见 [分布式.md](分布式.md)；Redis 侧实现当前尚未在仓库建设，可参考 Redis 官方文档「Distributed Locks with Redis」章节。

### Q10：Redisson 的原理？ `P1` `中频`

**30 秒回答**：Redisson 的锁在 Redis 里是一个 Hash：key 是锁名，field 是「客户端 UUID + 线程 ID」，value 是重入计数；加锁、重入、释放都由 Lua 脚本原子完成；不传 leaseTime 时启动看门狗，默认锁 30 秒过期、每 10 秒续期一次，传了 leaseTime 就不再续期。RedLock 用多个独立 master 的多数派降低主从丢锁概率，但有争议、成本高，通常单锁加业务幂等就够。

**深入理解**：

- **Hash 结构的含义**：同一把锁同一线程重复加锁，只是 `HINCRBY` 计数加一，实现可重入；不同线程的 field 不同，`HLEN` 不为零说明锁被占。释放时计数减到零才真正 `DEL`，避免重入持有者提前释放。
- **加锁的 Lua 逻辑**（简化）：key 不存在 → `HSET` + `PEXPIRE`；存在且 field 是自己 → 重入计数 +1，重置过期时间；存在且 field 是别人 → 返回剩余 TTL，加锁失败。
- **看门狗**：`tryLock` 不传 leaseTime（默认 -1）时，加锁成功后启动后台定时任务，每 `internalLockLeaseTime / 3`（默认 30s/10s）执行一次 Lua 续期（`PEXPIRE` 重置），直到 `unlock` 或线程退出；传了 leaseTime 则以传入值为准、看门狗不启动，到期自动释放。这是最容易答错的点。
- **tryLock(waitTime, leaseTime, unit)**：waitTime 内自旋重试，并借助 Redis 的发布订阅在锁释放时被唤醒，避免纯 sleep 轮询。
- **公平锁**：Redisson 另用 List（等待队列）+ ZSet（排队权重）实现，先来先服务，代价是更高延迟和更复杂结构，只在确需公平时用。
- **RedLock 的争议**：Redisson 的 `RedissonRedLock` 向多个相互独立的 master 加锁，多数派成功才算成功，单节点故障切换丢锁的概率大幅降低；但它对时钟和进程暂停敏感（Kleppmann 的质疑：GC pause 期间锁可能已过期、续期却以为还在持有），运维上还要维护多组独立 Redis。结论：对正确性极端敏感、且能接受成本的场景才上；常规业务 Redisson 单锁 + 幂等兜底。
- **其他常用组件**：`RRateLimiter`（限流器，规则存 Redis、Lua 原子扣减配额，可做分布式全局限流）；`RSemaphore`（信号量， permits 计数，控制并发访问数）；还有 `RCountDownLatch`、`RBloomFilter` 等。

**为什么这样设计**：用 Hash 而不是 String，是因为重入计数、持有者校验、续期这三件事必须在 Redis 侧原子完成；用看门狗而不是固定长 TTL，是因为业务耗时不可预知——固定短 TTL 会误释放，固定长 TTL 会让宕机后的锁长时间空占，三分之一周期续期是「释放及时性」和「续期开销」之间的经验折中。

**面试官可能继续追问**：
- **看门狗续期是哪个线程做的，业务线程挂了怎么办？** —— 续期由 Redisson 的后台线程做，与业务线程解耦；业务线程异常中断时，只要 JVM 还活着且能执行到 unlock/finally，或线程被中断后 Redisson 的取消逻辑会释放锁；但进程被 kill -9 时只能等锁 TTL 到期，这是所有 Redis 锁的共同边界。
- **可重入锁的计数什么时候清零？** —— 同一线程每次 unlock 减一，减到零才删 key；如果漏调用 unlock（比加锁次数少），计数永远不为零，锁泄漏——这就是生产上偶发「锁莫名不释放」的常见原因。
- **Redisson 和原生 Lua 自己写的锁怎么选？** —— 只要能引依赖就优先 Redisson：看门狗、可重入、公平锁、发布订阅唤醒都是现成的，自己写容易在续期和取消边界上留坑；轻量场景或不想引重依赖时，`SET NX PX` + Lua 释放已经覆盖 80% 需求。

**实际工程场景**：WMS 的接口级限流（如出库查询接口按仓库维度限流）可以直接用 `RRateLimiter`，规则集中配置、多实例共享配额，比每台机器本地限流更可控；库存扣减的并发控制用 `RLock` 可重入特性可以让「扣减方法调用扣减子方法」不用重新设计锁粒度。注意这些是组件能力的适用场景，具体是否采用要结合团队对 Redisson 版本的运维能力。

**容易答错的地方**：
- 说「传了 leaseTime 看门狗还会续期」——传了就不续，这是高频错点。
- 认为看门狗能解决主从切换丢锁——它解决的是「业务没跑完锁过期」，不是复制延迟丢锁。
- 把 RedLock 当银弹，答不出时钟/GC pause 争议。
- 分不清 Redisson 的锁是客户端实现，以为是 Redis 服务端功能。

> 权威内容：Redisson 原理当前尚未在仓库建设，可参考 Redis 官方文档「Distributed Locks with Redis」与 Redisson 官方文档。

### Q11：Redis 主从复制？ `P1` `中频`

**30 秒回答**：主从复制分全量和增量：首次同步时主库 bgsave 生成 RDB 发给从库，期间的写命令进复制缓冲区，RDB 之后补发；日常命令传播带着 offset，从库断线重连后带上 offset 请求，只要 offset 还在 repl_backlog 环形缓冲区内就只补差额、不做全量，这就是增量同步。PSYNC2（4.0）让主从切换后的重连也能尽量部分重同步。读写分离要注意：复制是异步的，从库读可能读到旧值。

**深入理解**：

- **全量同步流程**：从库连接主库后完成 PING/认证，发送 `PSYNC <replid> <offset>`；首次发 `PSYNC ? -1`，主库返回 `+FULLRESYNC`，然后 fork 子进程执行 bgsave 生成 RDB，fork 之后到达的写命令写入复制缓冲区；RDB 发送完毕、从库清空旧数据并加载完成后，主库把缓冲区里累积的命令补发给从库，之后进入命令传播阶段。全量期间主库正常服务，但从库长时间处于同步中、不可用。
- **增量同步**：主库每传播一条命令，复制偏移 offset 递增；从库周期性 `REPLCONF ACK` 上报自己的 offset；断线重连后发 `PSYNC replid offset`，若 offset 落在 `repl_backlog`（默认 1MB 的环形缓冲区）内，只补发差额即部分重同步；超出缓冲区则退化为全量。
- **PSYNC2（4.0）**：从库被提升为主后，会同时记住旧主的 replid，其他从库重连时可以尝试用新旧 replid 做部分重同步，避免主从切换后从库集体全量重同步把主库拖垮。
- **读写分离的延迟**：复制默认异步，主从间有毫秒到秒级延迟（大写入、网络抖动、从库加载慢时更大）；从库读到的可能是旧值——刚提交的出库单在从库查不到是典型现象。监控看 `master_repl_offset - slave_repl_offset` 的差值和 `master_link_status_since_seconds`；延迟敏感的查询强制走主库，或等主从 offset 追平。
- **无盘复制**：`repl-diskless-sync` 让主库不落盘、直接把 RDB 流式发给从库，省一次磁盘写入，适合磁盘弱的机器。
- **从库只读**：`replica-read-only yes` 是默认，从库拒绝写命令，防止从库写入与主库分叉。

**为什么这样设计**：全量同步用 bgsave + fork 而不是阻塞主库生成快照，是因为同步期间主库必须继续服务；用环形缓冲区而不是「缓存全部历史命令」做增量，是因为缓冲区大小有界、内存可控，代价是断线太久（堆积命令超过 backlog）只能全量——这是用一次全量的成本换取日常增量的低开销。

**面试官可能继续追问**：
- **主从延迟突增怎么排查？** —— 先看是不是全量同步中（从库 loading）；再看主库写入 QPS 是否突增、从库机器性能（加载 RDB 是 CPU/IO 密集）；网络分区会让 offset 差持续扩大。RDB 传输期间的从库是「不可用」状态，容量规划要算进去。
- **为什么从库不主动删除过期 key？** —— 从库不主动清理过期 key，物理删除依赖主库同步过来的 DEL；读命令命中已过期 key 时按不存在处理。所以主从延迟期间的风险主要是「已删除/已更新的数据在从库还是旧值」，不是「读到未过期的脏数据」。
- **主从切换期间写请求会怎样？** —— 主库宕机到从库提升的几秒内，指向旧主的连接报错，客户端需要按哨兵/集群协议重定向（Q12）；业务侧要有重试和连接刷新逻辑。

**实际工程场景**：WMS 的报表类查询（出库统计、库存汇总）可以走从库，避免和交易写争抢主库；但刚提交的出库单详情查询必须走主库，否则会出现「提交成功、列表查不到」的客诉。生产中按「查询对时效的容忍度」拆分到主/从，是读写分离落地的关键动作。

**容易答错的地方**：
- 说「全量同步期间主库阻塞」——bgsave 是 fork 子进程，主库不阻塞（大实例 fork 卡顿是另一回事，见 Q02/Q15）。
- 以为从库可以写，或不知道 `replica-read-only` 默认开启。
- 分不清 repl_backlog（环形增量缓冲）和复制缓冲区（全量期间的命令缓存）两个概念。
- 不知道 PSYNC2 是 4.0 引入、解决的是主从切换后的部分重同步。

> 权威内容：Redis 主从复制当前尚未在仓库建设，可参考 Redis 官方文档「Replication」章节。

### Q12：Redis 哨兵和 Cluster？ `P1` `中频`

**30 秒回答**：哨兵解决高可用不解决分片：多个哨兵进程监控主从，主库主观/客观下线后由哨兵内部 Raft 选出的 leader 执行故障转移，把一个从库提升为主；Cluster 解决分片：16384 个哈希槽按 CRC16(key) mod 16384 分配，节点间用 gossip 交换状态，客户端按 MOVED/ASK 重定向访问，扩缩容就是迁移槽。两者可叠加但定位不同——容量受单机限制用哨兵，要横向扩容量用 Cluster。

**深入理解**：

- **哨兵三件事**：监控（每个哨兵每秒 PING 主从、定期 INFO 拿拓扑）、通知（故障时通知客户端和管理员）、自动故障转移 + 配置提供（客户端问哨兵「现在主是谁」）。
- **主观下线与客观下线**：单个哨兵超过 `down-after-milliseconds` 收不到心跳 → 主观下线 SDOWN；超过 quorum 数量的哨兵都判定 SDOWN → 客观下线 ODOWN，才触发转移。
- **选主过程**：哨兵集群用 Raft 选出一个 leader 执行转移：按优先级（`replica-priority`）、复制 offset（数据最新）、runid 挑从库，执行 `SLAVEOF NO ONE` 提升，并让其他从库指向新主。哨兵本身建议 3 或 5 个奇数节点。
- **Cluster 核心机制**：16384 个 slot；key 归属 `CRC16(key) % 16384`；`hash tag`（`{user:1000}:profile` 的形式）让多个 key 落同一 slot，用于 Lua/事务/多 key 操作；节点间通过集群总线（端口 +10000）gossip 交换 PING/PONG，做故障检测、配置传播、从库发现。
- **MOVED vs ASK**：MOVED 表示 slot 已永久归属别的节点，客户端应更新本地 slot 映射缓存；ASK 表示 slot 正在迁移中，先发 `ASKING` 再访问目标节点，是临时重定向。
- **扩缩容**：新节点 `CLUSTER MEET` 加入，用 `CLUSTER SETSLOT` + `MIGRATE`/`RESTORE` 把槽分批迁过去；迁移期间服务不中断，但该 slot 的请求要走 ASK 路径，延迟略升。
- **取舍**：哨兵方案客户端只需支持哨兵协议，容量仍受单机内存限制；Cluster 容量可横向扩，但客户端要维护 slot 映射、跨 slot 的多 key 操作和 Lua/事务受限（见 Q14）、`cluster-require-full-coverage yes` 时只要有一个槽没有节点负责整个集群拒绝服务、故障恢复期间对应 slot 短暂不可用。官方建议集群不超过 1000 个主节点（gossip 消息量随节点数增长）。

**为什么这样设计**：哨兵把故障检测和选主交给独立进程群而不是 Redis 实例自己，是因为「谁决定主挂了」这个问题不能由可能已经出问题的节点回答；Cluster 用固定 16384 个槽而不是按节点取模，是因为槽位是显式、可迁移的所有权单位，扩缩容只是「挪槽」，不需要重算所有 key 的归属，代价是每个 key 都要算一次 CRC16、客户端要缓存映射。

**面试官可能继续追问**：
- **为什么是 16384 个槽？** —— gossip 心跳里带 slots bitmap，16384 个槽压缩后几百字节，节点数上千也可控；换成 65536 bitmap 是 8KB，心跳包太大。同时 16384 对常规集群规模（几百节点）够用。
- **Cluster 是强一致吗？** —— 不是，每个分片内部仍是主从异步复制；写命中主库即返回，主库宕机未同步的部分会丢。需要更强一致仍是 etcd/ZK 那条线。
- **槽迁移期间读写怎么保证不丢？** —— 迁移是逐 key 的：源节点处理已迁移的 key 返回 ASK，目标节点对未迁移的 key 也返回 ASK 指回源；`ASKING` 命令让目标临时接受这个本不属于它的 key。期间源和目标对同一 key 的操作由客户端按重定向完成，理论上不丢但延迟升高。

**实际工程场景**：WMS 缓存如果单实例内存到了 30～40GB、fork 卡顿和碎片化开始影响稳定性，就该规划从「哨兵 + 主从」演进到 Cluster：按仓库/租户维度做槽位规划，用 hash tag 保证同一单据的头明细 key 同槽，迁移安排在低峰按槽灰度。这是容量与复杂度的权衡，不是「上了 Cluster 就高级」。

**容易答错的地方**：
- 说「哨兵可以分片/扩容」——哨兵只管高可用，数据仍在单主。
- 不知道 16384 的来源和 hash tag 的作用。
- 混淆 MOVED 和 ASK 的语义（永久 vs 迁移中）。
- 以为 Cluster 下任意多 key 操作都可用——跨 slot 的 `MGET`、Lua、事务都会报 CROSSSLOT 错。

> 权威内容：Redis 哨兵与 Cluster 当前尚未在仓库建设，可参考 Redis 官方文档「High availability with Redis Sentinel」「Redis Cluster specification」章节。

### Q13：热 Key 怎么发现和处理？ `P1` `中频`

**30 秒回答**：热 key 是访问频次远超其他的 key，可能把单个分片的单线程打满。发现手段：`--hotkeys`（基于 LFU 采样，有偏）、`monitor`（只能短时间小流量用）、客户端埋点统计、代理层统计；处理是分散流量——本地缓存挡一层、读请求引导到副本、或把 key 复制多份随机后缀读。热 key 和大 key 的区别是：一个考频次，一个考体积，解法相反。

**深入理解**：

- **发现手段与代价**：
  - `redis-cli --hotkeys`：依赖 LFU 淘汰策略的采样计数器（要求 `maxmemory-policy allkeys-lfu`），结果有偏、只反映采样到的 key，适合量级参考；可配合 `-i` 控制间隔。
  - `monitor`：实时流式输出全量命令，QPS 高时会把 CPU 和带宽打满、严重影响线上，只能短时间、低峰、小流量下用，用完立即退出。
  - 客户端 SDK 埋点：统计 top N key 的调用次数，最贴近真实访问模式，代价是客户端改造和统计上报。
  - 代理层统计：Codis/twemproxy 或自研 proxy 天然经过全量流量，统计最准，但不是所有架构都有这层。
  - 业务侧已知热点：置顶商品、爆款 SKU、活动配置——很多时候热 key 是设计出来的，先问「这个 key 为什么会热」。
- **三种处理手段**：
  - **本地缓存挡一层**：Caffeine 存 1～5 秒短 TTL，热 key 的读请求大部分在 JVM 内消化；代价是多实例不一致窗口、需要失效广播或接受秒级陈旧、应用内存占用。
  - **读写分离到副本**：把热 key 的读请求显式引导到 slave；代价是复制延迟、slave 成为新热点、副本能力上限。
  - **key 复制多份**：`key_1` 到 `key_n` 随机后缀分散到不同 slot/节点，读随机选一份，更新时删全部副本；代价是更新路径复杂、副本间不一致窗口、缓存命中率摊薄。
- **和大 key 的区别（Q03）**：热 key 是「访问频次高」，单体可能很小，阻塞来自请求量把单线程占满；大 key 是「单条命令执行/输出慢」，来自数据体积。热 key 用分散流量，大 key 用拆分数据，两者可能同时存在，要分别治理。

**为什么这样设计**：热 key 不能靠扩分片根治，是因为它天然集中在一个 key 上，无论怎么分片都落在同一个 slot、同一个节点——分片解决的是「总容量」，不解决「单点热度」；所以解法都是「把读压力从 Redis 单线程上挪走」，本地缓存是挪到应用进程，副本读是挪到从节点，key 复制是挪到多个 key。

**面试官可能继续追问**：
- **本地缓存之后缓存和 Redis 不一致了怎么办？** —— TTL 设短（秒级）把窗口压到业务可容忍；要求更高就配失效广播（Redis 发布订阅/MQ 通知各实例淘汰），代价是又多一套机制；没有免费的一致性。
- **key 复制之后旧值怎么清？** —— 更新时把 `key_1..key_n` 全部删掉，下次读各自回填；期间不同副本可能短暂不一致，和对缓存一致性的常规取舍一样。
- **hotkeys 没扫出来是不是就没有热 key？** —— 不一定：它基于 LFU 采样，突增的热点（活动刚开始）counter 还没涨起来，瞬时流量尖峰也扫不到；监控上报的 key 调用排行比一次性扫描更可靠。

**实际工程场景**：WMS 大促时的爆款 SKU 库存查询是典型热 key——库存数本身不适合缓存（写太频），但「SKU 基础信息 + 仓库库存概况」这类读多写少的数据可以先上本地缓存挡峰值，同时按调用排行监控 top key，发现单 key QPS 占实例 20% 以上就触发复制或副本读预案。注意这些是手段清单，是否启用取决于压测数据和一致性容忍度。

**容易答错的地方**：
- 拿 `monitor` 长期开着做热 key 监控，或说 `--hotkeys` 结果是精确的。
- 把热 key 当大 key 拆，或把大 key 当热 key 分散流量——两者的根因和药方是反的。
- 只说「加本地缓存」，不说一致性窗口和失效广播的代价。
- 以为「扩容/加从库」自动解决热 key——不加读写分离和复制改造，热 key 仍打在同一个主上。

> 权威内容：Redis 热 key 治理当前尚未在仓库建设，可参考 Redis 官方文档「redis-cli」「Latency troubleshooting」章节。

### Q14：Redis 事务和 Lua？ `P1` `中频`

**30 秒回答**：Redis 事务是 MULTI 到 EXEC 之间的命令入队后一次性顺序执行，没有隔离级别、也没有回滚——入队阶段的错误（命令不存在、参数错）会让 EXEC 整体放弃，执行阶段的错误（如对字符串做 INCR）不会回滚、其他命令照常执行；WATCH 提供乐观锁。Lua 脚本因为跑在 Redis 单线程上，整个脚本执行期间没有别的命令插入，所以天然原子，这就是库存扣减这类「查-改」逻辑用 Lua 保证一致性的原因。

**深入理解**：

- **事务命令**：`MULTI` 进入事务态，之后命令只入队返回 QUEUED；`EXEC` 顺序原子执行；`DISCARD` 放弃。`WATCH key` 在 EXEC 前监视 key，若被别的客户端修改过，EXEC 返回 nil 放弃执行——乐观锁，用于「先读后写」的并发控制。
- **两类错误必须分开说**：
  - 入队错误：命令名不存在、参数个数不对——EXEC 时返回错误，整个事务不执行（Redis 2.6.5 起的行为）。
  - 执行错误：命令语法对但运行时失败，比如对 String 做 `INCR`——不会回滚，该命令返回错误，其他命令正常执行并生效。
  - 没有回滚的原因：Redis 认为这类错误是编程错误，应在开发期发现；回滚需要反向补偿日志，复杂度和性能代价与 Redis 的定位不符。
- **Lua 原子性**：脚本在单线程上从头跑到尾，中间不会插入其他命令，所以脚本内的多个 redis.call 合起来是原子的。`EVAL script numkeys key...`，`EVALSHA` 用 SHA1 引用已加载脚本（`SCRIPT LOAD` 预加载或集群下减少传输），脚本本身不进 RDB/AOF（7.0 前的裸脚本需要客户端重新加载，7.0 Functions 才持久化，见 Q16）。
- **Cluster 下的硬限制**：脚本访问的 key 必须落在同一 slot，否则直接报 CROSSSLOT 错误；解法是 hash tag（`{sku:1001}` 形式）把相关 key 圈到同槽。多 key 事务同样受限。
- **非确定性命令的版本坑**：脚本里调用 `RANDOMKEY`、`TIME`、随机类命令后再写数据，旧版本会在复制时报错（写命令不允许跟在非确定性命令后）；Redis 6.0 起改为 effects replication（只复制脚本对数据的实际影响）才彻底解决。

**为什么这样设计**：事务不做回滚、Lua 不做嵌套事务，是因为 Redis 的一致性单位就是「命令」——单命令原子由单线程保证，多命令原子由 Lua 保证，两者都不需要 MVCC 和锁；这是拿「能力窄」换「行为可预测」，也意味着别用 Redis 事务实现需要回滚的业务流程。

**面试官可能继续追问**：
- **Lua 脚本执行太久会怎样？** —— 阻塞整个实例，其他命令全部排队；`lua-time-limit`（默认 5 秒）到点后允许其他脚本/命令插入，但正在执行的那个脚本不会被强杀，只会收到「busy」响应。所以脚本里不能写长循环和慢逻辑。
- **redis.call 和 redis.pcall 区别？** —— call 出错会中断脚本、已执行的效果保留；pcall 捕获错误返回错误表，可以脚本内处理。需要「尝试失败不炸全局」时用 pcall。
- **WATCH 和 Lua 哪个好？** —— 要「读出来在业务侧算、再写回」的乐观锁用 WATCH；要「读改写都在 Redis 内完成」的原子操作用 Lua；现代客户端基本都用 Lua，WATCH 事务的典型场景越来越少。

**实际工程场景**：WMS 库存扣减的「读当前库存 → 判断充足 → 扣减 → 记录流水」如果用客户端查再写，两个请求可能都读到 100 各扣 60；改成 Lua 把四步收敛成一个脚本，Redis 单线程保证中间不插入；如果扣减还涉及多个 key（库存 + 预占 + 流水），要么用 hash tag 圈到同槽，要么把多 key 的原子性下沉到数据库事务——跨槽强一致本来就不是 Redis 的领域。

**容易答错的地方**：
- 说「Redis 事务失败会回滚」——不会，两类错误的行为都要能说清。
- 把 WATCH 说成悲观锁/行锁——它是乐观锁，靠 EXEC 时检查版本。
- 说 Lua 脚本自动持久化、重启后还在——7.0 前裸脚本不进 RDB/AOF，要么客户端重载要么用 Functions。
- 不知道 Cluster 下 Lua 和事务的 key 必须同槽，或不知道 hash tag 的写法。

> 权威内容：Redis 事务与 Lua 当前尚未在仓库建设，可参考 Redis 官方文档「Transactions」「Scripting with Lua」章节。

### Q15：Redis 线上问题怎么排查？ `P1` `中频`

**30 秒回答**：有一套固定路径：慢命令看 `SLOWLOG GET`，大 key 用 `--bigkeys`/`--memkeys`，延迟问题用 `--latency-doctor`，线上永远用 SCAN 代替 KEYS，内存明细用 `MEMORY USAGE`，`monitor` 只能短时间低峰用；同时盯命中率、连接数、主从 offset 差。典型毛刺排查：P99 周期性尖刺但慢日志没有记录，latency doctor 显示 fork 事件，多半是大实例 bgsave 或 AOF 重写的 fork + 写时复制卡顿。

**深入理解**：

- **慢命令**：`SLOWLOG GET 10`，只记录命令执行耗时，不含网络 IO 和排队时间；阈值 `slowlog-log-slower-than` 默认 10ms，排查期可临时调到 1ms。慢日志为空不等于没问题——只覆盖执行阶段，阻塞在「排队等执行」的请求它看不见。
- **大 key**：`redis-cli --bigkeys`（SCAN 采样，`-i` 控制间隔）、`--memkeys`（6.0 起按内存排）、`MEMORY USAGE key` 定点精确确认；离线用 rdb-tools 全量分析。
- **延迟定位**：`redis-cli --latency`/`--latency-history`/`--latency-doctor`；doctor 会区分 intrinsic latency（机器本身的事件唤醒延迟，说明机器/虚拟化有问题）和具体事件：fork（bgsave/AOF rewrite）、AOF fsync、eviction cycle、swap。配 `INFO persistence` 的 `latest_fork_usec` 和大 value 查询一起看。
- **必须 SCAN 不 KEYS**：`KEYS` 是 O(N) 全表扫描，大库上一次就是秒级阻塞；`SCAN` 游标迭代，每次少量，对线上安全（结果可能有重复，去重由业务做）。
- **常盯指标**：`INFO stats` 的 `keyspace_hits/keyspace_misses`（命中率，掉了先查是 key 没了还是策略淘汰）；`used_memory` vs `maxmemory`（逼近上限要考虑淘汰和容量）；`mem_fragmentation_ratio`（>1.5 碎片化严重，4.0 起 `activedefrag yes` 可自动整理；<1 且 used 大于物理内存迹象说明在 swap）；`connected_clients` 与 `blocked_clients`；主从 `repl offset` 差（延迟）。
- **monitor 的边界**：输出全量命令流，QPS 高时会把单线程打满、带宽占住，只能短时间低峰抓现场，且它本身不进 pipeline、输出可能不完整。
- **典型排查路径**：P99 毛刺、周期性与写入峰相关 → `SLOWLOG GET` 没有记录（排除命令本身慢）→ `--latency-doctor` 显示 fork 事件、`latest_fork_usec` 达百毫秒级 → 定位为大实例 bgsave/AOF rewrite 的 fork + COW 写放大 → 规避：控制单实例内存、快照错峰、关闭 THP、`lazyfree` 系列开启、必要时迁 Cluster 分片。

**为什么这样设计**：这套工具组合的逻辑是「先分层再定位」——慢日志管执行层，latency 管时间线，大 key 管对象层，指标管趋势层；因为 Redis 是单线程黑盒，外部只能通过「它自己吐出的时间线和统计」定位，所以排查顺序比工具本身更重要：先看是不是真慢，再看慢在哪一层，最后才是调优。

**面试官可能继续追问**：
- **命中率突然下降怎么查？** —— 先看 key 是不是被淘汰了（`evicted_keys` 增长 + maxmemory 逼近）、是不是被批量删除/过期（`expired_keys` 突增）、是不是请求模式变了（新功能在查不存在的 key，转化为穿透问题，Q01）；对应到容量、TTL 策略、入口校验三个方向。
- **连接数打满怎么办？** —— 查是不是连接泄漏（客户端没用连接池、异常分支没归还）、`blocked_clients` 是否堆积（等锁/等 list）；短期 `CLIENT KILL` 清理空闲连接，长期修客户端池化配置和超时。
- **latency doctor 说 intrinsic latency 高说明什么？** —— 机器本身的问题：CPU 被抢占、虚拟化超售、NUMA 抖动、THP 未关——先解决机器层面的噪声，再谈 Redis 调优，否则所有优化都被底层抖动掩盖。

**实际工程场景**：一次典型排查的路径可以是：WMS 出库查询接口 P99 周期性尖刺（每小时准点）→ 慢日志无记录 → latency doctor 指出 fork 事件 → 对齐 `latest_fork_usec` 与尖刺时间吻合 → 确认是每小时一次的 RDB 快照在大实例上 fork 卡顿 → 短期把快照周期从 1 小时改为 4 小时并错峰，长期按容量规划拆 Cluster。这里给的是方法路径，具体数字以各自压测和监控为准。

**容易答错的地方**：
- 生产环境用 `KEYS *`、`FLUSHALL`、长开 `monitor`——这三条任何一条都够写进事故报告。
- 以为 `SLOWLOG` 为空就没问题（它不覆盖排队和网络）。
- 分不清 `used_memory` 和 `maxmemory` 的关系，或把碎片率 `>1.5` 当正常。
- 排查只会背工具名，给不出「先分层再定位」的顺序和一个完整案例路径。

> 权威内容：Redis 线上排查当前尚未在仓库建设，可参考 Redis 官方文档「Latency troubleshooting」「redis-cli」章节。

### Q16：Redis 6.0/7.0 的重要变化？ `P2` `低频`

**30 秒回答**：Redis 6.0 的多线程 IO（`io-threads`，默认关闭）、ACL 权限体系、RESP3 协议、client-side caching 服务端协助失效，以及 SSL 支持；Redis 7.0 的 Functions（取代裸 Lua 脚本管理，可持久化）、Multi-part AOF（manifest 管理多文件）、Sharded Pub/Sub（按 slot 分发，减少广播放大）。版本差异要说清：混合持久化和 LFU 是 4.0，多线程 IO 是 6.0，AOF 多文件是 7.0。

**深入理解**：

- **4.0 打底的几个点**（对比时先立坐标）：混合持久化 `aof-use-rdb-preamble`、LFU 淘汰策略、PSYNC2 部分重同步、`lazyfree`/`UNLINK` 异步释放、Modules 扩展机制。
- **6.0**：
  - 多线程 IO：`io-threads` 处理网络读写和协议解析，命令执行仍单线程，默认关闭；6.0 需要配合 `io-threads-do-reads yes`，7.0 起该参数移除、只需 `io-threads > 1`。
  - ACL：`user default on nkeys ...` 式的用户权限体系，命令和 key 两个维度授权，多租户共用实例的前提；`ACL WHOAMI`/`ACL LIST` 查看。
  - RESP3：新协议版本，支持 map/set 等属性型回复，客户端可选启用（`HELLO 3`）。
  - Client-side caching：服务端跟踪客户端缓存的 key，失效时推送通知（`CLIENT TRACKING`），需要客户端配合实现。
  - SSL/TLS 支持进入核心。
- **7.0**：
  - Functions：`FUNCTION LOAD` 把 Lua 函数库持久化进 RDB/AOF，重启和从库自动加载，替代裸 `EVAL` 脚本的「客户端各自管理」模式；注意 7.0 的函数仍要求 key 同 slot，集群函数（cluster functions）要到 7.4 才支持。
  - Multi-part AOF：`appendonlydir` 下 manifest 管理一个 base 全量文件加多个 incr 增量文件，重写只生成新 base，文件组织从「一个巨型 appendonly.aof」变为「全量 + 增量」的结构；7.0 启动时能自动识别并转换旧版单文件 AOF。
  - Sharded Pub/Sub：`SPUBLISH`/`SSUBSCRIBE` 按 slot 分发消息，接收方只收到自己分片的副本相关消息，解决大规模集群下普通 PUB/SUB 的广播放大和带宽浪费。
  - 另外 7.0 起混合持久化默认开启。
- **升级视角**：5.x → 7.x 的注意点是 AOF 目录结构变化、Lua 脚本迁移到 Functions、客户端驱动对 RESP2/3 的兼容；不要为了追新而升，升级收益要和「多线程 IO 是否真有需要、Functions 是否解决脚本管理痛点」对齐。

**为什么这样设计**：Functions 解决「脚本不在服务端持久化、重启后丢失、多客户端加载状态不一致」的管理问题——把脚本当数据管，复制和恢复就自动继承 Redis 既有机制；Multi-part AOF 把「全量」和「增量」在文件层面分开，重写只碰一个文件，降低重写期间的风险面；Sharded Pub/Sub 承认广播模式在大集群下不可扩展，改用分片内通信。

**面试官可能继续追问**：
- **多线程 IO 是 6.0 的，7.0 有什么变化？** —— 配置简化（`io-threads-do-reads` 移除），读写都默认走多线程路径；但「命令执行单线程」这个底线没变过。
- **混合持久化哪一版、默认开吗？** —— 4.0 引入，7.0 起默认开启；引入前 AOF 重写产物是纯命令流，大实例恢复慢。
- **裸 Lua 脚本和 Functions 选哪个？** —— 新项目直接用 Functions（可持久化、可管理、集群下 7.4+ 可用）；存量 5.x/6.x 升级时把 `EVAL` 调用收敛到函数库，别新旧混用。

**实际工程场景**：WMS 缓存如果仍跑在 5.x，升级评估清单可以是：先把 Lua 脚本集中登记（为迁 Functions 做准备）→ 灰度 7.0 关注 AOF 多文件目录的备份脚本兼容性（老脚本按 appendonly.aof 单文件拷贝会漏 incr 文件）→ 视压测结果决定是否开 `io-threads`。版本升级的收益要对应到具体痛点，不是「新版更快」这么笼统。

**容易答错的地方**：
- 说「6.0 之后命令执行也支持多线程」——只有 IO 层。
- 说 7.0 的 Functions 支持集群——7.0 不支持，cluster functions 是 7.4。
- 把混合持久化、LFU、PSYNC2、lazyfree 这些 4.0 特性说成 6.0/7.0 的。
- 把 Multi-part AOF 说成「取代了混合持久化」——它是文件组织方式，混合持久化在 7.0 反而默认开启。

> 权威内容：Redis 版本演进当前尚未在仓库建设，可参考 Redis 官方文档各版本 Release Notes 与「Redis 7.0 新特性」系列说明。

## 本专题常见追问链

一次典型的 Redis 面试追问路径如下，每一跳的验证点都不同——答不上下一跳，往往说明上一跳只是背过结论：

```text
「Redis 有哪些数据结构，ZSet 底层是什么」                        Q04
   │ 验证：编码与场景的匹配度，是否知道 skiplist + hashtable 双结构、
   │ 跳表 vs 红黑树的取舍（范围查询 + 实现简单 + 内存）
   ▼
「那 Redis 为什么快」                                            Q05
   │ 验证：能否把「快」拆成内存/单线程/epoll/结构/RESP 多点，
   │ 并且主动纠正「单线程 = 命令执行单线程」
   ▼
「单线程具体是什么模型，IO 多路复用怎么工作」                     Q06
   │ 验证：Reactor 事件循环 + 文件事件分派器是否讲得出来；
   │ 6.0 多线程 IO 的边界（只 IO、执行仍单线程、默认关闭）
   ▼
「数据在内存里，宕机怎么办——持久化怎么选」                       Q02
   │ 验证：RDB/AOF/fork/混合持久化的代价，能否说出「最多丢 1 秒」
   ▼
「缓存三兄弟：穿透、击穿、雪崩」                                 Q01
   │ 验证：能否按根因选方案，而不是「统一加随机 TTL」的组合拳
   ▼
「缓存和数据库怎么保持一致」                                     Q08
   │ 验证：Cache Aside 的窗口量化、删 vs 更新、异步方案的代价；
   │ 警惕用「Redis 一定比 MySQL 快」当加缓存的理由
   ▼
「并发扣减怎么保证不超——分布式锁」                              Q09/Q10
   │ 验证：SET NX PX 原子性、value 校验、看门狗续期、主从丢锁；
   │ 是否承认锁是优化、幂等才是兜底
   ▼
「量大了怎么办——哨兵和 Cluster」                                Q12
   │ 验证：哨兵管高可用、Cluster 管分片的定位区分；
   │ 16384 槽、MOVED/ASK、gossip、扩缩容迁槽的机制
```

追问链的终点通常是容量与演进的综合题：「现在这套架构有什么问题，下一步怎么演进」——能顺着上面每一跳说出代价的人，才答得好这种题。

## 面试前速记

- 穿透/击穿/雪崩按根因答：数据从未存在 / 单个热点过期 / 大面积失效；解法分别是布隆+空值 / 互斥+逻辑过期 / 随机 TTL+限流。
- RDB 恢复快、AOF 丢数据少，生产双开；混合持久化 4.0 引入、7.0 默认开；AOF 7.0 起是 manifest 多文件。
- 大 key：`--bigkeys`/`--memkeys`/`MEMORY USAGE` 发现，拆分处理，`UNLINK` 异步删（4.0）；大 key 是体积问题，热 key 是频次问题，解法相反。
- 五种结构各有编码：String int/embstr/raw，Hash/Set/ZSet 小对象 listpack、大了 hashtable/skiplist，List 是 quicklist；ZSet 用跳表是因为范围查询友好、实现简单、内存省。
- 快的原因：纯内存 + 命令执行单线程 + epoll + 高效结构；「单线程」指命令执行，6.0 起网络 IO 可多线程且默认关。
- 过期 = 惰性 + 定期抽样，从不过点即删；淘汰 8 种策略，LRU 是采样近似，LFU 4.0 才有；纯缓存用 allkeys 系列。
- 一致性首选 Cache Aside：先更新 DB 再删缓存；删不是更新（幂等 + 免维护顺序）；只能最终一致，窗口要能量化。
- 分布式锁：`SET NX PX` 原子加锁、value 唯一标识、Lua 比对后删、看门狗续期；异步复制下主从切换会丢锁，幂等才是兜底。
- Redisson：Hash 存锁名+线程+重入计数，看门狗 30s/10s，传 leaseTime 就不续；RedLock 有争议、成本高。
- 哨兵管高可用（SDOWN/ODOWN/Raft 选主），Cluster 管分片（16384 槽、CRC16 取模、MOVED/ASK、gossip）。
- 热 key 处理：本地缓存挡一层、读副本、key 复制随机读；`monitor` 只能短时用，`--hotkeys` 结果有偏。
- Lua 保证原子、事务没有回滚；Cluster 下脚本和事务的 key 必须同 slot；排查顺序：slowlog → bigkeys → latency doctor → fork/网络/swap，线上禁 `KEYS`。
