# 集合框架

> 一句话定位：集合框架考的是「HashMap/ConcurrentHashMap 的实现细节」与「按场景选型」——前者验证是否真读过源码（每个「为什么是这个数」都是追问入口），后者验证工程判断力；与 Java基础 的 equals/hashCode 契约、Java多线程 的 JMM 与锁分工，不越界。

## 专题定位

- 这一专题的细节密度全库最高：容量、负载因子、树化阈值、扩容迁移，每个常量背后都有可推导的取舍，答「书上写的」一定被继续追问。
- 面试官主要验证三件事：能否讲出 `put`/`resize` 的完整流程（而不只是结论）、能否说出每个设计「不选另一种方案的代价」、能否按场景给出选型决策。
- 5 年以上工程师要答到：JDK 8 源码级流程 + 并发容器选型 + 「语义先行、实现后选」的决策框架；只背 API 清单会在这个专题迅速暴露。
- 高频开场题几乎总是 HashMap 的阈值类问题（为什么是 8、为什么退化是 6、为什么负载因子 0.75），之后大概率滑向并发容器和 fail-fast。

## 题目正文

### Q01：HashMap 的容量为什么必须是 2 的幂？ `P0` `高频`

**30 秒回答**：因为下标计算用 `hash & (n - 1)` 代替 `hash % n`，这个等价关系只在 n 是 2 的幂时成立；而且扩容时的元素分派也依赖同一个性质。

**深入理解**：位运算比取模快只是表层理由，真正的价值在扩容。容量翻倍后，元素的新下标要么不变、要么变成「原下标 + 旧容量」，判断依据仅仅是 `(e.hash & oldCap) == 0`——**不需要重算哈希、也不需要取模**。若不是 2 的幂，这条规律不成立，扩容就得对每个元素重算。附带效果是 `n - 1` 的低位全为 1，能让哈希的低位充分参与分布，减少冲突。构造时传非 2 的幂（如 17）会被 `tableSizeFor` 向上取整到 32，所以「选一个传奇数容量」没有意义。

**为什么这样设计**：省下取模的 CPU 周期是次要的，「扩容从全量重算变成原地分流」才是关键收益。代价是容量被约束在 2 的幂，于是必须引入 `tableSizeFor` 向上取整，调用方不再完全掌控容量。

**面试官可能继续追问**：
- **`tableSizeFor` 具体怎么把 17 变成 32？** —— 高位补齐算法：把最高位的 1 右边的所有位全部置 1（`c |= c >>> 1/2/4/8/16`），再加 1 后右移一位。结果总是 2 的幂，且不小于入参。
- **构造时指定初始容量 10，实际生效的是多少？** —— 数组延迟到第一次 `put` 才分配，此时按 `tableSizeFor(10)` 取到 16，扩容阈值是 16 × 0.75 = 12。所以 `new HashMap<>(10)` 并不表示「能装 10 个不扩容」，需要按预估 size / 0.75 + 1 反推。
- **这是 Map 接口的要求吗？** —— 不是，只是 HashMap 的实现选择。TreeMap 的底层是红黑树，跟 2 的幂没有任何关系。

**实际工程场景**：已知元素数量时按 `size / 0.75 + 1` 指定初始容量，避免建树过程中反复扩容（每次扩容都是全量数组拷贝，大 Map 会造成延迟毛刺）。读多写少的常量级映射可以直接用 `Map.of(...)` 或 `Collections.unmodifiableMap` 包一层，结构更稳。

**容易答错的地方**：把「位运算快」当成主要原因（真正的收益在扩容分流）；说成「所有 Map 都要求 2 的幂」（只是 HashMap）；把「容量」和「阈值」混为一谈——阈值 = 容量 × 负载因子，不是容量本身。

### Q02：HashMap 的树化阈值为什么是 8？退化阈值为什么是 6？ `P0` `高频`

**30 秒回答**：8 来自泊松分布给出的极小概率（理想哈希下链表长度到 8 的概率约为千万分之六，正常使用几乎不会树化），6 则留出一个值的缓冲，避免在 8 附近反复增删导致链表与红黑树来回转换。

**深入理解**：树化的完整条件是「链表长度 ≥ 8 **且** 数组容量 ≥ 64」，容量不足时优先扩容——因为容量小造成的冲突，扩容比树化更划算。树化后节点变成 `TreeNode`，但仍保留 `next` 指针，所以树上同时维持一条链表，退化时可以按链表顺序还原。红黑树把最坏查询从 O(n) 降到 O(log n)，代价是节点对象更大、维护成本更高，因此只在分布确实很差或被恶意构造哈希时才值得。

**为什么这样设计**：两个阈值不能取在同一个值上。若树化和退化都用 8，长度在 8 附近抖动时两种结构会反复转换，而每次转换都要重建指针关系。留一个空档吸收抖动，是用一点确定性成本换掉不确定性成本。

**面试官可能继续追问**：
- **为什么还要「容量 ≥ 64」这个条件？** —— 源码里是 `MIN_TREEIFY_CAPACITY = 64`：链表长往往是因为容量太小、冲突集中，此时扩容（同样是把桶摊薄）比树化更彻底、代价更小。容量够大还冲突才是分布问题，才值得树化。
- **千万分之六是怎么来的？** —— 在「哈希值接近随机、负载因子 0.5」的假设下，桶内长度近似服从 λ=0.5 的泊松分布，长度恰好为 8 的概率约为 6×10⁻⁷。这是统计假设下的经验值，不是证明出来的最优解。
- **树化后的 TreeNode 为什么还留着 next 指针？** —— 红黑树操作（旋转、拆分）需要按链表顺序处理节点，`next` 保留了遍历链，扩容拆分和退化还原（`untreeify`）都依赖它。

**实际工程场景**：树化的现实意义是防御「哈希洪水」——攻击者构造大量碰撞 key 把查询打成 O(n)。自建缓存如果 key 不可控（如用户输入做 key），要评估这一层。日常业务 key 分布正常时，看到树化反而应该先怀疑哈希函数或 key 设计。

**容易答错的地方**：只答「8 是经验值」不展开泊松分布；以为树化之后链表就消失了；把退化阈值记成 7（是 6，且条件是「删除时长度 ≤ 6」才对整棵树做 untreeify）；忽略「容量 ≥ 64」这个并列条件。

### Q03：HashMap 的负载因子为什么默认是 0.75？ `P0` `高频`

**30 秒回答**：0.75 是冲突概率与空间利用率之间的经验折中点——它让链表长度的期望值足够小，同时不浪费太多桶。

**深入理解**：太小（如 0.5）冲突少但元素没填多少就要扩容，空间浪费且扩容频繁；太大（如 1.0）省了空间但冲突显著上升，链表变长、查询变慢。0.75 最有价值的推论是**扩容时机可预测**——`size > capacity × 0.75` 就翻倍，所以已知元素数量时应按 `size / 0.75 + 1` 反推初始容量并指定，避免反复扩容。注意这只是默认值：明确知道冲突会很少时调大它能省内存，但调小它几乎总是错的。

**为什么这样设计**：它不是在算法上推导出来的最优解，而是在「哈希分布接近随机」假设下的统计经验取值，Java 团队把它写进注释作为默认意图。因此被追问时正确的答法是讲清两侧代价，而不是把 0.75 当成定律背下来。

**面试官可能继续追问**：
- **为什么说调小负载因子「几乎总是错的」？** —— 调小会让扩容更早、更频繁，每次都付出全量数组拷贝的代价，换来的是本来就已经很低的冲突率进一步下降。只有当冲突已经低到可以忽略、而内存是硬约束时，调大才有意义；反向操作没有对应收益。
- **负载因子和 2 的幂容量共同决定什么？** —— 阈值 `threshold = capacity × loadFactor`，容量是 2 的幂、0.75 = 3/4，所以阈值总是「2 的幂的 3/4」这类整数，不会出现小数截取问题。
- **什么 key 适合调大负载因子？** —— key 是枚举、短字符串等分布天然均匀、数量可估的场景。前提是你能量化验证冲突率，而不是凭感觉调参。

**实际工程场景**：批量灌数据（缓存预热、字典加载）时按目标 size 反推初始容量，是收益最确定的一处优化；在线服务里调负载因子属于危险操作，改默认值前应有压测数据支撑。

**容易答错的地方**：把 0.75 当定律；说「调小能减少冲突所以更好」（无视扩容代价）；混淆阈值与容量；以为负载因子是 API 契约（它是实现细节，别的 Map 实现没有这个参数）。

### Q04：HashMap 扩容时元素是怎么迁移的？ `P0` `高频`

**30 秒回答**：容量翻倍后，桶内元素按 `(e.hash & oldCap)` 是否为零分成低位链和高位链——低位链留在原下标，高位链整体挪到「原下标 + 旧容量」，全程不重算哈希。

**深入理解**：这条规律成立的前提就是容量为 2 的幂。实现上把两条链分别挂在 `loHead/loTail` 与 `hiHead/hiTail` 上，最后一次性放入 `newTab[j]` 和 `newTab[j + oldCap]`，且保持原相对顺序（JDK 8 用尾插，顺序不反转）。JDK 7 用头插，并发扩容可能形成环形链表导致 `get` 死循环；JDK 8 改尾插避免了成环，但**并发写仍会丢数据**，所以并发场景必须换 `ConcurrentHashMap`。

**为什么这样设计**：一次位测试决定去留，把每元素的扩容成本从「重算哈希 + 取模」降到「比较 + 挂链」，这是 2 的幂约束换来的最大红利。JDK 7 的头插是反例——它在单线程下省了少量指针操作，却在并发下产生环，说明这点收益抵不上风险。

**面试官可能继续追问**：
- **扩容是后台线程做的吗？** —— 不是。HashMap 的 `resize` 由触发它的那个 `put` 线程同步完成，没有异步迁移；这也是大 Map 单次 put 出现延迟毛刺的原因。多线程协助迁移是 ConcurrentHashMap 的设计（`ForwardingNode`），两者不要混。
- **扩容会改变 size 吗？** —— 不会，resize 只换数组、重新分派节点，`size` 原样带到新表。
- **扩容期间其他桶还能访问吗？** —— 单线程语义下不存在这个问题；并发场景下旧的 `table` 引用随时可能被替换，另一个线程正往旧表写就是丢数据的一种成因。

**实际工程场景**：预估容量（见 Q03）本质就是减少扩容次数；对延迟敏感的热路径，要意识到一次 put 可能触发 O(n) 迁移，必要时用 ConcurrentHashMap 把迁移摊到多线程，或提前预热。

**容易答错的地方**：以为扩容会重算每个 key 的 hash（不需要，一次位测试即可）；以为 JDK 8 尾插之后并发扩容就安全了（只是不成环，丢数据与计数不准依旧）；以为迁移过程中集合不可访问（没有锁，但状态不一致才是危险所在）。

### Q05：HashMap 为什么线程不安全？ `P0` `高频`

**30 秒回答**：桶定位与链表写入、`size` 自增、`table` 替换三处都没有同步，结果是丢数据和 `size` 不准，JDK 7 还额外有扩容成环导致死循环。

**深入理解**：两个线程同时对同一个空桶 `put`，可能都判断为空、都写入，后写覆盖先写。`++size` 不是原子操作，并发下计数偏小，可能导致该扩容时没扩容、链表持续变长。JDK 7 头插扩容在并发下会成环，`get` 时无限循环、CPU 打满；JDK 8 尾插不再成环，但丢数据与计数不准依旧存在。这类问题的典型现象是「偶发数据丢失、重启后复现不了」。替代：并发读写用 `ConcurrentHashMap`；单线程构造、之后只读的 `HashMap`，通过安全发布（`final` 字段或静态初始化）也是安全的。

**为什么这样设计**：`HashMap` 的定位就是**单线程下的极致轻量**，加同步会把所有单线程使用者一起拖慢。JDK 另给 `Hashtable`（全表一把锁）与 `ConcurrentHashMap`（桶级锁）两条路，把选择权交给调用方——代价是调用方必须自己清楚当前是否并发。

**面试官可能继续追问**：
- **并发 put 一定抛异常吗？** —— 不一定。多数症状是静默的数据丢失、覆盖和 size 偏小；遍历时可能撞上 fail-fast 抛 `ConcurrentModificationException`，但那是尽力检测，不抛也不代表没有并发问题。
- **`Collections.synchronizedMap` 为什么不是好选择？** —— 它给每个方法套同一把锁，粒度是全表，任何读写都互斥；读多写少时吞吐远低于 ConcurrentHashMap，而且迭代仍需手工加锁。
- **什么用法是安全的？** —— 构造完成后不再修改、并安全发布（`final` 字段、静态初始化器、`volatile` 发布）的只读 HashMap。注意「不再修改」是承诺，不是机制保证的。

**实际工程场景**：Spring 容器里的单例 Bean 如果持有 Map，先确认是只读缓存还是共享可变状态；前者初始化后禁止写入，后者直接用 `ConcurrentHashMap`。微启动灌配置这种「构造完只读」的用法，安全发布即可，不必付并发容器成本。

**容易答错的地方**：把「没抛异常」当作「没有并发问题」；说 JDK 8 之后线程安全了（丢数据问题一直在）；以为加了 `volatile` 就安全（可见性解决不了「检查-写入」竞态）。

### Q06：ConcurrentHashMap 是怎么保证线程安全的？ `P0` `高频`

**30 秒回答**：JDK 8 起放弃分段锁，改成「空桶用 CAS 写入、非空桶用 `synchronized` 锁桶头」，锁粒度是单个桶；扩容做成多线程协作；`size` 由 `baseCount` 加各 `CounterCell` 累加，并发下不是精确的瞬时值。

**深入理解**：`put` 时桶为空就 `casTabAt` 写入（无锁），非空则锁住头节点再插入或更新，其他桶读写不受影响。扩容用 `ForwardingNode` 标记已迁移的桶，其他线程遇到标记会放下手上的 `put` 过来帮忙迁移，把一次扩容的耗时摊到多个线程。`get` 全程无锁，依赖 `volatile` 读与节点字段的 `final` 语义。不允许 `null` 键值——并发下 `get` 返回 `null` 无法区分「不存在」与「值就是 null」。

**为什么这样设计**：分段锁的段数是固定的，热点段照样争用；改成桶级锁让并发度随容量增长，同时保住了 `get` 无锁。代价是扩容期间要多线程协作（复杂度明显上升），并且 `size` 不再是精确值——所以它额外提供了 `mappingCount` 这类更合适的接口。

**面试官可能继续追问**：
- **`get` 无锁为什么还能读到正确值？** —— 写入路径上 `table` 数组是 `volatile` 引用，节点关键字段（`val`、`next`）在发布前靠 `final` 语义保证可见；读方看到节点就一定看到完整初始化的字段。这是「写侧保证发布、读侧直接读」的分工。
- **为什么 size 不精确还要提供？** —— 并发下任何时刻都有写在进行，精确瞬时值既拿不到也没意义。需要监控时用 `mappingCount`，需要精确计数的业务（如「达到 N 就 flush」）应该用原子计数器另记。
- **computeIfAbsent 有什么使用限制？** —— 官方文档明确警告：映射函数里不要修改同一个 Map。同一 bin 内递归更新可能死锁或造成内存问题，且函数应尽量快、无副作用。

**实际工程场景**：本地缓存首选 `ConcurrentHashMap`；热点计数器可以用它的 `merge`/`compute` 做分段之外的细粒度操作，但高频更新仍建议 `LongAdder`。`size()` 只用于监控和日志，不要进业务判断。

**容易答错的地方**：以为 `get` 有锁（无锁是它相对 `Hashtable` 的核心优势）；以为 `size()` 精确（是近似值）；把 JDK 7 分段锁的答案套到 JDK 8（实现已换）；忘记 null 键值限制。

### Q07：ArrayList 扩容为什么是 1.5 倍？ `P1` `中频`

**30 秒回答**：`newCapacity = oldCapacity + (oldCapacity >> 1)`，1.5 倍是「均摊追加成本」与「内存复用率」之间的折中——理论上任何大于 1 的因子都能给出均摊 O(1)。

**深入理解**：扩容调用 `Arrays.copyOf` 复制到新数组，单次是 O(n)，但均摊到每个元素仍是 O(1)。1.5 倍相对 2 倍的优势在内存分配上：2 倍增长时旧数组腾出的空间永远装不下一次扩容所需的新数组（1 + 2 = 3 < 4），必须重新申请连续内存；1.5 倍时旧数组加其前面的碎片有机会被复用（1 + 2 = 3 ≥ 3）。初始容量为 10；`new ArrayList<>()` 实际延迟到第一次 `add` 才分配数组。

**为什么这样设计**：既然任何大于 1 的因子都能保证均摊 O(1)，「1.5」就不是算法推导的结果，而是对内存分配器现实约束（能否复用相邻的已释放空间）更友好。这是工程取值，不是理论最优。

**面试官可能继续追问**：
- **拷贝具体用什么实现？** —— `Arrays.copyOf` 最终走 `System.arraycopy`，是 native 方法，按内存块整体搬移，比逐元素循环快得多。
- **怎么从根上避免扩容？** —— 已知规模时 `new ArrayList<>(size)`；`List.of(...)` 或预先灌满的数组可彻底消除扩容路径。
- **扩容因子是不是接口契约？** —— 不是，JDK 实现细节（`grow` 方法里），换 JDK 或换 List 实现不保证一致。

**实际工程场景**：批处理、报表导出这类「已知行数」的场景预分配容量，收益明确；未知规模的流式写入保持默认即可，为省一点内存把初始容量猜小反而导致多次扩容。

**容易答错的地方**：说「因为 1.5 在算法上最优」（均摊 O(1) 与因子大小无关，选 1.5 是内存分配现实）；以为 `new ArrayList<>()` 立即分配了 10 个元素空间（延迟到首次 add）；以为初始容量 10 是接口承诺。

### Q08：LinkedHashMap 是怎么实现 LRU 的？ `P0` `高频`

**30 秒回答**：它在哈希节点上追加 `before/after` 双向链，把 `accessOrder` 设为 `true` 后每次访问都会把节点移到链表尾部，于是链表头就是「最久未使用」，重写 `removeEldestEntry` 返回 `true` 即自动淘汰表头。

**深入理解**：三个要素缺一不可——用 `new LinkedHashMap<>(capacity, loadFactor, true)` 开启访问顺序；重写 `removeEldestEntry` 并在 `size > capacity` 时返回 `true`；自己包一层 `synchronized` 或改用 `ConcurrentHashMap` 保证线程安全（`LinkedHashMap` 本身同样不安全）。`accessOrder = true` 时，`put` 已存在的 key 也会把它移到尾部，视为一次访问。相比手写「双向链表 + HashMap」，它把淘汰逻辑和哈希结构放在同一份代码里，不会出现两处状态不同步；劣势是淘汰策略只能是「最久未使用」。

**为什么这样设计**：`HashMap` 已经解决了 O(1) 定位，`LinkedHashMap` 只补一条有序链，用最小改动把无序哈希变成有序——这正是「继承 + 少量钩子方法」的用法（`afterNodeAccess`、`afterNodeInsertion` 都是留给子类覆写的空实现）。代价是每个节点多两个引用，内存占用高于 `HashMap`。

**面试官可能继续追问**：
- **`accessOrder = true` 时，`put` 一个已存在的 key 会怎样？** —— 会被当作一次访问，`afterNodeAccess` 把节点移到尾部；如果它原本是「最久未使用」的表头，一次 put 就能把它救活。
- **迭代顺序受 accessOrder 影响吗？** —— 受。遍历按双向链表的当前顺序，accessOrder 模式下迭代顺序等于「从旧到新的访问顺序」，同一组数据两次遍历结果可能不同。
- **它线程安全吗？** —— 不安全，而且 `accessOrder = true` 时 `get` 也是结构性修改，并发迭代比普通 Map 更危险，必须外层同步。

**实际工程场景**：适合做教学级/小体量的本地 LRU（工具类缓存、有界字典）。生产本地缓存直接用 Caffeine——`LinkedHashMap` 没有过期时间、没有并发淘汰、没有统计，硬扛这些会重复造轮子且容易出错。

**容易答错的地方**：开了 `accessOrder` 却忘了重写 `removeEldestEntry`（只排序不淘汰）；以为它是线程安全的；以为 `accessOrder` 和插入顺序可以同时生效（两种模式二选一，`insertion-order` 是默认）。

### Q09：HashMap 的 put 完整流程是怎样的？ `P0` `高频`

**30 秒回答**：先对 key 算扰动后的 hash，再用 `(n - 1) & hash` 定位桶；桶为空直接写入新节点；桶非空则按红黑树或链表查找，key 相等就替换 value 返回旧值，否则插入新节点；插入后判断是否触发树化；最后 `size++`，超过阈值就扩容。Q01～Q04 回答「为什么是这个数」，这一题回答「完整流程长什么样」。

**深入理解**：以 JDK 8 `putVal` 为主线分六步：

```text
put(key, value)
  ① hash(key)：h = key.hashCode(); h ^ (h >>> 16)
     —— 扰动函数：把高 16 位的影响折进低 16 位
  ② 定位：i = (n - 1) & hash
     —— 只有低位参与，这正是 ① 存在的原因
  ③ 桶空：tab[i] = new Node<>(hash, key, value, null)
  ④ 桶非空：
     - 头节点是 TreeNode      → putTreeVal，红黑树查找/插入
     - 否则遍历链表：key 相等（hash 相同 && equals）→ e.value = value，返回旧值
       走到尾部仍没有        → 尾插新节点（JDK 8；JDK 7 是头插）
  ⑤ 树化判断：链表长度 ≥ 8 且数组容量 ≥ 64 → treeifyBin
     容量不足 64 时只扩容不树化
  ⑥ ++size > threshold → resize()（迁移逻辑见 Q04）
```

要点：替换和插入是两条路径，`put` 返回的是旧 value；判等是「hash 相等 **且** `==` 或 `equals`」两段式，哈希相同不等于对象相等；JDK 8 全程尾插，这也是 Q04 中「扩容不成环」的前提。

**为什么这样设计**：扰动函数（①）是因为 `(n - 1) & hash` 只取低位，若不把高位折下来，所有低位相同、高位不同的 key 会全部撞进同一个桶。两段式查找（hash 定位 + equals 判等）是用平均 O(1) 的代价换最坏 O(桶内长度)，再靠树化把最坏压到 O(log n)——每一层都是对上一层的兜底，而不是一步到位。

**面试官可能继续追问**：
- **`put` 一个已存在的 key，返回值是什么？** —— 旧 value；借此可以区分「插入」和「更新」，`putIfAbsent` 就是在这个返回值上做的并发版本。
- **扰动函数为什么只异或一次？** —— 经验设计。JDK 7 做多次异或加移位，JDK 8 简化为一次 `h ^ (h >>> 16)`：实测在常见 key 分布下已足够把高位折进低位，更复杂的扰动收益递减。
- **链表长度到 8 是数到 8 才树化吗？** —— 遍历时从 0 计数，走到 `TREEIFY_THRESHOLD - 1`（即 7）的位置时对下一个插入调用 `treeifyBin`；再叠加容量 ≥ 64 的判断。
- **树化之后查找还走 equals 吗？** —— 走，但用的是 `compareTo` 式的树内比较定位（`TreeNode` 按 key 的比较结果导航），前提是 key 可比较；不可比较时退化为链表遍历加 equals。

**实际工程场景**：面试里先用这道题立框架——把 hash 扰动、下标、桶内查找、树化、size 与扩容讲全，再让面试官挑任意一段深挖，比被零散提问更主动。工程上要注意：批量 put 大 Map 时的扩容毛刺来自第 ⑥ 步，预热容量是对策。

**容易答错的地方**：只说「hashCode 定位桶」，漏掉扰动函数和 `(n - 1) & hash`；说链表用头插（那是 JDK 7）；说「key 相同就比较 hashCode」——必须再加 equals，只比 hashCode 会把冲突 key 误判为相等；漏掉「替换返回旧值、插入返回 null」的路径差异。

### Q10：fail-fast 和 fail-safe 是什么？ `P1` `中频`

**30 秒回答**：fail-fast 是集合在迭代期间发现「结构性修改」就尽快抛 `ConcurrentModificationException` 的尽力而为机制，靠 `modCount` 与迭代器里的 `expectedModCount` 比对实现；fail-safe（如 `CopyOnWriteArrayList`）迭代的是写入时复制的快照，不抛异常，但可能读到旧数据。

**深入理解**：`add`/`remove` 等结构性修改会让 `modCount` 自增；迭代器创建时记下 `expectedModCount = modCount`，每次 `next()`/`remove()` 前做 `checkForComodification()`，两者不等就抛 CME。单线程遍历时删除的正确姿势是 `iterator.remove()`——它在删除的同时把 `expectedModCount` 同步回去；直接 `list.remove(i)` 或 for-each 里删都会触发 CME。`CopyOnWriteArrayList` 反过来：写操作加锁后整体复制底层数组再改，迭代器持有创建时那一版数组的快照（COWIterator，没有 `modCount` 概念，也不支持 `remove`/`set`）。它的遍历永远不抛 CME，但期间其他线程的写入不可见——这叫弱一致性。`ConcurrentHashMap` 同理是弱一致性迭代。

**为什么这样设计**：fail-fast 选择「尽早暴露 bug」而不是「花代价保证并发正确」——它的定位是帮你发现「遍历时被改」这个程序错误，检测本身不解决任何并发问题。COW 选择把成本从读路径挪到写路径：读完全无锁、无同步，写付出「整表复制」的代价，所以只在读远多于写时划算。

**面试官可能继续追问**：
- **CME 能保证发现所有并发修改吗？** —— 不能，是 best-effort。迭代器只在下一次 `next()` 时才检查，中间窗口的修改既看不到也不保证抛异常；不能把「没抛 CME」当作线程安全的证据。
- **`CopyOnWriteArrayList` 的 `add` 是线程安全的吗？** —— 是，但方式是「加锁 + 复制整个底层数组 + 替换引用」。代价是写放大：一次 add 的内存和时间成本随元素数增长，只适合读多写少（监听器列表、白名单、配置快照）。
- **`ConcurrentHashMap` 和 COW 的迭代有什么区别？** —— 都是弱一致性，但 CHM 不复制数组，迭代反映的是「某个时间点之后持续的近似状态」，且支持迭代器内的弱一致性 `remove`；COW 迭代器完全只读、严格对应创建瞬间的快照。

**实际工程场景**：单线程遍历删除统一用 `iterator.remove()` 或 `removeIf`；跨线程共享的读多写少集合用 `CopyOnWriteArraySet/List`；读写都频繁回到 `ConcurrentHashMap`。事件监听器广播是 COW 最典型的场景：注册/注销少、遍历极频繁。

**容易答错的地方**：把 fail-fast 当成线程安全机制（它是错误检测，两者目的相反）；以为 COW 迭代器能读到最新数据（那是快照语义）；以为 COW 写入不加锁（加锁，复制的是底层数组）；以为 CHM 遍历抛 CME（不抛，弱一致）。

> 权威内容：[集合框架体系与核心契约](../../02-集合框架/02-深度解析/集合框架体系与核心契约.md)；CopyOnWriteArrayList 的弱一致性语义当前尚未在仓库建设，可参考 JDK 官方 `java.util.concurrent` 包文档与《Java 并发编程实战》。

### Q11：集合应该怎么选型？ `P1` `中频`

**30 秒回答**：先问语义再选实现：是否允许重复、要不要顺序、要不要排序、主要操作是什么、是否跨线程、能不能存 null——语义定了，实现基本就定了。默认答案是 List 用 ArrayList、Map 用 HashMap、并发 Map 用 ConcurrentHashMap；LinkedList 几乎总是不如 ArrayList。

**深入理解**：按场景给一张选型表：

| 语义 | 首选 | 什么时候换 | 关键理由 |
| --- | --- | --- | --- |
| Map 默认 | `HashMap` | 要插入/访问顺序 → `LinkedHashMap`；要 key 排序与区间查询 → `TreeMap`；并发 → `ConcurrentHashMap` | O(1) 平均查询；后三者各自用「一条链」「一棵树」「桶级锁」换能力 |
| Set 默认 | `HashSet` | 要顺序 → `LinkedHashSet`；要排序 → `TreeSet`；读多写少 → `CopyOnWriteArraySet` | HashSet 就是 value 占位的 HashMap，契约完全复用 |
| List 默认 | `ArrayList` | 只在一端/两端进出 → `ArrayDeque`；读多写少的共享列表 → `CopyOnWriteArrayList` | 连续数组、索引 O(1)、节点开销为零 |
| Queue | `ArrayDeque` | 要按优先级出队 → `PriorityQueue`；生产者消费者 → `BlockingQueue` 家族 | 数组双端队列替代遗留的 `Stack`；线程池的工作队列就是 `BlockingQueue` |

LinkedList 为什么几乎总是不如 ArrayList：它的每个元素是一个独立节点对象（额外 2 个引用 + 对象头，局部性差）；「增删快」的前提是已经拿到节点，而 `List` 接口按索引定位，找到第 i 个本身就是 O(n)；中间插入省下的数组搬移，往往抵不过定位节点的成本。真正需要 Deque 语义时 `ArrayDeque`（循环数组 + 双指针）通常更直接，只有在高频拿到 `Iterator` 位置后插删的场景，LinkedList 才有优势。

**为什么这样设计**：选型方法论本身来自集合框架的分层——接口（`List`/`Set`/`Map`）只承诺契约，复杂度、顺序、并发、null 支持全是实现属性。所以正确顺序是「先确定语义，再核对实现的复杂度与边界」，反过来从 API 清单开始背必然选错。

**面试官可能继续追问**：
- **为什么 `Map` 不属于 `Collection`？** —— Map 表达 key-value 映射，不是单一元素序列；但它提供 `keySet`/`values`/`entrySet` 三个视图，用的时候仍然按集合遍历。
- **`PriorityQueue` 并发场景用什么？** —— `PriorityBlockingQueue`（无界，天然不会满）或 `DelayQueue`（延迟任务）；注意有界优先队列要自己另选型。
- **Java 21 之后有什么变化？** —— Sequenced Collections（`SequencedCollection`/`SequencedMap`）统一了 `getFirst`/`getLast`/`reversed` 这类双端操作，`List`/`Deque`/`SortedSet` 家族都收编了，新代码可以少记一套双端 API。

**实际工程场景**：接口参数/返回值优先面向接口声明（入参 `List`、返回 `Map`），把实现选择留在方法内部；性能敏感路径核对复杂度表再定实现。遗留类（`Vector`、`Hashtable`、`Stack`）在新代码里不应出现——它们的同步是全表锁，且破坏了接口设计。

**容易答错的地方**：新代码用 `Vector`/`Hashtable`/`Stack`；用 LinkedList 做随机访问（复杂度退化为 O(n)）；选 `TreeMap` 却放了不可比较或可变的 key；默认集合直接跨线程共享（忘了并发一列）。

### Q12：TreeMap 和 TreeSet 是怎么实现的？ `P1` `中频`

**30 秒回答**：底层都是红黑树（自平衡二叉搜索树），key 全程有序，增删查都是 O(log n)；排序要么靠 key 的自然顺序（`Comparable`），要么构造时传 `Comparator`；关键约束是 `compareTo` 与 `equals` 的口径必须一致，否则同一个容器里会出现两套「相等」标准。

**深入理解**：红黑树靠五条性质维持平衡：节点非红即黑、根是黑、红节点的两个子节点必须是黑（红不相邻）、从任一节点到其所有后代叶子的路径黑节点数相同（黑高一致）、新插入的节点默认是红。黑高一致保证最长路径不超过最短路径的两倍，因此树高是 O(log n)，查找、插入、删除都是 O(log n)（删除的旋转调整比插入多，常数更大）。与 HashMap 的根本区别：TreeMap 定位节点靠 key 之间的比较导航，**不用 `hashCode`/`equals`**。`TreeSet` 内部就是一个 value 恒为同一个占位对象的 `TreeMap`，和 `HashSet` 复用 `HashMap` 是同一手法。排序 Map 的典型场景是区间查询（`subMap`/`headMap`/`tailMap` 返回视图）和动态排行榜（如实时 TopK）。

**为什么这样设计**：「有序 + 区间操作」是哈希结构给不了的能力，而排序数组的插入是 O(n)。平衡 BST 是这两者之间的折中：插入删除保持 O(log n)、顺序遍历与区间查询天然高效。无锁并发场景另有 `ConcurrentSkipListMap`（跳表）——区间操作同样高效、实现更简单、并发友好，是并发有序 Map 的标准答案。

**面试官可能继续追问**：
- **`compareTo` 和 `equals` 不一致会出什么问题？** —— 经典反例是 `BigDecimal`：`new BigDecimal("1.0")` 与 `new BigDecimal("1.00")` 的 `equals` 是 false，但 `compareTo` 返回 0。放进 `TreeSet` 会被判为重复只留一个，放进 `HashSet` 则是两个——同一份数据在两个容器里去重结果不同，是隐蔽的 bug 源。
- **key 可以是 null 吗？** —— 自然排序下不行（`compareTo` 直接 NPE）；自定义 `Comparator` 显式处理了 null 就可以。
- **`subMap` 返回的是副本吗？** —— 是视图。对原 Map 的修改会反映到子 Map，反向也支持部分写操作；迭代原 Map 时结构性修改同样会触发 fail-fast。
- **为什么并发不用 TreeMap 加锁？** —— 一把全局锁会让所有操作串行；有序 + 并发的需求直接用 `ConcurrentSkipListMap`，它是无锁读、CAS 辅助写。

**实际工程场景**：动态排行榜（分数 → 用户，取前 N 用 `pollFirstEntry`）、区间检索（价格区间、时间范围）、范围派发任务。注意可变 key 的坑：放入后修改参与比较的字段，树结构会被破坏且查询现象比 HashMap 更难看懂（不是找不到，而是找到错的位置）。

**容易答错的地方**：说 TreeMap 用 `hashCode`/`equals` 定位（是 `compareTo`）；忽略 `compareTo`/`equals` 一致性要求（`BigDecimal` 是标准案例）；以为 `TreeMap`/`TreeSet` 线程安全；以为子 Map 是独立副本。

> 权威内容：TreeMap 与 TreeSet 当前尚未在仓库建设，可参考 JDK 官方文档 `SortedMap` / `NavigableMap` 接口说明与《算法（第 4 版）》红黑树章节。

## 面试前速记

- 2 的幂是为了 `(n-1) & hash` 与「扩容按 `(e.hash & oldCap)` 原地分流」，位运算快只是表层理由。
- 树化条件是「链表 ≥ 8 **且** 容量 ≥ 64」；退化是 6，与 8 之间留缓冲防止抖动；8 来自泊松分布的极小概率。
- 负载因子 0.75 是经验折中：可预测扩容时机（size / 0.75 + 1 反推初始容量），调小几乎总是错的。
- put 六步：扰动 hash → `(n-1) & hash` 定位 → 桶空写入 → 桶非空查找（相等则替换）→ 树化判断 → size++ 与扩容。
- 判等是「hash 相等 **且** equals」两段式；哈希相同不等于对象相等。
- HashMap 三处无同步：桶写入、`++size`、`table` 替换；JDK 7 头插会成环，JDK 8 尾插不成环但照样丢数据。
- ConcurrentHashMap：空桶 CAS、非空桶 `synchronized` 锁头、`get` 无锁、`size` 近似、禁 null；JDK 7 分段锁已废弃。
- ArrayList 扩容 1.5 倍（`old + old >> 1`），选 1.5 是为了让旧数组加相邻碎片可能被复用，不是算法最优。
- LinkedHashMap LRU 三要素：`accessOrder=true`、重写 `removeEldestEntry`、外层同步；生产缓存用 Caffeine。
- fail-fast 靠 `modCount`/`expectedModCount` 比对，是错误检测不是并发安全；COW 迭代快照、弱一致、读多写少才划算。
- 选型顺序：语义（重复/顺序/排序/并发/null）→ 实现；默认 ArrayList + HashMap + ConcurrentHashMap；LinkedList 几乎总是不如 ArrayList。
- TreeMap/TreeSet 是红黑树，靠 `compareTo` 导航不用 hashCode；`compareTo` 与 `equals` 必须一致（`BigDecimal` 是反例）；并发有序用 `ConcurrentSkipListMap`。
