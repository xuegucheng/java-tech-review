## 专题定位

- 操作系统题不要求极深，但要能准确说清基本机制——含糊的答案（「epoll 就是快」「零拷贝就是不拷贝」）在这个专题最容易露底。
- 面试官主要验证：每个结论背后有没有机制支撑（为什么线程切换比进程便宜、为什么 mmap 能少一次拷贝）、能不能把 OS 概念和线上故障对上（Page Cache 与 fsync、磁盘随机 IO 与数据库慢查询）。
- 5 年以上工程师要答到：机制层 + 取舍层——知道每个方案适合什么场景、代价是什么，而不是只会背定义和算法名字。
- 高频出口是「IO 模型」和「零拷贝」：前者连着 Java NIO/Netty，后者连着 Kafka、RocketMQ 的传输设计，都要求能讲到工程选型。

## 题目正文

### Q01：select / poll / epoll 的区别是什么？ `P0` `高频`

**30 秒回答**：三者都是 I/O 多路复用，select 和 poll 每次调用都要把整个 fd 集合从用户态拷进内核并线性扫描，epoll 把 fd 登记在内核的事件结构里，只返回就绪的那部分。

**深入理解**：select 用位图表示 fd 集合，受 FD_SETSIZE 限制（通常 1024），fd 的取值范围也受限；poll 改用 pollfd 数组，没有数量上限，但仍然是 O(n) 遍历且每次都要整体拷贝。epoll 由三个系统调用组成：epoll_create 创建内部结构（一棵红黑树加一个就绪链表），epoll_ctl 负责增删改，epoll_wait 只从就绪链表取事件。触发模式有两种：LT 是默认模式，只要缓冲区还有数据就持续通知；ET 只在状态变化时通知一次，必须一次读到 EAGAIN，因此要配非阻塞 fd，好处是减少了通知次数，坏处是漏读会直接丢事件。需要说明的是，epoll 的优势只在连接数大、同时活跃比例低时才明显，连接少且都很活跃时，事件回调和额外数据结构带来的开销可能反而比 poll 更差。

**为什么这样设计**：用红黑树加就绪链表代替无差别轮询，是把「找出就绪 fd」的代价从 O(总连接数) 降到 O(活跃连接数)，代价是每次增删监听要付一次 epoll_ctl 的开销，以及额外的内核内存；所以它适合海量长连接，不适合连接频繁增删的小规模场景。

**面试官可能继续追问**：
- **LT 和 ET 分别适合什么场景？** —— LT 编程简单、不容易漏事件，适合连接数不多的常规服务；ET 单次通知成本低但必须非阻塞 fd 配「读到 EAGAIN」的循环，适合海量连接的单线程 Reactor（Nginx、Redis）。选 ET 却用阻塞 IO 是经典错误组合。
- **epoll_ctl 每次调用也有开销，频繁增删会怎样？** —— 增删走红黑树插入/删除（O(log n)）且涉及内核锁，秒级建销大量短连接的场景（如每请求一条连接的代理）epoll 的注册成本会被放大，这正是「epoll 不是万能」的边界。
- **Java 层怎么用上 epoll？** —— NIO 的 `Selector` 在不同系统用不同实现：Linux 是 `EPollSelectorImpl`，macOS 是 `KQueueSelectorImpl`；Netty 的 `EpollEventLoop` 还提供 `EPOLLEXCLUSIVE` 等原生特性。用 NIO 不等于自动获得 epoll 的全部收益，模型写错（如每连接一线程）照样退化。

**实际工程场景**：C10M 类高并发服务（网关、推送、IM）选 epoll + ET + 单/少线程 Reactor；内部小工具、连接数固定的客户端用 select/poll 甚至阻塞 IO 都更简单。判断依据是「连接数 × 活跃比例」，不是「听说 epoll 快」。

**容易答错的地方**：只说 epoll 快、不说适用边界（连接少且活跃时可能更差）；说 epoll 返回所有 fd 的状态（只返回就绪链表）；混淆 LT/ET 与阻塞/非阻塞（ET 必须配非阻塞，是两回事）；以为用了 Java NIO 就一定在用 epoll（取决于平台与实现）。

> 权威内容：I/O 多路复用的内核实现当前尚未在仓库建设，可参考 Linux man-pages 的 select(2)、poll(2)、epoll(7) 与《UNIX 网络编程 卷 1》。

### Q02：进程和线程的区别？为什么线程切换开销更小？ `P0` `高频`

**30 秒回答**：进程是资源分配与隔离的单位，线程是 CPU 调度的单位；同进程内的线程共享地址空间和文件描述符，切换时不必换页表、不会导致 TLB 大范围失效，所以更快。

**深入理解**：每个进程拥有独立的虚拟地址空间、页表和文件描述符表；同一进程内的线程共享这些资源，但各自持有栈、寄存器上下文、程序计数器和线程局部存储。切换成本的差异主要来自地址空间：进程切换要更换 CR3 指向的页表，原来缓存的地址映射全部失效，之后访问内存需要重新走多级页表填充 TLB；线程切换停留在同一地址空间内，TLB 中大部分映射依然有效。另一处差异是通信方式：跨进程要借助管道、共享内存、socket 等内核机制并发生数据拷贝，线程之间直接读写同一块内存即可，代价是必须自己做同步，否则出现竞态。Linux 内核并不区分二者，线程是用 clone 带上 CLONE_VM 等标志实现的共享地址空间的轻量级进程。

**为什么这样设计**：把「资源隔离」和「执行调度」拆成两层，是为了让需要隔离的任务付隔离成本、需要共享数据的任务不付隔离成本；若只保留进程，高频协作就必须反复陷入内核做拷贝；若只保留线程，则一处崩溃会带走整个地址空间。

**面试官可能继续追问**：
- **线程切换具体要保存恢复什么？** —— 用户栈与内核栈、寄存器组（含栈指针、程序计数器）、线程状态、调度相关信息。这些是固定的结构拷贝，真正的变量成本来自 TLB/缓存失效的间接影响。
- **Java 线程和 OS 线程什么关系？** —— 取决于版本与实现：经典 HotSpot 是 1:1（每个 Java 线程一个 OS 线程，Thread 的 start 走 pthread_create）；Java 21 的虚拟线程仍是 1:1 挂载，但由 JVM 调度器把大量虚拟线程复用到少量载体线程上，让「阻塞」几乎免费——这是对「线程切换贵」问题的另一种回答。
- **协程（有栈/无栈）省掉了什么？** —— 省掉陷入内核的切换成本：用户态调度、用户态栈，上下文切换只保存少量寄存器；代价是调度器自己实现、CPU 密集型任务不会主动让出，且生态要全面异步化。

**实际工程场景**：隔离性优先用进程（浏览器多进程、Chrome 沙箱、崩溃恢复），吞吐与共享优先用线程/协程。Java 服务里线程数不是越多越好：线程切换、栈内存（默认 1MB 虚拟内存）、锁竞争都会随线程数恶化；阻塞型业务上 Java 21 虚拟线程、同步型业务上调线程池与队列。

**容易答错的地方**：只说「线程轻量」不讲页表/TLB 这个根因；说线程切换零成本（只是比进程小一个量级）；以为 Linux 有独立的线程概念（是共享地址空间的轻量级进程）；把「共享内存」等同于「没有同步问题」——共享正是竞态的来源。

> 权威内容：进程与线程的实现模型当前尚未在仓库建设，可参考《操作系统概念》与 Linux man-pages 的 clone(2)。

### Q03：虚拟内存解决什么问题？缺页中断呢？ `P1` `中频`

**30 秒回答**：虚拟内存给每个进程一套独立、连续、可以大于物理内存的地址空间，通过页表映射到物理页；缺页中断是访问的页当前不在物理内存时由硬件触发、内核负责加载的异常。

**深入理解**：它解决三件事：隔离（进程无法直接访问别人的物理内存）、简化链接与分配（程序看到的地址始终连续）、按需占用物理内存并支持换出。缺页分两类：软缺页指页仍在页缓存或 swap 中，只需建立映射或从 swap 读回；硬缺页必须读磁盘或从文件加载，代价可能高出几个数量级。由于页表是多级的，每次地址翻译理论上要多访问几次内存，靠 TLB 缓存最近的映射来摊薄，TLB 命中率一降性能立刻受影响，这也是进程切换比线程切换贵的另一个原因。页面置换普遍采用 LRU 的近似实现，Linux 用活跃与非活跃链表；抖动指缺页过于频繁，CPU 大部分时间耗在等待 I/O 上。

**为什么这样设计**：物理内存装不下所有进程的全部数据，「按需加载 + 换出」是必然选择；而给每个进程一套独立地址空间，是把「内存保护」从软件约定变成硬件强制——MMU 在地址翻译时查权限位，用户态碰内核页直接异常。这两件事（隔离与按需）一个都不能少，构成了虚拟内存存在的全部理由。

**面试官可能继续追问**：
- **软缺页和硬缺页差多少？** —— 软缺页只是补一次映射（页已在 Page Cache 或 swap 缓存里），纳秒到微秒级；硬缺页要触发磁盘 IO，毫秒级，差三四个数量级。排查手段：`sar -B` 的 `majflt`（硬缺页）与 `minflt`（软缺页）。
- **Copy-On-Write 和虚拟内存什么关系？** —— fork 时父子进程共享物理页、页表项标为只读，任一方写入才触发缺页并复制该页。这让 fork 几乎零成本（Redis RDB 的 bgsave、Java 之外的 C 系服务都吃这个红利），前提是写操作少。
- **什么是 thrashing（抖动）？** —— 工作集超过物理内存后，页面反复换入换出，CPU 大量时间花在缺页处理上，系统看起来忙但吞吐崩掉。解法是降并发、加内存、减单进程工作集。

**实际工程场景**：JVM 堆不是虚拟内存的全部——堆外内存（直接内存、元空间、CodeCache）、线程栈、mmap 文件都占虚拟地址空间，容器里要盯 `-Xmx` 与实际 RSS 的差。容器 `memory.limit` 触及后 OOM Killer 杀进程，而不是优雅抛 OOM，是云上 Java 事故的常见形态。

**容易答错的地方**：把虚拟内存等同于 swap（swap 只是它按需换出能力的一小部分）；说缺页一定读磁盘（软缺页不读）；忽略 TLB 与多级页表带来的翻译成本（这是理解进程切换贵的关键一环）。

> 权威内容：虚拟内存与缺页处理当前尚未在仓库建设，可参考《深入理解计算机系统》与《操作系统概念》。

### Q04：死锁的四个必要条件是什么，怎么预防？ `P1` `中频`

**30 秒回答**：死锁的四个必要条件是互斥、占有并等待、不可剥夺和循环等待，只要在工程上破坏其中任意一个，死锁就无法形成。

**深入理解**：互斥指资源同一时刻只能被一个线程持有；占有并等待指持有资源的同时还去申请新资源；不可剥夺指已获得的资源不能被强行收回；循环等待指存在一条首尾相接的等待链。预防手段与之一一对应：把资源改造成可共享（并非总是可行）、一次性申请全部资源或申请不到就先释放（破坏占有并等待）、允许抢占（破坏不可剥夺）、给资源统一编号并强制按序号升序申请（破坏循环等待，实施成本最低，也最常用）。除预防外还有避免（银行家算法，需要预先知道线程的最大资源需求）以及检测加恢复（允许发生，周期性检查等待图）。Java 里最常见的诱因是多把锁的加锁顺序不一致，可以用 jstack 看是否存在 "Found one Java-level deadlock"，或者改用带超时的 tryLock 替代 synchronized 嵌套。

**为什么这样设计**：选择「按序申请」而不是银行家算法，是因为避免死锁要求提前知道每个线程的最大资源需求，这在真实工程里基本拿不到；按序加锁只要求一条全局约定，用最低的实施成本消除了循环等待。

**面试官可能继续追问**：
- **Java 里 synchronized 会发生死锁吗，怎么发现？** —— 会。多线程以不同顺序嵌套获取多把监视器锁即构成循环等待。发现靠 jstack（找 "Found one Java-level deadlock"）、arthas thread -b、或 JMC 的线程转储；线上复现不了的死锁先用 thread dump 抓现场。
- **tryLock 超时算哪一路？** —— 属于「检测 + 恢复」的轻量版：不预防，而是等不下去就放弃并回滚已持有的锁，把死锁降级为一次失败重试。代价是业务要能处理「抢锁失败」这条路径。
- **线程池之间互相提交任务为什么会死锁？** —— 这是 Java 特有的形态：A 池任务里同步等 B 池结果，B 池任务里又同步等 A 池，加上池打满，形成跨池的循环等待。解法是拆分池职责、拒绝嵌套等待、或用 CompletableFuture 的回调编排替代同步阻塞。

**实际工程场景**：工程上的标准做法是「约定加审查」：全局锁序约定（如先账户后订单、先全局后局部）+ 代码评审 checklist + 静态检查；对存量不确定的路径，用 tryLock 超时兜底。分布式场景下死锁跨越了进程，四个必要条件依然适用，但检测要靠超时与对端心跳，本地 jstack 无能为力。

**容易答错的地方**：把四个条件说成「充分条件」（是必要条件，破坏任一即可预防）；答预防时只背银行家算法不讲按序加锁（后者才是工程主流）；只说 Java 层锁，忽略线程池嵌套等待这种 Java 特有形态。

> 权威内容：死锁成因与处理策略当前尚未在仓库建设，可参考《操作系统概念》与《Java 并发编程实战》。

### Q05：用户态和内核态怎么切换，开销在哪？ `P2` `低频`

**30 秒回答**：用户态和内核态是 CPU 的两种特权级别，应用程序通过系统调用、中断或异常陷入内核，内核处理完再返回用户态；开销主要是特权级切换与寄存器保存恢复，以及流水线、分支预测器和缓存受到的扰动。

**深入理解**：x86-64 上通常用 ring 0 与 ring 3，由段选择子和页表项的权限位共同约束，用户态代码不能执行特权指令也不能访问内核页。进入内核只有三类途径：系统调用（主动请求）、中断（设备等异步事件）、异常（缺页、除零等同步事件）。系统调用入口在 x86-64 上是 syscall 指令，进入时就要切换到内核栈、保存用户寄存器。真正的时间成本不只是保存恢复那几十个寄存器的周期数，还包括流水线被部分冲刷、L1/L2 缓存和 TLB 被新数据挤占，以及内核后续的处理逻辑本身。所以高频的小粒度系统调用会成为瓶颈，这正是缓冲区、批量提交、mmap 等优化手段存在的理由。

**为什么这样设计**：特权分级是「不可信代码不能直接碰硬件」的唯一硬件强制手段——没有它，任何一个进程的 bug 都能让整台机器崩溃。代价是所有合法访问都要支付切换成本，于是催生了整个「减少陷入次数」的优化谱系：缓冲、批处理、io_uring（共享环形缓冲区，批量提交系统调用）、mmap（把后续访问变成普通内存读写）。

**面试官可能继续追问**：
- **系统调用和函数调用差在哪？** —— 函数调用是同特权级的跳转，只做栈帧与寄存器保存；系统调用要切换特权级、换栈、走内核入口（还需对 KPTI/Meltdown 缓解带来的额外页表切换付账），并完整保存用户态上下文。
- **为什么 io_uring 是近期的重要演进？** —— 传统 IO 每次操作两个系统调用（submit + reap），高频小 IO 时切换成本占比很高。io_uring 用内核与用户态共享的环形队列，提交和完成都通过队列批量进行，大幅减少陷入次数，且支持轮询模式完全不陷入。
- **Java 里哪里在为这个成本买单？** —— 每次 `FileInputStream.read`、`DatagramSocket.receive` 都是一次陷入；NIO 的 `DirectByteBuffer`、`FileChannel.transferTo`、Netty 的池化 buffer，本质都是在减少调用次数和拷贝，把系统调用成本摊薄。

**实际工程场景**：这题是零拷贝、IO 模型、Netty 设计的总底座——看到「批量提交」「共享内存队列」「mmap」这类方案，都要能回落到「减少用户态-内核态切换」这条主线上。排查上，`strace -c` 统计系统调用次数与耗时，是定位「CPU 没高但就是慢」类问题的常规武器。

**容易答错的地方**：把开销只算成「保存寄存器的几十个周期」（缓存与流水线扰动往往更大）；说只有系统调用才进内核（中断和异常也会）；以为切换成本在现代 CPU 上可以忽略（高频小粒度场景它仍是主要成本）。

> 权威内容：用户态与内核态切换当前尚未在仓库建设，可参考《深入理解计算机系统》与 Linux man-pages 的 syscall(2)。

### Q06：零拷贝是什么？ `P0` `高频`

**30 秒回答**：零拷贝指减少数据在用户态与内核态之间、以及内核内部的不必要拷贝和上下文切换。传统 `read + write` 发一个文件要 4 次拷贝、4 次上下文切换；`sendfile` 把数据直接在内核态从文件描述符送到 socket，只留 1 次 DMA 拷贝、2 次切换；Kafka 用 sendfile、RocketMQ 用 mmap，Java 侧对应 `FileChannel.transferTo` 和 `MappedByteBuffer`。

**深入理解**：以「把磁盘文件通过网络发出」为例看每一步的演变：

```text
传统 read + write：
  磁盘 →DMA→ Page Cache →CPU 拷贝→ 用户 buffer
  用户 buffer →CPU 拷贝→ Socket buffer →DMA→ 网卡
  共 4 次拷贝、4 次用户态/内核态切换

sendfile（Linux 2.1+，DMA gather 后 2 次拷贝）：
  磁盘 →DMA→ Page Cache →（SG-DMA 直接把页描述符交给网卡）→ 网卡
  数据始终不离开内核，1 次 DMA 拷贝、2 次切换
  JDK 侧：FileChannel.transferTo（依赖内核 sendfile，上限约 2GB）

mmap + write：
  磁盘 →DMA→ Page Cache（与用户空间共享映射，省掉 read 那次拷贝）
  写时仍需把用户页拷进 Socket buffer，共 3 次拷贝、4 次切换
  JDK 侧：MappedByteBuffer
```

两个工程样本的分工很典型：Kafka 的消费走 sendfile——page cache 直接进网卡， broker CPU 压力小；RocketMQ 的 CommitLog 用 mmap——写入时映射文件像写内存，顺序追加没有随机寻道，还能让 Page Cache 参与读写。代价也要说清：mmap 有缺页开销、映射管理成本、`SIGBUS` 风险（文件被截断时访问映射页会直接崩进程）；sendfile 的 2GB 上限和「数据不过用户态」意味着不能边发边改内容。

**为什么这样设计**：拷贝的根源是「数据必须过用户态」这个假设，而文件转发的场景里应用根本不需要读内容——把数据路径整个搬进内核，既省拷贝也省切换。内核选择提供 sendfile 和 mmap 两条路而不是一条，是因为转发（不过用户）和映射（要随机访问）是两类不同需求，前者省到底，后者保留灵活性。

**面试官可能继续追问**：
- **零拷贝真的零拷贝吗？** —— 不是。DMA 到 Page Cache 那次拷贝通常省不掉（除非网卡和磁盘支持更激进的直通），所谓零拷贝省的是「内核↔用户态」的 CPU 拷贝与上下文切换。面试里说清这一点比背「零拷贝」三个字加分。
- **为什么 mmap 不适合做网络发送？** —— 它省的是 read 那一次拷贝，write 时仍要把用户页拷进 socket buffer，切换次数也没降；且随机访问映射文件会带来缺页与 SIGBUS 管理成本。纯转发场景 sendfile 严格更优。
- **transferTo 有什么限制？** —— 依赖操作系统 sendfile 支持，单次大小受限（Linux 约 2GB，Netty 里会分块循环）；对已经解密/要改内容的流（HTTPS、压缩中转）不适用——数据不过用户态就没法加工。

**实际工程场景**：判断标准是「数据要不要过应用逻辑」——静态文件、消息转发不过逻辑，上 sendfile（Nginx 的 `sendfile on`、Netty 的 `DefaultFileRegion`、Kafka 消费）；要逐条处理的消息存储用 mmap + 顺序写（RocketMQ）；要加工的走普通缓冲。反向案例：给 HTTPS 静态资源硬上零拷贝没有意义，TLS 必须过用户态。

**容易答错的地方**：以为零拷贝是「一次拷贝都没有」（省的是 CPU 拷贝与切换，DMA 那次常在）；说 mmap 比 sendfile 更省（转发场景恰恰相反）；只会背 Kafka 用 sendfile，讲不清 mmap 的 SIGBUS 与缺页代价。

> 权威内容：零拷贝与文件 IO 路径当前尚未在仓库建设，可参考 Linux man-pages 的 sendfile(2)、mmap(2) 与《Linux 系统编程》。

### Q07：进程调度算法有哪些？ `P2` `低频`

**30 秒回答**：经典算法有先来先服务、短作业优先、优先级、时间片轮转和多级反馈队列；Linux 实际用的是 CFS（完全公平调度器），按虚拟运行时间让每个进程公平分享 CPU；Java 的线程优先级只是给内核的提示，不保证行为。

**深入理解**：逐个说定位：

| 算法 | 规则 | 问题 |
| --- | --- | --- |
| FCFS | 按到达顺序执行 | 长作业堵死短作业，平均周转时间差 |
| SJF | 最短作业优先 | 理论平均周转最优，但需要预知运行时长，长作业可能饥饿 |
| 优先级 | 高优先级先执行 | 低优先级饥饿；需配老化（等待越久优先级越高） |
| 时间片轮转 | 每人一个时间片，用完排队 | 交互响应好，时间片大小是权衡（太大退化为 FCFS，太小切换开销占比高） |
| 多级反馈队列 | 多级队列 + 动态升降级 | 综合症最优解：新进程进高优先级短时间片队列，用不完时间片说明是 CPU 型就降级；兼顾响应与吞吐 |

Linux CFS 的思路又不一样：它不跑离散队列，而是给每个可运行任务记录虚拟运行时间 `vruntime`（实际运行时间按权重归一化，优先级高的任务 vruntime 涨得慢），全局永远选 `vruntime` 最小的任务执行——等价于「每人一份理想 CPU 时间的比例分配」，用红黑树组织 `vruntime` 快速取最小。调度延迟（目标让所有任务都跑一次的周期）和最小粒度是主要可调参数。Java 的 `Thread.setPriority` 映射到 OS 优先级，但实际效果依赖内核调度器与负载，不承诺顺序——依赖优先级保证执行顺序是错误设计。

**为什么这样设计**：调度器设计的永恒矛盾是「响应性」与「吞吐/公平」：轮转和多级反馈保交互响应，SJF 保平均周转，CFS 选择了公平性——每个任务拿到应得比例的 CPU，交互型任务因睡眠多自然 `vruntime` 小、醒来后优先执行，不需要单独的交互队列。这是把「调度目标」从「排序」改成「按比例分配」的思路转变。

**面试官可能继续追问**：
- **CFS 为什么选红黑树？** —— 需要频繁「取最小 vruntime」和「插入/删除」，红黑树三者都是 O(log n)，且实现成熟；调度频率是微秒级热点路径，常数因子经过专门优化。
- **时间片太大/太小分别怎样？** —— 太大：响应退化，交互任务等太久；太小：上下文切换占比升高，有效计算比例下降。轮转的时间片与 CFS 的调度延迟/最小粒度是同一个权衡的不同参数化。
- **Java 里能依赖线程优先级吗？** —— 不能。`setPriority` 只是提示，Linux 对 nice 值的响应是非线性的且受负载影响；要保证执行顺序用显式同步（锁、信号量、队列），不要指望调度器。

**实际工程场景**：这题在面试里是「了解即可」档，但它是理解两个真实问题的底座：容器里 `cpu.shares`/`cpu.cfs_quota` 为什么能让邻居进程影响你（CFS 的公平是按组计算的），以及为什么「CPU 100% 但业务吞吐掉」可能是调度延迟或优先级配置问题而不是 GC。

**容易答错的地方**：只背算法名字不讲各自的问题域与饥饿风险；说 Linux 用时间片轮转（是 CFS，vruntime 模型）；以为 Java 线程优先级可靠（只是提示）；把多级反馈队列说成「多个优先级队列」（关键是动态升降级）。

> 权威内容：进程调度算法当前尚未在仓库建设，可参考《操作系统概念》与 Linux 内核文档 `sched-design-CFS.rst`。

### Q08：分页、分段、段页式是什么？ `P1` `中频`

**30 秒回答**：分页把地址空间切成固定大小的页、物理内存切成同大小的页框，用页表建立映射，核心收益是消除外部碎片；分段按逻辑单位（代码段、堆、栈）划分、大小不等，保留「一段一语义」但重新引入外部碎片；段页式是先分段再在段内分页，兼顾两者。Q03 讲虚拟内存解决什么问题，这一题讲内存管理的具体机制。

**深入理解**：为什么分页：固定大小意味着任何一个空闲页框都能装任何一页，不存在「差一点装不下」的外部碎片，只剩页内碎片（平均半页，可调大页缓解）；配合请求调页，物理内存不必一次装下整个地址空间。页表项（PTE）的典型内容：物理页框号、有效位（在不在内存）、保护位（读写执行权限）、修改位（脏页，决定是否回写）、访问位（供置换算法参考）、以及各类架构的用户/管理位。多级页表的动机：单级页表要按「整个虚拟地址空间」连续存放，64 位下条目数爆炸；多级只给「实际用到的区域」建表，且每级页表本身可以离散存放、按需分配——x86-64 用四级。代价是每次地址翻译要走多次内存访问（TLB 命中时只查一次），这也是 Q01/Q02 里 TLB 命中率重要的原因；反向优化是大页（2MB/1GB，一条 TLB 条目覆盖更多内存，JVM 加 `-XX:+UseLargePages` 是真实受益点）。分段的存在理由是「权限按逻辑单元给」：代码段只读可执行、栈可写不可执行，页内权限做不到这么贴语义；代价是外部碎片和大小管理复杂。段页式（x86 历史上就是段选择子 + 页偏移）保留分段语义、内部再分页消碎片，复杂度最高，现代 64 位系统基本把分段降到只剩权限容器，主力是分页。

**为什么这样设计**：分页用「固定大小」换「无外部碎片 + 离散分配 + 换入换出」，这是虚拟内存一切能力的物理基础；分段用「逻辑语义」换「按单元设权限」，是安全需求的产物。两者不是竞争关系而是不同约束下的产物——现代系统选择段页式（甚至近乎纯分页），是因为安全需求（NX、ASLR）最终在页级也能表达，而碎片和离散分配只能在页级解决。

**面试官可能继续追问**：
- **内部碎片和外部碎片的区别？** —— 内部碎片是「分配单元内没用完的部分」（固定大小分配的固有浪费）；外部碎片是「空闲空间被切成小块，总量够但连续不够」（可变大小分配的病）。分页消外部碎片、留内部碎片，分段反之。
- **TLB 未命中会发生什么？** —— 硬件走多级页表（或 OS 处理，视架构）完成翻译并填充 TLB；多级就是多次内存访问，所以 TLB miss 的代价等于「页表深度次访存」，大页/巨页直接减少需要的 TLB 条目数。
- **JVM 为什么要关心页大小？** —— JVM 堆是连续映射的大区域，4KB 页会让 TLB 覆盖几百 MB 就饱和，大对象遍历和 GC 扫描都吃 TLB miss；HugeTLB/`-XX:+UseLargePages` 让 TLB 覆盖扩展到 GB 级，是堆大于 8GB 时值得评估的调优。

**实际工程场景**：真实调优几乎都落在 TLB 与大页上：大堆服务开 THP 或显式 large pages，观察 `TLB` 相关指标；理解「缺页 = 页表 + 磁盘/文件」这条链，才能把 Q03 的抖动、Q09 的 Page Cache 串成一条线。面试里把这一题和虚拟内存、零拷贝连起来答，比孤立背定义更有说服力。

**容易答错的地方**：把分段和分页说成「先后替代关系」（是不同约束的产物，现代是段页式混合）；漏掉多级页表的动机（省表空间、按需分配）；只说页表项是「页号到框号」（还有有效位、保护位、脏位、访问位）；忽略 TLB 这个翻译缓存的存在。

> 权威内容：分页与段页式机制当前尚未在仓库建设，可参考《深入理解计算机系统》与《操作系统概念》。

### Q09：磁盘 IO 和文件系统是怎么回事？ `P1` `中频`

**30 秒回答**：机械磁盘的瓶颈是随机 IO——每次寻道加旋转是毫秒级，顺序 IO 却接近内存带宽的十分之一，所以数据库类系统的核心设计命题就是「把随机 IO 换成顺序 IO」；文件系统在磁盘之上提供 Page Cache、预读、日志（ext4 的 journal）和 fsync 语义，MySQL 与 Page Cache 之间还存在「双写」这类数据一致性问题。

**深入理解**：HDD 的物理成本模型：顺序读写吞吐可达 100～200MB/s，随机寻道只有每秒几百次 IOPS——差两三个数量级，这就是「随机 IO 是数据库瓶颈根源」的量化版本。文件系统的三层优化都在围绕它：预读（顺序访问模式检测，一次多读，把随机读归并成顺序读）、Page Cache（文件数据缓存，读命中不碰盘）、日志（ext4 journal 先写日志再写数据，崩溃后按日志重放/回滚，保证元数据一致）。fsync 的语义是「把 Page Cache 里的脏页真正刷到盘并返回」，代价是同步等盘，Redis AOF 的 `everysec`、MySQL 的 `innodb_flush_log_at_trx_commit` 都是在这个点上做取舍。MySQL 与 Page Cache 的关系是经典考点：InnoDB 有自己的 buffer pool 做数据页缓存，而 redo/undo 落盘时又依赖文件系统的 Page Cache——同一条数据路径上两层缓存，刷盘策略若配置不当（如 `O_DIRECT` 与 fsync 语义不清）会出现「双写」：InnoDB 为防部分页写入（torn page）用 doublewrite buffer 先顺序写再原位写，这正是「顺序 IO 优先」原则在数据库内部的应用。SSD 改变的是常数而不是模型：没有寻道，随机 IOPS 高两三个数量级，4KB 随机读写仍是主流工作负载的天花板，且引入写放大、磨损均衡、TRIM 等新问题——「SSD 上随机 IO 不要钱」是错的，只是便宜了很多。

**为什么这样设计**：预读、日志、doublewrite、LSM 树（RocksDB）本质上是同一思想的不同实现：既然顺序便宜随机贵，就全部围绕「把随机写归并成顺序写」做文章。B+ 树减少树高、追加日志代替原地改、批量合并刷盘，都是这条原则的推论——理解这一条，比背任何单个组件的细节都值钱。

**面试官可能继续追问**：
- **fsync 和 fdatasync 的区别？** —— fsync 刷数据 + 元数据（大小、mtime），fdatasync 只刷数据、仅把影响后续读取的元数据（size）一起刷。日志场景常用 fdatasync，少刷一次元数据更新。
- **Page Cache 什么时候会坑你？** —— 脏页堆积后集中回写造成延迟毛刺；`vm.dirty_ratio` 触发同步回写阻塞业务进程；内存吃紧时回收缓存引发直接回收（direct reclaim）卡顿。监控 `dirty` 页与回写速率比看 `free` 更直接。
- **为什么 WAL（redo log）普遍是顺序的？** —— 崩溃恢复只需要「按顺序重放已提交的变更」，顺序写同时满足「盘上最快」和「恢复语义最简」两个约束——写放大和寻道成本都最低。LSM 把这条推到极致：所有写都是顺序追加，后台 compaction 合并。
- **SSD 上数据库设计会变吗？** —— 会放松一部分：随机 IO 便宜后「为省随机 IO 而做的复杂结构」收益下降；但写放大和寿命仍是约束，顺序写与合并策略依然有价值。

**实际工程场景**：调优路径几乎都落在这条线上：MySQL 关 `query cache`、用 `O_DIRECT` 让 InnoDB 自己管缓存（避免双缓存）、redo 盘单独划分、大事务拆小防 redo 峰值；Redis AOF `everysec` + `no-appendfsync-on-rewrite` 的组合拳；Kafka/RocketMQ 顺序写 + 预分配文件 + Page Cache 读。看到「数据库偶尔卡顿几秒」，先查 fsync 队列和脏页回写，再怀疑业务本身。

**容易答错的地方**：只说「磁盘慢」不说量化差距（顺序 vs 随机 IOPS 差两三个数量级）；把 doublewrite 说成「双缓存」（是防部分写的一致性机制）；以为 SSD 上随机 IO 免费（写放大与磨损仍在）；漏掉 Page Cache 与 fsync 的关系（写文件不等于落盘，进程崩了数据在，机器崩了可能没在）。

> 权威内容：磁盘 IO 与文件系统当前尚未在仓库建设，可参考《深入理解计算机系统》第 6 章与 MySQL 官方文档 InnoDB Disk I/O 与 File Space Management 章节。

## 面试前速记

- epoll = 红黑树（登记 fd）+ 就绪链表（只返就绪）；优势限于「连接多、活跃比例低」，ET 必须配非阻塞 fd 且要读到 EAGAIN。
- 线程切换省在不用换页表、TLB 大部分有效；通信直接共享内存但必须自己做同步；Linux 线程是带 CLONE_VM 的轻量级进程。
- 虚拟内存三件事：隔离、连续地址、按需换入换出；软缺页补映射、硬缺页读盘，差三四个数量级；fork 靠 COW 近乎零成本。
- 死锁四条件：互斥、占有并等待、不可剥夺、循环等待；破坏任一即可预防，工程上按序加锁成本最低；Java 特有形态是线程池嵌套等待。
- 用户态/内核态切换的真实成本在缓存与流水线扰动，不只是寄存器保存；批量提交、缓冲、io_uring、mmap 都在为减少陷入次数服务。
- 零拷贝：read+write 是 4 次拷贝 4 次切换，sendfile 省到 1 次 DMA 拷贝 2 次切换，mmap 是 3 次拷贝；Kafka 用 sendfile、RocketMQ 用 mmap；省的是 CPU 拷贝与切换，不是 DMA 那次。
- mmap 有缺页开销和 SIGBUS 风险（文件被截断时访问映射会崩），随机访问才用；`transferTo` 依赖内核 sendfile 且有大小上限。
- 调度算法：FCFS/SJF/优先级/轮转/多级反馈队列各有饥饿或权衡问题；Linux CFS 按 vruntime 取最小（红黑树），优先级高的任务 vruntime 涨得慢；Java 线程优先级只是提示。
- 分页消外部碎片、留内部碎片（平均半页）；PTE 含页框号、有效位、保护位、脏位、访问位；多级页表为按需分配、TLB 是翻译缓存，大页直接扩大 TLB 覆盖。
- 磁盘：顺序 IO 比随机寻道快两三个数量级，数据库一切设计围绕「随机换顺序」：预读、WAL、doublewrite、LSM。
- Page Cache 是读写缓冲，fsync 才是「落盘并返回」；MySQL buffer pool 与文件系统 Page Cache 双层缓存，doublewrite 防部分页写入。
- SSD 没有寻道但仍有写放大与磨损均衡，随机 IO 便宜不是免费。
