## 追问链示例

### 例一：秒杀系统，一路追到数字

```text
面试官：设计一个秒杀系统。
你（L1）：入口限流，Redis 预减库存，然后发消息队列异步下单。
面试官：限流阈值定多少？
你（L2）：这个要看压测结果，一般按单机能承受的峰值的 70%～80% 设。
面试官：那你得知道单机能力。假定你有 100 台应用服务器，
        单机压测能到 2000 QPS，整体是多少？
你（L3）：理论上 20 万 QPS。但真实瓶颈通常不在这儿——
        应用层能扩，数据库扩不了。如果下单最终落到一个库，
        写入可能就是几千 TPS，所以队列必须能扛住这个落差。
面试官：那队列积压了怎么办？
你（L4）：先看是消费慢还是消息量突增。消费慢就加消费者，
        但要确认下游能不能承受；消息量突增且下游跟不上，
        就得在入口做更激进的限流或者直接拒绝，
        而不是让队列无限堆积——队列满了会反压到生产者。
面试官：秒杀结束后，那些没抢到的请求怎么处理？
你（L5）：在入口就快速失败返回「已抢完」，不要进入后续链路。
        可以在 Redis 里维护一个「已售罄」标记，
        前置判断直接短路，避免无效流量穿透到下游。
```

**这道题在考什么**：秒杀是人人都会背的题，**分水岭在于能不能把「多少 QPS、多少台机器、瓶颈在哪」说清楚**。数字比方案更能证明你真的思考过。

权威内容：[场景设计题](../04-场景设计题/README.md)

### 例二：库存扣减的方案取舍

```text
面试官：库存扣减用乐观锁还是悲观锁？
你（L1）：高并发下用乐观锁，冲突少的时候性能更好。
面试官：那如果冲突很激烈呢？
你（L2）：乐观锁会大量失败重试，CPU 空转，
        这时候悲观锁反而更稳。
面试官：那到底怎么选？
你（L3）：看冲突概率和冲突代价。秒杀这种极端场景，
        其实两者都不合适——应该先把请求收敛到一个窄队列里串行化，
        或者用 Redis 的原子操作挡在前面，让数据库只处理少量请求。
面试官：乐观锁的 SQL 大概怎么写？
你（L4）：UPDATE stock SET count = count - 1, version = version + 1
        WHERE id = ? AND version = ? 然后看影响行数。
面试官：这样有什么问题？
你（L5）：如果 count 本身也参与判断，可以把 version 省掉，
        直接用 UPDATE ... WHERE count >= 1，这样更简单，
        也避免了 version 字段的维护成本。
```

**这道题在考什么**：不是二选一，而是**说明选择依据，并指出更优方案**。答「看场景」但说不出看什么，是常见的伪回答。

权威内容：[CAS 与原子类](../../03-并发编程/02-深度解析/CAS与原子类.md)

### 例三：缓存问题的区分

```text
面试官：缓存穿透、击穿、雪崩的区别？
你（L1）：穿透是查不存在的数据，击穿是热点 key 失效，
        雪崩是大量 key 同时失效。
面试官：分别怎么解决？
你（L2）：穿透用布隆过滤器或缓存空值；击穿用互斥锁重建；
        雪崩用随机过期时间。
面试官：缓存空值有什么风险？
你（L3）：如果攻击者用大量随机不存在的 key 来查，
        缓存里会塞满这些空值，占用内存还可能把真实数据挤掉。
        所以要给空值设短过期时间，或者用布隆过滤器前置拦截。
面试官：布隆过滤器的缺点呢？
你（L4）：有误判率，判断「不存在」是准确的，
        判断「存在」可能误判；而且标准布隆过滤器不支持删除。
        对库存这种需要频繁变更的场景不太适合。
面试官：那热点 key 失效的互斥锁，加在什么粒度上？
你（L5）：按 key 加，不是全局锁。可以用 ReentrantLock 的
        分段实现或者用 Redis 的 SETNX。关键是拿到锁的线程
        一定要二次检查缓存，否则还是会重复查库。
```

**这道题在考什么**：三个词人人会背，**但每个方案的副作用才是区分点**。拼多多特别爱问「那这个方案有什么问题」。

权威内容：[ConcurrentHashMap 并发容器](../../03-并发编程/02-深度解析/ConcurrentHashMap并发容器.md)

## 高频失分点

| 失分点 | 表现 | 怎么改 |
| --- | --- | --- |
| 方案没有数字 | 「加缓存」「加限流」 | 每个方案补一个量级：多少 QPS、多少内存、几台机器 |
| 只说优点 | 被问缺点卡住 | 主动说一句「这个方案的代价是……」 |
| 概念混淆 | 穿透/击穿/雪崩说不清 | 用「查什么数据、什么时候失效、影响范围」三个维度区分 |
| 忽略成本 | 方案全靠堆机器 | 提一句成本和收益的平衡 |
| 不懂装懂 | 猜数字 | 直接说「这个需要压测才知道，我的估算依据是……」 |

## 一句话准备建议

拼多多的场景题有一个固定套路：**先给方案 → 主动给数字 → 主动说代价 → 说故障时的表现**。把这四句话练成习惯，比多背两个框架有用得多。
