## Q01. == 与 equals() 的区别

`==` 是 Java 的运算符，比较的是"值本身"；`equals()` 是 `Object` 类定义的方法，比较的是"对象自己认定的相等"。两者的差别在引用类型上才真正体现出来。

对基本类型，`==` 直接比较数值是否相等，此时不存在 `equals()` 的用法。对引用类型，`==` 比较两个引用是否指向同一个对象实例，也就是地址相同。而 `equals()` 在 `Object` 中的默认实现是：

```java
public boolean equals(Object obj) {
    return (this == obj);
}
```

也就是说，如果子类不重写 `equals()`，它的行为和 `==` 完全一致。`String`、包装类、集合类以及多数值对象都重写了 `equals()`，把它改成"按内容或业务主键判断相等"。

| 场景 | `==` | `equals()` |
| --- | --- | --- |
| 基本类型之间 | 比较数值 | 不适用 |
| 引用类型，未重写 `equals()` | 同一实例才为 `true` | 等价于 `==` |
| 两个 `String` 字面量 | 命中常量池则为 `true` | 逐字符比较 |
| `new String("a")` 与 `"a"` | `false` | `true` |
| `Integer` 的 128 与 128 | `false`（超出缓存区间） | `true` |

两个容易忽略的边界。第一，`String` 的 `==` 结果取决于实例是否来自常量池：`"a" + "b"` 在编译期折叠为字面量，与 `"ab"` 比较为 `true`；而含变量的拼接（如 `s + "b"`，`s` 非 `final`）在运行期生成新对象，比较为 `false`。第二，包装类的 `==` 受缓存区间影响：`Integer.valueOf()` 缓存了 -128 到 127，这个区间内复用同一实例，区间外每次新建。

重写 `equals()` 需要重写 `hashCode()`，并遵守自反、对称、传递、一致、对 `null` 返回 `false` 这五条约定，否则对象在 `HashMap`、`HashSet` 中的行为不可预测。数组没有重写 `equals()`，比较内容要用 `Arrays.equals()`；对可能为 `null` 的引用，用 `Objects.equals(a, b)`。枚举实例由 JVM 保证唯一，直接用 `==` 比较即可。

## Q02. 如何创建线程池？线程池常见参数是什么？

创建线程池有两种方式：一是通过 `Executors` 的工厂方法，如 `newFixedThreadPool`、`newCachedThreadPool`、`newScheduledThreadPool`；二是直接 `new ThreadPoolExecutor(...)` 显式构造。生产环境用第二种，因为 `Executors` 的几个常用工厂方法都隐藏了队列或线程数的边界：`newFixedThreadPool` 使用近似无界的 `LinkedBlockingQueue`，`newCachedThreadPool` 的 `maximumPoolSize` 是 `Integer.MAX_VALUE`，两者在流量突增时都可能堆积任务或无限创建线程。

`ThreadPoolExecutor` 的构造参数有七个：

| 参数 | 含义 | 常见取值与影响 |
| --- | --- | --- |
| `corePoolSize` | 核心线程数，默认长期驻留 | CPU 密集型起点取"核数 + 1"，IO 密集型按阻塞比例估算 |
| `maximumPoolSize` | 线程数上限 | 队列满后才向这个上限扩张 |
| `keepAliveTime` | 非核心线程空闲存活时间 | 配合 `TimeUnit`，流量峰谷明显时可同时作用于核心线程 |
| `unit` | 时间单位 | `TimeUnit.SECONDS` 等 |
| `workQueue` | 任务队列 | 有界 `ArrayBlockingQueue` 或 `LinkedBlockingQueue(capacity)` |
| `threadFactory` | 线程工厂 | 自定义线程名，便于排查线程栈 |
| `handler` | 拒绝策略 | 见下文四种 |

任务提交后的处理顺序是：当前线程数小于 `corePoolSize` 就新建核心线程执行；否则尝试入队；入队失败（队列满）时，若线程数未达 `maximumPoolSize` 就新建非核心线程；仍然失败则执行拒绝策略。这个顺序意味着无界队列会让 `maximumPoolSize` 永远不生效——队列不会满，线程数就停在核心线程数上，任务全部堆在队列里等待。

四种拒绝策略：`AbortPolicy` 抛 `RejectedExecutionException`，是默认值；`CallerRunsPolicy` 由提交任务的线程自己执行，形成天然的背压；`DiscardPolicy` 静默丢弃；`DiscardOldestPolicy` 丢弃队列中最老的任务再重试提交。核心业务一般用 `AbortPolicy` 配合上层重试或降级，也可自定义实现记录日志并落盘。

另外两个常用开关：`allowCoreThreadTimeOut(true)` 让核心线程也受 `keepAliveTime` 约束，适合流量有明显峰谷的场景，默认关闭；`prestartAllCoreThreads()` 在启动时预热核心线程，避免首批请求承担创建开销。线程数不是公式算出来的，CPU 核数、任务阻塞比例、下游连接池容量都要参与，最终值靠压测确定。

## Q03. ThreadLocal 的用法和实现原理

`ThreadLocal` 为每个线程维护一份独立的变量副本，读写的都是当前线程自己的那份。典型用法是在请求入口 `set`、在业务链路中 `get`、在结束时 `remove`：

```java
private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

try {
    CONTEXT.set(context);
    process();
} finally {
    CONTEXT.remove();
}
```

需要注意它不是"把值存在 `ThreadLocal` 对象里"。数据的实际归属是 `Thread`：

```text
Thread
  └── threadLocals: ThreadLocalMap
        └── Entry[]：key = WeakReference<ThreadLocal>，value = 强引用
```

`Thread` 内部有一个 `ThreadLocalMap` 字段，`ThreadLocal` 只作为 key。`set` 时以 `ThreadLocal` 的 `threadLocalHashCode` 定位槽位写入；`get` 时用同样方式定位，命中就返回，未命中则调用 `initialValue()` 初始化。`ThreadLocalMap` 没有用 `HashMap`，而是数组加开放寻址、线性探测：key 的身份就是 `ThreadLocal` 对象本身，不需要通用 Map 结构；每个线程只访问自己的 map，也不需要并发控制。它的哈希增量是一个固定步长，让连续创建的 `ThreadLocal` 在数组中分布得更均匀。

`Entry` 继承 `WeakReference<ThreadLocal<?>>`，key 是弱引用，value 是强引用。这样设计是为了让 `ThreadLocal` 对象本身可以被回收，但副作用是泄漏：当线程池的工作线程长期存活、任务创建的临时 `ThreadLocal` 又没有其他强引用时，key 被 GC 后槽位变成 stale entry，value 仍被这条 `Thread → ThreadLocalMap → Entry → value` 强引用链持有，直到 `ThreadLocalMap` 在某次 `get`、`set`、`remove` 或扩容时顺带清理。

清理是机会式的（`expungeStaleEntry`、`cleanSomeSlots`），不是后台任务，也不保证全表扫描，所以不能替代显式清理。`set(null)` 只是把 value 置空，key 和槽位仍然保留，和 `remove()` 不等价。在线程池里尤其要在 `finally` 中 `remove()`，否则除了内存占用，还会出现下一个任务读到上一个请求数据的串用问题。

`InheritableThreadLocal` 会在创建子线程时把值复制过去，但只覆盖线程创建这一时刻，线程池复用线程时不会重新传递，跨线程传递上下文应当显式传参或借助框架的上下文传播能力。

## Q04. 说说你了解的 JVM 内存模型

这道题问的通常是 JVM 运行时数据区的划分，不是并发语义里的 Java 内存模型（JMM）。按线程私有和线程共享可以分成两组。

| 区域 | 归属 | 存什么 | 溢出行为 |
| --- | --- | --- | --- |
| 程序计数器 | 线程私有 | 当前线程执行字节码的行号；执行 Native 方法时为 undefined | 唯一不会 OOM 的区域 |
| 虚拟机栈 | 线程私有 | 栈帧：局部变量表、操作数栈、动态链接、方法返回地址 | 栈深超限抛 `StackOverflowError` |
| 本地方法栈 | 线程私有 | Native 方法的执行上下文 | HotSpot 中与虚拟机栈合并实现 |
| 堆 | 线程共享 | 几乎全部对象实例和数组，GC 的主战场 | 容量不足抛 `OutOfMemoryError: Java heap space` |
| 方法区 | 线程共享 | 类元数据、运行时常量池、静态变量、JIT 编译后的代码 | 元空间不足抛 `OutOfMemoryError: Metaspace` |
| 直接内存 | 非规范区域 | NIO 的 `DirectByteBuffer` 等堆外内存 | 抛 `OutOfMemoryError: Direct buffer memory` |

虚拟机栈是最需要讲清楚的一层。每次方法调用创建一个栈帧，栈帧里存放局部变量表（含基本类型和对象引用）、操作数栈、指向运行时常量池的方法引用（动态链接）以及返回地址。栈深度由 `-Xss` 控制，递归失控时抛出 `StackOverflowError`，这是单个线程栈帧数量的问题；而"无法创建新线程"（`unable to create new native thread`）属于内存和线程数问题，两者不要混淆。

方法区的实现有两个关键版本变更。JDK 7 把字符串常量池从永久代移到了堆中，让 `intern()` 产生的字符串可以正常参与 GC；JDK 8 用元空间替代永久代，类元数据改放在本地内存，由 `-XX:MaxMetaspaceSize` 限制，默认不设上限——这也是线上需要显式设置该参数的原因，否则动态生成类或类加载器泄漏会持续消耗本机内存。

堆是唯一需要细分的共享区域：按分代分为新生代（Eden 与两块 Survivor，默认 8:1:1）和老年代，比例由 `-XX:NewRatio`、`-XX:SurvivorRatio` 调整，这个结构直接决定了新生代采用复制算法。直接内存不在 JVM 规范定义内，但 `-XX:MaxDirectMemorySize` 不设时会退化为受堆最大值约束，Netty 等大量使用堆外内存的框架需要单独监控。

## Q05. 说说 JVM 的垃圾回收算法

回收的第一步是判断对象是否存活，JVM 采用可达性分析：从 GC Roots（虚拟机栈中的引用、方法区静态属性与常量引用、JNI 引用、活跃线程等）出发遍历引用链，不可达的对象才可回收。引用计数因为无法处理循环引用，主流 JVM 没有采用。

在此基础上只有三种基础算法：

| 算法 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 标记-清除 | 标记存活对象，回收未标记对象 | 实现简单，不移动对象 | 产生内存碎片，分配需走空闲列表；碎片累积后大对象可能提前触发 Full GC |
| 标记-复制 | 内存分两块，存活对象复制到空闲块，整块清空原块 | 无碎片，分配用指针碰撞；只遍历存活对象 | 可用内存减少；存活率高时复制成本急剧上升 |
| 标记-整理 | 标记后把存活对象向一端移动，清理边界之外的空间 | 无碎片，也不浪费空间 | 移动对象需更新所有引用，停顿时间最长 |

实际 JVM 把三者组合成**分代收集**，依据是两条经验假设：绝大多数对象朝生夕灭（弱分代假说），熬过越多次回收的对象越难死亡（强分代假说）。新生代存活率通常不到 10%，复制成本与存活对象数量成正比，因此用复制算法，Eden 与两块 Survivor 按 8:1:1 划分，每次把 Eden 和一块 Survivor 的存活对象复制到另一块，只有约 10% 的空间被闲置；当 Survivor 放不下时通过分配担保进入老年代。老年代存活率高，复制等于把大半堆搬一遍，因此用标记-清除或标记-整理。对象晋升老年代的路径包括达到年龄阈值（`-XX:MaxTenuringThreshold`，默认 15）、大对象直接进入、Survivor 中同龄对象总大小超过一半（动态年龄判定）、以及分配担保失败。

标记阶段与用户线程并发执行时会引入新的问题：三色标记中，如果黑色对象新增了指向白色对象的引用，同时原本指向该白色对象的灰色引用被删除，这个白色对象就会被漏标。两种解法对应两种屏障：CMS 用增量更新，记录新增的引用并在重新标记阶段重新扫描；G1 用原始快照（SATB），记录被删除的旧引用，按起始快照标记，代价是把已死对象多标为存活，产生浮动垃圾。

算法落到具体实现就是收集器，两者的对应关系常被混答：

| 收集器 | 作用区域 | 核心算法 | 版本边界 |
| --- | --- | --- | --- |
| Serial / Serial Old | 新生代 / 老年代 | 复制 / 标记-整理 | 单线程，客户端模式和小堆场景仍在使用 |
| ParNew | 新生代 | 复制 | Serial 的多线程版本 |
| Parallel Scavenge / Parallel Old | 新生代 / 老年代 | 复制 / 标记-整理 | JDK 8 默认，吞吐优先 |
| CMS | 老年代 | 标记-清除 | JDK 9 弃用，JDK 14 移除 |
| G1 | 整堆，按 Region 划分 | 局部复制，整体标记-整理语义 | JDK 7 引入，JDK 9 起成为默认 |
| ZGC | 整堆 | 并发标记-复制，染色指针 + 读屏障 | JDK 11 实验，JDK 15 生产可用，JDK 21 支持分代 |

## Q06. 说说你对 IoC 的理解

IoC（Inversion of Control，控制反转）指把对象的创建、依赖装配和生命周期管理从业务代码交给容器，对象不再自己 `new` 依赖，而是声明"我需要什么"，由容器在启动时注入。DI（Dependency Injection，依赖注入）是 IoC 的具体实现方式，两者是同一思想的两个层面。它并非 Spring 独有，本质是依赖倒置原则的工程化落地——高层模块和低层模块都依赖于抽象，具体实现由外部装配。

没有容器时，`OrderService` 要用 `OrderRepository` 就在内部 `new`，依赖关系硬编码在类里，替换实现要改代码，单元测试也必须拉起真实依赖。交给容器后，依赖通过构造器、Setter 或字段注入，替换实现只需换一个 Bean 定义，测试时可以直接注入 mock。

三种注入方式的差异：

| 方式 | 写法 | 适用场景 | 局限 |
| --- | --- | --- | --- |
| 构造器注入 | 依赖作为构造参数 | 必需依赖，推荐默认使用 | 依赖多时构造器签名变长，暴露设计问题 |
| Setter 注入 | `@Autowired` 标注 setter | 可选依赖、允许后续替换 | 对象可能处于依赖未注入的中间状态 |
| 字段注入 | `@Autowired` 标注字段 | 写法最短 | 无法用于 `final` 字段，隐藏依赖，脱离容器难以实例化 |

Spring 4.3 起，类只有一个构造器时可以省略 `@Autowired`。`@Autowired` 的解析顺序是：先按类型找候选，候选多于一个时按字段名或参数名匹配，再不行则看 `@Qualifier`、`@Primary`，仍有歧义就抛 `NoUniqueBeanDefinitionException`。

容器启动的大致流程：读取注解或 XML 配置生成 `BeanDefinition`，执行 `BeanFactoryPostProcessor` 修改定义，实例化非懒加载的单例并按上述规则注入依赖，期间 `BeanPostProcessor` 在初始化前后介入（AOP 代理就产生在 `postProcessAfterInitialization`），最后发布容器刷新完成事件。

循环依赖方面，字段注入和 Setter 注入形成的环可以靠三级缓存解决：提前暴露刚实例化但未完成属性填充的对象，让另一方能先拿到引用。构造器注入形成的环无法这样处理，启动期直接失败——这实际上是好事，它把依赖环暴露在启动阶段而不是运行期。

## Q07. 说说你对 AOP 的理解

AOP（Aspect Oriented Programming，面向切面编程）处理的是横切关注点：日志、事务、鉴权、耗时统计这类逻辑，每个业务方法都需要，但不属于任何单个方法的业务语义。把它们抽出来集中定义成切面，再在目标方法执行前后织入，能同时解决两个问题——业务代码里混杂通用逻辑，以及同一段逻辑在几十个方法中重复。

常见术语及其在 Spring 中的对应：

| 术语 | 含义 | Spring 中的落地 |
| --- | --- | --- |
| JoinPoint（连接点） | 程序执行中可以插入增强的点 | Spring AOP 只支持方法执行这一个维度 |
| Pointcut（切点） | 匹配连接点的表达式 | `@Pointcut("execution(* com.example.service.*.*(..))")` |
| Advice（通知） | 增强的动作及其执行时机 | `@Before`、`@After`、`@AfterReturning`、`@AfterThrowing`、`@Around` |
| Aspect（切面） | 切点与通知的模块化组合 | `@Aspect` 标注的类 |
| Weaving（织入） | 把切面接入目标对象的过程 | Spring AOP 在运行期通过代理完成 |

织入时机决定能力上限。编译期织入（AspectJ 的 `ajc`）能拦截方法、字段、构造器甚至 `final` 方法，代价是更换编译器；类加载期织入（LTW）能力相同，但需要 `javaagent` 介入，部署复杂度上升；运行期代理是 Spring AOP 的默认方式，通过 `BeanPostProcessor.postProcessAfterInitialization` 为目标 Bean 生成代理对象，容器最终持有的是代理而不是原始实例。这种方式零侵入，但只能拦截 Bean 的外部方法调用——同类自调用走的是 `this`，不经过代理，通知链根本不会进入，`private`、`final`、`static` 方法同样无法增强。`@Transactional` 在自调用时失效，根因就是这条边界，而不是事务配置写错了。

多个切面作用在同一方法上时，顺序由 `@Order` 或 `Ordered` 决定，值小的优先级更高；进入时按序执行，退出时逆序，形成栈式结构；异常路径上 `AfterThrowing` 与 `After` 的相对顺序会反转。

## Q08. JDK 动态代理是什么？和 CGLIB 有什么区别？

JDK 动态代理是 JDK 在运行期生成代理类的机制，核心是 `java.lang.reflect.Proxy` 和 `InvocationHandler`：

```java
Object proxy = Proxy.newProxyInstance(
        target.getClass().getClassLoader(),
        target.getClass().getInterfaces(),
        (p, method, args) -> method.invoke(target, args));
```

`newProxyInstance` 在运行期生成一个名为 `$Proxy0` 的类，它实现传入的全部接口，每个接口方法内部都转调 `InvocationHandler.invoke()`，同时在 `invoke` 里可以插入增强逻辑，也可以直接短路返回。因此它的前提是目标类必须实现接口，且只能代理接口中声明的方法；`hashCode`、`equals`、`toString` 这几个 `Object` 方法也会被转发到 `invoke`。

CGLIB 走的是另一条路：用 ASM 生成目标类的子类，覆写所有非 `final`、非 `private` 的方法，方法调用先进入 `MethodInterceptor.intercept()`，再决定是否调用父类实现。它不要求接口，因此能代理没有实现接口的类；但因为是继承，`final` 类和 `final` 方法无法被增强，`private` 方法不可见也无法覆写，目标类必须有可访问的构造器。

| 维度 | JDK 动态代理 | CGLIB |
| --- | --- | --- |
| 实现方式 | 生成实现同一接口的代理类 | 生成目标类的子类并覆写方法 |
| 前提条件 | 目标类必须实现接口 | 目标类不能是 `final`，方法不能是 `final` 或 `private` |
| 代理范围 | 仅接口中声明的方法 | 所有可覆写的方法 |
| 依赖 | JDK 自带，无第三方依赖 | 需要引入字节码库（Spring 已内置 repackage 版本） |
| 成本 | 代理类生成快，调用经反射 | 生成较慢，调用接近直接调用 |

Spring 的选型逻辑是：目标 Bean 实现了接口且未强制使用 CGLIB 时，用 JDK 动态代理；没有接口时用 CGLIB。Spring Boot 2.x 起 `spring.aop.proxy-target-class` 默认为 `true`，即使有接口也优先 CGLIB，目的是避免"注入接口拿到的代理无法强转为实现类"这类问题，以及解决字段上没有接口类型可用时的注入失败。这也意味着在默认配置下，给 `final` 类加 `@Transactional` 等注解不会生效，而且不会报错。

性能上不必迷信早期结论。JDK 8 之后反射调用经过优化，单次调用开销与 CGLIB 差距很小，真正的成本集中在代理类生成阶段；生成一次、长期复用的 Bean 场景下，两者差异可以忽略，选型更多取决于目标类是否适合被继承。

## Q09. 如何评估、判断索引是否生效？

判断索引是否生效主要靠 `EXPLAIN` 查看执行计划，MySQL 8.0.18 起还可以用 `EXPLAIN ANALYZE` 拿到实际执行耗时和行数，比纯预估更可信。

`EXPLAIN` 输出里需要重点看的字段：

| 字段 | 关注点 |
| --- | --- |
| `type` | 访问类型，从好到差大致是 `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `possible_keys` | 理论上可用的索引 |
| `key` | 优化器实际选择的索引，为 `NULL` 表示没有用到索引 |
| `key_len` | 实际使用的索引字节数，可反推联合索引用到了前几列 |
| `rows` | 预估需要扫描的行数 |
| `filtered` | 扫描行中满足剩余条件的比例，`rows × filtered` 才接近实际返回行数 |
| `Extra` | 是否覆盖索引、是否额外排序、是否使用临时表 |

各字段的判读方式：

`type` 为 `ref`、`range`、`eq_ref`、`const` 说明索引起作用；为 `ALL` 是全表扫描；为 `index` 是扫完整棵索引树但只读索引列，虽比 `ALL` 轻，仍属于需要继续优化的信号。

`key` 与 `possible_keys` 不一致时，说明优化器认为另一个索引代价更低，这本身就是一个值得追查的信号。`key_len` 是判断联合索引用了几列的关键：`utf8mb4` 下 `varchar(50)` 可空列的完整长度为 `50 × 4 + 2 + 1 = 203` 字节，如果 `key_len` 只有 203 的若干分之一，说明只用到了前一两列，后面的条件没有走索引。只看 `key` 非空就断定索引生效，是最常见的误判。

`Extra` 中，`Using index` 表示覆盖索引，不需要回表；`Using index condition` 表示索引下推生效，条件下推到存储引擎层过滤；`Using where` 表示需要在取回行之后再做过滤；`Using filesort` 表示额外做了一次排序，排序字段没有利用索引顺序；`Using temporary` 表示使用了临时表，常见于 `group by`、`distinct` 无法利用索引的情况。

索引"失效"的典型原因，也是 `key` 为 `NULL` 或 `type` 退化时要对照排查的清单：在索引列上使用函数或表达式；发生隐式类型转换，例如字符串列与数字比较；`like` 以 `%` 开头；联合索引未遵循最左前缀；`or` 连接的条件中存在无索引列；列的选择性过低，优化器判断走索引不如全表扫。这些情况下索引并非不可用，而是优化器估算后放弃了它，需要改写 SQL 或调整索引设计，而不是"假装索引已经生效"。若需确认优化器的判断依据，可以临时打开 `optimizer_trace` 查看成本计算过程。

## Q10. 什么是主从同步？MySQL 如何实现？

主从同步是把主库上的数据变更复制到一个或多个从库，用于读写分离、备份和故障切换。MySQL 的实现基于 binlog 的中继式复制，分为三个步骤、三个线程：

```text
主库：事务提交 → 写 binlog
        │
        ├── dump thread 把 binlog 事件发给从库
        ▼
从库：IO thread 接收并写入 relay log
        │
        └── SQL thread 读取 relay log 并重放
```

主库的 `dump thread` 负责把 binlog 事件推送给从库；从库的 IO 线程接收后原样写入本地的 relay log，同时记录已拉取的位点；SQL 线程再按顺序读出 relay log 并在从库上重放，使数据逐步追上主库。这个结构决定了两个从库侧的关键点：IO 线程断开重连后从记录的位点续传，所以位点（或 GTID）的准确性直接决定复制的正确性；SQL 线程的重放速度决定从库延迟。

binlog 有三种格式：`STATEMENT` 记录原始 SQL，日志量小，但含 `now()`、`uuid()`、`limit` 无排序等不确定语义的语句会导致主从数据不一致；`ROW` 记录每行数据的变更前后镜像，最安全，日志量较大；`MIXED` 由 MySQL 自动在两者间切换。生产环境一般用 `ROW`。

按一致性强度，复制模式分三档：

- **异步复制**：默认模式，主库提交后立即返回，不等从库确认。性能最好，但主库宕机时尚未传出的 binlog 会丢失。
- **半同步复制**：主库等待至少一个从库确认收到 binlog（写入 relay log）后才向客户端返回提交成功。MySQL 5.5 引入，5.7 增加 `AFTER_COMMIT` 与无损复制（`rpl_semi_sync_master_wait_point=AFTER_SYNC`）的改进，减少了主库在等待期间崩溃导致的丢失窗口。它保证的是"至少一个从库收到了日志"，不是"从库已经应用"，因此仍不等同于强一致。
- **组复制（MGR）**：基于 Paxos 协议的多数派提交，事务在多数节点确认后才提交，能提供更强的一致性，代价是部署和运维复杂度明显上升。

GTID（全局事务标识）给每个事务分配全局唯一的编号，从库按 GTID 集合判断哪些事务已执行。它替代了基于文件名和位点的复制，主库切换、从库重建时不必再精确计算位点，也是 MySQL 8.0 推荐的复制方式。

主从延迟是异步链路的常态，根因通常是大事务（大批量 `UPDATE`、大表 `DDL` 让 SQL 线程长时间重放单条语句）、从库硬件弱于主库、并行复制未开启。MySQL 5.7 起支持基于 `LOGICAL_CLOCK` 的并行复制，让多个 worker 线程按组提交顺序并行重放；MySQL 8.0 增加了基于 `WRITESET` 的并行方式，冲突检测更细。延迟的观测不能只看 `Seconds_Behind_Master`，它反映的是 SQL 线程相对 IO 线程的进度，网络中断时会显示为 0 造成假象，用已执行 GTID 与主库 GTID 的差集更可靠。
