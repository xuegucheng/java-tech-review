# 真题记录

> 按「一套题」为单位保存的面试题集记录：**一题不删、一题不乱序**，能复用的答案只给跳转，不复制第二份。
> 与 [企业专项首页](../README.md) 的分工：那里放**跨时间成立的考察画像**，这里放**可溯源的具体题集**——画像会就地更新，题集会一直留着当时的顺序。

返回 [企业专项首页](../README.md) · [面试首页](../../README.md) · [仓库首页](../../../README.md)。

## 为什么要有这一层

[专题题库](../../01-专题题库/README.md) 按技术专题组织，一道题只能属于一个专题；但真实面试是**按公司成套出现**的。想在面试前完整过一遍「这家公司这一套题」，按专题翻会漏、会跳。

于是这一层只做一件事：**保持题集的原始形状**。同一道题在华为、腾讯、阿里的题集里各出现一次，各自保留一次；答案只在题集里第一次需要时写一次，其余全部链接过去。

> 题集标注的年份与公司来自**来源页面本身的标注**，不代表本仓库核实过每道题的真实出处。被截断的题目一律标为「整理标题」，不与原题混同。

## 命名与位置

```text
面试/02-企业专项/真题记录/
├── README.md                                  ← 本页：规范与索引
└── {年份}-{公司}-{岗位方向}-{题集特征}.md
```

- 文件名用中文语义名，年份只有**来源页面明确标注**时才写；写不出就省略年份，不要猜。
- 一个题集一个文件。**不要**按技术专题拆成多个文件——拆了就失去「整套复习」的意义。
- 题集横跨多个专题是常态，每题用一行元数据标注所属模块，不靠目录归类。

## 收录一套题的固定流程

以后拿到一张或多张截图，按这十步走，不跳步：

| 步骤 | 做什么 | 判据 |
| --- | --- | --- |
| 1 | 识别来源平台、页面标注的年份、公司、岗位、题集名称、题目总数 | 只写页面上真实可见的信息；URL 没给就写「未提供」，**不补全、不猜测** |
| 2 | 按截图原有顺序编号 Q01…Qn，不增不减不排序 | 题集数量必须与页面标注一致 |
| 3 | 逐题标注题干状态：`原题完整` / `原题部分截断` | 截断的题，标题是整理版，正文保留 `*原题可见部分：…*`，不能当作原题引用 |
| 4 | 为每题评 1～5 星，写在标题末尾 | 口径见「星级口径」；禁止整套题一律五星 |
| 5 | 标注所属模块 | 对齐 [专题题库](../../01-专题题库/README.md) 的分类名 |
| 6 | 扫描全部专题题库与知识层，判断是否已有**语义相同且回答完整**的答案 | 判定规则见「去重四档」 |
| 7 | 重复题：只留标题、元数据行、核心答案与延伸阅读，**不复制正文** | 核心答案指向该题的**独立答案文件**；跨文件不追加 `#anchor`。规则见「链接兼容」 |
| 8 | 新题：先把标准答案写进专题题库，题集里只留入口 | 见「新增答案写在哪」；该题若还在长文件里，顺手独立成文件；企业题集不承担技术原理 |
| 9 | 建立双向关联 | 题集 → 独立答案文件 / 知识层；企业画像页 → 题集 |
| 10 | 校验：链接可达、统计与正文一致、题号连续 | 跑 `python scripts/check_markdown.py` 与 `python scripts/check_text_sanity.py`；核心答案不得指向专题总文件，跨文件链接不得带 `#` |

## 题集格式（固定版式）

所有题集都用这一版式，不另创变体。目的是「扫一眼就能找到答案」，而不是留一份审计记录。

### 文件头

```markdown
# 2025 华为通用软件 Java 高频面试题

> 来源：牛客网 · 10 道题（已有答案 8 · 新增答案 2）· 收录于 2026-10-19
> 页面标注：2025 年 · 华为 · 通用软件 Java。来源链接未提供（截图导入）。
> Q02、Q03 的题干在截图中被截断，标题为整理版；每题保留截图可见原文。

## 题目导航

| 编号 | 题目 | 重要程度 | 答案状态 |
| --- | --- | --- | --- |
| [Q01](#q01--与-equals-的区别-) | == 与 equals() 的区别 | ⭐⭐⭐⭐ | 已有答案 |
```

导航表的题目文字必须与正文标题（去掉星级）**逐字一致**，编号列跳到对应题目；表里只放复习要用的四列，不塞说明文字。

### 单题

```markdown
### Q03. ThreadLocal 的用法和实现原理 ⭐⭐⭐⭐⭐

> **并发编程** · 已有答案 · 原题部分截断

**核心答案：**
[ThreadLocal 原理与内存泄漏](真实路径)

**延伸阅读：**
- [Q06 · 内存泄漏与线程池数据串味](真实路径)

*原题可见部分：ThreadLocal 的用法和实现原…*
```

| 位置 | 规则 |
| --- | --- |
| 标题 | `### QXX. 题目 ⭐⭐⭐⭐⭐`：编号两位、星级在**末尾**、连续 `⭐`（不用 `★ ★ ★ ★ ★`）、1～5 颗 |
| 元数据 | 一行引用块 `**模块** · 答案状态 · 原题状态`；不再单列「状态：」「所属模块：」多行 |
| 核心答案 | 只放**一个**最能完整覆盖题干的入口；链接文字用「Q 号 · 短标题」，不贴长路径 |
| 延伸阅读 | 0～2 条相关知识点；需要 3 条以上说明该题应拆题或答案该补全，而不是堆链接 |
| 原题 | 原文完整的题**不重复抄题干**；截断的题保留 `*原题可见部分：…*`，禁止补全不可见部分 |
| 分隔 | 题与题之间用 `---`，前后各留一个空行；不额外加空节或装饰 |
| 小标题 | 只用 `####` 或加粗，同一篇内不混用 |

正文不粘贴答案全文、不写「覆盖判定」这类审计段落——需要解释「为什么算重复」时，写进提交说明或本页，不写进题集。

### 精确跳转是强制要求

企业真题的**核心答案必须指向该题自己的独立 Markdown 文件**，点一次就落到答案正文第一屏。

「链接能打开 `Java基础.md` 这个专题文件」不算通过——读者还得在几百行里翻到 Q 号，等于没跳转。

### 答案文件的组织方式

专题题目**按需**独立成文件，原专题文件退化为索引：

```text
面试/01-专题题库/
├── Java基础.md              ← 索引：编号 + 兼容入口
├── Java基础/
│   ├── Q02-equals与hashCode.md
│   └── Q09-等号与equals.md
├── JVM.md
└── JVM/
    ├── Q09-JVM内存区域.md
    └── Q18-垃圾回收算法.md
```

独立文件的结构固定，不另创变体：

| 位置 | 内容 |
| --- | --- |
| 第 1 行 | `# QXX. 题目` —— 进来第一眼就是题干 |
| 第 3 行 | `> 专题名 · P0 · 高频`，一行元数据，不放背景说明 |
| 正文 | 原样搬移：30 秒回答 → 深入理解 → 追问 → 工程场景 → 易错点 → 权威内容 |
| 末尾 | `---` + 返回专题与专题题库首页的链接 |

原专题里对应的位置**不删标题**，改成一行兼容入口：

```markdown
### Q09：`==` 和 equals 的区别？ `P0` `高频`

完整标准答案已独立成页：[Q09 · == 和 equals 的区别](Java基础/Q09-等号与equals.md)
```

标题文本一个字都不改，所以旧锚点仍然解析得到、旧深链接落在这个入口上，编号也保持连续。

### 链接兼容

| 场景 | 写法 |
| --- | --- |
| 企业题集指向答案 | 直接指向独立文件：`[Q09 · == 与 equals 的区别](../../01-专题题库/Java基础/Q09-等号与equals.md)` |
| 专题导航表指向已独立题目 | 编号列改成链接，目标是 `Java基础/Q09-等号与equals.md`——按**专题文件自身目录**解析 |
| 专题文件内的同文件导航 | 继续用 `#anchor`（同文件链路正常） |
| 任何跨文件链接 | **一律不加 `#anchor`** |

跨文件加锚点在 IDEA 预览里会直接弹「找不到要导航到的标头」。这不是锚点拼错：GitHub 与 IDEA 生成的标题锚点在本仓库全部标题上逐字一致（含星级产生的尾随 `-`、连续 `--` 不合并）；真正的原因是 IDEA 跨文件跳转走 `HeaderAnchorIndex` 的 StubIndex 查询，取不到索引就报错，属 JetBrains 侧缺陷（IJPL-258256 / IJPL-243759 一类）。独立文件的第一屏本身就是答案，所以不再需要靠锚点定位。

**不要**用 HTML `<a id="...">` 手动补锚点来绕过：GitHub 会剥离或转义，IDEA 预览也不保证支持，两边都不稳。

### 按需拆分（不要一次全拆）

只有当某道题**第一次被企业真题引用、且仍与其他题共用一个长文件**时，才把它拆成独立文件。

- 已有完整独立文章（如 `03-并发编程/02-深度解析/ThreadLocal原理与内存泄漏.md`）直接复用，不复制一份；
- 没被引用到的题目保持现状，不为「将来可能用到」提前建文件；
- 拆分不改变题量：182 道题拆成 182 个文件也还是 182 道题，别把文件数统计成新增题。

### 保持唯一答案

同一个 Q 号只能有一份完整答案：独立文件是唯一副本，原专题只留标题与入口，企业题集只留入口——任何一处都不复制答案正文。

### 新增答案写在哪

题目进企业题集，**标准答案进专题题库**：

1. 先扫专题题库与知识层，判断是否已有语义相同且完整的答案（见「去重四档」）；有则直接复用它的独立文件；
2. 没有则在对应专题追加下一号，编号接续，**不改既有编号、不重排**；
3. 若该专题仍是「多题共用一个长文件」，新题直接写成独立文件（`QXX-短标题.md`），并在专题导航表里链接过去；
4. 同步更新专题导航表与 [专题题库首页](../../01-专题题库/README.md)、[面试首页](../../README.md) 的题量统计——**按题号计数，不按文件计数**；
5. 企业题集里留「核心答案」入口指向该独立文件，答案状态写「新增答案」。

这样第二家公司问到同一道题时直接链接同一处，不会出现两份需要同步维护的技术答案。

### 未来维护成本

这套结构不引入数据库、后台系统或爬虫。加一套新题集的完整动作就是：读本页 → 按上面的版式写一个 md → 把每道题的核心答案指向它的独立文件 → 跑两个校验脚本 → 提交。

## 去重四档（这是全套规范里最容易做错的地方）

题目**不去重**，答案**去重**：同一个知识点在 10 家公司的题集里出现，就保留 10 条题目记录，只维护 1 份答案。判断「算不算重复」按下面四档，不要只看技术名词：

| 档位 | 情形 | 处理 |
| --- | --- | --- |
| 1 | 字面相同 | 直接复用 |
| 2 | 表达不同但考察点与回答范围相同 | 复用 |
| 3 | 部分重合，但有独立的追问要求 | **不能**标为完整重复：补写缺的那一段，其余链接过去 |
| 4 | 已有答案不完整 | 先补全权威位置，再建立关联；不要制造第二份半成品 |

反面例子（都真实存在于这类题集里）：

- 「ThreadLocal 的实现原理」与「ThreadLocal 为什么会内存泄漏」——关联紧密但考察点不同，不能直接合并。
- 「JVM 内存模型」与「Java 内存模型 JMM」——前者是运行时数据区，后者是并发语义，**混淆是硬伤**。
- 「AOP 的理解」与「JDK 代理和 CGLIB 的区别」——后者是实现细节，前者是概念与织入时机。

## 星级口径

以 **5 年以上 Java 后端岗位的面试价值**判断，不看题目长短：

| 星级 | 含义 | 标准 |
| --- | --- | --- |
| ⭐⭐⭐⭐⭐ | 核心高频，必须能口述并扛住深入追问 | 答不出会直接影响评价 |
| ⭐⭐⭐⭐ | 重要题，要掌握原理与常见延伸 | 答得出结论，追问会掉一层 |
| ⭐⭐⭐ | 中等，能解释和应用即可 | 出现频率不高或深度有限 |
| ⭐⭐ | 低频或特定场景 | 知道方向即可 |
| ⭐ | 了解即可 | 不必准备 |

一套题里五星占比通常不应超过一半；如果超过了，说明评的是「这道题难」而不是「这道题值钱」。

## 边界（不要越界）

- **不爬网页、不调接口、不做 OCR**：截图由人提供，识别由人校对。没有原始页面就不写原始链接。
- **不复制他人题解**：截图里其他用户的回答只当线索，正文一律自己写。
- **不改写已有技术结论**：复用前先判断对不对；发现错误单独记录并做最小修复，不顺手重写整篇。
- **不为架构而建目录**：只有出现第二个题集时才有必要扩表，不要预建空公司目录。
- **不虚构**：题干、追问、来源链接、项目经历，缺什么就标「未提供」。

## 加一套新题集

1. 按上面十步整理成一个文件，放在本目录；
2. 在「已有题集」表里加一行；
3. 如果是新公司，在 [企业专项首页](../README.md) 的公司表里补入口；
4. 如果发现某道题在专题题库里没有权威答案、且**大概率会被别的公司重复问到**，把它补进 [专题题库](../../01-专题题库/README.md) 对应专题，本页改为链接——**同一份完整答案只维护一次**。
