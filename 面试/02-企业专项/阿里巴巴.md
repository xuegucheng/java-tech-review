## 考察权重分布

以下为公开面经中出现频率的相对印象，用于分配复习时间：

| 技术块 | 相对权重 | 典型深度 | 复习优先级 |
| --- | --- | --- | --- |
| Java 基础与对象模型 | 高 | L3～L5 | 必答，不能停在 L1 |
| 并发与 JUC | 高 | L3～L5 | 必答，追问链最长 |
| JVM 与性能 | 高 | L3～L4 | 必答，偏好结合线上症状问 |
| 项目深挖 | 高 | L4～L5 | 决定二面走向 |
| 框架与中间件（Spring / 分布式） | 高 | L2～L4 | 答得出原理即可，不追求源码级 |
| 数据库与缓存 | 中 | L2～L3 | 索引与事务边界要清楚 |
| 算法 | 中 | — | 中等题为主，不卡时限 |

**准备策略**：把精力放在「解释设计动机」上。能说出「这样做是为了解决什么问题、代价是什么」，比多背两个字段名更有用。

## 追问链示例

### 例一：从 HashMap 追到设计哲学

```text
面试官：HashMap 的容量为什么必须是 2 的幂？
你（L1）：因为计算下标用位运算更快。
面试官：具体快在哪？
你（L2）：index = hash & (n - 1)，等价于对 n 取模，但位运算比取模快。
面试官：那只解释了一半。如果只是快，为什么要"必须"，而不是"尽量"？
你（L3）：因为扩容时元素的新位置依赖这个性质——容量翻倍后，
        元素要么留在原位，要么移动到"原位置 + 旧容量"，
        这正好是 hash 的倒数第二位决定的。不是 2 的幂，这个规律不成立，
        扩容就得对每个元素重新计算 hash 和对容量取模。
面试官：那如果我在构造时传了 17 会怎样？
你（L4）：tableSizeFor 会向上取整到 32，实际容量仍然是 2 的幂。
        这也是为什么别传奇数容量，没有意义。
面试官：JDK 7 扩容时的头插法在并发下会怎样？
你（L5）：可能形成环形链表导致 get 死循环。JDK 8 改成尾插避免了环，
        但并发写仍然会丢数据；需要并发就用 ConcurrentHashMap。
```

**这道题在考什么**：不是记忆容量值，而是「设计约束如何互相咬合」。能答到 L3 就超过了大多数人。

权威内容：[HashMap 原理与源码分析](../../02-集合框架/02-深度解析/HashMap原理与源码分析.md) · [ConcurrentHashMap 并发容器](../../03-并发编程/02-深度解析/ConcurrentHashMap并发容器.md)

### 例二：从线程池追到容量评估

```text
面试官：线程池的核心线程数你怎么定？
你（L1）：CPU 密集型设成核数 + 1，IO 密集型设成核数 × 2。
面试官：这个公式在你们线上是什么值？
你（L2）：我们是 8 核，按 IO 密集型设的核心 16、最大 32。
面试官：实际跑下来队列积压过吗？为什么是 32 不是 64？
你（L3）：积压过。后来发现瓶颈不在线程数，而在下游数据库连接池只给了 20，
        线程再加也是排队，所以把最大线程数压到 24 并加了队列监控。
面试官：那你怎么发现是数据库连接池的瓶颈？
你（L4）：看线程 dump 发现大量线程卡在获取连接上，同时连接池的
        等待指标在涨，而不是 CPU 跑满。
面试官：如果下游是老系统，加不了连接池，还有别的办法吗？
你（L5）：在该调用外面做限流或者降级，把压力挡在入口，
        同时用批量查询减少连接占用次数。
```

**这道题在考什么**：公式人人会背，面试官真正想看的是**你有没有真实的容量判断经验**。答「书上说是核数 × 2」和答「我们试过，瓶颈其实在下游」是两个层次。

权威内容：[ThreadPoolExecutor 线程池](../../03-并发编程/02-深度解析/ThreadPoolExecutor线程池.md)

### 例三：从 Spring 循环依赖追到设计取舍

```text
面试官：Spring 怎么解决循环依赖？
你（L1）：用三级缓存。
面试官：三级缓存分别存什么？为什么需要第三级？
你（L2）：一级存完整 bean，二级存早期引用，三级存可以生成早期引用的工厂。
面试官：二级缓存就能存早期引用，为什么要再绕一层工厂？
你（L3）：为了在需要时才决定是否生成代理对象。如果只有二级缓存，
        那就得在暴露引用的那一刻就决定要不要 AOP 代理，
        这会提前触发代理逻辑，破坏 bean 的生命周期。
面试官：那构造器注入的循环依赖能解决吗？
你（L4）：不能。因为对象还没构造出来，无法提前暴露引用，
        Spring 会直接抛异常。这也是建议用 setter 或字段注入的原因之一——
        不过更本质的解法是重新审视依赖方向。
```

**这道题在考什么**：L3 是分水岭。多数人能背出「三级缓存」三个字，但说不出「为什么不能是二级」。

权威内容：Spring 相关机制当前尚未在仓库建设，可参考 Spring 官方文档中关于循环依赖的解释。

## 高频失分点

| 失分点 | 表现 | 怎么改 |
| --- | --- | --- |
| 只答结论不答动机 | 问「为什么」时重复结论 | 每个结论后面准备一句「为了解决 X，代价是 Y」 |
| 项目经不起追问 | 说用了某技术，说不出为什么和效果 | 简历上每个技术点准备一条「问题→方案→数据」的线 |
| 不懂装懂 | 猜一个听起来合理的答案 | 直接说「这块我只是了解概念，没在生产用过」，然后讲你会的相邻部分 |
| 把八股当结论 | 答「书上说……」 | 换成「在我遇到的场景里，验证下来是……」 |
| 忽略量级 | 讲方案不讲规模 | 主动给出 QPS、数据量、机器数等约束 |

## 一句话准备建议

阿里面试的胜负手不在「知道多少」，而在**你能不能把知道的讲清楚、讲到底、讲出取舍**。练法是每题都追问自己三遍「为什么」，追问到答不上为止，那里就是你该补的地方。
