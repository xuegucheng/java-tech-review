## 追问链示例

### 例一：从防超卖追到全局设计

```text
面试官：大促怎么防止超卖？
你（L1）：用 Redis 扣减库存，扣减成功才下单。
面试官：Redis 扣减就万无一失了吗？
你（L2）：不是。Redis 可能丢数据，而且扣减成功不代表订单一定创建成功，
        中间失败库存就少卖了，所以需要回补或者对账。
面试官：那数据库那一层还扣不扣？
你（L3）：要扣，但可以异步。最终以数据库为准做对账，
        Redis 只是挡在前面的第一道闸。
面试官：如果 Redis 和数据库对不上怎么办？
你（L4）：定时对账，以数据库的实际扣减记录为准，
        把 Redis 库存拉回正确值。对账要能定位到具体订单，
        否则只能全量重置，那会放大误差。
面试官：极端情况，Redis 集群故障，前门全丢了，会发生什么？
你（L5）：会直接打穿到数据库。所以要么数据库层保留了
        条件更新（UPDATE ... WHERE stock >= n）作为最后一道防线，
        要么在入口限流把流量压到数据库能承受的水平。
        单靠 Redis 一层，本身就是设计缺陷。
```

**这道题在考什么**：京东的场景题会一直追到「你的方案在故障时会怎样」。**只讲正常流程的方案会被认为没做过线上。**

权威内容：[场景设计题](../04-场景设计题/README.md)

### 例二：从幂等追到实现细节

```text
面试官：支付回调怎么做幂等？
你（L1）：用订单号做唯一索引，插入冲突就认为重复了。
面试官：如果回调是并发进来的呢？
你（L2）：唯一索引本身能挡住，数据库会保证只有一个成功，
        另一个抛异常，捕获后按已处理返回。
面试官：那如果业务逻辑不只是插入，还要改订单状态呢？
你（L3）：那就用状态机。只允许从「待支付」流转到「已支付」，
        用条件更新 UPDATE ... WHERE status = '待支付'，
        受影响行数为 0 就说明已经处理过了。
面试官：为什么推荐状态机而不是加锁？
你（L4）：加锁只能保证同一时刻不并发，但如果同一个请求
        重试两次间隔很久，锁已经释放了，还是会重复处理。
        状态机是把幂等性编码进业务状态里，不依赖时序。
面试官：还有别的思路吗？
你（L5）：可以在入口用一个去重表，用业务唯一键加过期时间，
        先占位再处理，适合非状态流转类的接口。
```

**这道题在考什么**：幂等是京东的高频题，**关键区分点是「并发重试」和「延迟重试」**，很多人只考虑了前者。

权威内容：分布式幂等方案当前尚未在仓库建设，可参考对应中间件官方文档。

### 例三：从事务失效追到生效条件

```text
面试官：Spring 事务什么情况下会失效？
你（L1）：方法不是 public、自调用、异常被吞了。
面试官：为什么自调用会失效？
你（L2）：因为事务是通过代理对象增强的，自调用走的是 this，
        没经过代理，自然没有事务逻辑。
面试官：还有别的情况吗？
你（L3）：异常类型不对也会失效。默认只对 RuntimeException
        和 Error 回滚，抛受检异常不会回滚，需要显式配置。
        另外事务传播行为设成 NOT_SUPPORTED 之类也会失效。
面试官：如果数据库引擎不支持事务呢？
你（L4）：那事务注解完全没有效果，比如 MyISAM。
        这类问题一般发生在建表时选错引擎。
面试官：怎么排查事务到底有没有生效？
你（L5）：先看是否是代理调用，再看异常类型和传播行为，
        最后确认引擎和连接是否在同一个事务里。
        实际排查时打日志看开启和提交时机最直接。
```

**这道题在考什么**：事务失效是「一答就停」的典型题目，**列出五种失效场景才算及格**。

权威内容：Spring 事务机制当前尚未在仓库建设，可参考 Spring 官方文档的事务章节。

## 高频失分点

| 失分点 | 表现 | 怎么改 |
| --- | --- | --- |
| 方案只顾正常流程 | 被问「故障时怎样」就卡住 | 每个方案准备一句「它挂了会怎样、兜底是什么」 |
| 不会估算量级 | 说不出 QPS、库存规模 | 提前给方案配一组数字 |
| 中间件只会用不会讲 | 用 MQ 但说不清可靠性保证 | 至少掌握丢失、重复、积压三个问题 |
| 幂等只想到一种方案 | 只会唯一索引 | 准备唯一键、状态机、去重表三类 |
| 稳定性方案太理想 | 上来就讲完美闭环 | 承认限制，讲清代价和取舍 |

## 一句话准备建议

京东的题几乎都能还原成一句话：**「大促时你的系统会怎么表现，你怎么知道，坏了怎么救」**。准备时给每个技术点都挂上一个业务场景，答题时从场景切入，比直接背原理更贴合这里的节奏。
