## 追问链示例

### 例一：阈值类问题的完整追问

```text
面试官：HashMap 树化阈值为什么是 8？
你（L1）：因为链表长度到 8 时查询性能开始明显下降。
面试官：为什么恰好是 8？7 或者 9 不行吗？
你（L2）：源码注释里提到，理想哈希下链表长度服从泊松分布，
        长度到 8 的概率大概是千万分之六，属于极小概率事件。
        也就是说正常使用几乎不会树化，只有哈希被严重攻击
        或分布极差时才会走到。
面试官：那为什么退化阈值是 6，不是 7？
你（L3）：留一个缓冲区。如果树化和退化都用 8，
        在长度 8 附近反复增删会导致红黑树和链表之间来回转换，
        转换本身有开销。6 和 8 之间隔了一个值，避免抖动。
面试官：除了长度，树化还有别的条件吗？
你（L4）：还有最小容量 64。如果数组容量小于 64，
        优先扩容而不是树化——因为容量小的时候冲突多
        是容量不够导致的，扩容比树化更划算。
面试官：树化之后如果再插入元素，结构怎么变？
你（L5）：红黑树节点变成 TreeNode，同时保留了 next 指针，
        所以树上仍然维持一条链表，退化时可以按链表顺序还原。
```

**这道题在考什么**：任何一个「为什么是这个数」背后都有一个成本权衡。美团特别爱问这类问题，因为**答得出推导过程的人，通常也能自己设计阈值**。

权威内容：[HashMap 原理与源码分析](../../02-集合框架/02-深度解析/HashMap原理与源码分析.md)

### 例二：从线程池追到线上可观测性

```text
面试官：线程池的参数上线后能改吗？
你（L1）：不能，改了要重启。
面试官：确实 ThreadPoolExecutor 提供了 setCorePoolSize 之类的方法，
        为什么实际很少用？
你（L2）：因为参数变更的时机不好控制，正在执行的任务会受影响，
        而且改了之后没有回滚机制。
面试官：那你们线上怎么应对流量波动？
你（L3）：先做容量评估，把核心参数定在一档，然后加队列水位和
        拒绝计数的监控，超阈值告警。真要动态调整，
        也是走配置中心加人工确认，不做自动调参。
面试官：监控里你最先看哪个指标？
你（L4）：队列长度和活跃线程数的组合。如果活跃线程已满而队列在涨，
        说明处理不过来；如果活跃线程没满但队列在涨，
        说明核心线程数或任务粒度有问题。
面试官：如果是后者，你怎么进一步定位？
你（L5）：拉线程 dump 看线程都卡在哪，通常是某个外部依赖变慢，
        这时候调线程数没用，得治那个依赖。
```

**这道题在考什么**：美团重视「上线之后怎么办」。**能讲清监控指标和排障路径，比会背参数公式更能说明你真跑过线上。**

权威内容：[ThreadPoolExecutor 线程池](../../03-并发编程/02-深度解析/ThreadPoolExecutor线程池.md)

### 例三：数据库从索引追到执行计划

```text
面试官：为什么给字段加了索引还是不生效？
你（L1）：可能是违反最左前缀，或者对索引列做了函数运算。
面试官：还有吗？
你（L2）：类型隐式转换也会失效，比如字符串字段传了数字；
        还有以通配符开头的 LIKE、OR 连接非索引列、
        以及优化器判断全表扫描更快的情况。
面试官：联合索引 (a, b, c)，where a = 1 and c = 3 用得上索引吗？
你（L3）：用得上，但只能用到 a 这一列。c 因为中间断了 b，
        只能作为回表后的过滤条件，不能靠索引定位。
面试官：那如果我写成 where a = 1 and b > 2 and c = 3 呢？
你（L4）：a 和 b 能用索引，b 是范围查询，范围之后的 c
        同样只能过滤不能定位。这也是把等值条件放前面、
        范围条件放后面的原因。
面试官：怎么确认优化器实际用了什么？
你（L5）：看 explain 的 key 和 rows，重点看 type 是不是 range/ref，
        Extra 里有没有 Using filesort 或 Using temporary。
```

**这道题在考什么**：索引问题的失分点几乎都在「只知道最左前缀」这一层。**要把索引当成有序结构去想，而不是当成规则去背。**

权威内容：MySQL 索引与执行计划当前尚未在仓库建设，可参考 MySQL 官方文档的优化章节。

## 高频失分点

| 失分点 | 表现 | 怎么改 |
| --- | --- | --- |
| 阈值只记数字 | 说不出 8、6、0.75、64 的来历 | 每个阈值准备一句「怎么算出来的」 |
| 参数只背公式 | 问线上实际值就卡住 | 结合自己项目准备一组真实参数和依据 |
| 索引只背规则 | 追问联合索引顺序就乱 | 用「有序结构」的思路重新理解索引 |
| 不谈监控 | 方案讲完没有观测手段 | 每个方案补一句「怎么知道它出问题了」 |
| 场景题缺少量级 | 讲方案不给数字 | 主动补 QPS、数据量、机器规模 |

## 一句话准备建议

美团偏爱**能推导、能落地、能观测**的答案。复习时给每个结论都补一句「这个值/这个方案是怎么定的」，以及「上线后怎么发现问题」——这两句话往往就是拉开差距的地方。
