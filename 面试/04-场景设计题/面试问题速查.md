### 1. 设计一个秒杀系统，从入口到落库怎么设计？ `高频` `重点`

**一句话**：核心不是「服务全部流量」，而是用最便宜的层快速拒掉注定失败的请求——假设 100 万人抢 1000 件，99.9% 的请求应该在到达应用层之前就被拒掉。

**细节**：链路分层是 CDN 静态化挡住页面渲染 → 接入层按 IP／用户／设备限流防刷 → 应用层读本地「售罄标记」直接短路 → Redis 用 Lua 脚本把「读库存、判断、扣减」做成一个原子操作 → 只有扣减成功的才投递消息队列 → 订单服务异步落库并用条件更新兜底 → 定时对账。量级：假设 10 秒内打进来 100 万请求即 10 万 QPS，单机压测 2000 QPS 就需要约 50 台，而真正扣减成功的只有 1000 次，所以闸门必须放在最外面。代价：前端只能返回「排队中」，用户改成轮询拿结果，并且要多维护一套对账机制。故障表现：Redis 挂掉时请求会穿透到数据库，只能靠入口限流把流量压到数据库能承受的量级，此时吞吐骤降但不超卖。

**为什么这样设计**：因为「不超卖」和「扛住峰值」不该由同一个组件解决——正确性交给数据库条件更新这最后一道防线（少卖可以接受，超卖必须为零），吞吐交给前置拒绝。若直接用 `SELECT ... FOR UPDATE` 行锁扣库存，并发一上来锁等待剧增，吞吐可能只有几百 TPS。

> 权威内容：[秒杀与库存扣减](秒杀与库存扣减.md)

### 2. 大促时怎么防止超卖？ `高频` `重点`

**一句话**：防超卖是三道闸叠加，Redis 原子预扣挡掉绝大部分无效请求，数据库条件更新做最终防线，对账任务兜底补偿，任何一道都不能单独承担。

**细节**：Redis 侧用 Lua 脚本把「读库存、比较、扣减」合成一次调用，Redis 单线程执行不会被打断，所以不能用「先 GET 再 DECRBY」两步，中间会被其他请求插入。数据库侧必须用条件更新 `UPDATE stock SET count = count - 1 WHERE count >= 1`，看影响行数判断是否扣成功，而不是先查后改。量级：假设单节点 Lua 脚本在 1 万至 2 万 QPS 量级，数据库条件更新在几百到几千 TPS，两者差一个数量级，所以不能让数据库参与实时判断。代价：Redis 与数据库之间必然存在短暂不一致窗口，需要定时对账；对账发现不一致时只告警加人工介入，不做自动「修正」以免放大错误。

**为什么这样设计**：默认选「宁少卖不超卖」。实物商品超卖要赔付和道歉，虚拟券超卖直接是资损，而少卖可以事后补库存再卖，代价明显更小。

> 权威内容：[秒杀与库存扣减](秒杀与库存扣减.md)；乐观更新与重试的原理见 [CAS 与原子类](../../03-并发编程/02-深度解析/CAS与原子类.md)

### 3. 怎么保证接口幂等？ `高频` `重点`

**一句话**：幂等要把「这一次请求已经处理过」持久化下来，而不是依赖时序——加锁只能解决并发重复，解决不了延迟重试。

**细节**：三种主流方案各管一类场景：业务唯一键加唯一索引，适用创建类接口，捕获唯一键冲突后返回已存在的那条记录而不是报错；状态机条件更新 `WHERE status = '待支付'`，适用状态流转类，靠影响行数判断；去重表或 Token 先占位再处理，通用但多一次存储读写。量级：假设日均 1000 万次写请求、去重记录保留 7 天，去重表就是 7 亿行量级，必须带过期时间或按时间分区归档，否则去重表自己会先变成瓶颈。故障表现：唯一索引方案在数据库不可用时无法兜底，会直接把重复请求放到业务层，所以入口的 Token 校验和业务侧的唯一约束通常要同时存在。

> 权威内容：[缓存一致性与幂等](缓存一致性与幂等.md)

### 4. 你的系统 QPS 上限是多少，怎么算出来的？ `高频` `重点`

**一句话**：QPS 上限不是拍出来的，是先算单机容量再乘以实例数，并且必须能指出真正的瓶颈压在哪一层。

**细节**：推导链是日均请求数除以 86400 得到均值，再乘峰值系数（通常是均值的 3 到 10 倍）得到峰值 QPS；单机容量用压测拿，假设单机压测 2000 QPS，100 台实例理论上是 20 万 QPS，但真实上限往往被下游先卡住——数据库连接池大小、Redis 连接数、某条慢 SQL，而连接数近似等于 QPS 乘平均响应时间。报数字时要连带说明压测条件：数据量级、读写比、看的是均值还是 P99。代价：压测环境和生产的数据分布不同，这个上限只能当参考线，扩容前要先用生产流量验证。

> 权威内容：容量估算与压测当前尚未在仓库建设，可参考《SRE：Google 运维解密》中「处理过载」一章。

### 5. 接口限流怎么做，阈值怎么定？ `高频` `重点`

**一句话**：限流要回答「在哪一层限、按什么维度限」，而阈值只能从压测出的单机容量反推，不能从「我们想要多少」正推。

**细节**：分层上，接入层做粗粒度全局限流，应用层做用户或接口维度的细粒度限流，最外层再按 IP 和设备挡刷子。算法上，固定窗口计数器有临界问题，令牌桶允许突发（桶容量就是突发额度），漏桶把突发削平。分布式限流常用 Redis 加 Lua 保证计数原子，但每个请求都打一次 Redis 会让限流器自己变成瓶颈，所以更常用「本机分片配额」：把全局阈值按实例数均分，各实例只用本地令牌桶，只在明显异常时回源校正。量级：假设全局阈值 10 万 QPS、100 台实例，单机配额就是 1000 QPS，本地桶足够。代价：配额均分意味着实例数变化或流量不均时会出现部分实例被打满而其他实例空闲，必须留冗余或定期重平衡。故障表现：限流依赖的 Redis 挂掉时要提前定好默认策略，直接放行会雪崩、直接拒绝等于全站不可用，通常降级为本地限流并放行。

**为什么这样设计**：限流的目的是保护下游而不是惩罚用户，阈值定得高于真实容量等于没限，定得太低会误伤正常流量，所以顺序必须是「先知道容量，再定阈值」。

> 权威内容：接口限流当前尚未在仓库建设，可参考 Nginx 官方文档中 limit_req 模块的说明。

### 6. 缓存和数据库怎么保持一致？ `高频` `重点`

**一句话**：优先选 Cache Aside——先更新数据库、再删除缓存；是删除而不是更新，因为删除无论重复几次结果都一样，而更新缓存在并发下可能把旧值覆盖回去。

**细节**：四种策略的结论是：先更新数据库再更新缓存不推荐，两个写请求的更新顺序可能与数据库相反；先删缓存再更新数据库不推荐，删除之后、更新之前来的读请求会把旧值回填；先更新数据库再删缓存推荐，不一致窗口最小；订阅 binlog 更新缓存适合对顺序敏感的多级缓存，代价是引入延迟。前提判断是——缓存数据能从数据库重算出来，就只需要删，不需要更新。量级：假设读请求 10 万 QPS、命中率 95%，回源只有 5000 QPS，所以缓存的核心指标是命中率而不是容量。故障表现：删除缓存失败要重试加消息补偿；穿透用空值缓存加布隆过滤器；击穿用互斥锁重建加热点 key 不过期；雪崩用过期时间加随机扰动。

**为什么这样设计**：过期时间是最后一道兜底，它保证即使所有主动失效逻辑都失败，数据最终也会自愈，别为了「更高命中率」把它去掉。

> 权威内容：[缓存一致性与幂等](缓存一致性与幂等.md)

### 7. 服务雪崩怎么防？ `高频` `重点`

**一句话**：雪崩是「一个下游变慢，把上游线程池占满，再逐级把整条链路拖死」，所以核心是让每次调用都有超时、隔离和熔断，使故障止步于一个格子。

**细节**：四个手段配齐：超时时间必须小于上游超时并逐层递减；线程池或信号量隔离，每个下游用独立线程池，一个下游占满不会吃掉全部线程；熔断按错误率或慢调用比例触发，超阈值就快速失败一段时间，给下游恢复窗口；降级返回缓存值、默认值或「稍后重试」。量级：假设某下游 P99 从 50 毫秒恶化到 3 秒，上游 200 个工作线程能支撑的 QPS 就从 4000 掉到约 66，几秒内线程池排满。代价：隔离会牺牲一部分线程利用率，熔断阈值定得太灵敏会误熔断正常流量，降级意味着用户看到的是不完整结果。故障表现：熔断打开后该功能快速失败而主链路仍可用；不做降级的话错误会向上传播成整体 5xx。

**为什么这样设计**：因为上游能不能扛住，取决于它自己消耗了多少等待时间，而不是下游有多慢。把等待时间用超时截断、用隔离限制范围，才是可计算的控制方式。

> 权威内容：服务雪崩与熔断降级当前尚未在仓库建设，可参考 Resilience4j 官方文档中 CircuitBreaker 与 Bulkhead 的说明。

### 8. 热点数据怎么处理？ `中频` `重点`

**一句话**：热点要先分清是读热点还是写热点，前者靠分散读取，后者只能靠拆写路径，两者的解法不能互换。

**细节**：读热点（某个 key 被集中读）靠本地缓存挡一层，或把 key 复制成 N 份副本落在不同 Redis 节点、请求按随机数选副本。写热点（某一行被集中更新）单行条件更新必然串行，只能拆：把库存拆成 N 个分片桶，请求按用户哈希落桶，扣减分散到各桶，判断总量时再汇总。量级：假设单节点 Lua 脚本 1 到 2 万 QPS，某个 key 被打到 5 万 QPS 就必须拆副本或加本地缓存，否则该节点成为单点。代价：副本之间会有短暂不一致，只适用于允许最终一致的场景；分桶会让「剩余量」变成近似值，展示口径要提前和产品对齐。故障表现：热点 key 所在的单个 Redis 节点过载时，整节点上的其他 key 一起受影响，所以热点隔离要按节点维度预留余量。

**为什么这样设计**：热点 key 的根因是「所有请求都算出了同一个位置」，不修改路由规则、只在前面加缓存，只能缓解读热点，写热点永远解决不了。

> 权威内容：热点数据处理当前尚未在仓库建设，可参考 Redis 官方文档中集群与 hot key 相关章节。

### 9. 商品详情页怎么支撑大流量？ `中频` `重点`

**一句话**：详情页是典型的读多写少，把页面拆成静态和动态两部分，静态部分全量静态化推到 CDN，动态部分拆成小接口异步拉取并逐级缓存。

**细节**：分层：CDN 承载静态 HTML 与图片；接入层只做路由和限流，不再拼装页面；应用层提供价格、库存、促销等若干小接口，各自走本地缓存加 Redis 的多级缓存；库存这类高频变化字段不和页面绑定，前端异步拉、允许短暂延迟。量级：假设详情页 10 万 QPS，静态化后约 95% 由 CDN 直接返回，真正落到应用层的小接口请求只有 5000 QPS 左右，压力差两个数量级。代价：页面静态化意味着改版要重新发布，动态接口增多会让前端多几次往返、首屏体验略降。故障表现：CDN 回源异常时应用层要用旧版本页面兜底；库存接口挂掉时前端要展示「暂时无法获取」而不是沿用错误的价格。

> 权威内容：商品详情页静态化与多级缓存当前尚未在仓库建设，可参考 Nginx 官方文档中 proxy_cache 与静态资源缓存相关章节。
