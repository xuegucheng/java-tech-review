# 场景设计题

> **一句话定位**：场景题没有标准答案，考的是**你的回答有没有结构**。有结构的人讲 10 分钟面试官能跟上，没结构的人讲 10 分钟面试官只听到一堆名词。

## 答题框架

场景题的通用回答结构是这六步。**按顺序讲，每一步只讲结论和依据，别急着展开细节**——面试官会在他关心的地方打断你，那时再深入。

| 步骤 | 要说什么 | 常见失分 |
| --- | --- | --- |
| ① 澄清需求 | 量级、读写比、一致性要求、可用性要求 | 直接开始设计，方向完全跑偏 |
| ② 估算容量 | QPS、存储量、带宽、机器数 | 完全没有数字，方案无法判断可行性 |
| ③ 分层设计 | 入口 → 服务 → 缓存 → 存储，每层职责 | 上来就讲数据库表结构 |
| ④ 关键流程 | 正常路径的时序，标出瓶颈点 | 只讲组件不讲数据怎么流 |
| ⑤ 故障与兜底 | 每层挂了会怎样，怎么发现、怎么救 | 默认所有组件都可用 |
| ⑥ 权衡取舍 | 为什么这样选，代价是什么 | 只讲优点 |

### ① 澄清需求时的必问清单

不问清这几项，后面全是空谈：

- **量级**：日均多少、峰值多少、峰值是均值的几倍？
- **读写比**：读多写少还是写多读少？决定缓存策略和存储选型。
- **一致性**：能接受最终一致吗？不一致的窗口允许多长？
- **可用性**：单点故障能否容忍？降级后返回什么？
- **数据规模**：单表多少行、保留多久、要不要归档？

### ② 容量估算的常用量级

不需要精确，但要能说出**数量级和推导过程**：

| 指标 | 推导方式 | 参考量级 |
| --- | --- | --- |
| QPS | 日请求数 ÷ 86400 × 峰值系数 | 峰值通常是均值 3～10 倍 |
| 单机 QPS | 简单查询 + 缓存命中 | 数千；有复杂计算则更低 |
| 存储 | 单行大小 × 行数 × 副本数 × 冗余系数 | 冗余系数通常取 2～3 |
| 连接数 | QPS × 平均响应时间 | 这是并发连接数的近似 |

**面试时的说法**：「假设日活 100 万，人均 10 次请求，日均 1000 万 QPS 约 116；按峰值 10 倍算大概 1200 QPS。单机压测 2000 QPS 的话，应用层 2～3 台就够，瓶颈会在数据库。」

### ③ 分层设计的通用职责

| 层 | 职责 | 常用手段 |
| --- | --- | --- |
| 接入层 | 限流、防刷、静态化 | Nginx、CDN、IP/设备限流 |
| 应用层 | 业务逻辑、参数校验、幂等 | 无状态、可水平扩容 |
| 缓存层 | 挡读、挡热点 | 多级缓存、布隆过滤器 |
| 异步层 | 削峰、解耦 | 消息队列、延迟任务 |
| 存储层 | 持久化、事务 | 分库分表、读写分离 |

### ⑤ 故障与兜底的思考方式

每个组件都问自己三个问题：

1. **它慢下来会怎样？** → 超时、熔断、降级返回默认值
2. **它挂掉会怎样？** → 多副本、切换、本地缓存兜底
3. **它数据错了会怎样？** → 对账、补偿、人工介入通道

## 练习方法

场景题靠「讲」不靠「读」。建议这样练：

1. 读完一篇文章后，**合上页面**，用手机录音讲 5 分钟；
2. 回放，检查有没有走完上面那六步；
3. 特别检查**有没有数字**——这是最容易被忽略、也最能拉开差距的部分；
4. 再找一个变体（比如把「秒杀」换成「抢券」），重新讲一遍，看能不能复用结构。

## 内容边界

- 本模块的场景都是**通用抽象案例**，用于说明技术取舍，不代表任何公司的真实系统。
- 场景中出现的数字是**估算示例**，不是实测结果或行业基准。
- 涉及的具体组件（Redis、MQ、Nginx 等）只讲其承担的职责，机制细节以各组件官方文档为准。
- 消息队列、分布式事务、Redis 集群等专题**尚未在仓库建设**，本模块只到「用什么、为什么、代价是什么」为止。
