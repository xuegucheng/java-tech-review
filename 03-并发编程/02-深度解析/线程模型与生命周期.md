# 线程模型与生命周期

> 面试定位：线程状态、协作式中断和 monitor 等待边界
> Java 版本：线程 API 语义按 JDK 8+，运行时观察重点按 Java 21
> P0/P1：P0
> 前置知识：Java 对象引用、方法调用和基本异常处理
> 本文不负责：操作系统调度器和 HotSpot 全部线程实现

## 先说结论

Thread 是 Java 对执行路径的抽象，Runnable 只是待执行的任务；调用 start 才会请求新的线程执行路径，直接调用 run 不会创建新线程。Java Thread.State 的 RUNNABLE 同时覆盖操作系统意义上的 ready 和 running。

BLOCKED 表示线程在等待进入某个 monitor；WAITING 和 TIMED_WAITING 表示线程已经进入显式协作或同步等待。sleep 不释放已经持有的 monitor，Object.wait 会释放当前 monitor 并在返回前重新获得它。interrupt 是协作式取消信号，不是强制杀线程。

## 30 秒回答

> 线程生命周期可以从 NEW、RUNNABLE、BLOCKED、WAITING、TIMED_WAITING 到 TERMINATED 理解。RUNNABLE 没有区分操作系统的 ready 和 running。BLOCKED 是等待进入 synchronized 对应的 monitor；WAITING 常见于 wait、join、park 或同步器等待。sleep 只是让当前线程在一段时间内不参与运行，不释放锁；wait 必须在持有 monitor 时调用，并释放该 monitor。interrupt 只是设置中断请求，阻塞方法可能以 InterruptedException 响应，业务代码需要决定退出、恢复中断状态或继续协作。

## Thread 与 Runnable

Runnable 描述要做什么，Thread 描述由哪个执行载体运行它。把 Runnable 交给 Thread 构造器后：

~~~java
Runnable task = () -> handle();
Thread worker = new Thread(task);
worker.start();
~~~

start 会让 JVM 建立新的执行路径，并最终在新线程中调用 run。下面的代码没有并发：

~~~java
worker.run();
~~~

一个 Thread 实例只能成功 start 一次。任务需要被线程池复用时，应把 Runnable 或 Callable 交给 Executor，而不是重复启动同一个 Thread。

## 六种状态如何理解

| 状态 | 面试含义 | 常见进入方式 |
| --- | --- | --- |
| NEW | Thread 对象已创建但还没有 start | new Thread |
| RUNNABLE | 可运行、正在运行或等待操作系统调度 | start、被唤醒后重新竞争 |
| BLOCKED | 等待进入 synchronized 对应的 monitor | 进入被其他线程持有的 synchronized |
| WAITING | 无限期等待协作或同步结果 | wait、join、park、AQS |
| TIMED_WAITING | 有时间上限的等待 | sleep、wait(timeout)、join(timeout)、parkNanos |
| TERMINATED | run 正常返回或异常结束 | 线程执行完成 |

Java 规范没有把 RUNNABLE 拆成 ready 和 running，因为操作系统调度状态不是 Java 跨平台 API 必须暴露的语义。线程 dump 中看到 RUNNABLE，不代表它正在某个 CPU 上执行。

## BLOCKED 与 WAITING 的本质区别

两者都可能表现为线程没有继续执行，但等待原因不同：

- BLOCKED：线程还没有进入 monitor，目标是取得 synchronized 的进入资格；
- WAITING：线程已经主动交出当前执行机会，等待某个条件、通知、线程终止或同步器状态变化。

Object.wait 的特殊点是：调用线程必须先持有对象 monitor，调用后释放该 monitor，进入等待集合；被 notify 或中断唤醒后，线程还要重新竞争同一个 monitor，成功后 wait 才能返回。

## sleep、wait、join、park

### sleep

sleep 是 Thread 的静态方法。它让当前线程进入 TIMED_WAITING，不会释放当前已经持有的 synchronized monitor。时间到后也只是重新变成可运行，还要等待调度。

### wait

wait 是 Object 方法，必须在该对象的 monitor 内调用。它释放 monitor，并且返回前重新获得 monitor。正确用法是围绕共享条件使用 while：

~~~java
synchronized (lock) {
    while (!ready) {
        lock.wait();
    }
    consume();
}
~~~

不能把一次 notify 当成条件永远成立，也不能用 if 代替 while；虚假唤醒、竞争线程先消费条件和状态变化都要求重新检查谓词。

### join

join 让当前线程等待目标线程终止。join(timeout) 只是等待上限，不代表目标线程一定已经结束；必须通过 isAlive、Future 或业务结果再次确认。

### park

LockSupport.park 直接提供许可式阻塞。unpark 最多积累一个许可，unpark 在 park 之前也不会丢失；park 因中断返回时不会自动清除中断状态。AQS 使用它把失败获取的线程从自旋转为阻塞。

## interrupt 到底做什么

interrupt 不是 Thread.stop 的替代品，而是协作信号：

1. 对普通运行线程，通常只是设置中断标志；
2. 对 sleep、wait、join 等可中断阻塞，通常抛出 InterruptedException，并清除中断状态；
3. 对 park，线程会返回，调用方应检查当前中断状态；
4. 业务代码要决定退出循环、向上抛出、恢复状态或转换成取消结果。

捕获 InterruptedException 后如果不能继续向上抛，通常应该恢复状态：

~~~java
try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
~~~

Thread.interrupted() 是静态方法，会读取并清除当前线程的中断状态；isInterrupted() 只读取而不清除。混淆二者会让上层取消协议失效。

Thread.stop 不安全，因为它可以在任意位置异步抛出 ThreadDeath，跳过业务不变量和锁内清理，导致部分更新、对象状态破坏和锁保护边界失真。

## wait / notify 的 monitor 规则

wait、notify 和 notifyAll 都要求调用线程持有接收对象的 monitor，否则抛出 IllegalMonitorStateException。notify 只唤醒一个等待线程，notifyAll 唤醒全部等待线程；被唤醒的线程仍需重新竞争 monitor。

选择原则：

- 等待条件彼此互斥且能明确保证被唤醒者一定有资格时，notify 可能足够；
- 多种条件共享一个 monitor、状态谓词复杂或难以证明时，优先 notifyAll；
- 生产代码更应该考虑 BlockingQueue、Condition 或其他有明确协议的同步器。

## 关键源码路径

- Thread.start：从 Java 层进入本地启动路径，最终在新线程执行 run；
- Object.wait/notify：对象监视器等待与唤醒的语言 API 边界；
- LockSupport.park/unpark：许可式阻塞，是 AQS 的底层协作入口；
- Thread.interrupt、isInterrupted 和 interrupted：中断请求的状态 API；
- Thread.getState：对外暴露的状态观察，不等于操作系统完整调度状态。

## 工程边界

- 线程生命周期必须有结束、取消和异常传播策略；
- 不用 sleep 作为线程同步协议，使用 CountDownLatch、Future、Condition 或队列；
- 不把 interrupt 当作回滚；它只能请求停止，资源清理仍由 finally 负责；
- 线程池任务必须处理 InterruptedException，否则关闭和超时可能变成假成功；
- wait/notify 只围绕明确谓词使用，复杂生产协作优先使用高层并发工具。
