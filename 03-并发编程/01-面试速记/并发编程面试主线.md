# 并发编程面试主线

> 面试定位：5 年以上 Java 后端并发主线复盘
> Java 版本：基础语义按 JDK 8+，实现观察优先 Java 21
> P0/P1：P0 总览
> 前置知识：Java 对象、final、equals/hashCode 和 HashMap 基础
> 本文不负责：逐行翻译 JDK 源码、JUC API 大全和低频工具的完整实现

## 先说结论

并发面试不要从类名开始背。先把问题分层：

1. 线程如何运行和协作；
2. 共享变量为什么出现可见性、原子性和有序性问题；
3. volatile、CAS、synchronized 和 AQS 分别提供什么边界；
4. 线程池如何控制任务、线程和队列；
5. ThreadLocal 与并发容器如何降低共享状态冲突；
6. CompletableFuture 和 Virtual Thread 如何改变任务组织方式，但不消除资源约束。

30 秒回答可以这样说：

> Java 并发的核心是把共享状态、执行顺序和资源容量边界说清楚。JMM 用 happens-before 定义线程之间哪些写入对哪些读取可见；volatile 主要提供可见性和有序性，不保证复合操作原子性；CAS 通过比较并交换实现乐观更新，适合单变量状态但会遇到 ABA、自旋和高竞争退化；synchronized 和 AQS 把互斥、等待和唤醒组织起来；线程池再把任务提交、排队、扩容和拒绝连接到系统容量。工程上不能只比较某个工具快不快，而要看一致性、阻塞、取消、上下游容量和故障边界。

## 一条因果主线

~~~text
线程启动与生命周期
    ↓
共享内存语义：可见性、原子性、有序性
    ↓
JMM 与 happens-before
    ↓
volatile：发布状态，但不包住复合更新
    ↓
CAS / Atomic：乐观更新单个状态
    ↓
synchronized：对象监视器互斥
    ↓
AQS：state + 等待队列 + park/unpark
    ↓
ReentrantLock / Condition：可重入锁和多个条件队列
    ↓
ThreadPoolExecutor：任务、线程、队列和拒绝
    ↓
ThreadLocal / ConcurrentHashMap：减少共享状态冲突
    ↓
CompletableFuture / Virtual Thread：重新组织等待模型
~~~

## 高频回答入口

### 线程生命周期

- start 会创建新的执行路径；直接调用 run 仍在当前线程执行。
- Java 的 RUNNABLE 同时覆盖操作系统意义上的 ready 和 running，Thread.State 没有把二者拆开。
- BLOCKED 表示等待进入 monitor；WAITING 通常表示等待显式协作、条件或同步器信号。
- sleep 不释放已经持有的 monitor；Object.wait 会释放当前 monitor，返回前必须重新获得它。
- interrupt 是协作式取消信号，不是强制杀线程；InterruptedException 通常表示阻塞点发现并消费了中断请求。

完整链路见 [线程模型与生命周期](../02-深度解析/线程模型与生命周期.md)。

### JMM 与 volatile

- happens-before 是可观察性和顺序约束，不是时间线，也不是“线程 A 一定先跑完”。
- volatile 写对后续 volatile 读建立可见性边界，但 count++ 仍然是读、改、写三步。
- synchronized 同时提供互斥和释放/获取 monitor 之间的可见性；它不是只为“防止两个线程同时执行”。
- DCL 的实例引用必须配合 volatile，否则发布可能暴露未完成初始化的对象。

完整链路见 [Java 内存模型与 happens-before](../02-深度解析/Java内存模型与happens-before.md) 和 [volatile 原理与使用边界](../02-深度解析/volatile原理与使用边界.md)。

### synchronized、CAS 与 AQS

- synchronized 锁住的是 monitor 关联的对象；实例方法通常锁 this，static synchronized 锁 Class 对象。
- synchronized 可重入，但没有公平性承诺；Java 21 不能把旧版偏向锁升级口诀当作当前必然事实。
- CAS 不是“完全没有锁”，而是原子比较交换原语；高竞争下可能不断重试并消耗 CPU。
- AQS 不是一个具体锁，而是用 state、同步队列和 park/unpark 提供同步器骨架；tryAcquire/tryRelease 由子类定义语义。

完整链路见 [synchronized 原理与锁实现](../02-深度解析/synchronized原理与锁实现.md)、[CAS 与原子类](../02-深度解析/CAS与原子类.md) 和 [AQS 核心原理](../02-深度解析/AQS核心原理.md)。

### 线程池

不要只背“核心线程 → 队列 → 最大线程”。execute 的真实判断还要考虑运行状态、入队后的二次检查、worker 数量和拒绝策略：

~~~text
workerCount < corePoolSize
    → 尝试创建核心 Worker
否则尝试入队
    → 入队后再次检查线程池状态
队列满且 workerCount < maximumPoolSize
    → 创建非核心 Worker
仍不能接收
    → RejectedExecutionHandler
~~~

无界队列可能让 maximumPoolSize 基本没有机会生效；无界线程创建可能耗尽内存或把下游打穿。线程数只能从 CPU、等待比例、RT、上下游容量和压测结果综合估计。

完整链路见 [ThreadPoolExecutor 线程池](../02-深度解析/ThreadPoolExecutor线程池.md)。

### ThreadLocal 与并发容器

- ThreadLocal 的值在 Thread 关联的 ThreadLocalMap 中，不是存放在 ThreadLocal 对象本身。
- key 弱引用不能自动消除 value 的强引用；在线程池长生命周期线程中，必须在 finally 中 remove。
- ConcurrentHashMap 是局部并发，不是把所有操作变成事务；computeIfAbsent、merge 等方法只对各自的原子复合操作负责。
- HashMap 的结构和 equals/hashCode 契约分别由 [集合框架](../../02-集合框架/README.md) 和 [Java 核心](../../01-Java核心/README.md)维护。

## 明确拒绝的旧结论

- 不说“volatile 保证线程安全”。
- 不说“CAS 一定比锁快”。
- 不说“synchronized 一定比 ReentrantLock 慢”。
- 不把 AQS 简化成原始 CLH 自旋锁队列。
- 不把 ThreadLocal key 弱引用等同于不会泄漏。
- 不把 Java 21 synchronized 描述成固定的无锁、偏向、轻量、重量升级流程。
- 不把线程池大小等同于 CPU 核数加一。
- 不把 Virtual Thread 说成更快的 CPU 线程。
