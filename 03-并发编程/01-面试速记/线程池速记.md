# 线程池速记

> 面试定位：任务执行、容量控制和拒绝策略
> Java 版本：ThreadPoolExecutor 主线按 Java 21，使用语义按 JDK 8+
> P0/P1：P0
> 前置知识：线程生命周期、队列和中断协作
> 本文不负责：逐位背 ctl 的全部位运算

## 先说结论

线程池不是单纯的线程复用器，而是任务提交、工作线程、任务队列、生命周期、拒绝和资源隔离的容量控制器。execute 的决策不能简化成固定口诀，尤其要理解入队之后的二次检查和 shutdown 竞争。

## execute 主线

~~~text
运行状态允许且 workerCount < corePoolSize
    → 尝试创建核心 Worker
否则尝试把任务放入 workQueue
    → 入队后重新检查运行状态和 worker 数量
队列满且 workerCount < maximumPoolSize
    → 尝试创建非核心 Worker
仍然不能接收
    → RejectedExecutionHandler
~~~

## 高频回答

- 无界队列会让 maximumPoolSize 很难生效，任务堆积最终表现为延迟和内存压力。
- newFixedThreadPool 默认使用无界队列，不能因此认为它不会 OOM。
- newCachedThreadPool 允许大量临时线程，外部提交速度失控时可能耗尽线程和上下文切换资源。
- CPU 核数只能作为初始估计；线程数还要结合等待时间、CPU 利用率、RT、上下游容量和压测。
- CallerRunsPolicy 让提交线程执行任务，会降低提交速度，形成一种简单反压，但也可能把业务请求线程拖入慢任务。
- execute 中的异常可交给线程的未捕获异常处理器；submit 通常把异常封装到 Future，必须 get 或显式检查，否则异常看起来像消失。
- shutdown 不接收新任务但会处理队列；shutdownNow 尝试中断工作线程并返回尚未开始的任务，不能保证强制停止。

## 拒绝策略

| 策略 | 行为 | 工程风险 |
| --- | --- | --- |
| AbortPolicy | 抛 RejectedExecutionException | 失败显式，调用方必须处理 |
| CallerRunsPolicy | 提交者执行任务 | 有反压，但可能阻塞请求线程 |
| DiscardPolicy | 静默丢弃 | 适合极少数允许丢弃的任务，默认很危险 |
| DiscardOldestPolicy | 丢队头再重试 | 可能丢掉仍有价值的旧任务 |

完整链路见 [ThreadPoolExecutor 线程池](../02-深度解析/ThreadPoolExecutor线程池.md)。

## 一句话复盘

线程池配置的核心不是背 core/max 数字，而是让任务入口、队列容量、拒绝行为、取消和下游承载能力形成可观测的闭环。
