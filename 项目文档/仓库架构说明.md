# Repository Architecture

> 本文是后续维护者的架构契约。它解释仓库为什么这样组织，以及新增笔记、图和实验时应把内容放在哪里。

## 1. 产品定位

`java-tech-review` 面向 **3～10 年 Java 后端工程师**，服务跳槽前系统复习、日常回顾、面试突击、源码理解和疑难知识重新建模。

它不是 Java 初学教程、API 大全或百科式目录。每个主题都应尽量形成下面的闭环：

```text
Interview Answer → Mental Model → Deep Dive → Source Path → Runnable Example → Test
```

## 2. 信息架构原则

技术域是第一组织维度。Interview Review、Deep Dive、Diagram 和 Runnable Example 属于同一知识主题的不同表达层，应优先放在同一技术域中。跨模块共享仅用于真正无法归属单一技术域的仓库级基础设施，不为了减少少量重复而破坏知识导航。

本次结构重构只调整信息架构，不重写技术正文：已有文章保留在所属模块的 `02-深度解析/`，面试入口位于 `01-面试速记/`，图示位于 `03-图示/`，完整实验和测试位于 `04-示例代码/`。根目录不再承担跨模块图示或示例资源集散职责，也不保留历史资产目录；Git 历史负责追踪迁移前后的演进，仍有价值的位图按主题归位。

## 4. 内容层级

### Interview Review

目标是 5～15 分钟恢复一个明确主题的面试记忆。文件应优先放：

- 一句话面试结论；
- 30 秒回答或 mental model；
- 3～8 个因果式追问；
- 高频工程坑；
- 指向唯一 Deep Dive、图和实验的链接。

它不是完整教材，也不是“面试题 1～40”的平铺题库。

### Deep Dive

只有值得理解实现、规范边界、性能/并发取舍或源码路径的主题进入这里。长文可以保留，但一个文件要围绕一个可命名的认知主题；不能把 language、DI、ORM、JVM 和业务架构为了篇幅塞到一起。

Deep Dive 允许保留完整推理、关键源码片段、图和工程讨论，但源码只追关键路径，不复制整个 JDK 文件。

### Runnable Examples

完整的 `main` 类、多个协作类、可重复测试和验证输出进入所属模块的 `04-示例代码/`。正文只保留解释机制所需的短片段。每个示例必须有测试，并从笔记链接回来；示例失败时不应被文章描述成已验证结论。

### Diagrams

- Mermaid：流程、决策、生命周期、状态机和简单时序，靠近解释文字。
- SVG：桶、链表、对象布局、引用、指针和需要精确空间关系的结构图。
- PNG/JPG：只保留已有且不可替代的资产，新结构图默认创建 SVG。

图的职责是建立 mental model，不能把正文逐字重复一遍。每张图必须有技术域和知识主题归属。

## 5. P0 / P1 / P2

- **P0**：面试高频、核心机制、能够区分工程判断的主题。当前包括参数传递、对象模型与多态、equals/hashCode、集合契约、HashMap、Hash 集合和 LinkedHashMap/LRU。
- **P1**：常见且工程重要，或是理解 P0 的必要前置。当前包括运行链路、类型转换、方法重载、封装、继承/接口/组合、ArrayList、LinkedList 和泛型。
- **P2**：低频边缘 API、完整语法表或版本补充。内容可以准确保留，但不应遮住 P0/P1。

优先级是导航权重，不是正确性评级。一个 P2 Deep Dive 仍然可以有很高的技术价值，只是默认不出现在 1 天突击路线。

## 6. Markdown 笔记模板

下面是推荐骨架，不是每篇文章的强制标题清单。知识点不同就裁剪，不要为了统一而制造空章节。

```markdown
# Topic

> P0/P1/P2 · JDK 8+ / Java 17+ / Java 21+ / Java 25+ · 预计时间

## 面试结论

## 30 秒回答

## 核心结构或 mental model

## 核心流程

## 为什么这样设计

## 面试追问链

### 追问：为什么？

## 工程坑

## Deep Dive / 关键源码

## Runnable Example

## 一句话复盘
```

“面试追问链”必须表达因果顺序，例如 HashMap 的 `是什么 → 如何定位桶 → 冲突 → 树化 → resize → equals/hashCode → 并发边界`，不能只是罗列问题。

## 7. One Source of Truth：概念 ownership matrix

下面的矩阵是内容边界，而不是目录装饰。Owner 负责定义规则、版本边界和完整推理；Consumer 只能说明自己如何调用、继承或消费该规则，并链接回 Owner。

| 概念 | 唯一权威 Owner | Consumer 允许保留的内容 |
| --- | --- | --- |
| 变量、引用、参数传递 | `01-Java核心/02-深度解析/参数传递机制.md` | 对象创建、集合 API 可用短例子说明别名/所有权 |
| 泛型语言规则 | `01-Java核心/02-深度解析/Java泛型与类型安全.md` | Collections 只解释 `addAll`、`Comparator`、`Collections.copy` 等 API 签名 |
| `equals/hashCode` 契约 | `01-Java核心/02-深度解析/equals与hashCode契约.md` | Collections 只解释 HashMap/HashSet 如何消费 equality |
| 不可变对象、防御性复制、对象不变量 | `01-Java核心/02-深度解析/对象创建与不可变设计.md` | 参数传递只说明共享风险并链接回 Owner |
| `extends`、重写、协变返回、异常规则、构造链 | `01-Java核心/02-深度解析/继承与方法重写.md` | 抽象类/接口只写自身增量能力 |
| 抽象类、抽象方法、模板方法、骨架实现 | `01-Java核心/02-深度解析/抽象类.md` | 设计专题只比较何时使用，不重写语言规则 |
| 接口规则、default/static/private、冲突和函数式接口 | `01-Java核心/02-深度解析/接口.md` | 组合专题只讨论依赖方向和替换边界 |
| 继承 vs 组合、委托、变化轴、SOLID/DIP | `01-Java核心/02-深度解析/组合与设计原则.md` | 语言专题只引用设计取舍，不维护第二套 SOLID 教程 |
| `static` 语义、主动/被动使用、初始化顺序 | `01-Java核心/02-深度解析/static与类初始化.md` | Object/类设计只引用初始化边界 |
| `final`、blank final、常量内联、二进制兼容 | `01-Java核心/02-深度解析/final与常量设计.md` | 参数页只说明 final 参数不改变传参语义 |
| `wait/notify`、中断、LockSupport、条件队列 | 未来 `03-并发编程` | Object 页只保留监视器 API 边界和链接 |
| HashMap 的 hash、bucket、树化、resize | `02-集合框架/02-深度解析/HashMap原理与源码分析.md` | Hash 集合/LinkedHashMap 只写复用关系和增量结构 |
| 集合接口、视图、迭代器、fail-fast | `02-集合框架/02-深度解析/集合框架体系与核心契约.md` | 实现专题只引用契约，不重写全表 |
| HashSet/LinkedHashSet 的结构与顺序增量 | `02-集合框架/02-深度解析/HashSet与LinkedHashSet.md` | Hash consumer 页只写 equality 消费链 |
| LinkedHashMap 顺序链表、access-order、LRU | `02-集合框架/02-深度解析/LinkedHashMap与LRU缓存.md` | HashSet 只说明复用 LinkedHashMap 的增量 |

当前已落地的跨模块链接包括：

- [Java equality contract](../01-Java核心/02-深度解析/equals与hashCode契约.md) ← [Hash consumer](../02-集合框架/02-深度解析/Hash集合与equals-hashCode契约.md)；
- [Java generics owner](../01-Java核心/02-深度解析/Java泛型与类型安全.md) ← [Collection generic API](../02-集合框架/02-深度解析/集合泛型API设计.md)；
- [Object immutability owner](../01-Java核心/02-深度解析/对象创建与不可变设计.md) ← parameter passing / final 主题的共享边界说明。

当一个概念出现第二次时，先问它是在定义契约，还是在说明另一个组件如何消费契约；如果是后者，使用链接而不是复制完整解释。

## 8. Java 版本策略与构建

- 默认面试主线是 `JDK 8+`，不把现代语法强行写进经典答案。
- `Java 17+`、`Java 21+`、`Java 25+` 必须在标题、段落或代码块前显式标记。
- 当前示例默认 Java 21；如果未来必须验证 Java 25，新增独立 profile/module，不破坏默认 `mvn test`。
- 实现细节必须绑定 JDK 版本；规范保证、OpenJDK 实现和某个版本的观察结果分开写。
- 根 `pom.xml` 聚合所有已创建的示例模块；模块级测试和根级 `mvn test` 都必须保持可运行。

## 9. 模块 README 契约

每个主要模块 README 至少回答：

1. 模块解决什么问题；
2. 1 天突击从哪里开始；
3. P0/P1/P2 如何分层；
4. 推荐阅读顺序；
5. Deep Dive 在哪里；
6. 图示和 Runnable Example 在哪里；
7. 本模块不负责哪些概念，以及权威链接在哪里。

根 README 只负责跨模块地图、时间路线、统一构建和入口，不复制每篇文章的正文。

## 10. 新增内容的检查清单

- 能否给文件命名为一个明确的认知主题？
- 它属于哪个技术域和优先级？
- 是否应该先写 `01-面试速记/`，再链接 `02-深度解析/`？
- 是否已经有同概念的 authoritative source？
- 完整代码是否应移入所属模块的 `04-示例代码/`，并配测试？
- 图是在解释流程还是空间结构，应该用 Mermaid 还是 `03-图示/` 下的 SVG？
- 所有内部链接、图片、标题锚点和代码围栏是否可验证？
- 是否把未来计划误写成已完成？
