## 00.3 为什么集合需要泛型

没有泛型时，容器只能以 `Object` 保存元素：

```java
List values = new ArrayList();
values.add("A");
values.add(100);
String value = (String) values.get(1);
```

问题不是强制转换写得麻烦，而是错误在插入时没有被阻止，直到读取并转换时才暴露。

使用泛型：

```java
List<String> values = new ArrayList<>();
values.add("A");
// values.add(100); // 编译错误
String value = values.get(0);
```

泛型把“这个容器允许什么元素”的约束编码进静态类型系统。它主要提供：

- 编译期类型检查；
- 减少显式强制转换；
- 提升 API 自描述性；
- 让重构工具和 IDE 获得更准确信息；
- 让算法能够在保持类型关系的前提下复用。

## 00.4 类型参数、类型实参与参数化类型

以 `List<String>` 为例：

```text
List<E>
     ↑
类型参数 E：在 List 声明中使用的占位类型

List<String>
     ↑
类型实参 String：使用 List 时传入的具体类型

List<String>
↑──────────↑
参数化类型
```

典型声明：

```java
public interface Box<T> {
    T get();
    void set(T value);
}
```

使用：

```java
Box<String> box;
```

不要把泛型类型参数与方法参数混淆：

```java
static <T> T identity(T value)
        ↑             ↑
     类型参数       方法参数
```

## 00.5 泛型类与泛型接口

泛型类把类型关系提升到对象级别：

```java
public final class Pair<K, V> {
    private final K key;
    private final V value;

    public Pair(K key, V value) {
        this.key = key;
        this.value = value;
    }

    public K key() { return key; }
    public V value() { return value; }
}
```

泛型接口用于定义跨实现的类型契约：

```java
public interface Repository<ID, E> {
    E findById(ID id);
}
```

同一个泛型类型的不同参数化使用在源码层是不同静态类型：

```java
Pair<String, Integer>
Pair<Long, String>
```

但类型参数不会自动形成继承关系，参数化类型是否存在子类型关系要看泛型声明本身，而不是类型实参之间的继承关系。

## 00.6 泛型方法与类型推断

泛型方法在方法自己的作用域内声明类型参数：

```java
public static <T> T first(List<T> values) {
    return values.get(0);
}
```

`<T>` 必须出现在返回类型之前。方法可以位于普通类或泛型类中，其类型参数也可以独立于类类型参数。

调用时通常由编译器推断：

```java
String first = first(List.of("A", "B"));
Integer number = first(List.of(1, 2));
```

必要时可以显式提供类型实参：

```java
String value = GenericMethods.<String>identity("A");
```

工程上应优先让签名表达清晰关系，而不是依赖调用方写显式类型实参。

---

## 00.7 泛型构造器与菱形语法

构造器也可以声明自己的类型参数，即使类本身不是泛型类：

```java
public final class AuditEvent {
    public <T> AuditEvent(T payload) {
        System.out.println(payload);
    }
}
```

菱形语法让编译器从赋值上下文推断类的类型实参：

```java
Map<String, List<Integer>> index = new HashMap<>();
```

右侧的 `<>` 不表示“无类型”，而表示由编译器推断与左侧兼容的参数化类型。不要为了缩短代码退回原始类型：

```java
Map<String, List<Integer>> index = new HashMap(); // 非受检转换
```

## 00.8 类型参数命名与作用域

常见命名约定：

| 名称 | 常见含义 |
|---|---|
| `T` | Type，一般类型 |
| `E` | Element，集合元素 |
| `K` | Key，键 |
| `V` | Value，值 |
| `R` | Result，结果 |
| `U` | 第二个一般类型 |

单字母适合局部且关系清晰的泛型签名。复杂领域 API 可以使用更具语义的名称：

```java
interface Converter<SOURCE, TARGET> {
    TARGET convert(SOURCE source);
}
```

类型参数只在其声明作用域内有效。类类型参数不能直接从静态上下文使用，因为静态成员属于原始类级别，而不是某个实例的参数化类型。

## 00.9 上界类型参数

上界限制允许的类型实参，并让泛型代码获得可用能力：

```java
public static <T extends Number> double sum(List<T> values) {
    double result = 0;
    for (T value : values) {
        result += value.doubleValue();
    }
    return result;
}
```

`extends` 在泛型上界中同时覆盖“继承类”和“实现接口”。

多个上界写法：

```java
<T extends Number & Comparable<T>>
```

规则是类上界必须在第一个位置，后面可以跟接口。类型变量在方法体中可使用所有上界声明的成员。

---

## 00.10 递归类型边界

递归边界让类型参数约束引用自身：

```java
<T extends Comparable<? super T>>
```

这是排序 API 中很常见的签名。它表达：

- `T` 必须能够与 `T` 或 `T` 的某个父类型比较；
- 比单纯的 `Comparable<T>` 更兼容继承体系。

例如子类继承父类实现的 `Comparable<Parent>` 时，`Comparable<? super Child>` 仍可接受它。

递归边界的目标是表达真实类型关系，不是追求“签名越复杂越高级”。业务 API 若无法解释其必要性，应优先简化。

## 00.11 泛型不变性

Java 泛型默认是不变的：

```text
Integer 是 Number 的子类型
但
List<Integer> 不是 List<Number> 的子类型
```

否则以下代码会破坏类型安全：

```java
List<Integer> integers = new ArrayList<>();
// List<Number> numbers = integers; // 假设允许
// numbers.add(3.14);
Integer value = integers.get(0);
```

如果允许赋值，`List<Integer>` 可能被写入 `Double`。

不变性并不意味着完全不能复用。需要协变读取或逆变写入时，应使用受约束通配符，而不是绕过类型系统。

---

## 00.12 数组协变与泛型不变的差异

数组是协变的：

```java
Number[] numbers = new Integer[1];
```

但运行时仍知道数组真实元素类型，因此：

```java
numbers[0] = 3.14; // ArrayStoreException
```

泛型选择不变性，把同类错误提前到编译期：

```java
// List<Number> numbers = new ArrayList<Integer>(); // 编译错误
```

两者差异体现了 Java 不同时期的类型设计：

| 机制 | 类型关系 | 错误暴露 |
|---|---|---|
| 数组 | 协变 | 可能运行期抛 `ArrayStoreException` |
| 泛型 | 默认不变 | 通常编译期拒绝 |

## 00.13 无界通配符

`List<?>` 表示“某种确定但当前未知的元素类型的 List”。

```java
static int sizeOf(List<?> values) {
    return values.size();
}
```

可以安全读取为 `Object`：

```java
Object value = values.get(0);
```

不能写入任意非 `null` 值：

```java
// values.add("A"); // 编译错误
values.add(null);   // 类型系统允许，但业务上通常不推荐
```

`List<?>` 与原始类型 `List` 完全不同：

- `List<?>` 保留未知类型约束；
- 原始 `List` 关闭了部分泛型检查并产生兼容性风险。

---

## 00.14 上界通配符：extends

`? extends Number` 表示某个未知类型，该类型是 `Number` 或其子类型：

```java
static double total(List<? extends Number> values) {
    double result = 0;
    for (Number value : values) {
        result += value.doubleValue();
    }
    return result;
}
```

它可以接收：

```java
List<Integer>
List<Long>
List<Double>
```

读取时至少可视为 `Number`，但不能安全写入具体数字，因为真实类型可能是 `Integer`、`Long` 或其他子类型：

```java
// values.add(1);   // 不安全
// values.add(1.0); // 不安全
```

“extends 只能读”是便于记忆的简化说法；更准确地说，它不能写入无法证明兼容的非 `null` 值，仍可执行删除、清空等不引入新元素的操作。

---

## 00.15 下界通配符：super

`? super Integer` 表示某个未知类型，它是 `Integer` 或其父类型：

```java
static void addDefaults(List<? super Integer> target) {
    target.add(1);
    target.add(2);
}
```

可接收：

```java
List<Integer>
List<Number>
List<Object>
```

可以安全写入 `Integer` 及其子类型。读取时只能保证得到 `Object`：

```java
Object value = target.get(0);
```

因为真实容器可能是 `List<Object>`，其中原本就包含字符串等其他对象。

## 00.16 PECS 的准确理解

PECS：

```text
Producer Extends
Consumer Super
```

- 参数只向调用方提供 `T`：考虑 `? extends T`；
- 参数主要接收调用方写入的 `T`：考虑 `? super T`。

经典复制签名可近似表达为：

```java
static <T> void copy(
        List<? super T> destination,
        List<? extends T> source
)
```

但 PECS 不是机械规则：

- 一个对象可能既读又写；
- 返回类型通常不宜滥用通配符；
- 如果需要表达多个位置必须是同一个确定类型，应声明类型参数；
- 若 API 只需 `size()`、遍历为 `Object`，无界通配符可能已经足够。

---

## 00.17 通配符读写矩阵

| 声明 | 可安全读取为 | 可安全新增 | 典型用途 |
|---|---|---|---|
| `List<T>` | `T` | `T` | 内部持有确定元素类型 |
| `List<?>` | `Object` | 通常仅 `null` | 不关心元素类型的通用操作 |
| `List<? extends T>` | `T` | 通常仅 `null` | 读取生产者 |
| `List<? super T>` | `Object` | `T` 及其子类型 | 写入消费者 |

“可安全新增”讨论的是通过当前引用新增元素，不表示集合一定支持修改；实际实现还可能抛出 `UnsupportedOperationException`。

## 00.18 通配符与类型参数如何选择

类型参数适合表达多个位置之间的同一类型关系：

```java
static <T> T choose(T first, T second)
```

通配符适合表达单个参数中的未知类型边界：

```java
static void printAll(List<?> values)
```

常见判断：

- 只出现一次且不需要返回该类型：优先考虑通配符；
- 参数、返回值或多个参数必须保持同一类型关系：使用类型参数；
- 调用方不应关心捕获后的具体类型：通配符通常更自然；
- API 返回 `List<? extends X>` 会把通配符负担转嫁给调用方，应谨慎使用。

---

## 00.19 通配符捕获与辅助方法

编译器会把 `?` 当作某个未知但固定的捕获类型。某些看似合理的操作需要辅助泛型方法捕获它：

```java
static void reverseFirstTwo(List<?> values) {
    swap(values, 0, 1);
}

private static <T> void swap(List<T> values, int i, int j) {
    T tmp = values.get(i);
    values.set(i, values.get(j));
    values.set(j, tmp);
}
```

外层 API 不暴露具体类型，内部辅助方法获得同一个捕获类型并安全地读写。

不要用强制转换掩盖捕获错误；先判断是否可以通过引入私有泛型辅助方法表达真实关系。

## 00.20 原始类型

原始类型是省略类型实参的泛型类型：

```java
List values = new ArrayList();
```

它主要用于兼容泛型引入前的旧代码。原始类型允许执行本应被拒绝的写入：

```java
List<String> names = new ArrayList<>();
List raw = names;
raw.add(100); // 编译警告
```

随后读取时可能抛出 `ClassCastException`。

新代码应避免原始类型。需要表达未知元素类型时使用 `List<?>`，而不是 `List`。

---

## 00.21 非受检警告不是普通噪声

常见警告：

```text
unchecked assignment
unchecked conversion
unchecked cast
unchecked method invocation
```

它们表示编译器无法完整证明类型安全，而不是简单的代码风格问题。

处理顺序：

1. 优先重构为参数化类型；
2. 缩小与旧 API 交互的边界；
3. 在边界处校验元素；
4. 只有能证明安全时，才在最小作用域使用 `@SuppressWarnings("unchecked")`；
5. 写下注释说明不变量和证明依据。

禁止在整个类或模块级粗暴屏蔽所有非受检警告。

---

## 00.22 堆污染

堆污染是指某个参数化类型变量引用了不符合其静态类型承诺的对象。

```java
List<String> names = new ArrayList<>();
List raw = names;
raw.add(100);
```

`names` 的静态类型承诺“元素是 String”，底层集合却已包含 `Integer`，形成堆污染。

堆污染的危险在于：

- 污染点与异常点可能相距很远；
- 异常常在编译器插入的隐式转换处出现；
- 日志只显示读取处，真正问题可能来自旧 API、反射、数组或可变参数边界。

## 00.23 泛型可变参数与 SafeVarargs

可变参数本质上使用数组，而参数化类型数组可能造成堆污染：

```java
static <T> void accept(List<T>... lists) {
}
```

编译器通常给出潜在堆污染警告。

`@SafeVarargs` 是程序员承诺方法体不会对可变参数数组执行不安全操作。它不是“关闭警告的装饰”，而是一项需要证明的契约。

安全做法包括：

- 不向可变参数数组写入其他参数化类型；
- 不把数组暴露给不受控代码；
- 不依赖运行时识别泛型元素参数；
- 能改成 `List<List<T>>` 或普通集合参数时优先改造。

---

## 00.24 为什么不能创建泛型数组

以下代码非法：

```java
// List<String>[] array = new List<String>[10];
```

数组在运行时保留并检查组件类型，而泛型类型实参通常被擦除。若允许创建，就无法可靠执行数组存储检查。

可以创建通配符数组：

```java
List<?>[] array = new List<?>[10];
```

但大多数业务场景应优先使用集合嵌套：

```java
List<List<String>> groups = new ArrayList<>();
```

不要通过 `(List<String>[]) new List<?>[10]` 之类的强制转换把类型风险扩散到业务代码。

## 00.25 类型擦除的基本模型

Java 泛型主要通过擦除实现。编译器会：

- 检查类型约束；
- 在必要位置插入转换；
- 将类型变量擦除为其上界；
- 为保持多态兼容性生成必要的桥接方法；
- 在 class 文件的签名属性中保留部分泛型声明元数据。

示意：

```java
class Box<T> {
    T get();
}
```

擦除后的执行模型近似：

```java
class Box {
    Object get();
}
```

这是理解模型，不应据此手工把泛型代码改回 `Object`。泛型的核心价值正是编译器在擦除前建立并验证类型关系。

---

## 00.26 运行时类型身份

不同参数化类型通常共享同一个运行时类对象：

```java
List<String> strings = new ArrayList<>();
List<Integer> integers = new ArrayList<>();

System.out.println(
        strings.getClass() == integers.getClass()
); // true
```

因此不能写：

```java
// if (value instanceof List<String>) { }
```

运行时只能检查：

```java
if (value instanceof List<?>) { }
```

反射可以读取声明位置保留的部分泛型签名，但不能恢复任意对象中每个元素的真实泛型承诺。

---

## 00.27 泛型的静态上下文限制

类类型参数属于参数化实例视角，静态成员属于类本身：

```java
class Cache<T> {
    // static T value; // 编译错误
}
```

否则同一个 `Cache.class` 无法同时为 `Cache<String>` 和 `Cache<Integer>` 维护一个类型安全的静态 `T`。

同理，不能直接：

```java
// new T()
// T.class
// new T[10]
```

需要创建对象时可传入工厂：

```java
static <T> T create(Supplier<T> factory) {
    return factory.get();
}
```

---

## 00.28 擦除导致的重载冲突

以下两个方法擦除后签名相同，不能共存：

```java
// void process(List<String> values) { }
// void process(List<Integer> values) { }
```

二者都近似擦除为：

```java
void process(List values)
```

API 设计不能依赖泛型实参区分重载。应使用不同方法名、不同原始参数类型，或把行为建模成策略对象。

---

## 00.29 桥接方法概览

泛型擦除可能改变重写后的方法描述符。编译器会生成合成桥接方法维持多态。

```java
class Parent<T> {
    T value() { return null; }
}

class Child extends Parent<String> {
    @Override
    String value() { return "A"; }
}
```

执行层面需要同时兼容擦除后的 `Object value()` 和子类的 `String value()`。

本模块只需知道：

- 桥接方法由编译器生成；
- 反射或堆栈中可能看到它；
- 它不是开发者重复写出的业务方法；
- 完整字节码分析放在高级语言特性或 JVM 模块。

---

## 00.30 装箱类型与集合成本

泛型类型实参不能直接使用基本类型：

```java
List<int> // 非法
```

必须使用包装类型：

```java
List<Integer>
```

因此集合中的基本数值会发生装箱，并可能带来：

- 对象或缓存引用成本；
- 拆箱时的空指针风险；
- 大规模数据处理中的内存和 GC 压力；
- `remove(int)` 与 `remove(Object)` 的重载歧义。

不要因普通业务列表过早优化，但对百万级数值、热点算法或低延迟路径，应评估专用基本类型结构、数组或其他表示。

## 00.31 集合 API 中的 extends

典型添加批量元素的签名：

```java
boolean addAll(Collection<? extends E> values)
```

调用方可传入 `E` 的子类型集合：

```java
List<Number> numbers = new ArrayList<>();
List<Integer> integers = List.of(1, 2);
numbers.addAll(integers);
```

源集合向目标集合生产元素，因此使用 `extends`。若签名是 `Collection<E>`，就会不必要地拒绝 `Collection<Integer>` 写入 `Collection<Number>` 的安全场景。

---

## 00.32 集合 API 中的 super

排序和查找 API 常把比较器声明为：

```java
Comparator<? super T>
```

因为能比较 `T` 父类型的比较器，也能比较 `T`：

```java
Comparator<Object> byText =
        Comparator.comparing(Object::toString);

List<String> names = new ArrayList<>();
names.sort(byText);
```

比较器消费 `T`，因此使用下界更灵活。

另一个典型场景是写入目标：

```java
static <T> void fill(List<? super T> target, T value)
```

---

## 00.33 不要在返回类型上滥用通配符

返回：

```java
List<? extends Number> load()
```

会让调用方只能以未知子类型使用结果，通常无法安全新增元素，也难以继续组合 API。

若实现真正承诺返回 `Number` 列表，优先：

```java
List<Number> load()
```

通配符更常用于输入参数以扩大可接受范围。返回通配符只有在确实需要隐藏具体元素子类型、且调用方只应读取时才合理，并应记录设计原因。

---

## 00.34 泛型与 null

泛型本身不提供非空保证：

```java
List<String> names = new ArrayList<>();
names.add(null);
```

`String` 约束元素的静态类型，不表示非空。

非空策略必须由以下机制表达和执行：

- API 文档；
- 参数校验；
- `List.of()`、`List.copyOf()` 等特定工厂的契约；
- Bean Validation 或静态分析注解；
- 领域类型与构造不变量。

不要把 `Optional<T>` 机械当作集合元素的非空替代方案。

---

## 00.35 领域 API 的泛型设计

仓储分配示例：

```java
interface Loader<ID, E> {
    E load(ID id);
}

static <E> List<E> snapshot(
        Collection<? extends E> source
) {
    return List.copyOf(source);
}
```

设计时关注：

- 类型参数是否表达真实领域关系；
- 是否需要多个参数位置保持同一类型；
- 是否过度暴露实现类型；
- 是否把调用方困在复杂通配符中；
- 非受检转换是否被限制在适配层；
- 返回集合是否需要快照、不可修改或保持顺序。

泛型是契约工具，不是为了减少几行重复代码而增加难以理解的类型体操。

## 00.36 本章决策清单

审查集合相关泛型代码时，可以逐项检查：

1. 是否仍存在可以参数化的原始 `List`、`Map`、`Class`？
2. 非受检警告是否被逐个解释，而非全局屏蔽？
3. 只读来源是否可以使用 `? extends T`？
4. 写入目标是否可以使用 `? super T`？
5. 多个参数和返回值是否需要一个共同类型参数？
6. 返回值是否滥用了通配符？
7. 是否试图通过泛型实参区分重载？
8. 可变参数是否可能制造堆污染？
9. 是否把泛型当作非空、不可变或线程安全保证？
10. 复杂签名是否确实提升了调用方能力？

## 00.39 易错点

### 误区1：泛型只用于减少强制转换

**错误。** 它更重要的价值是把元素类型关系放入编译期契约，提前阻止非法写入。

### 误区2：`List<Integer>` 是 `List<Number>` 子类型

**错误。** 泛型默认不变，否则可以通过 Number 视角写入 Double，破坏 Integer 列表。

### 误区3：数组与泛型具有相同协变规则

**错误。** 数组协变并在运行时检查，泛型默认不变并在编译期拒绝。

### 误区4：`List<?>` 等同于原始 List

**错误。** 通配符保留未知类型约束，原始类型关闭了部分泛型检查。

### 误区5：`?` 表示元素可以是任意类型并任意写入

**错误。** 它表示某个未知但固定的类型，通常不能写入无法证明兼容的值。

### 误区6：`? extends T` 完全不能修改集合

**错误。** 不能安全新增具体非 null 值，但仍可能删除、清空或交换捕获类型元素。

### 误区7：`? super T` 读取时一定得到 T

**错误。** 底层可能是 Object 容器，读取只能保证 Object。

### 误区8：PECS 要求所有参数都必须写通配符

**错误。** 只有确实需要扩大输入兼容性时才使用，读写双向关系可能需要明确 T。

### 误区9：通配符永远优于类型参数

**错误。** 多个位置需要表达同一个确定类型时，类型参数不可替代。

### 误区10：返回 `List<? extends X>` 总是更灵活

**错误。** 它可能把未知类型负担转嫁给调用方，限制后续写入和组合。

### 误区11：菱形语法会擦掉类型

**错误。** 它让编译器推断类型实参，和原始类型不是一回事。

### 误区12：原始类型只是格式不美观

**错误。** 它会产生非受检操作并可能造成堆污染和延迟异常。

### 误区13：非受检警告不会影响运行

**错误。** 警告意味着编译器无法证明类型安全，运行期可能出现 ClassCastException。

### 误区14：可以在类级统一屏蔽 unchecked

**错误。** 屏蔽范围越大，越容易掩盖真正不安全的转换。

### 误区15：堆污染发生时一定立即抛异常

**错误。** 污染通常发生在写入处，异常可能在很远的读取转换处才出现。

### 误区16：`@SafeVarargs` 会让方法自动安全

**错误。** 它只是开发者承诺，需要方法体真实满足不污染数组的条件。

### 误区17：泛型可变参数与普通集合完全一样

**错误。** 它基于数组，数组和擦除交互会制造额外风险。

### 误区18：不能创建泛型数组只是编译器能力不足

**错误。** 根本冲突在于数组运行时具体化检查与泛型实参擦除。

### 误区19：类型擦除意味着泛型没有运行时影响

**错误。** 编译器会插入转换、生成桥接方法并保留部分签名元数据。

### 误区20：`List<String>` 和 `List<Integer>` 有不同运行时 Class

**错误。** 它们通常共享同一个原始类对象。

### 误区21：可以用 `instanceof List<String>` 检查元素类型

**错误。** 运行时无法按被擦除的类型实参执行这种检查。

### 误区22：反射总能恢复对象实际泛型实参

**错误。** 反射能读部分声明签名，不能神奇恢复任意对象和元素的真实承诺。

### 误区23：泛型类可以声明 `static T`

**错误。** 静态成员属于原始类，无法绑定到某个实例参数化类型。

### 误区24：可以通过 `T.class` 获得类型变量类对象

**错误。** 类型变量不是运行时具体类字面量。

### 误区25：泛型实参可以区分重载

**错误。** 擦除后方法签名可能相同，因此不允许。

### 误区26：桥接方法是开发者写重复代码产生的

**错误。** 它通常是编译器为擦除后多态兼容自动生成的。

### 误区27：泛型可以直接使用基本类型

**错误。** 类型实参必须是引用类型，基本值需要包装类型。

### 误区28：装箱没有任何工程成本

**错误。** 热点或大规模数据中可能增加内存、拆箱和 GC 成本。

### 误区29：泛型约束为 String 就自动非空

**错误。** 类型约束不表达 null 策略。

### 误区30：泛型集合一定不可变

**错误。** 泛型只约束类型，不约束可修改性。

### 误区31：泛型集合一定线程安全

**错误。** 线程安全由实现和同步策略决定。

### 误区32：上界只能写类不能写接口

**错误。** `extends` 同时用于类和接口上界。

### 误区33：多重上界可以把类放在任意位置

**错误。** 若包含类，上界列表中类必须最先出现。

### 误区34：递归边界只是语法炫技

**错误。** 排序和自比较类型中它能表达真实且重要的兼容关系。

### 误区35：`Comparator<T>` 一定比 `Comparator<? super T>` 更准确

**错误。** 下界比较器通常能接受父类型比较策略，复用性更好。

### 误区36：`addAll` 参数写 `Collection<E>` 已经最合理

**错误。** `? extends E` 能安全接受 E 的子类型集合。

### 误区37：通配符捕获只能靠强转解决

**错误。** 私有泛型辅助方法通常能在不破坏安全的前提下捕获未知类型。

### 误区38：复杂泛型签名越高级越好

**错误。** 无法解释类型关系的复杂签名会增加调用和维护成本。

### 误区39：泛型能替代领域校验

**错误。** 它只能检查静态类型，不能验证库存数量、状态和业务不变量。

### 误区40：擦除模型等价于手写 Object 容器

**错误。** 编译器在擦除前完成类型检查并插入必要转换，安全性完全不同。

## 00.40 工程实践建议

1. 新代码中的集合、Class、Comparator 等泛型类型必须参数化，禁止裸用原始类型。
2. 把所有非受检警告视为需要解释的风险，而不是统一关闭的提示。
3. 与旧 API 交互时建立窄小适配层，不让原始类型扩散到领域代码。
4. 只读来源参数优先评估 `? extends T`，扩大安全的调用范围。
5. 写入目标参数优先评估 `? super T`，允许父类型容器接收值。
6. 多个参数或返回值必须保持同一类型时声明显式类型参数。
7. 只需要 size、isEmpty 或 Object 遍历时使用 `Collection<?>`。
8. 避免把通配符放在公共返回类型，除非隐藏元素子类型是明确设计目标。
9. 使用私有泛型辅助方法解决通配符捕获，不用无依据强制转换。
10. 类型参数名称应简短但可解释；复杂领域关系可用语义化名称。
11. 多重上界只用于真实能力约束，不为展示技巧增加签名复杂度。
12. 排序类型优先理解 `Comparable<? super T>` 的兼容意义。
13. 对 `@SuppressWarnings("unchecked")` 使用最小作用域并说明安全证明。
14. 使用 `@SafeVarargs` 前审查方法是否写入或泄露可变参数数组。
15. 泛型可变参数能改为集合参数时，优先采用集合参数。
16. 不要尝试通过泛型实参设计重载，使用不同方法名表达不同语义。
17. 需要构造 T 时显式传入 `Supplier<T>`、工厂或 Class 令牌。
18. 不要依赖反射恢复任意对象的实际元素泛型类型。
19. 大规模数值集合评估装箱、内存和 GC 成本，小规模业务不提前优化。
20. 对集合元素的 null 策略单独声明和校验，不依赖泛型类型名。
21. 泛型 API 还需单独定义可变性、顺序、线程安全和所有权语义。
22. 返回集合时说明是实时视图、只读包装还是独立快照。
23. 不要使用 `Optional<T>` 机械替代集合元素的非空设计。
24. 公开 API 中避免嵌套过深的通配符，必要时引入领域类型。
25. 编写泛型方法前先写出输入、输出和类型等式，再决定 T 与通配符。
26. 保留编译器的 `-Xlint:unchecked` 检查，持续清理新增警告。
27. 代码评审中定位污染发生点，而不是只修复最后的 ClassCastException。
28. 把原始类型迁移分阶段完成：参数化、消除警告、增加边界测试。
29. 对第三方返回的无类型 Map 先验证键值，再转换为领域对象。
30. 不要把泛型类型安全误当作数据来源可信或业务合法。
31. 通配符 API 应配套调用示例，避免团队只背 PECS 口诀。
32. 泛型签名修改需要评估源兼容、二进制兼容和调用方推断变化。
33. 避免在公共 API 暴露实现类参数，优先使用合适的接口类型。
34. 测试泛型边界时同时覆盖父类型、子类型和不兼容类型的编译预期。
35. 通过 IDE 或 javac 查看桥接方法警告时区分编译器生成与业务代码。
36. 将深度泛型、反射泛型和类型令牌留到高级模块，不污染集合入门主线。
37. 领域仓储的 ID 与实体类型使用独立参数，避免把所有值都降为 Object。
38. 集合批量复制签名应表达来源生产、目标消费的方向。
39. 任何 unchecked cast 都应能回答：运行时为什么一定是目标类型。
40. 团队规范中明确：泛型提高编译期安全，但不提供不可变和并发保证。

## 00.41 本章小结

- 泛型把集合元素类型和 API 类型关系放到编译期检查。
- Java 泛型默认不变；数组协变与泛型不变不能混为一谈。
- `? extends T` 适合读取生产者，`? super T` 适合写入消费者。
- 通配符表达未知类型，类型参数表达多个位置之间的同一类型关系。
- 原始类型、非受检转换和不安全可变参数可能制造堆污染。
- 类型擦除不否定泛型价值，编译器仍完成检查、转换和桥接。
- 泛型不自动提供非空、不可变、线程安全或领域合法性。

## 00.42 面试口述版

Java 泛型的核心作用是把类型关系放到编译期，集合因此能够在插入阶段阻止错误元素，而不是读取时再依赖强制转换。泛型默认是不变的，所以 `List<Integer>` 不是 `List<Number>`；需要扩大参数兼容性时使用通配符。只读来源通常使用 `? extends T`，写入目标通常使用 `? super T`，也就是 PECS，但多个位置需要保持同一个确定类型时仍应声明 `<T>`。原始类型和非受检转换会绕过部分检查，可能造成堆污染。Java 泛型主要通过擦除实现，不同参数化类型通常共享运行时 Class，但编译器在擦除前已经完成类型检查、插入转换，并可能生成桥接方法。泛型只保证静态类型关系，不代表集合非空、不可变或线程安全。
