## 10.2 对象创建的总体路径

常见创建方式：

```text
对象创建
├── 直接构造
│   └── new + 构造器
├── 静态工厂
│   └── Type.of(...) / Type.from(...)
├── Builder
│   └── Type.builder()...build()
├── 工厂对象
│   ├── 简单工厂
│   ├── 工厂方法
│   └── 抽象工厂
├── 框架创建
│   ├── 依赖注入容器
│   ├── ORM
│   └── 序列化框架
└── 复制创建
    ├── 拷贝构造器
    ├── 拷贝工厂
    └── withXxx(...)
```

选择创建方式时，应关注：

- 必填参数数量；
- 可选参数数量；
- 参数之间是否存在约束；
- 是否需要返回子类型；
- 是否需要缓存或复用实例；
- 是否需要隐藏具体实现；
- 是否需要表达对象来源；
- 是否需要分阶段组装；
- 是否允许对象创建失败；
- 是否需要框架接管生命周期。

## 10.3 new 表达式与构造器的职责

```java
User user = new User("Java");
```

可以拆为：

```text
new 表达式
→ 请求创建对象

构造器
→ 校验输入
→ 初始化对象状态
→ 建立对象不变量

表达式结果
→ User 引用值
```

### 10.3.1 构造器适合做什么

- 校验必填参数；
- 规范化输入；
- 初始化字段；
- 防御性复制；
- 建立对象不变量；
- 委托到统一初始化路径。

### 10.3.2 构造器不适合做什么

- 网络请求；
- 数据库查询；
- 启动线程；
- 注册全局监听器；
- 发布领域事件；
- 长时间阻塞；
- 复杂重试；
- 大量业务编排；
- 依赖尚未完成构造的子类行为。

### 10.3.3 构造器应尽量确定

相同参数通常应得到具有相同初始语义的对象。

危险：

```java
public User(String id) {
    this.profile =
            remoteService.loadProfile(id);
}
```

问题：

- 创建可能很慢；
- 外部服务失败；
- 隐藏 I/O；
- 难以测试；
- 构造异常复杂；
- 对象创建和数据加载耦合。

更适合由服务或工厂先完成加载，再创建对象。

## 10.4 创建即合法

对象一旦返回给调用方，应尽量已经满足全部不变量。

```java
public final class Percentage {

    private final int value;

    public Percentage(int value) {
        if (value < 0 || value > 100) {
            throw new IllegalArgumentException(
                    "value must be between 0 and 100"
            );
        }

        this.value = value;
    }

    public int value() {
        return value;
    }
}
```

### 10.4.1 不允许半成品

不推荐：

```java
Percentage percentage =
        new Percentage();

percentage.setValue(120);
```

对象可能长期处于非法状态。

### 10.4.2 创建失败应明确

当输入不合法时：

- 抛出参数异常；
- 返回明确结果类型；
- 返回 `Optional`；
- 使用校验结果对象；
- 由工厂区分可恢复失败和编程错误。

不能创建一个“先凑合用”的非法对象。

### 10.4.3 合法状态不等于业务流程完成

订单刚创建时可以是：

```text
合法的 CREATED 状态
```

而不是必须已经支付、发货。

对象需要合法，但不必处于最终状态。

## 10.5 构造器参数设计

### 10.5.1 必填参数直接表达

```java
public Order(
        OrderId id,
        CustomerId customerId,
        List<OrderItem> items
) {
}
```

### 10.5.2 使用值对象减少混淆

不推荐：

```java
public Order(
        String orderId,
        String customerId,
        String addressId
) {
}
```

更清晰：

```java
public Order(
        OrderId orderId,
        CustomerId customerId,
        AddressId addressId
) {
}
```

### 10.5.3 避免布尔参数

```java
new Task(true, false);
```

调用点无法理解。

更适合：

```java
new Task(
        ExecutionMode.ASYNC,
        RetryPolicy.DISABLED
);
```

### 10.5.4 参数顺序应稳定

同类型参数越多，越容易传错：

```java
new Range(10, 20);
```

需要明确：

```java
new Range(
        startInclusive,
        endExclusive
);
```

或者使用静态工厂命名。

## 10.6 伸缩构造器问题

伸缩构造器是通过不断增加重载表达可选参数：

```java
public User(String name) {
    this(name, null);
}

public User(
        String name,
        String email
) {
    this(name, email, true);
}

public User(
        String name,
        String email,
        boolean enabled
) {
}
```

### 10.6.1 主要问题

- 参数顺序难记；
- 同类型参数容易传错；
- 重载数量膨胀；
- 调用点可读性差；
- 默认值分散；
- 新增参数影响多个构造器；
- 布尔参数语义不清；
- 某些组合无法自然表达。

### 10.6.2 何时仍可接受

只有一两个稳定可选参数时：

```java
new Timeout(30);
new Timeout(30, TimeUnit.SECONDS);
```

重载构造器仍然简单清晰。

### 10.6.3 何时切换 Builder

出现以下信号时：

- 四个以上参数；
- 多个可选参数；
- 多个同类型参数；
- 参数存在组合约束；
- 调用点需要自解释；
- 构造过程需要分步骤；
- 未来可能持续扩展。

## 10.7 静态工厂

静态工厂是返回类实例的静态方法。

```java
public final class User {

    private final String name;

    private User(String name) {
        this.name = name;
    }

    public static User of(String name) {
        return new User(name);
    }
}
```

调用：

```java
User user = User.of("Java");
```

### 10.7.1 静态工厂不是设计模式中的工厂方法

`User.of(...)` 是一种创建 API。

GoF 工厂方法模式强调：

- 由抽象方法决定创建哪种产品；
- 子类或实现参与创建逻辑；
- 创建行为属于多态扩展点。

两者不要混为一谈。

---

## 10.8 静态工厂命名

常见命名：

| 名称 | 常见语义 |
|---|---|
| `of(...)` | 由多个明确值创建 |
| `from(...)` | 由另一个表示转换创建 |
| `valueOf(...)` | 根据值获得实例，可能缓存 |
| `parse(...)` | 从文本解析 |
| `getInstance(...)` | 获取实例，可能复用 |
| `newInstance(...)` | 每次倾向创建新实例 |
| `create(...)` | 通用创建 |
| `copyOf(...)` | 复制或规范化创建 |
| `builder()` | 返回 Builder |
| `empty()` | 返回空值对象 |
| `defaultXxx()` | 返回默认配置 |

### 10.8.1 名称表达来源

```java
Money.fromYuan(
        new BigDecimal("105.20")
);
```

比：

```java
new Money(
        new BigDecimal("105.20")
);
```

更明确单位和转换语义。

### 10.8.2 不机械套命名

名称必须与真实行为一致。

例如：

```java
newInstance()
```

若实际返回缓存单例，会误导调用方。

## 10.9 静态工厂的优势

### 10.9.1 有名称

```java
LocalDate.of(2026, 7, 29);
```

比多个同类型构造参数更容易理解。

### 10.9.2 可以返回已有实例

```java
Boolean.valueOf(true);
```

静态工厂可以：

- 缓存；
- 复用；
- 返回单例；
- 返回空对象；
- 返回规范化实例。

构造器每次通常表示新对象创建路径。

### 10.9.3 可以返回子类型

```java
public static List<String> empty() {
    return Collections.emptyList();
}
```

调用方依赖接口或抽象类型，不必知道具体实现。

### 10.9.4 可以隐藏实现类

```java
PaymentGateway gateway =
        PaymentGateways.create(config);
```

具体实现可保持包级或私有嵌套类型。

### 10.9.5 可以在创建前完成复杂决策

```java
public static Parser forFormat(
        Format format
) {
    return switch (format) {
        case JSON -> new JsonParser();
        case XML -> new XmlParser();
    };
}
```

### 10.9.6 可以表达失败

```java
public static Optional<Port> parse(
        String text
) {
}
```

但对违反编程契约的输入，不应滥用 `Optional` 静默吞错。

## 10.10 静态工厂的局限

### 10.10.1 不像构造器那样显眼

调用方需要知道：

```text
of
from
parse
create
getInstance
```

哪个才是创建入口。

### 10.10.2 私有构造器限制继承

如果类只有私有构造器，外部无法继承。

这对值对象通常是优点，但对扩展型框架可能是限制。

### 10.10.3 容易堆积过多工厂方法

```java
create(...)
createDefault(...)
createEmpty(...)
createForTest(...)
createUnsafe(...)
createLegacy(...)
```

需要保持命名和职责清晰。

### 10.10.4 静态方法不便替换

如果调用方直接依赖：

```java
PaymentGateways.create(...)
```

测试和扩展可能比注入工厂接口更困难。

## 10.11 工厂类型边界

### 10.11.1 静态工厂

```java
User.of(name)
```

由类型自身提供创建入口。

### 10.11.2 简单工厂

```java
final class ParserFactory {

    static Parser create(
            Format format
    ) {
        return switch (format) {
            case JSON -> new JsonParser();
            case XML -> new XmlParser();
        };
    }
}
```

集中根据条件创建对象。

### 10.11.3 工厂方法模式

```java
abstract class Application {

    protected abstract Button createButton();
}
```

由子类决定具体产品。

### 10.11.4 抽象工厂

创建一组相互匹配的对象：

```java
interface UiFactory {

    Button createButton();

    Dialog createDialog();
}
```

例如不同操作系统提供一套一致 UI 组件。

### 10.11.5 不要为模式而模式

只有当创建逻辑存在：

- 多实现；
- 家族一致性；
- 扩展需求；
- 外部依赖；
- 测试替换；

才需要独立工厂对象。

## 10.12 Builder 模式

Builder 用于分步骤收集参数，最终一次性创建对象。

```java
User user = User.builder()
        .name("Java")
        .email("java@example.com")
        .enabled(true)
        .build();
```

### 10.12.1 适合场景

- 参数多；
- 可选参数多；
- 参数顺序不直观；
- 需要链式可读性；
- 构造前需要统一校验；
- 目标对象希望保持不可变；
- 配置对象需要逐步组装。

### 10.12.2 不适合场景

只有两个必填参数：

```java
Point.of(10, 20);
```

通常不需要 Builder。

### 10.12.3 Builder 不是 Setter 对象

Builder 可以暂时可变，但目标对象应在 `build()` 时获得独立、合法状态。

## 10.13 手写 Builder

```java
public final class User {

    private final String name;
    private final String email;
    private final boolean enabled;
    private final List<String> roles;

    private User(Builder builder) {
        this.name = builder.name;
        this.email = builder.email;
        this.enabled = builder.enabled;
        this.roles = List.copyOf(builder.roles);
    }

    public static Builder builder() {
        return new Builder();
    }

    public static final class Builder {

        private String name;
        private String email;
        private boolean enabled = true;
        private final List<String> roles =
                new ArrayList<>();

        private Builder() {
        }

        public Builder name(String name) {
            this.name = name;
            return this;
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public Builder enabled(
                boolean enabled
        ) {
            this.enabled = enabled;
            return this;
        }

        public Builder addRole(
                String role
        ) {
            roles.add(role);
            return this;
        }

        public User build() {
            validate();
            return new User(this);
        }

        private void validate() {
            if (
                    name == null
                    || name.isBlank()
            ) {
                throw new IllegalStateException(
                        "name must not be blank"
                );
            }
        }
    }
}
```

### 10.13.1 目标对象复制 Builder 数据

```java
this.roles = List.copyOf(builder.roles);
```

避免已构建对象继续共享 Builder 的可变集合。

### 10.13.2 Builder 可以复用吗

技术上可以：

```java
User first = builder.name("A").build();
User second = builder.name("B").build();
```

前提是目标对象已经复制所有可变状态。

但复用会增加理解成本，工程上通常将 Builder 视为一次性组装器。

## 10.14 Builder 校验

### 10.14.1 单字段即时校验

```java
public Builder retryCount(
        int retryCount
) {
    if (retryCount < 0) {
        throw new IllegalArgumentException();
    }

    this.retryCount = retryCount;
    return this;
}
```

适合与其他字段无关的局部约束。

### 10.14.2 build 时整体校验

```java
public Config build() {
    if (
            secure
            && certificate == null
    ) {
        throw new IllegalStateException(
                "secure mode requires certificate"
        );
    }

    return new Config(this);
}
```

适合跨字段约束。

### 10.14.3 两层校验

推荐：

```text
参数方法
→ 校验局部值

build()
→ 校验组合关系

目标对象构造器
→ 最终防线
```

不要只依赖调用方遵守 Builder 顺序。

### 10.14.4 异常类型

Builder 参数方法：

```text
非法实参
→ IllegalArgumentException
```

`build()` 时缺少必填项或组合非法：

```text
Builder 当前状态不完整
→ IllegalStateException
```

项目也可以统一使用领域校验异常。

## 10.15 Builder 常见陷阱

### 10.15.1 build 后共享集合

危险：

```java
private User(Builder builder) {
    this.roles = builder.roles;
}
```

后续：

```java
builder.addRole("ADMIN");
```

会影响已构建对象。

### 10.15.2 Builder 暴露内部集合

危险：

```java
public List<String> roles() {
    return roles;
}
```

外部可任意修改。

### 10.15.3 必填字段不明显

链式 API：

```java
User.builder().build();
```

直到运行时才发现缺少 `name`。

可考虑分阶段 Builder，但复杂度较高。

### 10.15.4 生成工具不替代设计

Lombok 等工具可以生成 Builder，但不会自动解决：

- 不变量；
- 深度不可变；
- 集合复制；
- 默认值；
- 继承；
- 框架兼容；
- 语义命名。

### 10.15.5 Builder 不应执行业务 I/O

```java
builder.loadFromDatabase();
```

会混淆组装和外部访问。

## 10.16 对象不变量

对象不变量是在对象可被使用时必须始终成立的规则。

例如配置对象：

```text
host 非空
port 在 1～65535
启用 TLS 时证书不能为空
连接超时必须为正数
```

### 10.16.1 创建边界统一校验

```java
private ClientConfig(Builder builder) {
    validate(builder);
    // 再赋值
}
```

### 10.16.2 修改行为继续维护

如果对象可变：

```java
public void changePort(int port) {
    requireValidPort(port);
    this.port = port;
}
```

### 10.16.3 不变量不是 UI 校验

前端校验、Controller 校验和对象校验可以同时存在。

对象边界应防止任何调用路径创建非法状态。

## 10.17 不可变对象

不可变对象表示：

> 对象创建完成后，其对外可观察状态不再改变。

典型类型：

- `String`；
- `Integer`；
- `BigDecimal`；
- `LocalDate`；
- 多数 record 值对象；
- 自定义金额、坐标、标识符。

### 10.17.1 不可变不等于字段少

一个对象可以包含多个字段，只要创建后状态不能变化。

### 10.17.2 不可变不等于没有方法

```java
Money total = price.add(tax);
```

方法可以返回新对象。

### 10.17.3 不可变不等于对象永不变化

变量可以重新指向另一个不可变对象：

```java
Money amount = Money.yuan("10.00");
amount = amount.add(
        Money.yuan("2.00")
);
```

改变的是变量保存的引用值，不是原对象状态。

---

## 10.18 不可变对象的优势

### 10.18.1 状态稳定

创建后不再变化，更容易推理。

### 10.18.2 线程安全基础更好

真正不可变对象可以在多个线程之间共享，而不需要为内部状态变化加锁。

### 10.18.3 适合作为 Map 键

对象状态不会在放入哈希表后改变，避免哈希值漂移。

### 10.18.4 适合缓存

同一个实例可以安全复用。

### 10.18.5 减少防御性复制

不可变对象本身可以共享，不需要每次复制。

### 10.18.6 异常安全

操作失败时，原对象保持不变。

### 10.18.7 缺点

- 每次“修改”可能创建新对象；
- 大对象复制成本高；
- 复杂对象图构建较繁琐；
- ORM 和部分框架适配困难；
- 高频数值更新可能产生分配压力。

---

## 10.19 设计不可变类的基本条件

常见条件：

1. 不提供修改对象状态的方法；
2. 字段通常声明为 `private final`；
3. 构造时完成全部初始化；
4. 不暴露内部可变对象；
5. 对输入可变对象防御性复制；
6. 对输出可变对象返回副本或快照；
7. 防止子类破坏不可变性；
8. 不在构造期间泄漏 `this`；
9. 所依赖对象本身不可变，或被隔离；
10. 派生缓存不改变逻辑状态。

### 10.19.1 防止继承破坏

可以：

```java
public final class Money {
}
```

或者：

- 构造器私有；
- 只暴露受控子类；
- 使用 sealed class；
- 明确为继承设计。

最简单可靠的是 `final` 类。

---

## 10.20 final 字段不等于对象不可变

```java
public final class Group {

    private final List<String> members;

    public Group(
            List<String> members
    ) {
        this.members = members;
    }
}
```

虽然字段不能重新指向另一个列表，但列表内容仍可改变。

### 10.20.1 外部别名修改

```java
List<String> source =
        new ArrayList<>();

Group group = new Group(source);

source.add("A");
```

`group` 的可观察状态变化。

### 10.20.2 Getter 泄漏

```java
public List<String> members() {
    return members;
}
```

调用方可以修改。

### 10.20.3 正确隔离

```java
public Group(
        List<String> members
) {
    this.members =
            List.copyOf(members);
}

public List<String> members() {
    return members;
}
```

当字段本身已是不可修改快照时，可以安全返回同一引用。

前提是元素也满足目标不可变边界。

## 10.21 构造输入的防御性复制

### 10.21.1 集合

```java
this.items = List.copyOf(items);
```

### 10.21.2 数组

```java
this.bytes = bytes.clone();
```

### 10.21.3 可变日期对象

旧式 `Date`：

```java
this.createdAt =
        new Date(createdAt.getTime());
```

现代代码优先使用不可变时间类型：

```java
Instant
LocalDate
LocalDateTime
ZonedDateTime
```

### 10.21.4 自定义可变对象

```java
this.address =
        Address.copyOf(address);
```

### 10.21.5 先校验还是先复制

若输入可能被并发修改，理想流程是：

```text
先复制
↓
校验副本
↓
保存副本
```

避免：

```text
校验原对象
↓
原对象被修改
↓
保存不同状态
```

普通单线程边界也应保持逻辑一致。

## 10.22 输出的防御性复制

### 10.22.1 返回数组副本

```java
public byte[] bytes() {
    return bytes.clone();
}
```

### 10.22.2 返回不可修改集合

字段已保存不可修改快照：

```java
public List<Item> items() {
    return items;
}
```

字段仍为可变集合：

```java
public List<Item> items() {
    return List.copyOf(items);
}
```

### 10.22.3 不可修改外层不代表元素不可变

```java
List<MutableItem> items
```

即使列表不能增删：

```java
items.get(0).setName("changed");
```

仍可能修改元素。

### 10.22.4 返回投影

不需要暴露元素对象时：

```java
public List<ItemView> itemViews() {
    return items.stream()
            .map(ItemView::from)
            .toList();
}
```

## 10.23 数组与不可变设计

数组始终可变。

```java
private final byte[] digest;
```

`final` 只保证字段引用不能重新赋值。

### 10.23.1 构造复制

```java
public Digest(byte[] digest) {
    this.digest = digest.clone();
}
```

### 10.23.2 Getter 复制

```java
public byte[] bytes() {
    return digest.clone();
}
```

### 10.23.3 二维数组

```java
int[][] matrix
```

只调用：

```java
matrix.clone()
```

仅复制外层数组。

需要逐行复制。

### 10.23.4 大数组性能

频繁复制大数组成本较高。

可考虑：

- 只读缓冲区；
- 分片；
- 所有权转移；
- 明确不再使用原数组；
- 内部流式处理；
- 文档化借用协议。

Java 没有内建所有权类型，必须谨慎表达。

## 10.24 集合复制语义

### 10.24.1 可修改浅拷贝

```java
List<Item> copy =
        new ArrayList<>(source);
```

- 新列表结构；
- 可增删；
- 源列表结构变化不可见；
- 元素引用共享。

### 10.24.2 不可修改视图

```java
List<Item> view =
        Collections.unmodifiableList(
                source
        );
```

- 不允许通过视图增删；
- 源列表变化可见；
- 元素引用共享。

### 10.24.3 不可修改快照语义

```java
List<Item> snapshot =
        List.copyOf(source);
```

- 不允许增删；
- 不允许 `null` 元素；
- 通常隔离源列表后续结构变化；
- 允许实现复用已有不可修改实例；
- 元素引用共享。

### 10.24.4 深度不可变集合

需要：

```text
外层集合不可修改
+
每个元素不可变
+
元素内部引用也满足不可变边界
```

## 10.25 record 与不可变设计

```java
public record Group(
        String name,
        List<String> members
) {
}
```

record 组件字段具有 final 语义，但 `members` 列表仍可变。

### 10.25.1 紧凑构造器复制

```java
public record Group(
        String name,
        List<String> members
) {
    public Group {
        if (
                name == null
                || name.isBlank()
        ) {
            throw new IllegalArgumentException();
        }

        members =
                List.copyOf(members);
    }
}
```

### 10.25.2 自动访问器返回字段引用

```java
group.members()
```

如果构造时已经保存不可修改快照，可以直接返回。

### 10.25.3 record 不是完整不可变保证

仍需检查：

- 数组组件；
- 可变集合；
- 自定义可变对象；
- 懒加载代理；
- 可变缓存；
- 静态共享状态。

## 10.26 拷贝构造器

```java
public User(User source) {
    this.name = source.name;
    this.roles =
            List.copyOf(source.roles);
}
```

### 10.26.1 优点

- 类型明确；
- 可自定义复制边界；
- 不依赖 `Cloneable`；
- 可以执行校验；
- 可以复制父类可见状态；
- 调用简单。

### 10.26.2 局限

- 只能接受当前类型或显式父类型；
- 子类复制可能丢失运行时类型；
- 复制语义需要文档；
- 深层对象处理复杂。

### 10.26.3 适合值对象和配置对象

尤其是：

```java
new Config(oldConfig)
```

用于创建独立副本。

---

## 10.27 拷贝工厂

```java
public static User copyOf(
        User source
) {
    return new User(source);
}
```

### 10.27.1 优势

- 有名称；
- 可以返回原实例；
- 可以返回子类型；
- 可以规范化；
- 可以缓存；
- 可以接收接口类型；
- 可以根据来源选择复制策略。

### 10.27.2 返回原实例

当来源已经不可变且类型满足要求：

```java
public static ImmutableValue copyOf(
        ImmutableValue source
) {
    return source;
}
```

静态工厂可以避免无意义复制。

### 10.27.3 名称必须说明语义

```text
copyOf
→ 调用方通常期望结果与来源逻辑独立

from
→ 更偏向表示转换

wrap
→ 可能共享底层对象

viewOf
→ 明确是视图
```

## 10.28 withXxx 方法

不可变对象需要修改一个属性时，可以返回新对象。

```java
public User withEmail(
        String newEmail
) {
    return new User(
            name,
            newEmail,
            roles
    );
}
```

### 10.28.1 原对象不变

```java
User updated =
        original.withEmail(
                "new@example.com"
        );
```

### 10.28.2 可以复用当前实例

```java
public User withEmail(
        String newEmail
) {
    if (Objects.equals(
            email,
            newEmail
    )) {
        return this;
    }

    return new User(
            name,
            newEmail,
            roles
    );
}
```

### 10.28.3 适合少量属性变化

如果属性很多且一次修改多个：

```java
user.toBuilder()
        .email(...)
        .enabled(...)
        .build();
```

可能更清晰。

### 10.28.4 名称区别

```text
setEmail
→ 通常暗示修改当前对象

withEmail
→ 通常暗示返回新对象
```

API 应保持一致。

## 10.29 toBuilder

```java
public Builder toBuilder() {
    return new Builder()
            .name(name)
            .email(email)
            .enabled(enabled)
            .roles(roles);
}
```

### 10.29.1 Builder 必须复制集合

```java
public Builder roles(
        Collection<String> roles
) {
    this.roles.clear();
    this.roles.addAll(roles);
    return this;
}
```

不能让 Builder 与原对象共享可变集合。

### 10.29.2 用途

```java
User updated =
        original.toBuilder()
                .email("new@example.com")
                .build();
```

### 10.29.3 风险

- Builder 代码较多；
- 复制成本；
- 默认值覆盖；
- 字段新增时遗漏复制；
- 生成工具与手写逻辑不一致。

需要测试所有字段能否完整保留。

## 10.30 浅拷贝与深拷贝

### 10.30.1 浅拷贝

```text
复制外层对象
内部引用继续共享
```

### 10.30.2 深拷贝

```text
复制外层对象
并复制需要隔离的内部可变对象
```

### 10.30.3 深拷贝没有通用深度

例如订单包含：

```text
Customer
Address
Product
PaymentGateway
Logger
```

不应机械复制所有对象。

### 10.30.4 按所有权复制

```text
对象拥有的可变值
→ 复制

共享的不可变对象
→ 复用

外部服务和资源
→ 不复制

实体引用
→ 根据领域语义决定
```

### 10.30.5 序列化深拷贝

通过 JSON 或 Java 序列化复制对象：

- 性能差；
- 丢失类型细节；
- 依赖序列化配置；
- 无法处理资源；
- 可能触发安全问题；
- 不是通用推荐方案。

## 10.31 不可变对象的派生值缓存

不可变对象状态不变，派生值可以缓存。

```java
public final class Polygon {

    private final List<Point> points;
    private volatile Double cachedArea;

    public double area() {
        Double result = cachedArea;

        if (result != null) {
            return result;
        }

        double calculated =
                calculateArea(points);

        cachedArea = calculated;
        return calculated;
    }
}
```

### 10.31.1 逻辑不可变

缓存字段发生变化，但对象对外业务状态不变。

这种对象通常称为：

```text
逻辑不可变
```

### 10.31.2 仍需线程安全

多个线程可能同时计算并写入缓存。

如果重复计算无害，可以接受。

若要求严格一次计算，需要：

- `volatile`；
- 同步；
- 初始化持有者；
- 原子更新；
- 预计算。

### 10.31.3 优先预计算简单值

若派生值便宜，构造时直接计算更简单。

不要为了极小收益引入复杂懒加载。

---

## 10.32 安全发布边界

正确构造的不可变对象还需要被安全发布给其他线程。

常见方式：

- 静态初始化；
- `final` 字段持有；
- `volatile` 引用；
- 锁保护；
- 并发集合；
- 线程启动前完成赋值；
- 依赖注入容器的安全生命周期。

### 10.32.1 构造期间不泄漏 this

否则其他线程可能看到半初始化状态。

### 10.32.2 final 字段语义

正确构造且未提前泄漏时，`final` 字段具有特殊可见性保证。

完整 Java 内存模型规则见并发模块。

## 10.33 实例控制

类可以通过受控创建限制实例数量或身份。

### 10.33.1 单例

```java
public enum ApplicationClock {
    INSTANCE;
}
```

枚举单例具有：

- 语言级单实例语义；
- 序列化支持；
- 防止普通反射重复构造；
- 简洁线程安全初始化。

### 10.33.2 静态 final 实例

```java
public final class EmptyValue {

    public static final EmptyValue INSTANCE =
            new EmptyValue();

    private EmptyValue() {
    }
}
```

### 10.33.3 缓存小对象

```java
public static Percentage of(
        int value
) {
    return CACHE[value];
}
```

适合有限值域。

### 10.33.4 实例控制的风险

- 全局状态；
- 测试污染；
- 生命周期不明确；
- 隐藏依赖；
- 内存长期占用；
- 错误缓存可变对象。

## 10.34 单例不等于全局可变状态

单例只是：

```text
某类型受控地只有一个实例
```

该实例可以是：

- 无状态服务；
- 不可变配置；
- 有状态全局对象。

真正风险来自：

```text
单例
+
可变状态
+
隐藏依赖
+
并发共享
```

### 10.34.1 依赖注入优于硬编码获取

不推荐：

```java
GlobalConfig.getInstance()
```

散落在业务代码中。

更适合：

```java
public Service(
        Config config
) {
    this.config = config;
}
```

### 10.34.2 容器单例作用域

Spring 单例通常表示：

```text
每个容器一个实例
```

不等于：

```text
整个 JVM 永远唯一
```

具体范围取决于容器和类加载边界。

## 10.35 对象池

对象池复用昂贵资源：

- 数据库连接；
- 网络连接；
- 线程；
- 大型缓冲区；
- 本地资源句柄。

### 10.35.1 不适合普通小对象

不要池化：

- DTO；
- `StringBuilder` 小实例；
- 短生命周期值对象；
- 普通命令对象；
- 轻量集合。

现代 JVM 对短生命周期小对象分配通常优化良好。

对象池反而增加：

- 状态重置；
- 并发控制；
- 污染风险；
- 泄漏；
- 生命周期复杂度；
- 池耗尽问题。

### 10.35.2 池对象必须重置

复用前需要清理：

- 用户数据；
- 缓冲区位置；
- 事务状态；
- 超时配置；
- 异常标记；
- 安全凭据。

遗漏重置会造成严重数据串扰。

## 10.36 依赖注入与对象创建

依赖注入容器负责：

- 创建对象；
- 解析依赖；
- 管理作用域；
- 生命周期回调；
- 代理；
- 配置；
- 销毁。

### 10.36.1 构造器注入

```java
public OrderService(
        OrderRepository repository,
        PaymentGateway paymentGateway
) {
    this.repository = repository;
    this.paymentGateway = paymentGateway;
}
```

优势：

- 依赖明确；
- 对象创建即完整；
- 便于测试；
- 可使用 `final` 字段；
- 减少空依赖。

### 10.36.2 Setter 注入

适合真正可选、可替换依赖。

但可能出现：

- 半初始化对象；
- 运行时缺失；
- 状态变化；
- 并发可见性问题。

### 10.36.3 服务定位器

```java
ServiceLocator.get(...)
```

隐藏依赖，通常不如构造器注入清晰。

## 10.37 框架创建与不变量

### 10.37.1 ORM

ORM 可能要求：

- 无参构造器；
- 字段反射写入；
- Setter；
- 代理子类；
- 延迟加载。

### 10.37.2 序列化框架

可能：

- 绕过普通工厂；
- 直接设置字段；
- 使用反射；
- 使用无参构造器；
- 根据注解调用指定创建器。

### 10.37.3 风险

对象可能绕过：

```text
公共构造器校验
静态工厂校验
Builder 校验
```

### 10.37.4 处理方式

- 框架专用构造器限制可见性；
- 反序列化后校验；
- 使用不可变类型专用创建器；
- DTO 与领域对象分离；
- 映射层调用领域工厂；
- 使用数据库约束作为最后防线。

## 10.38 反序列化与不变量

反序列化输入可能来自不可信来源。

需要校验：

- 必填字段；
- 范围；
- 枚举未知值；
- 集合大小；
- 重复项；
- 字符串长度；
- 对象图深度；
- 类型白名单；
- 敏感字段；
- 版本兼容。

### 10.38.1 不信任构造器曾经执行

某些机制可能不经过普通构造路径。

### 10.38.2 映射到命令对象

推荐边界：

```text
JSON
↓
DTO
↓ 校验
领域工厂
↓
合法领域对象
```

避免直接把外部数据灌入领域实体。

## 10.39 金额值对象示例

```java
public final class Money {

    private final long amountInFen;
    private final Currency currency;

    private Money(
            long amountInFen,
            Currency currency
    ) {
        this.amountInFen = amountInFen;
        this.currency =
                Objects.requireNonNull(currency);
    }

    public static Money cnyFen(
            long amountInFen
    ) {
        return new Money(
                amountInFen,
                Currency.getInstance("CNY")
        );
    }

    public static Money cnyYuan(
            String amount
    ) {
        BigDecimal yuan =
                new BigDecimal(amount);

        long fen = yuan
                .movePointRight(2)
                .longValueExact();

        return cnyFen(fen);
    }

    public Money add(Money other) {
        requireSameCurrency(other);

        return new Money(
                Math.addExact(
                        amountInFen,
                        other.amountInFen
                ),
                currency
        );
    }

    private void requireSameCurrency(
            Money other
    ) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException(
                    "currency mismatch"
            );
        }
    }
}
```

## 10.41 可变对象何时合理

不可变不是唯一正确答案。

可变对象适合：

- 聚合实体的生命周期状态；
- GUI 控件；
- 缓冲区；
- Builder；
- 累加器；
- 状态机；
- ORM 实体；
- 高性能原地算法；
- 线程封闭的工作对象。

### 10.41.1 可变对象设计要求

- 修改入口少；
- 方法表达业务语义；
- 每次修改维护不变量；
- 不暴露内部可变状态；
- 并发策略明确；
- 生命周期明确；
- 失败时避免半修改。

### 10.41.2 可变与不可变组合

常见设计：

```text
实体
→ 可变状态
→ 通过业务方法转换

值对象
→ 不可变
→ 安全共享

DTO
→ 可变或 record
→ 仅用于边界传输
```

## 10.42 常见错误

### 10.42.1 构造器参数未复制

```java
this.items = items;
```

外部可修改内部状态。

### 10.42.2 Getter 返回内部数组

```java
return bytes;
```

调用方可修改。

### 10.42.3 Builder 与目标对象共享集合

```java
this.roles = builder.roles;
```

Builder 后续变化污染对象。

### 10.42.4 record 包含可变集合但未复制

组件 final 不等于列表不可变。

### 10.42.5 `unmodifiableList` 当作快照

源列表变化仍可见。

### 10.42.6 `List.copyOf` 当作深拷贝

元素对象仍共享。

### 10.42.7 单例持有请求状态

多个请求共享可变字段，产生竞态和数据串扰。

### 10.42.8 为小对象建立对象池

增加复杂度却未必提升性能。

### 10.42.9 Builder 只为两参数对象服务

API 冗长，失去直接构造的简洁性。

### 10.42.10 静态工厂名称与行为不一致

`newInstance()` 返回缓存对象，会误导调用方。

## 10.45 易错点

### 误区一：对象只能通过 new 创建

**错误。**

还可能通过工厂、框架、反射、反序列化和复制路径创建。

### 误区二：构造器应该完成对象相关的所有工作

**错误。**

构造器应建立合法状态，不应承担网络、数据库和复杂编排。

### 误区三：构造器参数越多越能保证对象完整

**错误。**

过多参数会降低可读性并暴露职责过重问题。

### 误区四：所有对象都应该使用 Builder

**错误。**

简单值对象直接构造或静态工厂更清晰。

### 误区五：Builder 就是把 Setter 改成链式调用

**错误。**

Builder 应最终创建独立、合法的目标对象。

### 误区六：Builder 构建后可以与目标对象共享可变集合

**错误。**

Builder 后续修改会污染已创建对象。

### 误区七：生成 Builder 后就不需要手写校验

**错误。**

生成工具不会理解业务不变量。

### 误区八：静态工厂每次都创建新对象

**错误。**

它可以缓存、复用或返回子类型。

### 误区九：静态工厂和 GoF 工厂方法模式是同一概念

**错误。**

两者的抽象层次和扩展机制不同。

### 误区十：静态工厂一定比构造器好

**错误。**

简单直接创建时，构造器更显式。

### 误区十一：不可变对象就是所有字段 final

**错误。**

字段引用对象可能仍然可变。

### 误区十二：final List 表示列表内容不可变

**错误。**

只限制字段不能重新赋值。

### 误区十三：返回不可修改列表就一定实现深度不可变

**错误。**

列表元素仍可能是可变对象。

### 误区十四：`Collections.unmodifiableList()` 会复制源列表

**错误。**

它通常提供不可修改视图。

### 误区十五：`List.copyOf()` 会递归复制元素

**错误。**

它只隔离列表结构语义。

### 误区十六：record 天然深度不可变

**错误。**

组件引用对象仍可能可变。

### 误区十七：record 自动访问器会返回集合副本

**错误。**

默认返回组件字段引用。

### 误区十八：拷贝构造器天然是深拷贝

**错误。**

复制深度由实现决定。

### 误区十九：深拷贝越彻底越好

**错误。**

资源对象和共享实体通常不应被机械复制。

### 误区二十：JSON 序列化是可靠通用深拷贝方案

**错误。**

存在性能、类型、配置和安全问题。

### 误区二十一：不可变对象不能缓存计算结果

**错误。**

可以进行不改变逻辑状态的缓存，但需处理线程安全。

### 误区二十二：有缓存字段就一定不是不可变对象

**不准确。**

可区分逻辑状态和内部派生缓存。

### 误区二十三：单例天然线程安全

**错误。**

实例创建可以线程安全，但内部可变状态仍需同步。

### 误区二十四：单例一定是反模式

**错误。**

无状态或不可变的受控实例可以合理存在。

### 误区二十五：Spring 单例在所有容器和类加载器中只有一个

**错误。**

通常是每个容器一个实例。

### 误区二十六：对象池可以减少所有对象分配成本

**错误。**

普通小对象池化往往增加复杂度和竞争。

### 误区二十七：池中对象归还后无需清理

**错误。**

残留状态会造成数据串扰。

### 误区二十八：构造器注入只是框架风格问题

**错误。**

它能明确依赖并帮助对象创建即完整。

### 误区二十九：Setter 注入更灵活，所以应默认使用

**错误。**

它会扩大可变状态并产生半初始化风险。

### 误区三十：反序列化一定经过公共构造器

**错误。**

具体机制可能绕过普通创建路径。

### 误区三十一：数据库约束可以替代对象不变量

**错误。**

二者处于不同边界，应协同保证一致性。

### 误区三十二：不可变对象适合所有实体

**错误。**

具有持续生命周期和状态转换的实体通常需要受控可变性。

### 误区三十三：可变对象一定设计不好

**错误。**

Builder、缓冲区、状态机和实体都可能合理可变。

### 误区三十四：防御性复制不需要考虑性能

**错误。**

大集合和大数组复制成本可能很高。

### 误区三十五：为了性能可以完全不复制

**错误。**

必须明确所有权、共享和修改契约。

### 误区三十六：`withXxx()` 一定创建新对象

**错误。**

值未变化时可以返回当前实例。

### 误区三十七：`copyOf()` 一定创建新实例

**错误。**

来源已经不可变时可以复用。

### 误区三十八：静态工厂返回接口就一定降低耦合

**不一定。**

调用方仍可能依赖静态入口和隐藏全局配置。

### 误区三十九：私有构造器只用于单例

**错误。**

还可用于静态工厂、工具类和实例控制。

### 误区四十：创建 API 只影响写法，不影响系统设计

**错误。**

创建方式决定不变量、实现隐藏、生命周期和依赖边界。

## 10.46 工程实践建议

1. 对象创建完成后立即满足全部不变量。
2. 构造器只执行确定、快速、无外部副作用的初始化。
3. 必填参数使用构造器或命名静态工厂明确表达。
4. 同类型参数较多时引入值对象或命名工厂。
5. 两三个清晰参数不强行使用 Builder。
6. 可选参数多、组合约束复杂时使用 Builder。
7. Builder 在 `build()` 时统一校验跨字段规则。
8. 目标对象复制 Builder 中的所有可变数据。
9. 默认把 Builder 视为一次性对象。
10. 静态工厂名称准确表达来源、单位和复用语义。
11. 不让 `newInstance()` 返回缓存对象。
12. 创建逻辑需要可替换时注入工厂接口，而不是硬编码静态工厂。
13. 不可变类优先声明为 `final`。
14. 不可变对象字段使用 `private final`，但继续检查字段对象的可变性。
15. 构造器先复制可变输入，再校验并保存副本。
16. 数组在输入和输出边界都复制。
17. 集合区分可修改副本、不可修改视图和不可修改快照。
18. 深度不可变要求元素及其内部状态也不可变。
19. record 包含集合或数组时显式复制。
20. 拷贝 API 的名称清楚说明复制、视图还是包装语义。
21. `withXxx()` 用于少量不可变更新，批量更新使用 `toBuilder()`。
22. `toBuilder()` 编写字段完整性回归测试。
23. 深拷贝按所有权和领域边界定义。
24. 不使用通用序列化作为默认深拷贝方案。
25. 派生值便宜时优先直接计算，避免复杂懒缓存。
26. 懒缓存跨线程使用时明确可见性和重复计算语义。
27. 不在构造期间发布 `this`。
28. 单例内部尽量保持无状态或不可变。
29. 业务代码通过构造器注入单例服务，不直接查找全局实例。
30. 只池化真正昂贵且可安全重置的资源。
31. 框架专用创建路径不能绕过领域不变量。
32. 外部 DTO 经过校验和映射后再创建领域对象。
33. 金额使用十进制或最小货币单位，不使用 `double`。
34. 可变实体通过业务方法维护状态，不开放任意 Setter。
35. 对创建失败、复制隔离和非法组合编写单元测试。
36. 性能优化前测量复制成本，不凭感觉牺牲封装。

## 10.48 本章总结

### 10.48.1 创建方式

```text
简单、必填参数少
→ 构造器或命名静态工厂

可选参数多、组合复杂
→ Builder

需要隐藏实现或选择子类型
→ 静态工厂或工厂对象

需要复制已有对象
→ 拷贝构造器、copyOf、withXxx
```

### 10.48.2 创建目标

```text
输入校验
↓
规范化
↓
防御性复制
↓
建立不变量
↓
返回合法对象
```

### 10.48.3 不可变对象

```text
private final 字段
+
创建完成后无状态修改
+
不暴露内部可变对象
+
防止子类破坏
+
构造期间不泄漏 this
=
可靠不可变设计
```

### 10.48.4 复制语义

```text
new ArrayList
→ 可修改浅拷贝

unmodifiableList
→ 不可修改视图
→ 源变化可见

List.copyOf
→ 不可修改快照语义
→ 元素仍共享

深拷贝
→ 按领域所有权复制内部可变对象
```

### 10.48.5 面试口述版

对象创建 API 的目标是让对象从诞生开始就处于合法状态。参数少且语义明确时可以直接使用构造器；需要表达来源、单位、缓存、子类型或实现隐藏时适合静态工厂；可选参数多、组合约束复杂时适合 Builder。Builder 只是临时可变组装器，`build()` 必须完成统一校验，并让目标对象复制所有可变数据。

不可变对象创建后对外可观察状态不再改变。仅有 `final` 字段并不足以保证不可变，因为字段可能引用可变集合、数组或自定义对象。构造器应复制可变输入，Getter 应避免暴露内部状态。`new ArrayList<>(source)` 是可修改浅拷贝，`Collections.unmodifiableList(source)` 是不可修改视图，`List.copyOf(source)` 提供不可修改快照语义，但都不会自动深拷贝元素。

不可变对象容易推理、缓存和跨线程共享，但并不适合所有实体。具有生命周期和状态转换的实体可以保持受控可变，关键是通过业务方法维护不变量。单例、对象池、依赖注入和框架创建都属于对象生命周期设计的一部分，必须明确所有权、共享范围和创建约束。
