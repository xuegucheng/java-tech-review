# Java 接口设计

> 本章聚焦 Java 接口的语言规则、契约设计和工程边界。接口不是“只有抽象方法的特殊类”，而是独立的引用类型：它可以定义行为契约、默认实现、静态工厂和内部复用逻辑，并允许一个类同时承担多个角色。

## 14.2 接口解决什么问题

接口主要解决三个问题：

1. **统一角色**：不同类只要满足同一契约，就能被统一调用；
2. **多能力组合**：类只能直接继承一个类，却可以实现多个接口；
3. **隔离依赖方向**：调用方依赖稳定契约，而不是具体实现细节。

例如支付网关：

```java
public interface PaymentGateway {

    PaymentResult pay(
            PaymentRequest request
    );
}
```

不同实现可以拥有完全不同的状态和依赖：

```text
CardPaymentGateway
→ HTTP 客户端、签名密钥、重试策略

WalletPaymentGateway
→ 钱包 SDK、商户号、风控服务

FakePaymentGateway
→ 测试数据和调用记录
```

调用方只依赖：

```text
PaymentGateway.pay(PaymentRequest)
```

### 14.2.1 接口描述“角色”，不是存放代码的容器

合理接口应能回答：

```text
这个对象在当前协作中扮演什么角色？
调用方可以依赖哪些稳定承诺？
```

不合理接口常常只能回答：

```text
为了让 Spring 注入方便
为了 Mock
为了每个类都有一个 I 前缀
```

### 14.2.2 接口不自动带来低耦合

如果接口：

- 暴露几十个实现细节方法；
- 参数和返回值全是具体框架类型；
- 每次实现变化都必须修改接口；
- 只有一个调用方却复制整个提供方 API；

即使代码中出现 `interface`，耦合仍然很高。

## 14.3 接口是独立的引用类型

声明接口：

```java
public interface InventoryReader {

    int availableQuantity(String skuId);
}
```

接口不是类，但和类一样属于引用类型。

它可以用于：

- 局部变量；
- 字段；
- 方法参数；
- 方法返回值；
- 泛型参数和边界；
- 数组元素类型；
- `instanceof` 模式；
- sealed 类型层次；
- Lambda 的目标类型（函数式接口）。

### 14.3.1 接口没有对象布局模板

接口本身不声明普通实例字段，也没有构造器。

真正对象由实现类创建：

```java
InventoryReader reader =
        new DatabaseInventoryReader();
```

这里：

```text
编译时类型
→ InventoryReader

运行时类型
→ DatabaseInventoryReader
```

### 14.3.2 接口可以扩展多个接口

```java
public interface ReadWriteChannel
        extends ReadableChannel,
                WritableChannel {
}
```

接口多继承的是契约和可继承方法，不是多份对象状态。

---

## 14.4 接口不能直接实例化

错误：

```java
// InventoryReader reader =
//         new InventoryReader();
```

接口没有完整实现和构造过程，不能直接通过 `new` 创建。

### 14.4.1 可以创建实现类对象

```java
InventoryReader reader =
        new DatabaseInventoryReader();
```

### 14.4.2 可以创建匿名实现

```java
InventoryReader reader =
        new InventoryReader() {

            @Override
            public int availableQuantity(
                    String skuId
            ) {
                return 100;
            }
        };
```

实际创建的是编译器生成的匿名实现类对象，不是接口对象。

### 14.4.3 函数式接口可由 Lambda 提供实现

```java
InventoryReader reader = skuId -> 100;
```

Lambda 也不会让接口“自身被实例化”；运行时会产生满足该目标类型的函数对象表示。

---

## 14.5 类实现接口

类通过 `implements` 声明实现关系：

```java
public final class DatabaseInventoryReader
        implements InventoryReader {

    @Override
    public int availableQuantity(
            String skuId
    ) {
        return 100;
    }
}
```

### 14.5.1 具体类必须完成抽象契约

若具体类没有实现所有继承到的抽象方法，编译失败。

```java
// 编译错误：未实现 availableQuantity
// public final class BrokenReader
//         implements InventoryReader {
// }
```

### 14.5.2 抽象类可以只实现一部分

```java
public abstract class BaseInventoryReader
        implements InventoryReader {

    protected final void validateSku(
            String skuId
    ) {
        if (skuId == null || skuId.isBlank()) {
            throw new IllegalArgumentException(
                    "skuId is blank"
            );
        }
    }
}
```

抽象类可以把未实现契约继续留给具体子类，详细规则见第 13 章。

### 14.5.3 一个类可以实现多个接口

```java
public final class WarehouseDevice
        implements Startable,
                   Stoppable,
                   Monitorable {
}
```

这表示同一个对象可以同时扮演多个角色。

## 14.6 接口抽象方法

最简声明：

```java
public interface InventoryReader {

    int availableQuantity(String skuId);
}
```

没有 `private`、`default` 或 `static` 修饰，并且没有方法体的接口实例方法，隐式为：

```java
public abstract
```

完整写法：

```java
public abstract int availableQuantity(
        String skuId
);
```

通常不显式书写 `public abstract`，以减少噪声。

### 14.6.1 抽象方法以分号结束

```java
int size();
```

不能给普通抽象接口方法写方法体：

```java
// int size() {
//     return 0;
// }
```

需要方法体时，应使用 `default`、`static` 或 `private`。

### 14.6.2 接口抽象方法是实例行为契约

它描述实现对象必须提供的行为：

```text
任何 InventoryReader 对象
都能回答 availableQuantity(skuId)
```

接口本身不规定对象如何保存数据库连接、缓存、远程客户端或测试数据。

---

## 14.7 接口方法的访问权限与非法修饰符

接口抽象方法和默认方法对实现对象的调用方可见，因此必须是 `public`。

实现时不能缩小权限：

```java
public final class DatabaseInventoryReader
        implements InventoryReader {

    @Override
    public int availableQuantity(
            String skuId
    ) {
        return 100;
    }
}
```

错误：

```java
// @Override
// int availableQuantity(String skuId) {
//     return 100;
// }
```

### 14.7.1 不支持 `protected` 接口实例方法

接口用于公开契约，不提供类继承体系中的 `protected` 扩展点。

若需要受控子类扩展点，应考虑抽象类或组合对象。

### 14.7.2 抽象接口方法不能是 `final`

```text
abstract
→ 要求实现

final
→ 禁止重写
```

语义冲突。

### 14.7.3 抽象接口方法不能是 `static`

静态方法属于接口本身，不由对象实现，不参与实例方法动态分派。

### 14.7.4 接口实例方法不能使用 `synchronized` 或 `native`

同步策略和本地实现属于具体实现细节，不应由无方法体的接口抽象方法直接声明。

接口契约可以用文档说明线程安全要求，但实现方式由实现类决定。

---

## 14.8 实现方法的重写规则

实现接口方法本质上仍然是方法重写，因此遵循重写规则。

### 14.8.1 方法签名必须匹配

```java
public interface Converter {

    Number convert(String value);
}
```

实现：

```java
public final class IntegerConverter
        implements Converter {

    @Override
    public Integer convert(
            String value
    ) {
        return Integer.valueOf(value);
    }
}
```

### 14.8.2 允许协变返回类型

接口返回 `Number`，实现可返回更具体的 `Integer`。

### 14.8.3 受检异常只能保持或缩小

```java
public interface Loader {

    String load()
            throws java.io.IOException;
}
```

实现可以：

- 抛同一异常；
- 抛其子类；
- 不抛受检异常。

不能扩大为更宽的受检异常。

### 14.8.4 `@Override` 应始终保留

它能让编译器发现：

- 方法名拼写错误；
- 参数列表不匹配；
- 泛型签名误差；
- 意外重载而非重写。

## 14.9 接口字段规则

接口字段隐式为：

```java
public static final
```

示例：

```java
public interface Protocol {

    int VERSION = 1;
}
```

等价于：

```java
public static final int VERSION = 1;
```

### 14.9.1 接口字段必须在声明时初始化

错误：

```java
// public interface Protocol {
//     int VERSION;
// }
```

接口没有构造器，不能等待对象构造时赋值。

### 14.9.2 接口字段属于接口本身

推荐访问方式：

```java
int version = Protocol.VERSION;
```

不要通过实现类或对象访问，以免误导读者认为它是实例状态。

### 14.9.3 `final` 引用不代表对象不可变

```java
public interface Registry {

    java.util.List<String> NAMES =
            new java.util.ArrayList<>();
}
```

`NAMES` 引用不能重新赋值，但列表内容仍可修改。

公开可变接口字段会形成全局共享状态，应避免。

---

## 14.10 接口字段不一定是编译期常量

编译期常量变量必须满足：

- 基本类型或 `String`；
- `final`；
- 使用常量表达式初始化。

```java
public interface Limits {

    int DEFAULT_SIZE = 100;

    String PREFIX = "WMS-";
}
```

这些通常是常量变量。

但下面不是编译期常量：

```java
public interface RuntimeConfig {

    int SIZE = Integer.parseInt("100");

    Object MARKER = new Object();
}
```

虽然字段仍是 `public static final`，初始化表达式不是常量表达式。

### 14.10.1 常量可能被调用方内联

调用方编译时可能把 `Limits.DEFAULT_SIZE` 的值直接写入自身字节码。

只替换提供方 JAR、不重新编译调用方时，调用方可能继续使用旧值。

### 14.10.2 非常量字段访问通常触发接口初始化

访问运行期计算字段时，JVM 需要执行接口字段初始化逻辑。

接口初始化的详细 JVM 过程见 JVM 模块；本章只需记住：

```text
public static final
不等于
一定是编译期常量
```

## 14.11 常量接口反模式

反例：

```java
public interface OrderConstants {

    String CREATED = "CREATED";

    String COMPLETED = "COMPLETED";
}
```

然后某个类仅为了省略限定名而实现接口：

```java
public final class OrderService
        implements OrderConstants {
}
```

问题：

- `implements` 没有角色语义；
- 常量被污染到实现类公共 API；
- 调用方误以为实现类具备某种行为能力；
- 后续删除或移动常量更困难；
- 容易演变成杂物抽屉。

### 14.11.1 更合适的选择

状态集合：

```java
public enum OrderStatus {
    CREATED,
    COMPLETED
}
```

普通常量：

```java
public final class OrderLimits {

    public static final int MAX_LINES = 1000;

    private OrderLimits() {
    }
}
```

领域值：

```java
public record WarehouseCode(String value) {
}
```

### 14.11.2 接口内常量并非一律错误

若常量是接口协议不可分割的一部分，例如标准标志位或固定协议值，可以保留。

关键是：

```text
常量是否属于该契约
而不是
是否方便少写类名
```

## 14.12 接口没有普通实例状态和构造器

接口不能声明普通实例字段：

```text
接口字段
→ 一律 static
```

接口也没有构造器：

```java
// public interface Invalid {
//     Invalid() {
//     }
// }
```

### 14.12.1 状态由实现类保存

```java
public final class RemoteInventoryReader
        implements InventoryReader {

    private final InventoryClient client;

    public RemoteInventoryReader(
            InventoryClient client
    ) {
        this.client = client;
    }
}
```

接口只声明可观察行为，实现类决定：

- 字段；
- 构造参数；
- 缓存；
- 线程安全机制；
- 生命周期；
- 资源释放策略。

### 14.12.2 默认方法不能访问实现类私有状态

默认方法只能依赖：

- 接口抽象方法；
- 其他默认方法；
- 接口私有方法；
- 接口静态成员；
- `this` 上公开可见的接口能力。

这促使默认实现基于契约推导，而不是耦合具体表示。

## 14.13 默认方法

Java 8 起，接口可通过 `default` 提供实例方法实现：

```java
public interface InventoryReader {

    int availableQuantity(String skuId);

    default boolean isAvailable(
            String skuId,
            int required
    ) {
        return availableQuantity(skuId)
                >= required;
    }
}
```

### 14.13.1 默认方法仍是实例方法

调用：

```java
boolean available =
        reader.isAvailable("SKU-1", 10);
```

它参与实例方法动态分派，实现类可以重写。

### 14.13.2 默认实现应从核心契约可靠推导

上例中：

```text
isAvailable
可由
availableQuantity
可靠计算
```

这是合理默认方法。

若默认实现只能猜测业务策略，例如默认重试三次、默认忽略失败、默认使用系统时间，则需要更谨慎。

### 14.13.3 默认方法不应模拟实例字段

接口无法保存每个对象独立状态。

需要状态时应由实现类或组合对象承担。

---

## 14.14 默认方法的主要设计目的

默认方法最初的重要用途是接口演进。

假设旧接口：

```java
public interface Sequence<T> {

    java.util.Iterator<T> iterator();
}
```

若新增抽象方法：

```java
// java.util.Spliterator<T> spliterator();
```

所有现有具体实现重新编译时都必须实现。

通过默认方法，可基于已有能力提供实现：

```java
default java.util.Spliterator<T> spliterator() {
    return java.util.Spliterators
            .spliteratorUnknownSize(
                    iterator(),
                    0
            );
}
```

### 14.14.1 默认方法不是“接口里的工具类方法”

只有当行为属于每个实现对象的契约，并能由接口能力合理推导时，才适合放入默认方法。

与接口相关但不依赖实例的工厂或工具逻辑，应使用静态方法。

### 14.14.2 默认方法是公共 API

一旦发布，默认方法同样需要维护：

- 语义；
- 异常；
- 性能；
- 线程安全假设；
- 空值规则；
- 与实现类重写的兼容性。

---

## 14.15 默认方法的适用边界

适合：

- 可由更小核心方法推导的复合操作；
- 接口演进中的兼容实现；
- 通用组合器；
- 不依赖实现状态的便利方法；
- 明确且安全的默认行为。

不适合：

- 持有可变状态；
- 隐藏远程调用；
- 隐式开启事务；
- 默认吞掉异常；
- 固化某个供应商实现；
- 需要大量可覆盖钩子的复杂模板；
- 具有强生命周期语义的流程。

### 14.15.1 默认方法过多会形成“接口基类”

当接口包含几十个默认方法并依赖复杂调用顺序时：

- 契约边界模糊；
- 重写组合难以推理；
- 多接口冲突增加；
- 行为变化影响所有实现。

这时可能更适合：

- 抽象骨架类；
- 独立组合对象；
- 装饰器；
- 策略对象。

---

## 14.16 接口静态方法

Java 8 起，接口可声明静态方法：

```java
public interface InventoryReader {

    int availableQuantity(String skuId);

    static InventoryReader fixed(
            int quantity
    ) {
        return skuId -> quantity;
    }
}
```

调用：

```java
InventoryReader reader =
        InventoryReader.fixed(100);
```

### 14.16.1 静态方法属于接口本身

它不被实现类继承：

```java
// DatabaseInventoryReader.fixed(100);
// 编译错误
```

应使用接口名限定：

```java
InventoryReader.fixed(100);
```

### 14.16.2 适合的用途

- 静态工厂；
- 组合器；
- 规范化或校验函数；
- 空实现、恒定实现和适配实现；
- 与该契约紧密相关的创建入口。

### 14.16.3 不要塞入无关工具

若方法与接口实例或契约无关，应放入其他领域类型，而不是把接口变成工具类命名空间。

---

## 14.17 接口私有方法

Java 9 起，接口可声明私有实例方法和私有静态方法。

```java
public interface AuditLogger {

    default void info(String message) {
        log("INFO", message);
    }

    default void error(String message) {
        log("ERROR", message);
    }

    private void log(
            String level,
            String message
    ) {
        System.out.println(
                "[" + level + "] " + message
        );
    }
}
```

### 14.17.1 私有方法只在接口内部可见

实现类不能：

- 调用；
- 重写；
- 继承；
- 通过 `Interface.super` 访问。

### 14.17.2 私有实例方法服务默认方法

它可以调用其他实例接口方法，并使用 `this`。

### 14.17.3 私有静态方法服务静态或默认逻辑

它不依赖某个实现对象。

### 14.17.4 私有方法不是扩展点

若希望实现类定制行为，私有方法不合适；接口也没有 `protected` 方法，应考虑公开契约或抽象类。

---

## 14.18 接口方法类型总表

| 方法类型 | 是否有方法体 | 是否属于实例 | 是否被实现类继承 | 是否可重写 |
|---|---:|---:|---:|---:|
| 抽象方法 | 否 | 是 | 形成待实现契约 | 必须或可以实现 |
| `default` 方法 | 是 | 是 | 是 | 可以 |
| `static` 方法 | 是 | 否 | 否 | 否 |
| `private` 实例方法 | 是 | 是 | 否 | 否 |
| `private static` 方法 | 是 | 否 | 否 | 否 |

### 14.18.1 不能混淆继承与可调用

- 默认方法可由实现对象调用；
- 静态方法只能通过接口名调用；
- 私有方法只供接口内部使用；
- 抽象方法由具体实现提供。

### 14.18.2 方法修饰符表达不同所有权

```text
abstract/default
→ 实现对象的实例行为

static
→ 接口命名空间行为

private
→ 接口内部实现细节
```

## 14.19 多接口实现

```java
public interface Startable {

    void start();
}

public interface Stoppable {

    void stop();
}

public interface Monitorable {

    Health health();
}
```

实现：

```java
public final class Conveyor
        implements Startable,
                   Stoppable,
                   Monitorable {

    @Override
    public void start() {
    }

    @Override
    public void stop() {
    }

    @Override
    public Health health() {
        return Health.UP;
    }
}
```

### 14.19.1 组合多个独立角色

同一对象可以分别传给只依赖某一能力的调用方：

```java
void boot(Startable value) {
    value.start();
}

void inspect(Monitorable value) {
    value.health();
}
```

### 14.19.2 多实现不等于类多继承

接口没有普通实例状态和构造器，因此不会直接产生多个父类状态布局冲突。

但方法契约和默认实现仍可能冲突，需要显式解决。

## 14.20 接口继承

接口通过 `extends` 扩展一个或多个接口：

```java
public interface Readable {

    byte[] read();
}

public interface Writable {

    void write(byte[] value);
}

public interface ReadWrite
        extends Readable, Writable {
}
```

### 14.20.1 子接口继承契约

实现 `ReadWrite` 的具体类必须满足：

- `read()`；
- `write(byte[])`；
- 子接口新增的其他方法。

### 14.20.2 子接口可以细化返回类型

```java
public interface EntityLoader {

    Object load();
}

public interface OrderLoader
        extends EntityLoader {

    @Override
    Order load();
}
```

### 14.20.3 子接口可以把默认方法重新声明为抽象

这会取消继承来的默认实现，要求下游实现类显式提供行为，详见 14.25。

---

## 14.21 方法签名合并与同擦除冲突

继承多个接口时，相同签名的抽象方法通常可以合并为一个契约：

```java
public interface A {
    Number value();
}

public interface B {
    Integer value();
}

public interface C extends A, B {
}
```

因为 `Integer` 是 `Number` 的协变返回类型，实现可返回 `Integer`。

### 14.21.1 不兼容返回类型会编译失败

```java
// interface X {
//     String value();
// }
//
// interface Y {
//     Integer value();
// }
//
// interface Z extends X, Y {
// }
```

不存在一个返回类型能同时满足两个契约。

### 14.21.2 泛型擦除可能制造名称冲突

```java
// interface A {
//     void process(java.util.List<String> values);
// }
//
// interface B {
//     void process(java.util.List<Integer> values);
// }
```

擦除后都类似：

```text
process(List)
```

不能在同一类型中形成两个可区分的方法。

完整擦除和桥接方法规则见泛型专题。

---

## 14.22 默认方法冲突

两个无继承关系的接口提供同签名默认方法：

```java
public interface A {

    default void execute() {
        System.out.println("A");
    }
}

public interface B {

    default void execute() {
        System.out.println("B");
    }
}
```

实现类不能保持沉默：

```java
// 编译错误
// public final class C implements A, B {
// }
```

### 14.22.1 实现类必须显式消歧

```java
public final class C implements A, B {

    @Override
    public void execute() {
        A.super.execute();
    }
}
```

### 14.22.2 可以组合多个默认实现

```java
@Override
public void execute() {
    A.super.execute();
    B.super.execute();
}
```

但组合顺序和语义必须由实现类明确承担。

### 14.22.3 `Interface.super` 只能引用直接超接口

不能任意跨层调用一个祖先接口默认方法。

---

## 14.23 类优先规则

父类中存在可继承的同签名实例方法时，类层次声明优先于接口默认方法。

```java
public class Parent {

    public void execute() {
        System.out.println("Parent");
    }
}

public interface Executor {

    default void execute() {
        System.out.println("Executor");
    }
}

public final class Child
        extends Parent
        implements Executor {
}
```

调用：

```text
new Child().execute()
→ Parent.execute()
```

### 14.23.1 这是“类胜过接口”

它保护已有类继承体系，不让接口新增默认方法悄悄覆盖父类行为。

### 14.23.2 父类方法必须满足接口契约

例如接口方法是 `public`，父类同签名方法若权限不足，具体类仍可能需要显式提供公共实现。

### 14.23.3 类优先不代表类设计永远更好

这只是语言冲突解析规则，不是“优先使用继承”的架构建议。

---

## 14.24 更具体接口优先

```java
public interface ParentOperation {

    default String name() {
        return "parent";
    }
}

public interface ChildOperation
        extends ParentOperation {

    @Override
    default String name() {
        return "child";
    }
}
```

实现：

```java
public final class Operation
        implements ChildOperation {
}
```

结果：

```text
operation.name()
→ child
```

### 14.24.1 原因

`ChildOperation` 已明确覆盖父接口默认方法，是更具体的契约。

### 14.24.2 菱形继承不一定冲突

若两个路径最终继承同一个未被分别重写的默认方法，通常只有一个最具体声明，不需要消歧。

真正冲突发生在：

```text
存在两个互不更具体的默认实现
```

---

## 14.25 抽象类或子接口可以压制默认方法

父接口：

```java
public interface Retryable {

    default void retry() {
        System.out.println("default retry");
    }
}
```

抽象父类重新声明：

```java
public abstract class StrictTask
        implements Retryable {

    @Override
    public abstract void retry();
}
```

具体子类必须实现：

```java
public final class NetworkTask
        extends StrictTask {

    @Override
    public void retry() {
        System.out.println("network retry");
    }
}
```

### 14.25.1 子接口也可重新抽象

```java
public interface StrictRetryable
        extends Retryable {

    @Override
    void retry();
}
```

### 14.25.2 适用场景

当上层默认行为对某个更严格角色不安全或不完整时，可以要求实现方重新确认契约。

这不是常规写法，应有明确设计理由。

---

## 14.26 接口与 Object 方法

接口可以声明与 `Object` 公共实例方法相同的抽象签名：

```java
public interface ValueLike {

    boolean equals(Object other);

    int hashCode();

    String toString();
}
```

但不能提供这些方法的 `default` 实现：

```java
// 编译错误
// default String toString() {
//     return "value";
// }
```

### 14.26.1 原因

所有普通实现对象都处于类继承体系中，并继承 `Object` 方法。

类方法优先，语言禁止接口默认方法与这些核心对象方法竞争。

### 14.26.2 声明不等于实现

接口重新声明 `equals()` 主要用于强调契约，真正语义仍由实现类提供。

### 14.26.3 不建议轻率声明

如果接口不能给出比 `Object` 更具体且可测试的相等性契约，重复声明只会增加噪声。

---

## 14.27 函数式接口

函数式接口是满足特定条件的接口，其核心具有一个函数描述符，可作为 Lambda、方法引用或构造器引用的目标类型。

```java
@FunctionalInterface
public interface Validator<T> {

    boolean test(T value);
}
```

使用：

```java
Validator<String> notBlank =
        value -> value != null
                && !value.isBlank();
```

### 14.27.1 核心不是“只写了一个方法”

更准确地说，需要只有一个可用于函数描述符的抽象方法契约。

以下成员不增加抽象方法数量：

- 默认方法；
- 静态方法；
- 私有方法；
- 与 `Object` 公共实例方法匹配的抽象声明。

### 14.27.2 `@FunctionalInterface` 不是必需条件

即使不加注解，只要满足规则，仍可作为 Lambda 目标类型。

注解的价值是：

- 表达设计意图；
- 让编译器阻止后续误加第二个不兼容抽象方法；
- 改善 API 文档。

### 14.27.3 sealed 接口不是函数式接口

即使表面上只有一个抽象方法，JLS 对函数式接口的定义排除声明为 `sealed` 的接口。

sealed 层次强调受控实现集合，而 Lambda 需要自由创建实现对象，两种设计目标不同。

---

## 14.28 继承多个方法仍可能是函数式接口

```java
public interface A {

    Number value();
}

public interface B {

    Integer value();
}

@FunctionalInterface
public interface C extends A, B {
}
```

`C` 仍可具有一个统一函数描述符：

```text
() -> Integer
```

因为协变返回类型可以合并。

### 14.28.1 Object 方法不计入 SAM

```java
@FunctionalInterface
public interface NamedAction {

    void run();

    boolean equals(Object other);
}
```

`equals(Object)` 与 `Object` 公共方法匹配，不额外破坏函数式接口判定。

### 14.28.2 不兼容抽象方法会破坏函数式接口

```java
// @FunctionalInterface
// interface Invalid {
//     void run();
//     int size();
// }
```

### 14.28.3 完整 Lambda 规则放在后续专题

本章只建立接口设计边界，不展开：

- 目标类型推断；
- 捕获变量；
- 方法引用适配；
- 交叉类型；
- 序列化 Lambda；
- 原始类型专用函数接口。

---

## 14.29 函数式接口的设计原则

函数式接口应表达单一、清晰的行为：

```java
@FunctionalInterface
public interface AllocationRule {

    AllocationDecision evaluate(
            AllocationContext context
    );
}
```

### 14.29.1 方法名应表达领域语义

相比通用的：

```text
apply
execute
handle
```

领域边界中更清晰的命名可能是：

```text
evaluate
reserve
authorize
transform
```

### 14.29.2 不要重复 JDK 已有接口

如果语义确实就是：

- `Predicate<T>`；
- `Function<T, R>`；
- `Consumer<T>`；
- `Supplier<T>`；
- `UnaryOperator<T>`；

可直接使用 JDK 接口。

但公共领域 API 若需要更强语义、专门异常或稳定方法名，自定义函数式接口仍可能合理。

### 14.29.3 谨慎加入默认方法

组合器如 `and`、`or`、`negate` 必须定义清楚：

- 短路顺序；
- 异常传播；
- null 行为；
- 副作用顺序；
- 线程安全假设。

---

## 14.30 标记接口

标记接口没有业务方法，只通过类型关系表达某种属性或能力。

JDK 例子：

- `Serializable`；
- `Cloneable`；
- `RandomAccess`。

```java
public interface TrustedMessage {
}
```

调用方可以通过类型系统限制：

```java
static <T extends TrustedMessage>
void publish(T message) {
}
```

### 14.30.1 标记接口的价值

- 可作为泛型边界；
- 可参与重载和多态；
- 可被 `instanceof` 检查；
- 能表达“只有此类对象才允许进入”的静态类型约束。

### 14.30.2 标记接口与注解

注解适合：

- 附加元数据；
- 由框架或工具反射读取；
- 不希望改变类型层次；
- 需要属性参数。

标记接口适合：

- 需要编译期类型约束；
- 需要泛型边界；
- 该标记确实代表可替换角色。

### 14.30.3 新代码不要机械模仿历史接口

`Serializable`、`Cloneable` 有历史背景，不代表所有标签都应设计成空接口。

---

## 14.31 sealed 接口

sealed 接口限制哪些类或接口可以直接实现或扩展它：

```java
public sealed interface CommandResult
        permits Success, Failure {
}
```

实现：

```java
public record Success(String message)
        implements CommandResult {
}

public record Failure(String code)
        implements CommandResult {
}
```

### 14.31.1 适合封闭类型集合

例如：

- 解析结果；
- 命令结果；
- 领域事件变体；
- AST 节点；
- 协议消息；
- 状态机事件。

### 14.31.2 配合模式匹配穷尽处理

```java
static String describe(
        CommandResult result
) {
    return switch (result) {
        case Success success ->
                success.message();
        case Failure failure ->
                failure.code();
    };
}
```

### 14.31.3 不适合开放插件接口

若第三方需要自由实现：

```text
PaymentPlugin
DatabaseDriver
CodecProvider
```

sealed 会直接限制扩展，应使用普通非 sealed 接口。

---

## 14.32 sealed 接口的直接子类型规则

允许的直接子类型需要显式或由编译单元推断。

直接实现类通常必须明确继续层次的方式：

- `final`；
- `sealed`；
- `non-sealed`。

record 隐式为 `final`。

enum 不能被普通类继承，其封闭性由语言规则保证。

### 14.32.1 模块和包边界

在命名模块中，允许的直接子类型必须位于同一模块。

在未命名模块中，通常要求位于同一包。

### 14.32.2 `non-sealed` 重新开放层次

```java
public non-sealed interface ExternalFailure
        extends CommandResult {
}
```

从该节点继续向下可以自由扩展。

### 14.32.3 演进风险

向 sealed 接口增加新的允许子类型，虽然可能保持二进制兼容，但旧代码中已编译的穷尽 `switch` 遇到新类型时可能失败。

封闭类型也需要版本演进策略。

---

## 14.33 record 和 enum 实现接口

record 不能继承自定义类，但可以实现接口：

```java
public interface Identified {

    String id();
}

public record OrderId(String id)
        implements Identified {
}
```

record 访问器 `id()` 自动满足接口契约。

### 14.33.1 record 适合值型实现

- 不可变数据载体；
- 命令和结果；
- 领域值对象；
- sealed 接口分支。

### 14.33.2 enum 可以实现接口

```java
public interface CodeValue {

    String code();
}

public enum OrderState
        implements CodeValue {

    CREATED("C"),
    DONE("D");

    private final String code;

    OrderState(String code) {
        this.code = code;
    }

    @Override
    public String code() {
        return code;
    }
}
```

### 14.33.3 枚举常量可提供差异行为

常量特定类体可以重写接口方法，但若行为和状态复杂，应检查是否更适合独立策略对象。

## 14.34 嵌套接口

接口可以声明在：

- 顶层；
- 类内部；
- 接口内部；
- 方法或代码块的局部上下文中（局部接口受语言版本和声明上下文规则约束，工程中极少使用）。

常见成员接口：

```java
public final class Parser {

    public interface Listener {

        void onToken(String token);
    }
}
```

### 14.34.1 接口中的成员类型隐式为 public static

```java
public interface Protocol {

    interface Frame {
    }
}
```

通过：

```text
Protocol.Frame
```

访问。

### 14.34.2 类中的成员接口按声明权限控制

可使用：

- `public`；
- `protected`；
- 包访问；
- `private`。

成员接口本质上不依赖外部类实例。

### 14.34.3 嵌套位置应表达归属

只有当接口确实只服务于外部类型的协议或回调时才嵌套；被多个模块复用的公共角色应独立命名。

---

## 14.35 接口契约不仅是方法签名

方法签名只能表达：

- 名称；
- 参数类型；
- 返回类型；
- 受检异常；
- 泛型边界。

完整契约还包括：

- 参数是否允许 null；
- 返回值是否可为空；
- 幂等性；
- 副作用；
- 异常类别；
- 线程安全；
- 阻塞行为；
- 超时与取消；
- 调用顺序；
- 资源所有权；
- 性能级别；
- 一致性语义。

### 14.35.1 示例：库存预留接口

```java
public interface InventoryReservation {

    ReservationResult reserve(
            ReservationCommand command
    );
}
```

仅凭签名无法知道：

- 重复 commandId 是否幂等；
- 库存不足是返回失败还是抛异常；
- 是否立即落库；
- 是否跨仓库原子；
- 方法是否会阻塞远程调用；
- 成功后谁负责释放预留。

这些必须通过文档、类型和测试明确。

### 14.35.2 用类型减少文字歧义

优先使用：

- 值对象；
- 枚举；
- sealed 结果类型；
- 明确命令对象；
- `Optional`（仅在合适返回场景）；
- 专门异常。

不要只依靠 `Map<String, Object>` 和布尔值表达复杂协议。

---

## 14.36 角色接口与能力接口

角色接口描述对象在协作中的职责：

```java
public interface OrderRepository {

    java.util.Optional<Order> findById(
            OrderId id
    );

    void save(Order order);
}
```

能力接口描述对象是否具备某一独立能力：

```java
public interface Cancelable {

    void cancel();
}
```

### 14.36.1 好接口通常可用一句话解释

```text
OrderRepository
→ 保存和读取订单聚合

Cancelable
→ 支持取消
```

### 14.36.2 避免以实现技术命名公共角色

业务层接口不宜直接命名：

```text
RedisOrderRepositoryInterface
MyBatisOrderDaoInterface
HttpInventoryClientInterface
```

更稳定的名称应面向角色；具体实现名称再体现技术。

### 14.36.3 能力接口应避免伪能力

如果接口只有 `getXxx/setXxx`，它可能只是数据结构拆分，而不是独立行为角色。

---

## 14.37 接口隔离的语言层准备

调用方不应依赖自己不使用的方法。

反例：

```java
public interface WarehouseSystem {

    void receive();

    void putAway();

    void pick();

    void pack();

    void ship();

    void audit();
}
```

某个盘点组件可能只需要：

```java
public interface InventoryAuditor {

    AuditResult audit(AuditCommand command);
}
```

### 14.37.1 小接口不是越碎越好

接口隔离强调：

```text
围绕调用方角色保持内聚
```

不是：

```text
每个方法单独建接口
```

### 14.37.2 拆分信号

- 实现类大量空实现；
- 方法经常抛 `UnsupportedOperationException`；
- 调用方只使用很小子集；
- 不同方法由完全不同团队演进；
- 实现类依赖集合差异巨大。

系统设计原则将在第 15 章展开。

## 14.38 消费方拥有接口

在分层或六边形架构中，接口常由需要能力的一侧定义。

例如应用服务需要库存查询：

```java
public interface InventoryQueryPort {

    InventorySnapshot query(
            WarehouseId warehouseId,
            SkuId skuId
    );
}
```

基础设施层实现：

```java
public final class HttpInventoryAdapter
        implements InventoryQueryPort {
}
```

### 14.38.1 优点

- 接口只暴露消费方真正需要的能力；
- 依赖方向指向业务核心；
- 外部 SDK 类型被适配器隔离；
- 测试可提供内存实现；
- 更换传输或存储技术不改变业务契约。

### 14.38.2 不要复制整个提供方 API

消费方接口若机械镜像远程服务所有方法，仍然被提供方模型绑死。

接口应以本地用例为中心。

## 14.39 SPI 与服务提供者接口

SPI 用于允许外部实现提供某类服务。

JDK `ServiceLoader` 的基本结构：

```java
public interface CodecProvider {

    String name();

    Codec create();
}
```

提供者实现：

```java
public final class JsonCodecProvider
        implements CodecProvider {
}
```

消费方：

```java
java.util.ServiceLoader<CodecProvider> loader =
        java.util.ServiceLoader.load(
                CodecProvider.class
        );
```

### 14.39.1 SPI 接口要求更稳定

外部提供者无法与主项目同步修改，因此需要特别重视：

- 最小契约；
- 版本兼容；
- 默认能力；
- 能力探测；
- 错误隔离；
- 生命周期；
- 类加载器边界；
- 安全校验。

### 14.39.2 不要假设只有一个实现

SPI 天生面向多提供者，应明确：

- 选择规则；
- 优先级；
- 重名处理；
- 初始化失败策略；
- 是否允许热加载。

### 14.39.3 模块系统

命名模块可通过：

```text
uses
provides CodecProvider with JsonCodecProvider
```

声明服务消费和提供。完整模块系统见专门章节。

## 14.40 接口与骨架实现类

常见组合：

```text
公共接口
+
可选 AbstractXxx 骨架实现
+
一个或多个具体实现
```

例如 JDK 集合框架：

```text
List
→ AbstractList
→ ArrayList
```

### 14.40.1 接口定义角色

第三方实现可以：

- 直接实现接口；
- 继承骨架实现；
- 继承其他业务父类后再实现接口。

### 14.40.2 骨架类减少实现成本

它基于少量原语实现复合操作。

### 14.40.3 避免强迫继承

如果只提供抽象类而不提供接口，已经有其他父类的实现方无法复用契约。

接口与骨架类结合兼顾：

- 多实现自由；
- 公共代码复用；
- 单继承限制。

详细骨架实现设计见第 13 章。

## 14.41 接口演进与源码兼容

公共接口发布后，修改会影响所有实现者和调用者。

### 14.41.1 新增抽象方法

对已有具体实现重新编译时，通常会失败，除非它已从父类等位置获得匹配实现。

因此公共接口新增抽象方法是高风险源码变更。

### 14.41.2 新增默认方法

已有实现通常无需修改即可重新编译，因此常用于兼容演进。

但它仍可能：

- 与其他接口默认方法冲突；
- 被已有类方法压制；
- 改变调用到的实际行为；
- 引入新的异常或性能成本；
- 破坏实现者原本隐含语义。

### 14.41.3 新增静态或私有方法

因为不形成实现类待实现契约，通常对实现者影响较小。

但公共静态方法仍增加 API 面积，私有方法仍影响接口自身行为。

---

## 14.42 接口演进与二进制兼容

源码兼容和二进制兼容不是同一概念。

### 14.42.1 新增抽象方法的细节

旧实现类的已编译字节码可能仍能被加载，因为类文件在编译时并未包含新方法。

但当新调用方真正对旧实现对象调用新增方法时，可能出现：

```text
AbstractMethodError
```

因此不能把“JLS 视为某种二进制兼容”误解为运行一定安全。

### 14.42.2 新增默认方法的冲突

若旧类同时实现两个接口，而接口升级后出现两个不相关的同签名默认方法，旧二进制在调用时可能出现链接或调用冲突错误。

### 14.42.3 删除或改变方法签名

通常会直接破坏已有调用方，可能出现：

- `NoSuchMethodError`；
- `AbstractMethodError`；
- `IncompatibleClassChangeError`；
- 重新编译失败。

### 14.42.4 兼容性必须做矩阵测试

公共库应至少测试：

```text
新调用方 + 新实现
新调用方 + 旧实现
旧调用方 + 新实现
旧调用方 + 旧实现
```

---

## 14.43 默认方法的行为兼容风险

默认方法可以保持链接，却仍破坏业务语义。

例如接口新增：

```java
default boolean supportsBatch() {
    return true;
}
```

旧实现没有批量能力，却会继承 `true`。

### 14.43.1 默认值必须保守

能力探测默认通常应遵循：

```text
不知道
→ 不支持
```

而不是乐观假设。

### 14.43.2 不要默认吞错

```java
// 危险
// default void executeSafely() {
//     try {
//         execute();
//     } catch (Exception ignored) {
//     }
// }
```

这会改变失败语义并隐藏故障。

### 14.43.3 不要偷偷增加昂贵操作

一个看似便利的默认方法若循环调用远程方法，可能带来 N+1、事务扩大或锁持有时间增加。

### 14.43.4 默认方法需要文档化复杂度

例如：

```text
O(1)
O(n)
可能阻塞
可能执行远程调用
```

## 14.44 泛型接口设计

```java
public interface Repository<ID, E> {

    java.util.Optional<E> findById(ID id);

    void save(E entity);
}
```

### 14.44.1 类型参数应表达稳定关系

避免：

```text
Repository<A, B, C, D, E, F>
```

过多参数会增加实现和调用复杂度，可能说明接口职责过大。

### 14.44.2 输入输出变型

方法级 API 可使用通配符：

```java
void saveAll(
        java.util.Collection<? extends E> values
);
```

但公共接口中过度嵌套通配符会降低可读性。

### 14.44.3 不要泄漏实现类型参数

业务接口不应因某个 ORM 或序列化框架需要而暴露无关泛型参数。

### 14.44.4 擦除冲突需提前验证

设计多继承泛型接口时，应编译验证桥接方法和同擦除签名，不能只看源码表面类型。

---

## 14.45 接口设计坏味道

### 14.45.1 万能接口

几十个不相关方法聚集在一个接口中。

### 14.45.2 接口爆炸

每个类、每个方法都创建接口，导航成本超过替换价值。

### 14.45.3 一实现一接口仪式化

只有一个稳定实现、无替换边界、无独立角色，却机械增加接口。

### 14.45.4 getter/setter 接口

接口只复制数据对象全部字段访问器，缺少行为语义。

### 14.45.5 框架类型泄漏

核心接口参数直接使用：

- ORM EntityManager；
- HTTP Request；
- 某供应商 SDK 响应；
- Spring 上下文对象。

### 14.45.6 弱类型返回值

```java
Map<String, Object> execute(
        Map<String, Object> params
);
```

会把契约推迟到运行时。

### 14.45.7 大量默认空实现

说明方法并非所有实现都应支持，接口可能需要拆分。

## 14.46 WMS 接口设计案例

需求：出库分配流程需要：

- 查询可用库存；
- 创建库存预留；
- 释放预留；
- 选择库位；
- 记录审计。

不推荐把所有能力塞进一个接口：

```java
public interface InventoryService {
    // dozens of unrelated methods
}
```

可以按用例角色拆分：

```java
public interface InventoryQueryPort {

    InventorySnapshot query(
            WarehouseId warehouseId,
            SkuId skuId
    );
}
```

```java
public interface ReservationPort {

    ReservationResult reserve(
            ReservationCommand command
    );

    ReleaseResult release(
            ReleaseCommand command
    );
}
```

```java
@FunctionalInterface
public interface LocationSelectionRule {

    LocationId select(
            AllocationContext context
    );
}
```

### 14.46.1 契约必须明确

`ReservationPort.reserve()` 应说明：

- `requestId` 是否幂等；
- 库存不足如何表示；
- 是否允许部分预留；
- 是否跨 SKU 原子；
- 超时和取消语义；
- 重试是否安全；
- 返回的 reservationId 生命周期。

### 14.46.2 基础设施实现

```text
DatabaseReservationAdapter
RedisReservationAdapter
RemoteReservationAdapter
```

业务调用方不直接依赖数据库、Redis 或 HTTP SDK。

### 14.46.3 测试实现

```text
InMemoryReservationPort
FaultInjectingReservationPort
RecordingReservationPort
```

它们必须通过相同契约测试，而不是只满足编译。

## 14.47 接口契约测试

接口有多个实现时，应为所有实现运行同一套测试。

以下代码依赖 JUnit 与业务测试夹具，用于展示测试结构，不是独立运行 Demo：

```java
abstract class ReservationContractTest {

    protected abstract ReservationPort createPort();

    @org.junit.jupiter.api.Test
    void duplicateRequestMustBeIdempotent() {
        ReservationPort port = createPort();
        ReservationCommand command = sample();

        ReservationResult first =
                port.reserve(command);
        ReservationResult second =
                port.reserve(command);

        org.junit.jupiter.api.Assertions
                .assertEquals(first, second);
    }
}
```

具体实现测试继承：

```java
final class DatabaseReservationContractTest
        extends ReservationContractTest {

    @Override
    protected ReservationPort createPort() {
        return createDatabaseReservationPort();
    }
}
```

### 14.47.1 契约测试关注什么

- 正常输入输出；
- 边界值；
- null 和非法输入；
- 异常类型；
- 幂等性；
- 顺序；
- 资源释放；
- 并发语义；
- 超时和取消；
- 兼容性。

### 14.47.2 Mock 不能替代契约测试

Mock 通常只验证调用方按预期交互，不能证明真实实现满足接口语义。

### 14.47.3 接口越抽象，测试越重要

编译器只检查方法形状，不检查业务承诺。

## 14.48 接口调用的运行时边界

接口实例方法调用在字节码层通常使用接口调用语义，具体实现由运行时对象决定。

现代 JVM 可通过：

- 类型剖析；
- 单态或双态调用点识别；
- 去虚拟化；
- 内联；
- 类层次分析；

优化大量接口调用。

### 14.48.1 不要为“性能”拒绝合理接口

业务代码中，合理抽象和可维护性通常比理论上的一次分派差异重要。

### 14.48.2 高度多态热点需要测量

同一调用点出现大量实现类型时，JIT 优化可能更困难。

是否构成瓶颈应使用：

- JMH；
- JFR；
- async-profiler；
- 编译日志；
- 生产指标。

### 14.48.3 远程和数据库开销远大于接口分派

不要在毫秒级 IO 路径中纠结纳秒级调用形式，却忽略：

- N+1；
- 无索引查询；
- 重试风暴；
- 序列化；
- 锁竞争。

## 14.49 常见错误

### 14.49.1 忘记实现方法必须是 public

导致权限缩小编译错误。

### 14.49.2 把接口字段当实例字段

所有实现共享同一个静态字段。

### 14.49.3 暴露可变集合常量

形成全局可变状态。

### 14.49.4 认为所有 static final 都会被内联

只有满足常量变量规则的值才是编译期常量。

### 14.49.5 把默认方法当万能兼容方案

忽略冲突和行为变化。

### 14.49.6 通过实现类调用接口静态方法

静态方法不被继承。

### 14.49.7 认为 private 接口方法是扩展点

实现类不可见也不可重写。

### 14.49.8 忽略默认方法菱形冲突

多个无关默认实现必须显式消歧。

### 14.49.9 认为接口只要一个抽象方法就一定是函数式接口

sealed 接口等情况需要按 JLS 精确定义判断。

### 14.49.10 把接口数量当设计质量指标

接口应围绕真实角色和变化边界，而不是追求数量。

### 实验18：接口与骨架实现

```java
public class SkeletalImplementationDemo {

    interface TextSequence {
        int size();
        String get(int index);

        default boolean isEmpty() {
            return size() == 0;
        }
    }

    static abstract class AbstractTextSequence
            implements TextSequence {
        @Override
        public String toString() {
            StringBuilder builder = new StringBuilder();
            for (int i = 0; i < size(); i++) {
                if (i > 0) {
                    builder.append(',');
                }
                builder.append(get(i));
            }
            return builder.toString();
        }
    }

    static final class Pair
            extends AbstractTextSequence {
        private final String left;
        private final String right;

        Pair(String left, String right) {
            this.left = left;
            this.right = right;
        }

        @Override
        public int size() {
            return 2;
        }

        @Override
        public String get(int index) {
            return switch (index) {
                case 0 -> left;
                case 1 -> right;
                default -> throw new IndexOutOfBoundsException(index);
            };
        }
    }

    public static void main(String[] args) {
        TextSequence value = new Pair("A", "B");
        System.out.println(value.isEmpty());
        System.out.println(value);
    }
}
```

观察点：验证接口定义角色、默认方法提供简单推导、骨架类复用复杂实现。

### 实验19：简单契约测试

```java
import java.util.List;

public class InterfaceContractTestDemo {

    interface Counter {
        int increment();
        int current();
    }

    static final class SimpleCounter implements Counter {
        private int value;

        @Override
        public int increment() {
            return ++value;
        }

        @Override
        public int current() {
            return value;
        }
    }

    static final class StepCounter implements Counter {
        private int value;

        @Override
        public int increment() {
            value += 1;
            return value;
        }

        @Override
        public int current() {
            return value;
        }
    }

    static void verify(Counter counter) {
        if (counter.current() != 0) {
            throw new AssertionError("initial");
        }
        if (counter.increment() != 1) {
            throw new AssertionError("increment");
        }
        if (counter.current() != 1) {
            throw new AssertionError("current");
        }
    }

    public static void main(String[] args) {
        List<Counter> counters = List.of(
                new SimpleCounter(),
                new StepCounter()
        );
        counters.forEach(InterfaceContractTestDemo::verify);
        System.out.println("all implementations passed");
    }
}
```

观察点：验证同一套契约断言可以应用到多个实现。

## 14.52 易错点

### 误区1：接口是不能实例化的抽象类

**错误。** 错误。接口与类是不同种类的引用类型，接口没有类的实例状态和构造体系。

### 误区2：接口没有对象，所以接口引用没有运行时类型

**错误。** 错误。引用可指向实现类对象，运行时类型仍是具体实现类。

### 误区3：匿名实现直接创建了接口对象

**错误。** 错误。创建的是匿名实现类的实例。

### 误区4：接口方法不写 public，实现时也可以不写

**错误。** 错误。接口抽象方法隐式 public，实现方法不能缩小访问权限。

### 误区5：接口可以定义 protected 抽象方法给子类使用

**错误。** 错误。接口没有 protected 实例方法；受控扩展点应考虑抽象类。

### 误区6：抽象接口方法可以 static

**错误。** 错误。static 属于接口本身，不形成对象待实现契约。

### 误区7：具体类可以只实现常用接口方法

**错误。** 错误。所有继承到的抽象方法都必须实现，否则类必须是 abstract。

### 误区8：接口字段是每个实现对象各有一份

**错误。** 错误。接口字段全部是 static，属于接口本身。

### 误区9：接口字段不能放对象

**错误。** 不准确。可以引用对象，但字段引用是 static final；若对象可变会形成危险的全局状态。

### 误区10：public static final 一定是编译期常量

**错误。** 错误。只有基本类型或 String 且由常量表达式初始化的 final 变量才可能是常量变量。

### 误区11：访问任何接口字段都会初始化接口

**错误。** 错误。编译期常量可能被调用方内联，访问时不一定初始化声明接口。

### 误区12：接口常量改值后替换 JAR 即可生效

**错误。** 错误。旧调用方可能已内联旧值，需要重新编译。

### 误区13：实现常量接口是复用常量的好方式

**错误。** 错误。这会污染类型关系和公共 API。

### 误区14：接口不能有任何方法体

**错误。** 错误。可以有 default、static、private 和 private static 方法。

### 误区15：default 方法是静态方法

**错误。** 错误。default 是实例方法，通过实现对象调用并可被重写。

### 误区16：default 方法只用于少写代码

**错误。** 错误。它首先是契约行为和接口演进机制，必须满足所有实现的安全默认语义。

### 误区17：新增 default 方法绝对兼容

**错误。** 错误。可能产生默认方法冲突、行为变化和运行时链接问题。

### 误区18：默认方法可以直接访问实现类字段

**错误。** 错误。接口不知道具体实现的私有表示。

### 误区19：接口 static 方法可以用实现类名调用

**错误。** 错误。接口静态方法不被实现类继承，应通过接口名调用。

### 误区20：private 接口方法是给实现类重写的

**错误。** 错误。它只在接口内部使用，不被继承。

### 误区21：两个默认方法冲突时 JVM 随机选一个

**错误。** 错误。编译器要求具体类显式消歧。

### 误区22：Interface.super 可以调用任意祖先默认方法

**错误。** 错误。语法受直接超接口和继承关系约束。

### 误区23：接口默认方法总是优先于父类方法

**错误。** 错误。类层次方法优先。

### 误区24：父类方法权限不足也能自动满足 public 接口方法

**错误。** 错误。实现必须提供满足 public 契约的方法。

### 误区25：菱形继承一定冲突

**错误。** 错误。若只有一个最具体默认声明，通常无需消歧。

### 误区26：抽象类不能重新声明接口默认方法

**错误。** 错误。抽象类可重新抽象，要求具体子类实现。

### 误区27：接口完全不能提到 Object 方法

**错误。** 错误。可以声明匹配的抽象方法，但不能为 Object 公共方法提供 default 实现。

### 误区28：有一个抽象方法就必然是函数式接口

**错误。** 错误。需按 JLS 函数描述符规则判断，sealed 接口也被排除。

### 误区29：必须加 @FunctionalInterface 才能写 Lambda

**错误。** 错误。注解用于表达和校验意图，不是成为函数式接口的必要条件。

### 误区30：default 和 static 方法都会破坏 SAM

**错误。** 错误。它们不是抽象方法。

### 误区31：标记接口已经完全被注解淘汰

**错误。** 错误。需要类型约束和泛型边界时，标记接口仍有独特价值。

### 误区32：sealed 接口适合所有接口

**错误。** 错误。它只适合确实封闭的实现集合。

### 误区33：sealed 接口加新子类型不会影响旧代码

**错误。** 错误。旧穷尽 switch 遇到新类型可能失败。

### 误区34：record 不能参与接口多态

**错误。** 错误。record 可实现接口，只是不能继承自定义类。

### 误区35：接口越小越好，所以每个方法一个接口

**错误。** 错误。应围绕调用方角色保持内聚，过度拆分会造成接口爆炸。

### 误区36：每个实现类都必须配一个接口

**错误。** 错误。没有替换边界和独立角色时，接口可能只是仪式。

### 误区37：接口方法签名就是完整契约

**错误。** 错误。null、异常、幂等、线程安全、阻塞和资源所有权也属于契约。

### 误区38：Mock 通过说明真实实现满足接口

**错误。** 错误。Mock 只模拟约定，真实实现仍需要契约测试。

### 误区39：新增接口抽象方法旧二进制一定立刻加载失败

**错误。** 错误。旧类可能仍可加载，但调用新增方法时可能出现 AbstractMethodError。

### 误区40：接口调用一定比类调用慢很多

**错误。** 错误。现代 JVM 可去虚拟化和内联，性能必须测量。

## 14.53 工程实践建议

1. 先从调用方需要的角色出发定义接口，不要从实现类机械抽取全部 public 方法。
2. 接口名称应表达业务角色或能力，避免无意义的 I 前缀和实现技术前缀。
3. 公共接口保持小而内聚，但不要走向每个方法一个接口的碎片化。
4. 接口方法优先使用领域类型，避免 Map<String, Object> 和框架原生对象泄漏。
5. 为每个方法记录 null、异常、幂等、副作用、阻塞和线程安全语义。
6. 实现接口方法始终保留 @Override。
7. 接口返回值优先表达成功、失败和缺失的明确类型，不要用含义模糊的 boolean。
8. 不要在接口中暴露可变集合或可变对象常量。
9. 常量属于协议时才放接口，否则使用枚举、值对象或常量类。
10. 修改公共常量后评估调用方内联和重新编译问题。
11. 默认方法只实现能从核心契约可靠推导的行为。
12. 默认方法的默认语义应保守，尤其是能力探测和安全策略。
13. 不要在默认方法中悄悄执行昂贵远程调用或吞掉异常。
14. 默认方法同样文档化复杂度、阻塞性和异常。
15. 静态工厂与接口强相关时可放在接口中，其他工具逻辑放到独立类型。
16. 使用接口私有方法减少默认方法重复，但不要把接口发展成复杂基类。
17. 出现多个独立默认方法冲突时，让具体类显式决定语义，不要依赖隐含顺序。
18. 若某一角色不接受父接口默认行为，可在子接口或抽象类中重新抽象。
19. 函数式接口加 @FunctionalInterface，锁定单一抽象方法意图。
20. 优先复用 JDK 函数式接口；领域语义、异常或长期 API 需要时再自定义。
21. 函数式组合器必须明确短路、顺序、副作用和异常传播。
22. 标记接口只在需要类型系统约束时使用；纯元数据优先注解。
23. sealed 接口只用于真正封闭的类型集合，并规划新增子类型的兼容策略。
24. 开放插件、驱动和 SPI 接口不要 sealed。
25. record 适合实现值型接口，enum 适合实现有限常量行为接口。
26. 嵌套接口只在协议确实从属于外部类型时使用。
27. 业务核心端口接口由消费方需求驱动，不要镜像外部系统完整 API。
28. SPI 接口保持最小稳定，并定义提供者选择、优先级和失败隔离。
29. 对公共契约同时提供可选骨架实现，避免强迫所有实现继承同一父类。
30. 公共接口新增抽象方法前优先考虑新子接口、默认方法或版本化接口。
31. 新增默认方法前扫描已有实现类和并行接口是否存在同签名方法。
32. 公共库对接口演进执行新旧调用方与新旧实现的兼容矩阵测试。
33. 不要把二进制兼容误解为业务行为兼容。
34. 泛型接口控制类型参数数量，并提前编译验证同擦除方法冲突。
35. 发现实现类大量 UnsupportedOperationException 时拆分接口。
36. 发现只有一个实现但接口承担清晰端口或 SPI 角色时可以保留；否则删除仪式化抽象。
37. 为每个重要接口建立契约测试，并让所有实现运行同一套用例。
38. Mock 用于调用方单元测试，真实适配器仍需集成测试和契约测试。
39. 性能优化前使用 JMH、JFR 或生产剖析验证接口分派是否真是热点。
40. 定期审查接口的实现数量、调用方数量和变更原因，按真实变化方向演进。

## 14.55 本章总结

```text
接口是独立引用类型，用于表达对象可承担的角色和行为契约
↓
接口没有普通实例字段和构造器，状态由实现类保存
↓
抽象接口方法隐式 public abstract，具体实现必须 public
↓
接口字段隐式 public static final，但不一定是编译期常量
↓
default 是可重写实例方法，应基于核心契约提供安全默认行为
↓
static 属于接口本身，private 只服务接口内部实现
↓
类可实现多个接口，接口可继承多个接口
↓
默认方法冲突按类优先、更具体接口优先和显式消歧处理
↓
函数式接口具有一个可合并的抽象函数描述符，注解用于校验意图
↓
sealed 接口适合封闭类型集合，普通接口适合开放扩展
↓
接口契约还包含 null、异常、幂等、线程安全、阻塞和资源语义
↓
公共接口演进必须同时评估源码、二进制和行为兼容
↓
契约测试验证每个实现真正可替换
```

关键判断：

```text
只需要描述独立角色或能力
→ 接口

需要共享状态、构造过程和复杂模板
→ 抽象类或接口 + 骨架类

需要运行时替换算法
→ 函数式接口或策略接口

类型集合封闭并需要穷尽处理
→ sealed 接口

需要第三方自由扩展
→ 普通非 sealed SPI 接口
```

## 14.56 面试口述版

> 接口是 Java 中独立的引用类型，用于表达对象能够承担的角色或行为契约。它不能直接实例化，也没有普通实例字段和构造器，但可以作为变量、参数、返回值和泛型边界。具体类通过 implements 提供实现，一个类可以实现多个接口，接口也可以继承多个接口，因此接口解决的是多角色契约组合，而不是多份父类状态继承。
>
> 接口抽象方法隐式是 public abstract，所以实现类必须用 public，不能缩小权限，并遵循普通重写的协变返回类型和受检异常规则。接口字段隐式是 public static final 且必须初始化，但 static final 不等于一定是编译期常量；只有基本类型或 String 且由常量表达式初始化的变量才可能被调用方内联，所以公共常量改值要注意旧调用方仍使用旧值。
>
> Java 8 引入 default 和 static 接口方法，Java 9 引入 private 接口方法。default 是实例方法，可以被重写，适合基于核心契约推导复合行为和兼容演进；static 属于接口本身，不被实现类继承；private 只用于接口内部复用。默认方法发生冲突时遵循类优先、更具体接口优先；两个无关接口同时提供同签名默认实现时，具体类必须显式重写并可通过 Interface.super 指定来源。抽象父类或子接口还可以重新声明默认方法为抽象方法。
>
> 函数式接口不是简单“源码里只有一个方法”，而是具有一个可合并的抽象函数描述符。default、static、private 方法和匹配 Object 公共方法的抽象声明不增加 SAM 数量，@FunctionalInterface 用于表达并校验意图；sealed 接口不属于函数式接口。sealed 接口适合结果类型、事件和 AST 等封闭层次，开放 SPI 和插件接口则不应 sealed。
>
> 工程上，接口质量取决于契约而不是数量。接口应围绕调用方角色保持小而内聚，方法签名之外还要说明 null、异常、幂等、副作用、线程安全、阻塞和资源所有权。公共接口新增抽象方法可能让旧实现调用时报 AbstractMethodError，新增默认方法也可能产生冲突或行为变化，因此需要兼容矩阵测试。对于多个实现，应建立统一契约测试；接口只定义角色，复杂共享实现可由可选 AbstractXxx 骨架类提供。
