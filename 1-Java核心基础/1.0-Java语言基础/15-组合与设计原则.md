## 15.2 学习主线

```text
识别对象之间的关系
↓
区分 is-a 与 has-a
↓
继承用于稳定类型关系
组合用于可变化能力
↓
通过委托把请求交给组件
↓
用 SOLID 检查职责、扩展和替换
↓
通过依赖倒置控制模块方向
↓
通过依赖注入组装对象
↓
用高内聚低耦合评价边界
↓
识别 Feature Envy、God Class、依赖环等坏味道
↓
按变化轴选择策略、装饰器、适配器、模板或模式匹配
↓
通过契约测试和渐进式重构验证设计
```

一套设计不能只看类图是否漂亮，还要看：

1. 新需求到来时要修改多少位置；
2. 一个组件失败时影响范围多大；
3. 单元测试是否需要启动大量基础设施；
4. 是否能替换实现而不破坏调用方；
5. 是否存在隐式顺序、共享可变状态或跨层泄漏；
6. 代码结构是否与业务语言一致。

## 15.3 对象关系总览

面向对象设计中常见关系可以从“知道、使用、拥有、负责生命周期”四个维度理解。

| 关系 | 典型含义 | Java 表现 | 生命周期责任 | 耦合强度 |
|---|---|---|---|---|
| 依赖 Dependency | 临时使用另一个对象 | 参数、局部变量、静态调用 | 不负责 | 较弱 |
| 关联 Association | 长期知道另一个对象 | 字段引用 | 通常不负责 | 中等 |
| 聚合 Aggregation | 整体包含可独立存在的部分 | 注入的集合或成员字段 | 部分独立 | 中等 |
| 组合 Composition | 整体拥有不可独立或强绑定的部分 | 构造时创建/接管组件 | 通常负责 | 较强 |
| 继承 Inheritance | 子类型可替代父类型 | `extends` | 父子共同生命周期语义 | 很强 |
| 实现 Realization | 类型承诺接口契约 | `implements` | 无实例状态继承 | 取决于契约 |
| 委托 Delegation | 把请求转交给内部对象 | 字段 + 转发方法 | 由组合关系决定 | 可控 |

这些概念是建模语言，不是 JVM 的运行时标签。Java 编译器不会区分“聚合字段”和“组合字段”，区别来自业务语义、创建方式和生命周期约束。

## 15.4 依赖关系

依赖表示一个对象在某个操作中临时使用另一个类型。

```java
public final class ReportService {

    public byte[] export(
            Report report,
            ReportRenderer renderer
    ) {
        return renderer.render(report);
    }
}
```

`ReportService` 的方法参数依赖 `ReportRenderer`，但不一定长期保存它。

### 15.4.1 常见依赖来源

- 方法参数；
- 局部变量；
- 返回类型；
- 静态方法调用；
- 泛型边界；
- 异常类型；
- 注解和反射元数据；
- 模块声明。

### 15.4.2 依赖不是越少越好

任何有意义的软件都存在依赖。目标是：

```text
依赖必要能力
而不是依赖不必要细节
```

例如方法只需要读取能力，应依赖 `Readable`，而不是拥有读写、删除、事务和管理能力的庞大接口。

## 15.5 关联关系

关联表示对象长期知道另一个对象，通常通过字段保存引用。

```java
public final class OrderService {

    private final OrderRepository repository;

    public OrderService(
            OrderRepository repository
    ) {
        this.repository = repository;
    }
}
```

`OrderService` 与 `OrderRepository` 存在关联。

### 15.5.1 关联的方向

单向关联：

```text
OrderService → OrderRepository
```

双向关联：

```text
Customer ↔ Order
```

双向关联会增加同步、序列化、递归输出和生命周期管理成本，除非业务确实需要，否则优先单向导航。

### 15.5.2 字段并不自动表示组合

下面字段可能是聚合，也可能是组合：

```java
private final Engine engine;
```

必须结合以下问题判断：

- `Engine` 是否可脱离当前对象独立存在？
- 是否可被多个对象共享？
- 谁创建它？
- 谁关闭或销毁它？
- 整体消失时部分是否仍有业务意义？

## 15.6 聚合关系

聚合表示“整体包含部分”，但部分可以独立存在、被替换或转移。

```java
public final class Team {

    private final List<Member> members;

    public Team(List<Member> members) {
        this.members = List.copyOf(members);
    }
}
```

成员离开当前团队后仍然是有效的 `Member`。

### 15.6.1 聚合常见场景

- 团队与成员；
- 课程与教师；
- 仓库与员工；
- 调度器与已注册任务；
- 服务与外部注入的客户端。

### 15.6.2 聚合不是 DDD 聚合根的同义词

UML 中的 aggregation 表示对象关系。

DDD 中的 Aggregate 表示：

- 一致性边界；
- 事务边界；
- 聚合根控制内部修改；
- 外部通过聚合根访问内部对象。

两者名称相同，但概念层次不同，不能混用。

## 15.7 组合关系

组合表示整体对部分具有更强的拥有关系，部分通常依赖整体存在。

```java
public final class Order {

    private final List<OrderLine> lines =
            new ArrayList<>();

    public void addLine(
            ProductId productId,
            int quantity
    ) {
        lines.add(
                new OrderLine(
                        productId,
                        quantity
                )
        );
    }
}
```

`OrderLine` 由 `Order` 创建和管理，通常不能脱离订单独立存在。

### 15.7.1 组合的关键不是 `new`

在构造器内部 `new` 一个对象只是信号，不是充分条件。

```java
this.clock = Clock.systemUTC();
```

`Clock` 仍可能是可替换基础设施，不一定属于整体的业务组成部分。

### 15.7.2 强组合应保护不变量

不推荐暴露可变内部集合：

```java
public List<OrderLine> getLines() {
    return lines;
}
```

更合理：

```java
public List<OrderLine> lines() {
    return List.copyOf(lines);
}
```

外部通过业务方法修改：

```java
order.changeQuantity(lineId, 3);
```

组合对象应保护内部状态一致性，而不是只把对象“装在一起”。

## 15.8 所有权与生命周期

判断聚合和组合时，生命周期比字段形态更重要。

需要明确：

- 谁创建组件？
- 谁关闭组件？
- 是否允许共享？
- 是否允许替换？
- 是否线程安全？
- 是否可跨请求复用？
- 是否持有外部资源？
- 整体销毁时是否必须释放部分？

### 15.8.1 资源型组件

```java
public final class FileBatch
        implements AutoCloseable {

    private final InputStream input;

    public FileBatch(Path path)
            throws IOException {
        this.input =
                Files.newInputStream(path);
    }

    @Override
    public void close()
            throws IOException {
        input.close();
    }
}
```

如果对象创建并拥有资源，就应清晰承担关闭责任。

### 15.8.2 注入对象通常不应随意关闭

```java
public final class ReportService {

    private final ExecutorService executor;
}
```

如果 `executor` 由外部容器注入并共享，`ReportService` 通常不应自行 `shutdown()`。

所有权不清是资源泄漏和误关闭的常见根源。

## 15.9 委托

委托表示当前对象接收请求后，把核心工作转交给内部组件。

```java
public final class AuditingPaymentGateway
        implements PaymentGateway {

    private final PaymentGateway delegate;
    private final AuditRecorder recorder;

    public AuditingPaymentGateway(
            PaymentGateway delegate,
            AuditRecorder recorder
    ) {
        this.delegate = delegate;
        this.recorder = recorder;
    }

    @Override
    public PaymentResult pay(
            PaymentCommand command
    ) {
        recorder.before(command);

        PaymentResult result =
                delegate.pay(command);

        recorder.after(command, result);
        return result;
    }
}
```

### 15.9.1 委托与转发

纯转发：

```java
@Override
public PaymentResult pay(
        PaymentCommand command
) {
    return delegate.pay(command);
}
```

增强型委托：

- 调用前校验；
- 缓存；
- 重试；
- 日志；
- 指标；
- 权限；
- 限流；
- 事务协调。

### 15.9.2 委托不是继承的语法糖

委托的优势是：

- 可以替换目标对象；
- 可以组合多个目标；
- 不暴露目标全部受保护成员；
- 不形成脆弱父子契约；
- 行为可以按对象实例配置。

代价是需要显式转发方法，类型数量可能增加。

## 15.10 `is-a` 与 `has-a`

继承通常表达：

```text
Dog is an Animal
```

组合通常表达：

```text
Car has an Engine
```

但自然语言读起来通顺，不代表设计一定正确。

### 15.10.1 更严格的 `is-a`

真正的 `is-a` 要求：

```text
任何需要父类型的地方
都可以透明使用子类型
并保持调用方可观察契约
```

这就是里氏替换的核心。

### 15.10.2 能说 `is-a` 仍可能不应继承

```text
ArrayList is a List
```

适合类型实现关系。

```text
Stack is a Vector
```

历史上语法成立，但从职责和公开能力看并不理想：栈不应该暴露任意位置插入、删除等向量能力。

### 15.10.3 `has-a` 也可能过于笼统

对象持有另一个对象并不自动证明组合合理。还需判断：

- 是否属于当前职责；
- 是否跨层依赖；
- 是否把太多服务塞进一个类；
- 是否形成服务定位器；
- 是否隐藏了真实依赖。

## 15.11 继承与组合对比

| 维度 | 继承 | 组合 |
|---|---|---|
| 关系 | `is-a` | `has-a` / uses-a |
| 绑定 | 类定义时固定 | 构造或运行时组装 |
| 复用方式 | 继承状态和实现 | 委托公共能力 |
| 扩展能力 | 单父类限制 | 可组合多个组件 |
| 封装 | 子类可能依赖 `protected` 细节 | 只依赖公开契约 |
| 替换 | 通常替换整个子类型 | 可替换单个组件 |
| 测试 | 可能需要构造复杂父类 | 可注入 Fake |
| 风险 | 脆弱基类、错误替换 | 转发代码、对象图复杂 |
| 适用 | 稳定类型层次和模板骨架 | 可变化策略和横切能力 |

### 15.11.1 继承是最强耦合之一

子类可能依赖：

- 父类字段；
- 父类初始化顺序；
- 可重写方法调用时机；
- 隐含调用协议；
- 异常语义；
- 线程安全假设；
- 未来新增方法。

父类修改可能在没有编译错误的情况下改变子类行为。

### 15.11.2 组合也不是零耦合

组合对象仍然依赖接口契约。接口设计过大、行为含糊或生命周期不清，同样会产生强耦合。

## 15.12 为什么通常优先组合

“优先组合”主要针对以下误用：

```text
为了复用几行代码而继承
为了获得工具方法而继承
为了覆盖一个变化行为而建立多层子类
为了配置差异而创建类型爆炸
```

组合把变化点放入可替换组件：

```java
public final class PriceCalculator {

    private final PricingPolicy policy;

    public PriceCalculator(
            PricingPolicy policy
    ) {
        this.policy = policy;
    }

    public Money calculate(Order order) {
        return policy.price(order);
    }
}
```

### 15.12.1 运行时可配置

同一个 `PriceCalculator` 可以组合：

- 普通定价；
- 会员定价；
- 大促定价；
- 灰度定价；
- 测试定价。

### 15.12.2 避免子类排列组合

如果变化维度有：

```text
渠道 × 地区 × 客户等级 × 活动
```

继承可能产生大量组合子类。

组合可以把独立维度拆成独立策略。

### 15.12.3 保留封装

组件只暴露契约，调用方不直接依赖其内部字段和执行细节。

## 15.13 继承仍然适合的场景

优先组合不等于完全禁止继承。

继承适合：

- 子类型严格满足父类型契约；
- 类型层次在业务上稳定；
- 父类专门为继承设计并有清晰文档；
- 模板方法需要固定流程骨架；
- 框架定义稳定扩展点；
- 需要统一类型多态；
- sealed 层次明确限制子类型集合；
- 骨架实现类帮助实现复杂接口。

### 15.13.1 为继承设计并写文档

可继承类应明确：

- 哪些方法可重写；
- 哪些方法会在构造期间调用；
- 调用顺序；
- 是否允许调用 `super`；
- 线程安全性；
- 异常约束；
- 状态不变量；
- 扩展点的幂等性和可重入性。

### 15.13.2 否则考虑 `final`

一个类如果没有为继承设计，应考虑声明为 `final`，通过组合扩展。

## 15.14 抽象类、接口与组合如何选择

### 15.14.1 选择接口

适合：

- 定义模块边界；
- 表达角色或能力；
- 需要多个独立实现；
- 一个类需要组合多个能力；
- 调用方只需稳定契约；
- 需要契约测试或测试替身。

### 15.14.2 选择抽象类

适合：

- 共享实例状态；
- 统一构造过程；
- 大量公共实现；
- 固定算法骨架；
- 受控的 `protected` 扩展点；
- 类型层次稳定。

### 15.14.3 选择组合

适合：

- 行为会独立变化；
- 需要运行时替换；
- 变化维度多个；
- 仅为复用实现；
- 需要隔离基础设施；
- 需要装饰、适配或策略。

### 15.14.4 常见组合方式

```text
接口
→ 定义对外契约

抽象类
→ 提供可选骨架实现

组合对象
→ 注入可变化策略和基础设施
```

三者可以配合，不是互斥关系。

## 15.15 SOLID 总览

SOLID 是五项面向对象设计原则的缩写：

| 原则 | 核心问题 | 典型信号 |
|---|---|---|
| SRP 单一职责 | 一个模块为何变化 | 多类变化原因混在一起 |
| OCP 开闭 | 如何增加能力 | 新需求总修改稳定核心 |
| LSP 里氏替换 | 子类型能否替代父类型 | 子类抛不支持、加强前置条件 |
| ISP 接口隔离 | 调用方是否依赖多余能力 | 空实现、无关方法、巨大接口 |
| DIP 依赖倒置 | 依赖应指向哪里 | 高层业务直接依赖技术细节 |

SOLID 不是：

- 每个类只能有一个方法；
- 所有依赖都必须有接口；
- 永远不能修改旧代码；
- 继承一定错误；
- 类越多越好；
- 设计模式越多越专业。

原则用于帮助权衡，不是机械验收清单。

---

## 15.16 单一职责原则 SRP

单一职责常被表达为：

> 一个模块应只有一个引起它变化的原因。

更准确地说，职责与“对哪一类参与者负责”有关。

### 15.16.1 混合职责示例

```java
public final class OrderService {

    public void create(OrderRequest request) {
        // 参数校验
        // 业务规则
        // SQL 拼接
        // 数据库存储
        // JSON 序列化
        // 邮件通知
        // 指标上报
    }
}
```

变化来源包括：

- 产品规则变化；
- 数据库变化；
- 消息格式变化；
- 通知渠道变化；
- 监控平台变化。

### 15.16.2 按变化原因拆分

```text
OrderApplicationService
OrderRepository
OrderPolicy
OrderEventPublisher
OrderMapper
```

拆分后并不意味着每个类只能做一件微小事情，而是每个模块围绕一个内聚职责协作。

### 15.16.3 SRP 的边界取决于层次

一个应用服务可以负责完整用例协调，但不应负责数据库驱动细节。

一个聚合可以负责多条内部规则，因为这些规则共同维护同一业务一致性边界。

---

## 15.17 开闭原则 OCP

开闭原则强调：

```text
对扩展开放
对修改关闭
```

它不是要求旧代码永远不修改，而是让稳定核心尽量不因新增变体反复变化。

### 15.17.1 条件分支增长

```java
switch (channel) {
    case EXPRESS -> expressFee(order);
    case AIR -> airFee(order);
    case SEA -> seaFee(order);
}
```

每新增渠道都要修改同一处。

### 15.17.2 策略扩展

```java
public interface ShippingFeePolicy {

    Money calculate(Order order);
}
```

新增渠道可以增加实现，并在组装层注册。

### 15.17.3 OCP 的成本

为了扩展点引入接口、注册表和对象装配会增加复杂度。

只有变化方向已经出现或成本可预测时，抽象才值得。

```text
第一次出现
→ 先实现清晰代码

第二次出现
→ 观察差异

第三次稳定重复
→ 提取变化轴
```

这不是绝对次数规则，而是提醒避免过早抽象。

---

## 15.18 里氏替换原则 LSP

里氏替换要求：

> 使用父类型的代码，在替换为任意合法子类型后，仍能保持父类型承诺的可观察行为。

语法上可赋值只是开始：

```java
Parent value = new Child();
```

还需满足行为契约。

### 15.18.1 前置条件不能加强

父类型允许任意非负数量：

```text
quantity >= 0
```

子类型不能要求：

```text
quantity >= 10
```

否则原本合法调用在子类型上失败。

### 15.18.2 后置条件不能削弱

父类型承诺成功后一定持久化，子类型不能悄悄只写缓存。

### 15.18.3 不变量必须保持

子类型不能破坏父类型对余额、状态机或集合一致性的约束。

### 15.18.4 异常契约应兼容

子类型不应对父类型正常支持的操作统一抛：

```java
throw new UnsupportedOperationException();
```

这通常说明继承关系错误或接口过大。

### 15.18.5 历史约束

子类型不应允许父类型禁止的状态变化。

LSP 是设计继承体系最重要的检查原则。

---

## 15.19 接口隔离原则 ISP

接口隔离强调：

> 调用方不应被迫依赖它不使用的方法。

不推荐：

```java
public interface WarehouseClient {

    Inventory query();

    void reserve();

    void release();

    void createWarehouse();

    void deleteWarehouse();

    void changePermission();
}
```

普通库存用例只需要前三项，却依赖管理能力。

### 15.19.1 按客户端角色拆分

```java
public interface InventoryReader {
    Inventory query(SkuId skuId);
}

public interface InventoryReservation {
    Reservation reserve(ReserveCommand command);
    void release(ReservationId id);
}

public interface WarehouseAdministration {
    void create(CreateWarehouseCommand command);
}
```

### 15.19.2 接口不是越小越好

如果每个方法都创建一个接口，会造成：

- 类型数量爆炸；
- 组装困难；
- 语义碎片化；
- 调用方需要持有大量依赖；
- 难以描述完整能力。

合理标准是：

```text
接口中的方法
是否服务同一调用方角色
并因同一原因共同变化
```

---

## 15.20 依赖倒置原则 DIP

依赖倒置强调：

1. 高层策略不依赖低层细节；
2. 二者都依赖抽象；
3. 抽象不依赖细节；
4. 细节依赖抽象。

错误方向：

```text
OrderApplicationService
        ↓
MyBatisOrderMapper
```

改进：

```text
OrderApplicationService
        ↓
OrderRepository
        ↑
MyBatisOrderRepository
```

### 15.20.1 抽象应表达业务需要

不推荐把框架 API 原样复制：

```java
public interface OrderRepository {
    int insert(Map<String, Object> row);
}
```

更合理：

```java
public interface OrderRepository {
    Order find(OrderId id);
    void save(Order order);
}
```

### 15.20.2 接口通常靠近消费方

如果业务层需要仓储能力，仓储接口通常由业务模块定义。

基础设施模块实现该接口。

这使依赖方向指向业务策略，而不是数据库框架。

---

## 15.21 依赖注入 DI

依赖注入表示：

> 对象不自行定位或创建外部依赖，而由组装者把依赖提供给它。

构造器注入：

```java
public final class OrderService {

    private final OrderRepository repository;
    private final PaymentGateway paymentGateway;

    public OrderService(
            OrderRepository repository,
            PaymentGateway paymentGateway
    ) {
        this.repository =
                Objects.requireNonNull(repository);
        this.paymentGateway =
                Objects.requireNonNull(paymentGateway);
    }
}
```

### 15.21.1 注入方式

- 构造器注入；
- 方法参数注入；
- Setter 注入；
- 字段注入；
- 工厂方法注入。

### 15.21.2 构造器注入通常优先

优点：

- 依赖显式；
- 对象构造后完整；
- 字段可 `final`；
- 便于手工测试；
- 不依赖反射；
- 循环依赖更容易暴露。

### 15.21.3 可选依赖谨慎使用

大量可选依赖可能说明一个类承担多个模式或职责。

与其注入 `Optional<Dependency>`，很多时候更适合拆分不同实现。

---

## 15.22 控制反转 IoC

控制反转描述一种更广义的结构变化：

```text
业务对象不控制整个创建和调用流程
框架或外部组装者负责调度
```

依赖注入是实现 IoC 的常见方式之一。

### 15.22.1 IoC 不等于 Spring

手工组装同样是依赖注入：

```java
OrderRepository repository =
        new MySqlOrderRepository(dataSource);

OrderService service =
        new OrderService(
                repository,
                paymentGateway
        );
```

### 15.22.2 好莱坞原则

```text
不要调用我们
我们会调用你
```

框架控制主流程，应用提供回调、处理器或插件。

例如：

- Servlet 容器调用 Controller；
- JUnit 调用测试方法；
- 消息框架调用 Listener；
- 模板方法调用子类钩子。

---

## 15.23 构造器注入的边界

构造器参数过多通常是设计信号。

```java
public OrderService(
        A a,
        B b,
        C c,
        D d,
        E e,
        F f,
        G g,
        H h
) {
}
```

可能说明：

- 职责过多；
- 用例边界太大；
- 把查询和命令混在一起；
- 缺少内聚协作者；
- 依赖层次错误；
- 只是一个流程脚本。

### 15.23.1 不要用依赖对象掩盖问题

把八个依赖塞进：

```java
OrderServiceDependencies
```

只会隐藏真实耦合，并没有降低它。

### 15.23.2 合理聚合协作者

如果多个依赖共同提供一个稳定能力，可以提取真正有行为的组件：

```java
FraudAssessment assessment =
        new FraudAssessment(
                riskClient,
                ruleRepository,
                clock
        );
```

这不是参数袋，而是内聚对象。

---

## 15.24 面向接口编程

面向接口编程是：

```text
调用方依赖最小、稳定、语义明确的契约
而不是依赖具体实现细节
```

它不等于：

```text
每个类都创建一个同名接口
```

### 15.24.1 值得抽象的边界

- 外部系统；
- 数据持久化；
- 时间、随机数和 ID；
- 可替换算法；
- 模块公开 API；
- 多供应商实现；
- 测试中昂贵或不确定的依赖。

### 15.24.2 不值得的形式主义

```text
UserService
UserServiceImpl
```

如果：

- 只有一个实现；
- 没有模块边界；
- 没有替换需求；
- 接口完整复制实现方法；
- 所有调用方都知道具体实现语义；

接口可能只是增加跳转成本。

### 15.24.3 先设计调用方需要什么

消费方接口：

```java
public interface StockAvailability {

    boolean available(
            SkuId skuId,
            Quantity quantity
    );
}
```

通常比供应方暴露完整 `InventoryService` 更符合 ISP 和 DIP。

---

## 15.25 依赖方向

架构质量很大程度取决于依赖箭头。

推荐方向：

```text
用户界面
→ 应用用例
→ 领域策略
← 基础设施实现
```

源代码依赖应指向更稳定、更核心的策略。

### 15.25.1 数据库不应定义业务模型

不推荐：

```text
数据库表结构
→ 自动生成 Entity
→ Entity 直接贯穿所有层
```

这会让数据库列、ORM 注解和延迟加载语义泄漏到业务层。

### 15.25.2 外部 DTO 不应成为领域对象

第三方接口字段变化不应直接传播到核心业务。

通过适配器转换：

```text
VendorResponse
→ Adapter
→ InternalModel
```

### 15.25.3 依赖方向与运行时调用方向不同

运行时可能是：

```text
业务服务调用数据库适配器
```

源代码依赖仍可是：

```text
数据库适配器实现业务定义的接口
```

不要把“谁调用谁”与“谁依赖谁的源码”混为一谈。

---

## 15.26 稳定性与抽象

稳定模块是：

- 被很多模块依赖；
- 修改成本高；
- 发布影响大；
- 契约变化困难。

不稳定模块是：

- 依赖很多外部细节；
- 容易被替换；
- 变化频繁；
- 位于系统边缘。

### 15.26.1 稳定依赖原则

依赖应尽量指向更稳定的模块。

```text
核心业务
不应依赖
具体数据库驱动版本
```

### 15.26.2 稳定模块需要适度抽象

被大量依赖的模块如果完全具体化，变化会扩散。

但“稳定”不等于“接口越多越好”。抽象应覆盖真实变化和公共契约。

### 15.26.3 波动性隔离

把容易变化的部分隔离：

- 供应商 SDK；
- JSON 格式；
- 数据库实现；
- 计费规则；
- 风控策略；
- 通知渠道；
- 系统时间。

---

## 15.27 循环依赖

循环依赖示例：

```text
OrderService
→ InventoryService
→ OrderService
```

问题包括：

- 初始化困难；
- 模块无法独立测试；
- 修改互相扩散；
- Spring 构造器注入直接失败；
- 包结构没有明确方向；
- 领域概念可能被错误切分。

### 15.27.1 解决方式

- 提取更高层协调者；
- 通过领域事件解耦时序；
- 合并实际上属于同一职责的组件；
- 把共享契约提取到更稳定模块；
- 改为单向查询接口；
- 使用应用服务协调两个领域对象；
- 重新划分聚合边界。

### 15.27.2 不要用 Setter 注入掩盖环

让容器“成功启动”不代表设计问题消失。

循环依赖是架构信号，应优先修正方向。

---

## 15.28 高内聚与低耦合

高内聚表示：

```text
一个模块内部元素
围绕同一职责紧密协作
```

低耦合表示：

```text
模块只了解协作者必要的公开契约
```

### 15.28.1 观察内聚

可通过以下问题判断：

- 字段是否被大多数方法共同使用？
- 方法是否围绕同一业务概念？
- 修改一个需求是否只影响该模块？
- 类名是否能准确描述全部行为？
- 是否存在互不相关的方法群？

### 15.28.2 观察耦合

- 是否知道协作者内部字段？
- 是否依赖调用顺序？
- 是否依赖具体异常实现？
- 是否需要跨多层取数据？
- 是否依赖框架类型？
- 是否共享可变集合？
- 是否需要一起部署和修改？

### 15.28.3 低耦合不是没有协作

把每个对象完全隔离会导致数据搬运和贫血脚本。

目标是通过清晰契约协作，而不是消灭依赖。

---

## 15.29 Tell, Don’t Ask

Tell, Don’t Ask 强调：

```text
告诉对象完成行为
而不是取出状态后在外部替它做决定
```

不推荐：

```java
if (order.getStatus()
        == OrderStatus.CREATED) {
    order.setStatus(
            OrderStatus.CANCELLED
    );
}
```

推荐：

```java
order.cancel();
```

由对象内部判断：

- 当前状态是否允许取消；
- 是否释放预留；
- 是否记录取消时间；
- 是否产生领域事件。

### 15.29.1 不是禁止所有 getter

查询 DTO、序列化、报表和展示天然需要读取数据。

该原则主要针对：

```text
外部获取对象内部状态
再执行本应属于对象的业务决策
```

---

## 15.30 迪米特法则

迪米特法则常被概括为“最少知识原则”。

对象应主要与以下对象交互：

- 自己；
- 参数；
- 自己创建的对象；
- 直接字段；
- 受控的全局对象。

不推荐的调用链：

```java
order.getCustomer()
     .getAddress()
     .getProvince()
     .getCode();
```

### 15.30.1 调用链的问题

- 暴露内部结构；
- 中间对象变化影响调用方；
- 空值处理分散；
- 业务含义不明确；
- 调用方知道过多导航细节。

### 15.30.2 使用语义方法

```java
String provinceCode =
        order.deliveryProvinceCode();
```

或由专门查询对象完成。

### 15.30.3 不要机械消灭点号

流式 API：

```java
stream.filter(...).map(...).toList();
```

并不违反迪米特法则，因为调用链操作的是同一抽象结果，不是在穿透复杂对象图。

---

## 15.31 Feature Envy

Feature Envy 表示一个方法对另一个对象的数据兴趣超过对自身数据的兴趣。

```java
public Money discount(Customer customer) {
    if (customer.level()
            == CustomerLevel.VIP
            && customer.points() > 1000) {
        return Money.of("20");
    }
    return Money.ZERO;
}
```

如果折扣规则属于客户行为，可能移动到：

```java
customer.discountFor(order);
```

### 15.31.1 不是所有跨对象计算都要移动

以下情况可保留在服务：

- 协调多个聚合；
- 策略本身独立变化；
- 计算不属于任一对象；
- 需要外部服务；
- 查询模型只是数据投影。

关键是把行为放到拥有必要知识且职责最合理的位置。

---

## 15.32 God Class

God Class 或上帝类通常表现为：

- 字段很多；
- 构造器依赖很多；
- 方法跨越多个业务概念；
- 大量 `if` 和 `switch`；
- 修改任何需求都要改它；
- 测试需要大量 Mock；
- 私有方法形成多个互不相关簇；
- 名称宽泛，如 `Manager`、`Helper`、`Util`、`Service`。

### 15.32.1 重构方向

- 按用例拆应用服务；
- 提取领域对象；
- 提取策略；
- 提取基础设施适配器；
- 提取值对象；
- 将查询和命令分离；
- 用事件解耦副作用；
- 删除无意义转发层。

### 15.32.2 不要一次性“大爆炸”重写

先通过测试锁定行为，再围绕稳定边界逐步移动代码。

---

## 15.33 贫血模型与充血模型

贫血模型通常只有字段和 getter/setter，业务逻辑集中在 Service。

```java
order.setStatus(CANCELLED);
order.setCancelTime(now);
```

充血模型把规则和状态变化放入对象：

```java
order.cancel(now);
```

### 15.33.1 充血模型优势

- 不变量集中；
- 状态变化语义明确；
- 减少重复判断；
- 更接近领域语言；
- 更容易测试规则。

### 15.33.2 贫血模型并非永远错误

适合：

- CRUD 管理后台；
- 报表查询模型；
- 外部 DTO；
- 简单数据转换；
- 规则很少且稳定；
- 以数据库表为中心的工具系统。

### 15.33.3 不要伪充血

把所有 Service 方法机械移动进实体，导致实体依赖：

- Repository；
- HTTP Client；
- MQ；
- Spring Bean；
- 数据库事务；

同样会破坏边界。

领域对象应主要维护自身规则和不变量，跨资源协调仍由应用服务负责。

---

## 15.34 策略模式

策略模式把可替换算法封装为共同契约。

```java
public interface AllocationStrategy {

    AllocationResult allocate(
            AllocationContext context
    );
}
```

实现：

```java
public final class FifoAllocation
        implements AllocationStrategy {
}

public final class NearestLocationAllocation
        implements AllocationStrategy {
}
```

使用：

```java
public final class AllocationService {

    private final AllocationStrategy strategy;
}
```

### 15.34.1 适合场景

- 算法独立变化；
- 多种规则互斥选择；
- 运行时配置；
- 避免大型条件分支；
- 需要独立测试；
- 不同客户或渠道策略。

### 15.34.2 策略选择器

策略对象不应自己判断“我是否适用”然后形成混乱链条。

可由明确选择器完成：

```java
AllocationStrategy select(
        AllocationType type
)
```

或者使用注册表：

```text
AllocationType → AllocationStrategy
```

---

## 15.35 装饰器模式

装饰器通过实现同一接口并持有委托对象，动态叠加能力。

```java
PaymentGateway gateway =
        new MetricsPaymentGateway(
                new RetryingPaymentGateway(
                        new HttpPaymentGateway()
                )
        );
```

### 15.35.1 与继承扩展对比

继承：

```text
RetryingHttpPaymentGateway
MetricsRetryingHttpPaymentGateway
AuditedMetricsRetryingHttpPaymentGateway
```

组合装饰器：

```text
基础实现
+ 重试
+ 指标
+ 审计
```

可按需要组合。

### 15.35.2 装饰器注意点

- 必须保持原接口契约；
- 顺序可能影响语义；
- 异常和重试边界要明确；
- `equals`、`hashCode` 和身份语义可能复杂；
- 装饰层过多会增加排查难度；
- 应提供可观测名称和结构。

---

## 15.36 适配器模式

适配器把不兼容接口转换为系统需要的接口。

系统需要：

```java
public interface SmsSender {
    void send(PhoneNumber number, String text);
}
```

供应商 SDK：

```java
vendorClient.push(
        String mobile,
        VendorPayload payload
);
```

适配器：

```java
public final class VendorSmsAdapter
        implements SmsSender {

    private final VendorClient client;

    @Override
    public void send(
            PhoneNumber number,
            String text
    ) {
        client.push(
                number.value(),
                VendorPayload.of(text)
        );
    }
}
```

### 15.36.1 适配器的价值

- 隔离供应商模型；
- 转换异常；
- 统一重试语义；
- 防止 SDK 类型扩散；
- 支持供应商替换；
- 保护核心模型。

### 15.36.2 不要让适配器承担业务决策

适配器负责协议和模型转换，不应决定订单能否发送短信等业务规则。

## 15.37 模板方法与策略

模板方法：

```text
继承
父类固定流程
子类重写步骤
```

策略：

```text
组合
上下文协调流程
策略对象提供算法
```

| 维度 | 模板方法 | 策略 |
|---|---|---|
| 复用 | 父类骨架 | 组合上下文 |
| 绑定 | 类定义时 | 构造或运行时 |
| 状态共享 | 方便 | 通过参数或上下文 |
| 变化步骤 | 受继承层次限制 | 可独立组合 |
| 流程控制 | 父类 | 上下文对象 |
| 测试 | 通过子类 | 直接测试策略 |

### 15.37.1 选择模板方法

- 流程非常稳定；
- 步骤顺序必须统一；
- 子类关系自然；
- 共享状态较多；
- 扩展点数量少。

### 15.37.2 选择策略

- 算法可独立替换；
- 运行时选择；
- 多个变化维度；
- 不希望暴露父类内部状态；
- 需要组合和测试。

## 15.38 状态模式

状态模式把随状态变化的行为封装到状态对象。

不推荐：

```java
if (status == CREATED) {
    ...
} else if (status == PAID) {
    ...
} else if (status == CANCELLED) {
    ...
}
```

状态对象：

```java
public interface OrderState {

    OrderState pay();

    OrderState cancel();
}
```

### 15.38.1 适合场景

- 状态较多；
- 每个状态行为差异明显；
- 状态转移规则复杂；
- 同类分支散落多个方法；
- 需要独立验证转移。

### 15.38.2 不适合简单状态机

只有两三个稳定状态、少量集中分支时，枚举或 sealed 类型加 `switch` 可能更直接。

## 15.39 责任链、管道与组合器

多个独立步骤可以通过组合形成管道：

```java
List<ValidationRule> rules =
        List.of(
                new StockRule(),
                new CreditRule(),
                new AddressRule()
        );
```

执行：

```java
for (ValidationRule rule : rules) {
    rule.validate(context);
}
```

### 15.39.1 适合

- 校验规则；
- 过滤器；
- 拦截器；
- 审批链；
- 数据转换；
- 中间件插件；
- 风控规则。

### 15.39.2 需要明确

- 顺序；
- 是否短路；
- 错误聚合；
- 幂等性；
- 上下文可变性；
- 并行执行；
- 重试边界。

没有这些契约，管道只是把复杂度从 `if` 转移到隐式列表。

## 15.40 条件分支如何重构

并非所有分支都要改成多态。

先分类：

### 15.40.1 类型分支

```java
switch (paymentType)
```

如果实现类型开放且行为长期绑定类型，可考虑策略或多态。

### 15.40.2 状态分支

```java
switch (order.status())
```

如果状态转移复杂，可考虑状态模式；如果类型集合封闭且操作集中，可用 sealed + `switch`。

### 15.40.3 规则分支

```java
if (amount > threshold)
```

可能是策略、规则对象或规格模式。

### 15.40.4 流程分支

```java
if (featureEnabled)
```

可能属于配置或发布策略，不必引入类型层次。

### 15.40.5 重构步骤

```text
先写 characterization test
↓
提取分支中的独立函数
↓
识别每个分支真正变化的数据和依赖
↓
定义最小契约
↓
迁移一个分支为实现
↓
引入选择器或注册表
↓
删除旧分支
```

## 15.41 多态、sealed 与模式匹配

现代 Java 提供两种主要建模方向。

### 15.41.1 开放多态

```java
interface Command {
    Result execute(Context context);
}
```

适合：

- 第三方可新增实现；
- 类型集合开放；
- 核心行为随类型一起扩展；
- 插件式系统。

### 15.41.2 封闭类型集合

```java
sealed interface Result
        permits Success, Failure {
}
```

配合模式 `switch`：

```java
return switch (result) {
    case Success success ->
            handleSuccess(success);
    case Failure failure ->
            handleFailure(failure);
};
```

适合：

- 类型集合受控；
- 需要穷尽检查；
- 操作比类型更常新增；
- 值对象、协议结果、AST、状态事件。

### 15.41.3 版本边界

- sealed 类和接口在 Java 17 正式发布；
- 类型模式 `switch` 在 Java 21 正式发布；
- 本章示例以 Java 21 正式语法为基线；
- Java 26 的原始类型模式仍属于预览能力，不作为企业基线示例。

## 15.42 开放类型与封闭操作的表达式问题

设计选择取决于更常变化的是：

```text
类型
还是操作
```

### 15.42.1 类型经常增加

对象多态适合：

```text
新增实现
无需修改已有调用方
```

### 15.42.2 操作经常增加

sealed 数据层次 + 模式匹配适合：

```text
新增一个操作
不必修改所有数据类型
```

### 15.42.3 两个方向无法同时最优

这就是经典表达式问题：

- 面向对象擅长新增类型；
- 函数式或模式匹配擅长新增操作。

设计应根据变化轴选择，不要以“多态一定高级”替代分析。

## 15.43 过度抽象与接口爆炸

过度抽象常见表现：

```text
一个实现
一个接口
一个抽象基类
一个工厂
一个注册器
一个提供器
一个管理器
```

但系统没有真实变化需求。

### 15.43.1 代价

- 阅读跳转多；
- 调试调用链长；
- 命名困难；
- 组装复杂；
- 测试大量 Mock；
- 修改需要同步多个空壳层；
- 新人难以理解真实业务。

### 15.43.2 抽象的证据

一个抽象通常至少应满足一项：

- 已存在多个实现；
- 明确的模块边界；
- 外部依赖需要隔离；
- 变化概率高且代价大；
- 测试需要替换不确定资源；
- 公开 API 需要稳定契约；
- 算法可以独立演进。

### 15.43.3 删除抽象也是重构

当接口不再表达真实边界，可以内联：

- 删除空接口；
- 合并单一实现；
- 删除无意义 Manager；
- 将只转发的方法移除；
- 使用具体类直到变化出现。

## 15.44 设计模式滥用

模式是对重复设计问题的命名，不是开发目标。

滥用示例：

- 两个分支就引入策略工厂注册中心；
- 简单对象创建使用抽象工厂；
- 普通方法调用使用命令总线；
- 只有一个处理器却实现责任链；
- 没有双重分派需求却使用 Visitor；
- 为显示“解耦”引入事件最终导致流程不可追踪。

### 15.44.1 判断模式是否值得

- 问题是否真实存在？
- 变化是否已经重复？
- 模式是否降低修改范围？
- 是否降低还是增加认知负担？
- 是否能用更简单函数或数据结构解决？
- 是否有清晰退出路径？

### 15.44.2 模式名称不能替代契约

即使名为 Strategy，也必须说明：

- 输入；
- 输出；
- 异常；
- 幂等；
- 线程安全；
- 选择规则；
- 生命周期。

## 15.45 围绕变化轴设计

变化轴表示可能独立变化的维度。

WMS 分配场景：

- 分配算法；
- 仓库；
- 货主；
- 商品属性；
- 批次规则；
- 优先级；
- 设备能力；
- 灰度版本。

### 15.45.1 不要提前为所有维度建类型

先观察哪些维度：

- 真的独立变化；
- 具有稳定规则；
- 有多个实现；
- 有独立测试价值；
- 会被配置选择。

### 15.45.2 正交变化应分离

如果重试和业务策略独立：

```text
业务策略
×
重试策略
```

不要创建：

```text
RetryingVipPricingStrategy
RetryingNormalPricingStrategy
```

应通过装饰器或组合分别建模。

### 15.45.3 同步变化应保持内聚

如果一组字段和方法总是一起变化，不应强行拆散。

## 15.46 从继承重构为组合

原结构：

```java
public class CachedUserService
        extends UserService {
}
```

问题：

- 缓存与业务服务类型绑定；
- 只能扩展一个父类；
- 缓存逻辑可能依赖父类内部方法；
- 难以重用到其他实现。

### 15.46.1 渐进步骤

1. 提取父类公开契约；
2. 让原父类实现契约；
3. 在新类中持有契约类型；
4. 把覆盖方法改为委托增强；
5. 迁移调用方到接口；
6. 删除不再需要的继承；
7. 收紧父类可见性或声明 `final`。

结果：

```java
public final class CachedUserService
        implements UserService {

    private final UserService delegate;
}
```

### 15.46.2 保持行为

重构时重点验证：

- 缓存键；
- 异常；
- 空值；
- 事务边界；
- 调用次数；
- 并发语义；
- 失效策略。

## 15.47 从条件分支重构为策略

原代码：

```java
Money calculate(
        CustomerType type,
        Order order
) {
    return switch (type) {
        case NORMAL -> normal(order);
        case VIP -> vip(order);
        case PARTNER -> partner(order);
    };
}
```

### 15.47.1 提取每个分支

```java
private Money vip(Order order) {
}
```

### 15.47.2 识别共同输入输出

```java
interface PricingPolicy {
    Money calculate(Order order);
}
```

### 15.47.3 建立选择器

```java
Map<CustomerType, PricingPolicy>
```

### 15.47.4 避免把 `switch` 隐藏到工厂

如果选择器内部仍然每次写同样 `switch`，只是移动位置。真正价值在于：

- 分支实现独立；
- 注册关系集中；
- 新增实现影响可控；
- 策略可单测和组合。

## 15.48 可测试性与可替换性

良好设计通常使测试更简单，但“为了 Mock 而接口化一切”同样错误。

### 15.48.1 值得替换的依赖

- 时间；
- 随机数；
- ID 生成；
- 网络；
- 文件；
- 数据库；
- 消息；
- 外部支付；
- 慢算法；
- 不确定资源。

### 15.48.2 Fake 优于过度 Mock

Fake 仓储：

```java
public final class InMemoryOrderRepository
        implements OrderRepository {

    private final Map<OrderId, Order> data =
            new HashMap<>();
}
```

它可以支持真实状态变化和契约测试。

### 15.48.3 契约测试

对所有实现运行相同测试：

```text
save 后可 find
不存在时返回约定结果
重复保存满足幂等或覆盖规则
异常语义一致
```

这比只验证方法被调用更能证明可替换性。

### 15.48.4 可替换不只看类型

还要保持：

- 语义；
- 性能量级；
- 事务；
- 并发；
- 错误；
- 安全；
- 可观测性。

## 15.49 WMS 场景：库存分配设计

需求：

```text
根据仓库、货主、SKU、批次、库位和订单优先级
选择可分配库存
```

不推荐把全部规则塞进：

```java
InventoryAllocationService
```

### 15.49.1 分层组合

```text
AllocationApplicationService
├── InventoryCandidateRepository
├── AllocationStrategy
├── AllocationRulePipeline
├── ReservationPort
└── AllocationEventPublisher
```

### 15.49.2 候选查询与决策分离

仓储负责：

```text
获取候选库存
```

策略负责：

```text
排序和选择
```

规则负责：

```text
过滤不合法候选
```

预留端口负责：

```text
原子占用库存
```

### 15.49.3 避免策略依赖数据库实体

策略输入应是稳定的领域视图，而不是 MyBatis DO。

### 15.49.4 一致性边界

真正扣减或预留仍需数据库条件更新、事务或分布式一致性机制。

对象设计不能替代并发控制。

### 15.49.5 可观测性

策略结果应记录：

- 选中规则；
- 被排除原因；
- 候选数量；
- 排序依据；
- 版本；
- 耗时；
- 最终预留结果。

否则组合结构可能难以排查。

## 15.50 设计权衡

任何设计都有成本。

### 15.50.1 组合的成本

- 对象数量增加；
- 装配复杂；
- 委托层较多；
- 调用链排查困难；
- 生命周期管理要求提高。

### 15.50.2 继承的成本

- 父子强耦合；
- 脆弱基类；
- 隐式控制流；
- 单继承限制；
- 状态暴露；
- 难以运行时替换。

### 15.50.3 多态的成本

- 类型数量增加；
- 行为分散；
- 全局查看所有分支困难；
- 序列化和注册更复杂。

### 15.50.4 模式匹配的成本

- 新增类型需要修改所有穷尽操作；
- 分支逻辑可能复制；
- 开放扩展受限。

### 15.50.5 最佳设计取决于上下文

判断维度：

- 变化频率；
- 团队熟悉度；
- 性能要求；
- 发布边界；
- 兼容性；
- 可观测性；
- 测试成本；
- 业务复杂度。

## 15.51 代码评审检查清单

### 对继承

- 子类是否真的满足父类契约？
- 是否只是为了复用实现？
- 父类是否为继承设计？
- 是否有构造器动态绑定风险？
- `protected` 是否暴露过多？
- 子类是否抛 `UnsupportedOperationException`？
- 是否可改为策略或装饰器？

### 对接口

- 接口由谁消费？
- 方法是否服务同一角色？
- 是否只有形式主义单实现？
- 是否泄漏框架类型？
- 是否有明确异常和线程安全契约？
- 是否支持契约测试？
- 新增方法会造成什么兼容风险？

### 对组合

- 所有权和关闭责任是否明确？
- 组件是否可共享？
- 委托顺序是否重要？
- 依赖是否太多？
- 是否形成循环依赖？
- 组合是否掩盖了上帝类？

### 对模式

- 真实变化是什么？
- 是否已有多个实现？
- 简单函数是否足够？
- 模式是否降低修改范围？
- 是否增加不必要类型和注册逻辑？
- 失败和可观测性如何处理？

## 15.52 建议实验

> 以下实验均为单文件示例，以 Java 21 正式语法为基线。每个实验都可分别保存为与 `public class` 同名的 `.java` 文件，再使用 `javac --release 21` 编译。


### 实验1：组合替代工具继承


```java
public class CompositionInsteadOfInheritanceDemo {

    interface JsonSerializer {
        String serialize(String value);
    }

    static final class SimpleJsonSerializer
            implements JsonSerializer {
        @Override
        public String serialize(String value) {
            return "\"" + value + "\"";
        }
    }

    static final class OrderService {
        private final JsonSerializer serializer;

        OrderService(JsonSerializer serializer) {
            this.serializer = serializer;
        }

        String export(String orderNo) {
            return serializer.serialize(orderNo);
        }
    }

    public static void main(String[] args) {
        OrderService service =
                new OrderService(
                        new SimpleJsonSerializer()
                );
        System.out.println(service.export("SO-100"));
    }
}
```


**观察重点：** 调用方只看到订单服务自己的能力，序列化实现可以独立替换。


### 实验2：委托与增强


```java
public class DelegationDemo {

    interface MessageSender {
        void send(String message);
    }

    static final class ConsoleSender
            implements MessageSender {
        @Override
        public void send(String message) {
            System.out.println("send: " + message);
        }
    }

    static final class AuditingSender
            implements MessageSender {
        private final MessageSender delegate;

        AuditingSender(MessageSender delegate) {
            this.delegate = delegate;
        }

        @Override
        public void send(String message) {
            System.out.println("before");
            delegate.send(message);
            System.out.println("after");
        }
    }

    public static void main(String[] args) {
        MessageSender sender =
                new AuditingSender(
                        new ConsoleSender()
                );
        sender.send("hello");
    }
}
```


**观察重点：** 验证当前对象可以在委托前后增加行为，而不继承具体发送器。


### 实验3：策略运行时替换


```java
public class StrategyRuntimeDemo {

    interface PricingPolicy {
        int price(int basePrice);
    }

    static final class NormalPricing
            implements PricingPolicy {
        @Override
        public int price(int basePrice) {
            return basePrice;
        }
    }

    static final class VipPricing
            implements PricingPolicy {
        @Override
        public int price(int basePrice) {
            return basePrice * 80 / 100;
        }
    }

    static final class Calculator {
        private final PricingPolicy policy;

        Calculator(PricingPolicy policy) {
            this.policy = policy;
        }

        int calculate(int basePrice) {
            return policy.price(basePrice);
        }
    }

    public static void main(String[] args) {
        System.out.println(
                new Calculator(
                        new NormalPricing()
                ).calculate(100)
        );
        System.out.println(
                new Calculator(
                        new VipPricing()
                ).calculate(100)
        );
    }
}
```


**观察重点：** 同一上下文通过组合不同策略得到不同行为，不需要建立多个计算器子类。


### 实验4：装饰器叠加能力


```java
public class DecoratorDemo {

    interface Operation {
        String execute();
    }

    static final class CoreOperation
            implements Operation {
        @Override
```

### 实验20：WMS 分配策略组合


```java
import java.util.Comparator;
import java.util.List;

public class WmsAllocationCompositionDemo {

    record Stock(
            String location,
            int quantity,
            int distance
    ) {
    }

    interface AllocationRule {
        boolean allowed(Stock stock);
    }

    interface AllocationStrategy {
        Stock choose(List<Stock> stocks);
    }

    static final class AllocationService {
        private final List<AllocationRule> rules;
        private final AllocationStrategy strategy;

        AllocationService(
                List<AllocationRule> rules,
                AllocationStrategy strategy
        ) {
            this.rules = List.copyOf(rules);
            this.strategy = strategy;
        }

        Stock allocate(List<Stock> stocks) {
            List<Stock> candidates =
                    stocks.stream()
                            .filter(stock ->
                                    rules.stream()
                                            .allMatch(rule ->
                                                    rule.allowed(stock)
                                            )
                            )
                            .toList();

            return strategy.choose(candidates);
        }
    }

    public static void main(String[] args) {
        AllocationRule enough =
                stock -> stock.quantity() >= 5;

        AllocationStrategy nearest =
                stocks -> stocks.stream()
                        .min(
                                Comparator.comparingInt(
                                        Stock::distance
                                )
                        )
                        .orElseThrow();

        AllocationService service =
                new AllocationService(
                        List.of(enough),
                        nearest
                );

        Stock selected =
                service.allocate(
                        List.of(
                                new Stock("A", 3, 1),
                                new Stock("B", 8, 5),
                                new Stock("C", 9, 2)
                        )
                );

        System.out.println(
                selected.location()
        );
    }
}
```


**观察重点：** 候选过滤和排序选择是两个独立变化轴，可以分别测试和替换。

## 15.54 易错点

### 误区一：只要能复用代码就继承

**错误或不完整。**

继承表达可替换类型关系，不是通用代码复用工具。仅为复用实现时优先提取组件或函数。

### 误区二：把“优先组合”理解为禁止继承

**错误或不完整。**

稳定的类型层次、骨架实现和模板流程仍然适合继承，关键是父类型契约是否稳定。

### 误区三：只用自然语言判断 `is-a`

**错误或不完整。**

必须进一步检查 LSP：前置条件、后置条件、不变量、异常和性能语义是否兼容。

### 误区四：把字段引用一律称为组合

**错误或不完整。**

字段只能说明对象长期关联，聚合或组合取决于所有权、独立性和生命周期。

### 误区五：注入的共享资源由使用者随意关闭

**错误或不完整。**

谁创建和拥有资源，谁通常负责关闭。共享线程池、连接池和客户端不应由普通业务对象自行销毁。

### 误区六：通过 `protected` 字段帮助子类复用

**错误或不完整。**

这会暴露父类表示并形成脆弱基类。优先 `private` 字段和受控的 `protected final` 方法。

### 误区七：子类用 `UnsupportedOperationException` 规避契约

**错误或不完整。**

父类型承诺的正常操作在子类不可用，通常说明违反 LSP 或接口过大。

### 误区八：把 SRP 解释为一个类只能做一件小事

**错误或不完整。**

职责是变化原因和负责对象，不是方法数量。过度拆分会破坏内聚。

### 误区九：为了 OCP 提前为所有分支建策略

**错误或不完整。**

没有真实变化证据时会增加类型和装配成本。先实现清晰代码，再提取稳定变化轴。

### 误区十：认为开闭原则禁止修改旧代码

**错误或不完整。**

重构、修复错误和调整错误抽象都需要修改。OCP关注新增变体不应反复破坏稳定核心。

### 误区十一：接口越小越好

**错误或不完整。**

接口应围绕调用方角色和共同变化保持内聚，过细会造成接口爆炸。

### 误区十二：所有 Service 都定义 `Service`/`ServiceImpl`

**错误或不完整。**

只有真实模块边界、替换需求或契约价值时才需要接口。

### 误区十三：业务接口复制 ORM 或 SDK 方法

**错误或不完整。**

这会让高层策略依赖低层技术语义，违反 DIP。

### 误区十四：字段注入让依赖更简洁

**错误或不完整。**

字段注入隐藏必需依赖、阻碍不可变性和手工测试，也容易掩盖循环依赖。

### 误区十五：用一个 Dependencies 参数袋解决构造器过长

**错误或不完整。**

依赖数量没有减少，只是被隐藏。应检查职责并提取内聚协作者。

### 误区十六：把 IoC 等同于 Spring 容器

**错误或不完整。**

手工工厂、回调和模板方法同样体现控制反转。

### 误区十七：通过 Setter 注入绕开循环依赖

**错误或不完整。**

容器能够启动不代表依赖方向合理，循环仍会增加测试和演进成本。

### 误区十八：低耦合等于没有依赖

**错误或不完整。**

对象必须协作。低耦合要求只依赖必要且稳定的契约。

### 误区十九：高内聚等于把所有相关代码放一个类

**错误或不完整。**

相关概念可能属于不同层次和变化原因，仍需按职责划分。

### 误区二十：Tell, Don’t Ask 禁止所有 getter

**错误或不完整。**

查询、展示和 DTO 需要读取；该原则针对外部替对象执行业务决策。

### 误区二十一：连续调用链一定违反迪米特法则

**错误或不完整。**

流式 API 操作同一抽象时没有穿透对象内部结构，不能只按点号数量判断。

### 误区二十二：看到 Feature Envy 就把方法移入实体

**错误或不完整。**

跨聚合协调、独立策略和基础设施逻辑不一定属于实体。

### 误区二十三：把充血模型理解为实体调用所有基础设施

**错误或不完整。**

实体应维护内部规则，不应直接依赖数据库、HTTP、MQ 或 Spring Bean。

### 误区二十四：贫血模型一定错误

**错误或不完整。**

CRUD、报表 DTO 和简单数据管道中，行为很少时贫血模型可能更直接。

### 误区二十五：策略对象自己判断是否适用

**错误或不完整。**

大量 `supports()` 遍历可能产生隐式优先级和冲突，应由明确选择器或注册规则控制。

### 误区二十六：装饰器可以任意改变返回语义

**错误或不完整。**

装饰器应保持原契约，否则调用方不能透明替换。

### 误区二十七：忽略装饰器顺序

**错误或不完整。**

缓存、重试、事务、指标和鉴权的顺序会改变行为，应显式约定。

### 误区二十八：适配器中混入业务规则

**错误或不完整。**

适配器负责协议、模型和异常转换，业务决策应留在核心层。

### 误区二十九：模板方法中暴露大量可重写钩子

**错误或不完整。**

扩展点过多会使控制流隐式且难以维护，可能更适合策略组合。

### 误区三十：简单状态枚举也使用完整状态模式

**错误或不完整。**

模式成本可能高于分支成本，类型集合封闭且逻辑简单时 `switch` 更清晰。

### 误区三十一：责任链没有明确短路和错误规则

**错误或不完整。**

只把处理器放进列表并不能形成可靠契约，必须说明顺序、短路、幂等和错误聚合。

### 误区三十二：把大型 `switch` 移到工厂就认为完成重构

**错误或不完整。**

如果分支实现仍耦合在一起，只是移动代码位置，并未隔离变化。

### 误区三十三：开放插件系统使用 sealed 封闭层次

**错误或不完整。**

sealed 限制直接子类型，适合受控集合，不适合第三方自由扩展。

### 误区三十四：封闭结果类型仍为每个操作增加实例方法

**错误或不完整。**

操作频繁增加时会迫使所有类型同步修改，模式匹配可能更合适。

### 误区三十五：为了模式而制造抽象

**错误或不完整。**

模式应解决已出现的问题，不应成为类图装饰。

### 误区三十六：用 Mock 数量衡量可测试性

**错误或不完整。**

大量 Mock 可能说明对象协作过细或测试耦合实现细节。

### 误区三十七：只验证类型可替换，不验证行为契约

**错误或不完整。**

实现还必须保持异常、事务、并发、性能量级和安全语义。

### 误区三十八：一次性重写上帝类

**错误或不完整。**

大爆炸重写容易丢失隐含行为，应先建立 characterization test 再渐进迁移。

### 误区三十九：领域策略直接接收数据库 DO

**错误或不完整。**

持久化模型变化会污染核心算法，应转换为稳定领域输入。

### 误区四十：认为对象设计能替代事务和并发控制

**错误或不完整。**

良好模型保护单对象规则，但跨线程、跨进程一致性仍需要锁、事务、幂等和消息机制。

## 15.55 工程实践建议

### 15.55.1 先写出变化假设

引入接口或策略前，明确预计变化的是供应商、算法、状态、协议还是部署方式。

### 15.55.2 继承前执行 LSP 检查

逐项检查合法输入、结果保证、异常、不变量和历史行为，而不只检查类型名称。

### 15.55.3 没有为继承设计的类默认关闭继承

可以使用 `final`，需要扩展时提供接口、委托或明确扩展点。

### 15.55.4 优先使用构造器注入必需依赖

保持对象完整、依赖显式并允许字段 `final`。

### 15.55.5 明确所有权和关闭责任

在类文档和工厂中说明组件是否共享、是否由当前对象关闭。

### 15.55.6 接口靠近消费方定义

让接口表达高层用例真正需要的能力，避免供应商 API 反向塑造业务。

### 15.55.7 接口使用领域语言

优先 `InventoryReservation`、`PaymentGateway`，避免宽泛 `Manager`、`Helper`。

### 15.55.8 保持接口角色内聚

方法应服务同一调用方并因同一原因变化。

### 15.55.9 不要机械创建 Impl

实现名称应表达策略、供应商或技术，如 `MySqlOrderRepository`。

### 15.55.10 变化行为使用策略组合

当算法可独立替换或运行时选择时，将其提取为策略或函数对象。

### 15.55.11 横切增强使用装饰器

缓存、重试、指标、审计等可通过同契约委托叠加。

### 15.55.12 外部协议使用适配器隔离

把 SDK 类型、错误码和载荷转换限制在系统边缘。

### 15.55.13 稳定流程才使用模板方法

父类应控制少量明确步骤，避免大量可重写钩子。

### 15.55.14 状态复杂度达到阈值再引入状态模式

状态少且逻辑集中时优先枚举或 sealed `switch`。

### 15.55.15 规则管道声明执行语义

明确顺序、短路、错误聚合、并行性、幂等和上下文可变性。

### 15.55.16 依赖环作为架构缺陷处理

优先调整职责、提取协调者或事件，不用容器技巧掩盖。

### 15.55.17 高层模块不得暴露框架类型

领域和应用接口避免直接出现 ORM、HTTP 客户端或消息 SDK 类型。

### 15.55.18 为外部不确定性建立端口

时间、随机数、ID、网络、文件和数据库应可替换。

### 15.55.19 优先使用 Fake 验证状态行为

对于仓储、缓存等有状态端口，Fake 往往比大量交互 Mock 更可靠。

### 15.55.20 为多实现接口建立契约测试

确保所有实现满足统一输入输出、异常和幂等规则。

### 15.55.21 在代码评审中追问修改范围

模拟新增一个变体，观察需要修改多少文件和稳定核心。

### 15.55.22 避免参数袋隐藏耦合

构造器过长时应拆职责或提取有行为的协作者。

### 15.55.23 保护组合对象内部集合

使用不可变副本和业务方法维护不变量，避免暴露可变集合。

### 15.55.24 避免双向对象导航

除非确有业务必要，优先单向关联以降低同步和序列化复杂度。

### 15.55.25 用语义方法替代对象图穿透

例如 `order.deliveryProvinceCode()`，避免调用方依赖内部导航结构。

### 15.55.26 把业务决策放到拥有知识的位置

减少 Feature Envy，但不要把跨资源协调塞进实体。

### 15.55.27 应用服务负责用例协调

领域对象维护规则，基础设施适配器处理外部技术细节。

### 15.55.28 分离查询模型与命令模型

复杂查询 DTO 不必强行使用充血领域对象。

### 15.55.29 围绕正交变化拆组件

渠道、重试、缓存和规则独立变化时，不要制造排列组合子类。

### 15.55.30 同步变化保持内聚

总是一起修改的字段和行为不要为了模式被拆散。

### 15.55.31 抽象出现前允许具体实现存在

清晰的具体代码通常比猜测未来变化的空接口更好。

### 15.55.32 删除失效抽象

没有边界价值的接口、工厂和转发层应及时内联。

### 15.55.33 重构前建立行为基线

使用 characterization test、日志和生产样本锁定隐含语义。

### 15.55.34 继承转组合时逐步迁移

先提取契约，再引入委托包装，最后删除继承关系。

### 15.55.35 条件转策略时先提取纯函数

降低每个分支的依赖，再形成最小共同接口。

### 15.55.36 对装饰链提供可观测结构

日志中记录真实实现、装饰层和顺序，便于排查。

### 15.55.37 评估抽象的性能语义

可替换实现不能只保证结果，还要考虑延迟、批量和资源上限。

### 15.55.38 在 WMS 策略中记录决策原因

保存候选、过滤规则、排序依据和策略版本，确保可解释。

### 15.55.39 对象设计与一致性机制配合

库存预留仍需条件更新、事务、幂等和冲突处理。

### 15.55.40 以认知负担衡量最终方案

在满足正确性和演进性的前提下，选择团队能理解和维护的最简单结构。

## 15.57 本章总结

### 15.57.1 对象关系

```text
依赖
→ 临时使用

关联
→ 长期知道

聚合
→ 包含但部分可独立

组合
→ 拥有并维护部分

委托
→ 把请求交给内部组件
```

Java 语法不会自动标记聚合和组合，必须通过业务语义、所有权和生命周期判断。

### 15.57.2 继承与组合

```text
稳定 is-a + 可替换契约
→ 可以继承

独立变化行为 + 运行时替换
→ 优先组合

仅为复用几行实现
→ 不应继承
```

优先组合是为了减少父子强耦合，不是禁止一切继承。

### 15.57.3 SOLID

```text
SRP
→ 控制变化原因

OCP
→ 隔离可扩展变体

LSP
→ 保证子类型行为替换

ISP
→ 只依赖调用方所需能力

DIP
→ 依赖稳定抽象而非技术细节
```

### 15.57.4 依赖方向

```text
核心业务定义需要的端口
基础设施实现端口
组装层把实现注入业务
```

依赖注入是组装方式，控制反转是更广义的控制权变化。

### 15.57.5 设计坏味道

重点识别：

- 脆弱基类；
- 不支持父类型操作；
- 巨大接口；
- God Class；
- Feature Envy；
- 对象图穿透；
- 循环依赖；
- 接口爆炸；
- 设计模式滥用；
- 贫血脚本与伪充血实体。

### 15.57.6 模式选择

```text
可替换算法
→ Strategy

同契约叠加能力
→ Decorator

转换外部协议
→ Adapter

稳定流程骨架
→ Template Method

复杂状态行为
→ State

封闭类型 + 操作常增加
→ sealed + pattern switch
```

### 15.57.7 最终判断标准

设计的目标不是类越多，而是：

```text
需求变化时
修改范围小
行为仍正确
依赖方向清晰
对象能够独立测试
故障容易观察
团队能够理解
```

## 15.58 面试口述版

> 组合和继承的选择，核心不是语法，而是关系和变化方向。继承表达稳定的 `is-a`，子类必须满足里氏替换，不能加强前置条件、削弱结果保证或把父类支持的操作改成不支持。仅为了复用实现时，继承会形成脆弱基类，所以通常优先把变化行为提取成接口，通过组合和委托注入。组合的优势是可以同时组合多个能力、运行时替换组件并保持封装，但需要额外对象装配和生命周期管理。
>
> SOLID 中，SRP 控制变化原因，OCP 隔离新增变体，LSP 保证子类型替换，ISP 让调用方只依赖所需能力，DIP 让高层业务和底层实现都依赖业务抽象。依赖注入是实现依赖倒置和控制反转的常见组装方式，构造器注入通常最清晰，但构造器参数过多也可能说明职责过大。
>
> 在模式选择上，可替换算法用策略，同契约叠加缓存、重试、指标等能力用装饰器，供应商 SDK 和内部接口不兼容时用适配器，流程稳定且步骤差异明确时可用模板方法。现代 Java 中，如果类型集合封闭、操作更常增加，可以使用 sealed 类型和模式 `switch`；如果实现集合开放、第三方需要扩展，则接口多态更自然。最终要围绕真实变化轴设计，避免所有类都建接口、一个方法一个接口以及为了模式而模式。好的设计应该让新增需求修改范围可控、实现可替换、行为可测试、依赖方向清晰，并且团队能够理解和排查。
