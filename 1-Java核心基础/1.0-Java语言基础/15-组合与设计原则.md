# 组合与设计原则

## 7.20 抽象类与接口的区别

维度 抽象类 接口
关键字 abstract class interface
类继承数量 只能继承一个类 可以实现多个接口
实例字段 可以 不可以
构造方法 可以 不可以
普通实例方法 可以 可通过 default 提供
抽象方法 可以 可以
静态方法 可以 可以
private 方法 可以 可以

## 7.21 抽象类与接口如何选择

**7.21.1 适合使用抽象类**

当多个实现：

- 有共享实例字段
- 有共同构造逻辑
- 有大量公共实现
- 存在稳定父子关系
- 需要 protected 扩展点
- 需要固定部分算法流程
- 需要限制子类行为
- 例如：

```java
public abstract class BaseMessageConsumer {
private final String topic;
private final int retryCount;
protected BaseMessageConsumer(
String topic,
int retryCount
) {
this.topic = topic;
this.retryCount = retryCount;
}
public final void consume(Message message) {
validate(message);
handle(message);
acknowledge(message);
}
protected abstract void handle(Message message);
}
```

**7.21.2 适合使用接口**

当需要表达：

- 独立能力
- 角色
- 调用契约
- 可替换实现
- 多个类之间没有共同状态
- 一个类需要同时具备多个能力
- 需要面向抽象解耦
- 例如：

```
public interface Retryable {
void retry();
}
public interface Closable {
void close();
}
```

不同类型都可以实现这些能力，不要求它们属于同一个父类体系。

**7.21.3 二者可以配合使用**

接口定义对外契约：

```
public interface PaymentProcessor {
PaymentResult pay(PaymentCommand command);
}
```

抽象类提供部分公共实现：

```
public abstract class AbstractPaymentProcessor
implements PaymentProcessor {
protected final void validate(
PaymentCommand command
) {
Objects.requireNonNull(command);
}
protected final void recordLog(
PaymentResult result
) {
}
}
```

具体实现：

```java
public class AlipayProcessor
extends AbstractPaymentProcessor {
@Override
public PaymentResult pay(
PaymentCommand command
) {
validate(command);
PaymentResult result =
doAlipayPayment(command);
recordLog(result);
return result;
}
}
```

这种设计兼顾：

```
接口
→ 对外契约与多实现
抽象类
→ 公共实现与代码复用
```

## 7.22 面向接口编程

面向接口编程意味着：
调用方依赖抽象契约，而不是直接依赖具体实现类。
不推荐：

```java
public class OrderService {
private final MySqlOrderRepository repository;
public OrderService(
MySqlOrderRepository repository
) {
this.repository = repository;
}
}
```

这种设计与 MySQL 实现强耦合。
更合理：

```java
public class OrderService {
private final OrderRepository repository;
public OrderService(
OrderRepository repository
) {
this.repository = repository;
}
}
```

接口：

```
public interface OrderRepository {
Order findById(String orderId);
void save(Order order);
}
```

具体实现：

```java
public class MySqlOrderRepository
implements OrderRepository {
}
```

也可以提供：

```java
public class InMemoryOrderRepository
implements OrderRepository {
}
```

**7.22.1 面向接口编程的价值**

替换实现更容易
单元测试更容易
降低模块耦合
业务层不依赖基础设施细节
支持依赖注入
支持多态扩展
职责边界更清晰

**7.22.2 不等于所有类都必须有接口**

机械地给每个类创建接口：

```
UserService
UserServiceImpl
OrderService
OrderServiceImpl
ProductService
ProductServiceImpl
```

并不一定合理。

如果某个类：

- 只有一个稳定实现
- 没有替换需求
- 不构成模块边界
- 不需要测试替身
- 没有对外契约价值
则不一定需要额外接口。
接口应该表达真实的抽象边界，而不是命名习惯。

## 7.23 接口命名

接口名称应表达：

- 能力
- 角色
- 业务契约
- 常见形式：

```
Runnable
Comparable
Serializable
Closeable
OrderRepository
PaymentProcessor
InventoryService
```

不建议所有接口都机械添加 I 前缀：

```
IOrderService
IPaymentProcessor
```

除非团队规范明确要求。
也不建议为了区分实现类，统一使用：

```
OrderServiceImpl
```

更有语义的实现名通常更好：

```
DefaultOrderService
RemoteOrderService
CachedOrderService
MySqlOrderRepository
RedisOrderRepository
```

## 7.24 接口隔离原则

接口隔离原则可以概括为：
调用方不应该被迫依赖它不需要的方法。
错误示例：

```
public interface Machine {
void print();
void scan();
void fax();
}
```

普通打印机：

```java
public class SimplePrinter
implements Machine {
@Override
public void print() {
}
@Override
public void scan() {
throw new UnsupportedOperationException();
}
@Override
public void fax() {
throw new UnsupportedOperationException();
}
}
```

这说明接口过于庞大。

**7.24.1 拆分小接口**

```
public interface Printable {
void print();
}
public interface Scannable {
void scan();
}
public interface Faxable {
void fax();
}
```

普通打印机：

```java
public class SimplePrinter
implements Printable {
@Override
public void print() {
}
}
```

多功能设备：

```java
public class MultiFunctionPrinter
implements Printable, Scannable, Faxable {
}
```

每个实现类只依赖自己真正支持的能力。

**7.24.2 接口不是越小越好**

如果接口拆得过细：

```
一个方法一个接口
```

也可能导致：

- 类型数量膨胀
- 调用关系复杂
- 难以理解完整职责
- 组合成本过高
- 合理标准是：
接口中的方法应该围绕同一个稳定职责共同变化。

## 7.25 依赖倒置原则

依赖倒置可以简化为：
高层业务模块不应依赖底层具体实现，二者都应依赖抽象。
错误结构：

```
OrderService
↓
MySqlOrderRepository
```

改进：

```
OrderService
↓
OrderRepository
↑
MySqlOrderRepository
```

高层业务依赖：

```
OrderRepository
```

底层数据库实现也实现：

```
OrderRepository
```

这样数据库实现可以替换，而业务层无需修改。

**7.25.1 抽象由谁定义**

接口通常应定义在更接近业务需求的一侧。
例如：

```
public interface OrderRepository {
Order findById(OrderId id);
void save(Order order);
}
```

它表达的是业务层需要的能力，而不是数据库框架提供的全部操作。
不应简单复制 MyBatis、JPA 或 Redis API 作为领域接口。

## 7.26 组合

组合表示：
一个对象通过持有其他对象引用，获得并协调它们的能力。
示例：

```java
public class OrderService {
private final OrderRepository orderRepository;
private final InventoryService inventoryService;
private final MessagePublisher messagePublisher;
public OrderService(
OrderRepository orderRepository,
InventoryService inventoryService,
MessagePublisher messagePublisher
) {
this.orderRepository = orderRepository;
this.inventoryService = inventoryService;
this.messagePublisher = messagePublisher;
}
}
```

OrderService 通过组合获得：

- 订单存储能力
- 库存操作能力
- 消息发布能力
它不需要继承这些类。

**7.26.1 组合表达 has-a**

```
OrderService has an OrderRepository
Car has an Engine
Order has OrderItems
Computer has a CPU
```

继承表达：

```
Dog is an Animal
SavingsAccount is an Account
```

**7.26.2 组合的优势**

可以组合多个能力
运行时可以替换组件
不受单继承限制
降低父子类强耦合
更容易单元测试
更容易控制对象生命周期
更容易通过接口隔离变化
不会暴露被组合对象的全部内部实现

## 7.27 组合与继承的选择

**7.27.1 仅为了复用代码时优先组合**

错误：

```java
public class OrderService
extends JsonUtils {
}
```

OrderService 并不是一种 JsonUtils。
更合理：

```java
public class OrderService {
private final JsonSerializer serializer;
}
```

或者直接使用明确的工具方法。

**7.27.2 需要替换策略时使用组合**

```
public interface PricingStrategy {
BigDecimal calculate(Order order);
}
```

实现：

```java
public class NormalPricingStrategy
implements PricingStrategy {
}
public class VipPricingStrategy
implements PricingStrategy {
}
```

组合：

```java
public class PriceCalculator {
private final PricingStrategy strategy;
public PriceCalculator(
PricingStrategy strategy
) {
this.strategy = strategy;
}
public BigDecimal calculate(Order order) {
return strategy.calculate(order);
}
}
```

运行时可以注入不同策略。
如果使用继承：

```
VipPriceCalculator extends PriceCalculator
NormalPriceCalculator extends PriceCalculator
```

容易把可变化的行为绑定到类型层次中，灵活性较低。

**7.27.3 需要真正类型替换时使用继承或接口**

例如：

```
List<PaymentProcessor> processors;
```

不同实现都可以被当成 PaymentProcessor 使用。
这种多态替换适合接口或抽象父类。

## 7.28 委托

组合经常与委托一起出现。
委托是：
当前对象收到请求后，将实际工作交给内部对象完成。

```java
public class CachingOrderRepository
implements OrderRepository {
private final OrderRepository delegate;
private final Cache cache;
public CachingOrderRepository(
OrderRepository delegate,
Cache cache
) {
this.delegate = delegate;
this.cache = cache;
}
@Override
public Order findById(String orderId) {
Order cached = cache.get(orderId);
if (cached != null) {
return cached;
}
Order order = delegate.findById(orderId);
cache.put(orderId, order);
return order;
}
}
```

这里：

```
CachingOrderRepository
↓ 委托
OrderRepository delegate
```

它通过组合和委托增加缓存能力。
这类设计是装饰器思想的基础。

## 7.29 默认方法是否适合承载大量业务逻辑

接口默认方法可以包含实现，但不应因此把接口当成普通基类使用。
不推荐：

```
public interface OrderService {
default void createOrder(...) {
// 大量数据库逻辑
// 大量事务逻辑
// 大量状态修改
}
}
```

接口默认方法更适合：

- 基于抽象方法组合出的通用行为
- 简单兼容逻辑
- 小型工具行为
- 不依赖实例字段的默认实现
- 复杂共享状态和生命周期管理仍更适合：
- 抽象类
- 独立协作对象
- 组合
- 默认实现类

## 7.30 标记接口

标记接口是没有方法的接口：

```
public interface Serializable {
}
```

它通过类型关系表达某种能力或标记。

传统常见例子：

- Serializable
- Cloneable
- RandomAccess
- 调用方可以通过类型判断：

```
if (value instanceof Serializable) {
}
```

**7.30.1 标记接口与注解**

标记接口的特点：

- 参与类型系统
- 可以作为方法参数类型
- 可以使用 instanceof
- 编译器可以检查类型关系
- 注解的特点：
- 可以携带元数据
- 可以标记类、方法、字段等多种元素
- 通常通过反射或编译工具读取
- 不直接形成子类型关系
- 选择标准：

```
需要表达“这个对象是一种某类型”
→ 标记接口
需要附加元数据或配置
→ 注解
```

注解后续高级语言特性笔记展开。

## 7.31 函数式接口概览

只包含一个抽象方法的接口称为函数式接口：

```
@FunctionalInterface
public interface Task {
void execute();
}
```

可以使用 Lambda：

```
Task task = () -> System.out.println("执行");
```

函数式接口可以包含：

- 一个抽象方法
- 多个默认方法
- 多个静态方法
- Object 公共方法声明
本章只建立概念，Lambda 和函数式接口的完整规则放到高级语言特性笔记。

## 7.32 接口演进风险

默认方法降低了接口增加方法的兼容成本，但不能完全消除风险。
假设接口新增：

```
default void execute() {
}
```

某个实现类继承的父类或另一个接口中已有同签名方法，可能产生：

- 方法冲突
- 行为改变
- 编译错误
- 二义性
因此公共接口演进仍然需要谨慎。
接口一旦被外部大量实现，新增抽象方法尤其危险。

## 7.33 抽象类中的可变状态风险

抽象类可以复用状态，但共享父类状态也会增强耦合。
例如：

```
public abstract class BaseTask {
protected int retryCount;
protected boolean completed;
}
```

所有子类直接操作：

```
retryCount++;
completed = true;
```

问题：

- 状态规则散落在子类
- 子类可以破坏父类不变量
- 父类难以控制状态变化
- 继承层次之间耦合过深
- 更合理：

```java
public abstract class BaseTask {
private int retryCount;
private boolean completed;
protected final void increaseRetry() {
retryCount++;
}
protected final void markCompleted() {
completed = true;
}
}
```

即使使用抽象类，也应保持封装。

## 7.34 protected 的使用边界

抽象父类常使用 protected 暴露扩展点：

```
protected abstract void doExecute();
```

但不建议把大量字段和方法都设为 protected。

过度使用 protected 会导致：

- 子类依赖父类内部实现
- 父类难以重构
- 子类容易破坏不变量
- 形成脆弱基类
- 建议：

```
公共稳定契约
→ public
明确扩展点
→ protected
内部实现
→ private
```

## 7.35 适配器式抽象类

当接口方法很多，但某些实现只需要其中一部分时，历史上常使用适配器抽象类。
接口：

```
public interface EventListener {
void onStart();
void onSuccess();
void onFailure();
void onFinish();
}
```

适配器：

```
public abstract class EventAdapter
implements EventListener {
@Override
public void onStart() {
}
@Override
public void onSuccess() {
}
@Override
public void onFailure() {
}
@Override
public void onFinish() {
}
}
```

子类只重写需要的方法：

```java
public class FailureListener
extends EventAdapter {
@Override
public void onFailure() {
System.out.println("处理失败");
}
}
```

现代 Java 也可以通过接口默认方法实现类似效果。
但如果大量实现都不需要多数方法，更可能说明接口违反了接口隔离原则。

## 7.36 实际场景：仓储任务执行器

定义任务执行接口：

```
public interface WarehouseTaskExecutor {
TaskResult execute(WarehouseTask task);
}
```

不同实现：

```java
public class PickingTaskExecutor
implements WarehouseTaskExecutor {
@Override
public TaskResult execute(
WarehouseTask task
) {
return TaskResult.success();
}
}
public class PackingTaskExecutor
implements WarehouseTaskExecutor {
@Override
public TaskResult execute(
WarehouseTask task
) {
return TaskResult.success();
}
}
```

调用方：

```java
public class WarehouseTaskService {
private final Map<TaskType, WarehouseTaskExecutor>
executors;
public WarehouseTaskService(
List<WarehouseTaskExecutor> executorList
) {
this.executors = buildMap(executorList);
}
public TaskResult execute(
WarehouseTask task
) {
WarehouseTaskExecutor executor =
executors.get(task.type());
if (executor == null) {
throw new IllegalArgumentException(
"不支持的任务类型"
);
}
return executor.execute(task);
}
}
```

新增一种任务时，只需增加新的接口实现。
调用方不需要不断增加：

```
if
else if
switch
```

这是接口、多态和组合的典型应用。

## 7.37 实际场景：抽象类固定处理流程

```
public abstract class AbstractOutboundTask {
public final void execute(
OutboundCommand command
) {
validate(command);
lockInventory(command);
doExecute(command);
recordResult(command);
}
protected void validate(
OutboundCommand command
) {
Objects.requireNonNull(command);
}
protected void lockInventory(
OutboundCommand command
) {
}
protected abstract void doExecute(
OutboundCommand command
);
protected void recordResult(
OutboundCommand command
) {
}
}
```

子类只实现差异逻辑：

```java
public class NormalOutboundTask
extends AbstractOutboundTask {
@Override
protected void doExecute(
OutboundCommand command
) {
System.out.println("普通出库");
}
}
```

这适用于：

- 流程稳定
- 步骤差异明确
- 需要复用公共状态或逻辑
- 需要限制执行顺序

## 7.38 建议实验

实验一：抽象类不能实例化

```
public abstract class Animal {
public abstract void speak();
}
```

尝试：

```
new Animal();
```

观察编译错误。
然后创建子类：

```java
public class Dog extends Animal {
@Override
public void speak() {
System.out.println("Dog");
}
}
```

验证：

```
Animal animal = new Dog();
animal.speak();
```

实验二：抽象类构造顺序

```java
public class AbstractConstructorDemo {
public static void main(String[] args) {
new Dog("旺财");
}
static abstract class Animal {
Animal(String name) {
System.out.println(
"Animal: " + name
);
}
}
static class Dog extends Animal {
Dog(String name) {
super(name);
System.out.println(
"Dog: " + name
);
}
}
}
```

预期：

```
Animal: 旺财

```

实验三：一个类实现多个接口

实验八：组合替代继承
接口：

```
interface MessageSender {
void send(String message);
}
```

实现：

```
class EmailSender
implements MessageSender {
@Override
public void send(String message) {
System.out.println(
"Email: " + message
);
}
}
```

组合：

```java
class NotificationService {
private final MessageSender sender;
NotificationService(
MessageSender sender
) {
this.sender = sender;
}
void notifyUser(String message) {
sender.send(message);
}
}
```

调用：

```
NotificationService service =
new NotificationService(
new EmailSender()
);
service.notifyUser("任务完成");
```

然后替换为其他实现，验证 NotificationService 不需要修改。

## 7.40 易错点

误区一：抽象类只能包含抽象方法
错误。

抽象类可以包含：

- 字段
- 构造方法
- 普通方法
- 静态方法
- final 方法
- 抽象方法
- 误区二：抽象类没有构造方法
错误。
抽象类不能直接实例化，但创建子类对象时仍然需要调用抽象父类构造方法。
误区三：抽象类必须有抽象方法
错误。
没有抽象方法的类也可以声明为抽象类。
误区四：接口只能定义抽象方法
错误。

现代接口还可以定义：

- default 方法
- static 方法
- private 方法
- private static 方法
- 误区五：接口字段是普通实例字段
错误。
接口字段默认是：

```java
public static final
```

属于接口常量。
误区六：接口默认方法使接口可以拥有实例状态
错误。
default 方法有实现，但接口仍然没有普通实例字段和构造方法。
误区七：接口静态方法可以被实现类继承
错误。
接口静态方法通过接口名调用：

```
InterfaceName.method()
```

误区八：一个类实现多个接口不会发生冲突
错误。
如果多个接口提供相同签名的默认方法，实现类必须显式解决冲突。
误区九：接口一定比抽象类更先进
错误。

二者解决的问题不同：

- 抽象类擅长状态和实现复用
- 接口擅长契约和多能力组合
- 误区十：所有 Service 都必须有 Service 接口
错误。
只有存在真实抽象边界、替换需求或模块契约时，接口才有明确价值。
误区十一：implements 表示复用了接口实现
不准确。
传统抽象接口只定义契约。
即使存在 default 方法，接口也不提供实例状态和统一构造过程。
误区十二：组合只适合没有继承关系的对象
不完整。
即使存在继承关系，也可以通过组合封装可变化的行为，减少继承层次。
误区十三：优先组合意味着完全禁止继承
错误。
稳定的 is-a 关系、框架扩展点和模板方法仍然适合继承。
误区十四：接口越小越好
不一定。
接口应保持职责单一，但过度拆分也会导致类型膨胀和组合复杂。
误区十五：default 方法可以无限增加而不影响兼容性
错误。
新增默认方法仍可能与父类方法、其他接口方法或实现类已有方法产生冲突。

## 7.41 工程实践建议

**7.41.1 对外契约优先使用接口**

模块边界处可以使用：

```
public interface OrderRepository {
}
```

调用方只依赖接口，不依赖数据库实现。

**7.41.2 公共状态与模板流程使用抽象类**

当多个实现共享：

- 字段
- 构造逻辑
- 公共校验
- 固定流程
可以使用抽象类。

**7.41.3 抽象类字段尽量 private**

不推荐：

```
protected int retryCount;
```

推荐：

```java
private int retryCount;
protected final void increaseRetry() {
retryCount++;
}
```

防止子类任意破坏父类状态。

**7.41.4 接口应围绕稳定职责设计**

推荐：

```
OrderRepository
PaymentProcessor
MessagePublisher
```

避免把大量无关能力塞进同一个接口。

**7.41.5 接口参数使用最小能力**

如果方法只需要读取能力：

```
void process(Readable source)
```

不要强制依赖：

```
void process(ReadWriteStorage source)
```

减少不必要依赖。

**7.41.6 不要机械创建 Impl 类**

不推荐只有：

```
OrderService
OrderServiceImpl
```

且永远只有一个实现，没有抽象意义。
实现名应表达具体策略或技术：

```
DefaultOrderService
RemoteOrderService
CachedOrderService
```

**7.41.7 变化行为优先通过组合注入**

```java
private final PricingStrategy strategy;
```

优于为每种策略创建一层继承关系。

**7.41.8 默认方法保持轻量**

接口 default 方法适合：

- 小型通用行为
- 兼容性扩展
- 基于抽象方法的简单组合
复杂业务逻辑应放在明确的实现类或协作对象中。

## 7.42 本章知识链路

```
多个具体类型具有共同特征
↓
提取抽象契约
↓
需要共享状态和实现
→ 使用抽象类
↓
需要表达独立能力和多实现
→ 使用接口
↓
具体类继承或实现抽象
↓
调用方依赖抽象类型
↓
运行时替换具体实现
↓
通过组合协调多个接口能力
↓
降低耦合并提高扩展性
```

- 抽象类用于表示不完整的父类型，可以包含实例字段、构造方法、普通方法和抽象方法，但不能直接实例化。普通子类必须实现父类中尚未完成的抽象方法。接口主要
- 用于定义行为契约，一个类可以实现多个接口，从而组合多种独立能力。接口中的普通抽象方法默认是 public abstract，字段默认是 public static final。现代接口还可
- 以定义 default、static 和 private 方法。多个接口出现相同默认方法时，实现类必须显式解决冲突；父类具体方法与接口默认方法冲突时，通常父类方法优先。抽象类
- 更适合共享状态、构造逻辑和模板流程，接口更适合定义可替换的能力契约。工程设计中应面向抽象编程，并优先使用组合封装变化行为，而不是仅为了复用代码建立
继承关系。
