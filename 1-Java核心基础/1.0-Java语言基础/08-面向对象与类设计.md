## 8.2 面向对象的核心思想

面向对象编程不是简单地把代码写进 `class`。

更准确地说，它强调：

```text
围绕对象组织系统
↓
对象封装状态和行为
↓
对象通过明确协议协作
↓
职责由合适的对象承担
```

### 8.2.1 三个基础概念

```text
封装
→ 隐藏内部状态和实现细节

继承
→ 在类型关系中复用和扩展行为

多态
→ 通过统一抽象调用不同实现
```

但类设计中通常还要补充：

```text
组合
→ 通过对象协作复用能力

委托
→ 把具体工作交给其他对象

抽象
→ 只暴露当前问题需要的核心特征
```

### 8.2.2 面向对象的目标

面向对象不是为了增加类的数量，而是为了：

- 降低变化影响范围；
- 让业务规则靠近数据；
- 建立清晰责任边界；
- 让对象维持自身合法状态；
- 通过抽象隔离实现差异；
- 提高代码可测试性；
- 降低共享可变状态；
- 让代码结构贴近业务语言。

## 8.3 类是什么

类是对一类对象的结构、行为和约束的定义。

```java
public class Account {

    private String owner;
    private long balanceInFen;

    public void deposit(long amountInFen) {
        balanceInFen += amountInFen;
    }
}
```

这个类描述：

```text
状态
├── owner
└── balanceInFen

行为
└── deposit(...)
```

### 8.3.1 类不是对象

```java
Account account;
```

这里只声明一个引用变量，没有创建对象。

```java
Account account = new Account();
```

才创建一个 `Account` 实例。

### 8.3.2 一个类可以创建多个对象

```java
Account first = new Account();
Account second = new Account();
```

`first` 与 `second` 通常引用两个独立对象。

### 8.3.3 类是类型

声明：

```java
Account account;
```

表示变量 `account` 的编译时类型是 `Account`。

编译器据此检查：

- 可以调用哪些方法；
- 可以访问哪些成员；
- 可以赋入哪些对象引用；
- 是否需要类型转换。

---

## 8.4 对象是什么

对象是类或数组在运行时的实例。

```java
Account account = new Account();
```

可以建立下面的语言层模型：

```text
引用变量 account
↓ 保存引用值
Account 对象
├── 字段状态
└── 可调用行为
```

### 8.4.1 对象具有运行时类型

```java
Animal animal = new Dog();
```

其中：

```text
引用变量编译时类型
→ Animal

实际对象运行时类型
→ Dog
```

完整规则见 `12-多态与动态绑定.md`。

### 8.4.2 对象具有身份

即使两个对象字段相同，也可能是两个不同对象：

```java
User first = new User("A");
User second = new User("A");
```

```java
System.out.println(first == second); // false
```

### 8.4.3 对象具有状态

对象状态由字段及其关联对象共同组成。

```java
Order order = new Order();
```

订单状态可能包括：

- 订单编号；
- 当前状态；
- 商品项；
- 收货地址；
- 金额；
- 创建时间。

### 8.4.4 对象具有行为

```java
order.cancel();
order.pay();
order.changeAddress(address);
```

行为不只是修改字段，还应体现业务规则。

## 8.5 类、对象、引用之间的关系

```java
User first = new User();
User second = first;
```

可以理解为：

```text
类 User
→ 定义对象结构和行为

对象
→ User 的一个运行时实例

first
→ 保存对象引用值

second
→ 保存同一引用值的副本
```

### 8.5.1 多个引用可以指向同一对象

```java
second.setName("Java");

System.out.println(first.getName());
```

`first` 也会观察到状态变化。

### 8.5.2 引用可以重新指向另一个对象

```java
second = new User();
```

现在：

```text
first
→ 原对象

second
→ 新对象
```

### 8.5.3 对象可以没有用户代码持有的引用

```java
new User();
```

创建对象后没有保存引用。

对象是否会立即被回收由 JVM 可达性和 GC 时机决定，不能依赖。

## 8.6 字段：对象的状态

### 8.6.1 实例字段

```java
public class User {

    private String name;
    private int age;
}
```

每个 `User` 对象通常拥有独立字段状态。

### 8.6.2 字段应表达业务含义

不清晰：

```java
private int value;
private int type;
private int flag;
```

更清晰：

```java
private int retryCount;
private OrderType orderType;
private boolean enabled;
```

### 8.6.3 使用适当类型表达状态

不推荐：

```java
private int status;
```

推荐：

```java
private OrderStatus status;
```

枚举能减少：

- 无效整数；
- 魔法值；
- 错误比较；
- 缺少语义。

### 8.6.4 不把所有临时数据都变成字段

如果数据只在某个方法内部使用：

```java
BigDecimal total =
        calculateTotal(items);
```

它通常应是局部变量，而不是对象长期状态。

字段越多：

- 对象状态越复杂；
- 不变量越难维护；
- 并发风险越高；
- 测试组合越多。

## 8.7 方法：对象的行为

### 8.7.1 行为应围绕对象职责

```java
public class Account {

    private long balanceInFen;

    public void deposit(long amountInFen) {
        if (amountInFen <= 0) {
            throw new IllegalArgumentException(
                    "amount must be positive"
            );
        }

        balanceInFen =
                Math.addExact(
                        balanceInFen,
                        amountInFen
                );
    }
}
```

`Account` 自己维护余额规则。

### 8.7.2 行为不只是 Setter

贫乏写法：

```java
account.setBalanceInFen(
        account.getBalanceInFen()
        + amountInFen
);
```

问题：

- 规则散落在调用方；
- 可以绕过校验；
- 容易出现并发问题；
- 对象无法维持不变量；
- 重复逻辑增多。

更好：

```java
account.deposit(amountInFen);
```

### 8.7.3 方法名表达意图

推荐：

```java
order.pay();
order.cancel();
order.confirmReceipt();
```

不推荐：

```java
order.setStatus(PAID);
order.setStatus(CANCELLED);
```

后者把状态机规则交给外部代码。

## 8.8 对象状态与状态转换

对象行为常常是状态转换。

```text
原状态
+
业务命令
+
业务规则
↓
新状态
```

### 8.8.1 示例

```java
public class Order {

    private OrderStatus status =
            OrderStatus.CREATED;

    public void pay() {
        if (status != OrderStatus.CREATED) {
            throw new IllegalStateException(
                    "only created order can be paid"
            );
        }

        status = OrderStatus.PAID;
    }
}
```

### 8.8.2 直接 Setter 的风险

```java
order.setStatus(OrderStatus.COMPLETED);
```

可能跳过：

- 支付；
- 发货；
- 收货；
- 权限；
- 审计；
- 时间约束。

### 8.8.3 状态转换应集中

同一状态规则散落在多个 Controller、Service 和任务中，会造成：

- 条件不一致；
- 漏校验；
- 状态跳跃；
- 修复困难。

可以集中在：

- 领域对象；
- 状态机；
- 专门领域服务。

## 8.9 对象不变量

对象不变量是：

> 对象处于可被外部使用状态时，必须始终成立的约束。

### 8.9.1 示例

账户不变量：

```text
账户编号不能为空
余额不能超出 long 范围
冻结账户不能转出
```

订单不变量：

```text
商品列表不能为空
金额不能为负
已取消订单不能支付
已完成订单不能再次发货
```

### 8.9.2 在对象内部维护

```java
public void withdraw(long amountInFen) {
    if (amountInFen <= 0) {
        throw new IllegalArgumentException();
    }

    if (amountInFen > balanceInFen) {
        throw new IllegalStateException(
                "insufficient balance"
        );
    }

    balanceInFen -= amountInFen;
}
```

### 8.9.3 Setter 会扩大非法状态空间

```java
account.setBalanceInFen(-100);
```

如果任何代码都能任意赋值，对象很难保证合法。

### 8.9.4 不变量与数据库约束

对象校验不能完全替代：

- 数据库非空约束；
- 唯一索引；
- 外键；
- check 约束；
- 事务隔离。

数据库约束也不能替代对象行为。

二者共同保证系统一致性。

## 8.10 对象创建后的合法状态

对象一旦对外可见，应尽量已经处于合法状态。

不推荐：

```java
Order order = new Order();
order.setUserId(userId);
order.setItems(items);
order.setAddress(address);
order.setStatus(CREATED);
```

中间阶段对象可能：

- 没有用户；
- 没有商品；
- 没有地址；
- 状态不完整。

更好：

```java
Order order = Order.create(
        userId,
        items,
        address
);
```

对象创建与不可变设计见 `10`。

### 8.10.1 两阶段初始化风险

```text
先创建空对象
↓
逐个 Setter
↓
某一步异常
↓
留下半初始化对象
```

### 8.10.2 框架要求的无参构造器

ORM、序列化框架可能要求特殊创建方式。

此时仍应：

- 限制构造器可见性；
- 在加载后校验；
- 避免业务代码直接创建半成品；
- 区分持久化模型与领域模型。

## 8.11 职责

职责回答：

```text
这个类应该知道什么？
这个类应该做什么？
这个类不应该做什么？
```

### 8.11.1 单一职责不是“一类一个方法”

单一职责更准确地说：

> 一个类应围绕一个稳定的变化原因组织。

例如 `Order` 可以包含：

- 商品项；
- 金额计算；
- 订单状态转换；
- 地址变更规则。

这些都围绕订单业务职责。

### 8.11.2 不相关职责应拆分

```java
public class Order {

    void pay() {
    }

    void exportExcel() {
    }

    void sendSms() {
    }

    void backupDatabase() {
    }
}
```

导出、短信和数据库备份通常不属于订单核心职责。

### 8.11.3 拆分后协作

```text
Order
→ 订单状态与规则

OrderApplicationService
→ 用例编排

PaymentGateway
→ 支付交互

NotificationService
→ 通知

OrderRepository
→ 持久化
```

## 8.12 高内聚

高内聚表示：

> 一个类中的状态和行为围绕紧密相关的职责组织。

### 8.12.1 高内聚示例

```java
public class Money {

    private final long amountInFen;

    public Money add(Money other) {
        return new Money(
                Math.addExact(
                        amountInFen,
                        other.amountInFen
                )
        );
    }
}
```

字段和行为都围绕金额。

### 8.12.2 低内聚示例

```java
public class CommonUtils {

    static String formatDate(...) {
    }

    static BigDecimal calculateTax(...) {
    }

    static void sendEmail(...) {
    }

    static byte[] compress(...) {
    }
}
```

完全无关的方法堆积在同一个类中。

### 8.12.3 高内聚的价值

- 更容易命名；
- 更容易测试；
- 变化影响小；
- 状态边界明确；
- 更容易复用；
- 更容易理解。

## 8.13 低耦合

耦合表示对象之间依赖的程度。

### 8.13.1 高耦合

```java
public class OrderService {

    private final MySqlOrderRepository repository =
            new MySqlOrderRepository();

    private final AliyunSmsClient smsClient =
            new AliyunSmsClient();
}
```

问题：

- 直接依赖具体实现；
- 难以测试；
- 难以替换；
- 配置写死。

### 8.13.2 通过构造器传入依赖

```java
public class OrderService {

    private final OrderRepository repository;
    private final NotificationService notificationService;

    public OrderService(
            OrderRepository repository,
            NotificationService notificationService
    ) {
        this.repository = repository;
        this.notificationService =
                notificationService;
    }
}
```

### 8.13.3 低耦合不等于没有依赖

对象要协作就必然存在依赖。

目标是：

- 依赖清晰；
- 依赖方向稳定；
- 接口边界合理；
- 生命周期可管理；
- 替换成本可控。

## 8.14 对象协作

对象通常通过方法调用协作。

```java
order.pay(paymentGateway);
```

或：

```java
paymentService.pay(order);
```

### 8.14.1 消息思维

调用：

```java
order.cancel();
```

可以理解为：

```text
向 order 对象发送 cancel 消息
```

对象根据内部状态和规则决定如何响应。

### 8.14.2 协作对象

一个订单支付用例可能涉及：

```text
ApplicationService
├── Order
├── PaymentGateway
├── OrderRepository
└── EventPublisher
```

每个对象承担不同职责。

### 8.14.3 编排与业务规则

应用服务适合：

- 加载对象；
- 调用领域行为；
- 调用外部系统；
- 保存结果；
- 发布事件；
- 控制事务。

领域对象适合：

- 维护自身状态；
- 执行业务规则；
- 保证不变量。

## 8.15 Tell, Don’t Ask

原则：

> 尽量告诉对象做什么，而不是把数据取出来后由外部决定怎么修改。

### 8.15.1 Ask 风格

```java
if (
        order.getStatus()
        == OrderStatus.CREATED
) {
    order.setStatus(
            OrderStatus.CANCELLED
    );
}
```

### 8.15.2 Tell 风格

```java
order.cancel();
```

### 8.15.3 优点

- 规则集中；
- 调用方更简洁；
- 不变量更容易维护；
- 状态修改入口更少；
- 代码更贴近业务语言。

### 8.15.4 不是禁止所有 Getter

Getter 适合：

- 展示；
- 序列化；
- 查询；
- 日志；
- 外部协议；
- 只读投影。

问题不是 Getter 本身，而是：

```text
所有业务规则都在外部
对象只保存数据
```

## 8.16 封装变化

封装不仅是隐藏字段，还包括隐藏变化。

### 8.16.1 示例

初始实现：

```java
public boolean isExpired() {
    return expired;
}
```

以后可能改为：

```java
public boolean isExpired(
        LocalDateTime now
) {
    return expireAt.isBefore(now);
}
```

调用方只依赖业务方法，可以减少变化影响。

### 8.16.2 暴露内部结构的风险

```java
public Map<String, Object> getData() {
    return data;
}
```

调用方依赖内部键名和结构，后续很难调整。

### 8.16.3 暴露稳定协议

```java
public CustomerSnapshot snapshot() {
}
```

或者：

```java
public String displayName() {
}
```

比直接暴露内部对象图更稳定。

## 8.17 实体

实体的核心特征是：

```text
具有连续身份
身份比当前属性更重要
```

### 8.17.1 示例

订单：

```java
public class Order {

    private final OrderId id;
    private OrderStatus status;
}
```

即使状态变化：

```text
CREATED
→ PAID
→ SHIPPED
```

仍然是同一个订单。

### 8.17.2 实体相等

实体相等通常围绕稳定身份设计。

但 `equals()` 是否使用数据库主键、业务标识或对象身份，需要结合生命周期和持久化框架。

完整规则见 `18-equals与hashCode.md`。

### 8.17.3 实体不等于数据库表

实体可以：

- 包含行为；
- 维护不变量；
- 跨多个表；
- 不直接对应表结构。

## 8.18 值对象

值对象的核心特征是：

```text
没有重要独立身份
由属性值共同定义
通常设计为不可变
```

### 8.18.1 示例

```java
public record Money(
        long amountInFen,
        Currency currency
) {
}
```

两个金额的属性相同，可以视为同一个值。

### 8.18.2 常见值对象

- 金额；
- 地址；
- 时间区间；
- 经纬度；
- 邮箱地址；
- 手机号；
- 订单编号；
- 百分比；
- 版本号。

### 8.18.3 使用基本类型的问题

```java
String phone;
String email;
String orderId;
```

都只是 `String`，容易传错。

值对象：

```java
PhoneNumber phone;
EmailAddress email;
OrderId orderId;
```

可以：

- 增强类型安全；
- 集中校验；
- 表达业务语义；
- 避免参数顺序错误。

---

## 8.19 服务对象

并非所有行为都自然属于某个实体或值对象。

### 8.19.1 应用服务

负责用例编排：

```java
public class TransferApplicationService {

    public void transfer(
            TransferCommand command
    ) {
    }
}
```

### 8.19.2 领域服务

表达跨多个领域对象、但仍属于业务规则的行为：

```java
public class PricingService {

    public Money calculate(
            Customer customer,
            Order order
    ) {
    }
}
```

### 8.19.3 基础设施服务

处理外部技术能力：

```java
public interface PaymentGateway {
    PaymentResult pay(
            PaymentRequest request
    );
}
```

### 8.19.4 避免 Service 万能化

如果所有逻辑都放在：

```java
OrderService
```

而 `Order` 只有 Getter/Setter，就可能形成贫血模型。

## 8.20 DTO、领域对象与持久化对象

### 8.20.1 DTO

DTO 用于跨边界传输数据。

```java
public record CreateOrderRequest(
        String userId,
        List<String> itemIds
) {
}
```

特点：

- 数据结构明确；
- 通常行为较少；
- 面向接口协议；
- 可与序列化框架配合。

### 8.20.2 领域对象

领域对象表达：

- 业务状态；
- 行为；
- 不变量；
- 业务语言。

### 8.20.3 持久化对象

持久化对象可能面向：

- 表结构；
- ORM；
- 数据库字段；
- 查询映射。

### 8.20.4 是否必须三套对象

不一定。

简单 CRUD 系统中，完全分离可能增加无意义映射。

复杂领域中，直接共用一个类可能导致：

- API 字段污染领域；
- ORM 注解侵入；
- 懒加载问题；
- 敏感字段泄漏；
- 数据库结构绑死业务模型。

应根据复杂度决定。

## 8.21 贫血模型

贫血模型通常指：

```text
对象只有字段和 Getter/Setter
业务逻辑集中在 Service
```

### 8.21.1 示例

```java
public class Account {

    private long balanceInFen;

    public long getBalanceInFen() {
        return balanceInFen;
    }

    public void setBalanceInFen(
            long balanceInFen
    ) {
        this.balanceInFen =
                balanceInFen;
    }
}
```

外部：

```java
account.setBalanceInFen(
        account.getBalanceInFen()
        - amountInFen
);
```

### 8.21.2 问题

- 规则散落；
- 对象无法保护状态；
- Service 变大；
- 重复条件；
- 状态修改入口过多；
- 测试依赖流程编排。

### 8.21.3 贫血模型并非永远错误

适合：

- 简单 CRUD；
- 报表查询；
- 数据转换；
- 外部协议 DTO；
- 业务规则极少的系统。

关键是不要把复杂领域误写成数据容器。

---

## 8.22 充血模型

充血模型强调：

```text
状态
+
行为
+
不变量
```

共同放在领域对象中。

### 8.22.1 示例

```java
public class Account {

    private long balanceInFen;

    public void withdraw(
            long amountInFen
    ) {
        if (amountInFen <= 0) {
            throw new IllegalArgumentException();
        }

        if (balanceInFen < amountInFen) {
            throw new IllegalStateException(
                    "insufficient balance"
            );
        }

        balanceInFen -= amountInFen;
    }
}
```

### 8.22.2 优点

- 规则集中；
- 对象始终合法；
- API 更接近业务语言；
- 测试更聚焦；
- 减少重复代码。

### 8.22.3 风险

如果把所有内容都塞进实体：

- 数据库调用；
- HTTP 调用；
- 消息发送；
- 复杂编排；
- 日志基础设施；

对象会变成另一个上帝类。

充血不等于“所有代码都放实体”。

---

## 8.23 依赖、关联、聚合与组合

这些概念用于描述对象关系。

### 8.23.1 依赖

临时使用另一个对象：

```java
public void pay(
        PaymentGateway gateway
) {
}
```

通常表现为：

- 方法参数；
- 局部变量；
- 静态方法调用；
- 临时创建。

### 8.23.2 关联

一个对象长期知道另一个对象：

```java
public class Order {

    private Customer customer;
}
```

### 8.23.3 聚合

整体持有部分，但部分可以独立存在或被共享。

```text
Team
→ Player
```

球员可以脱离球队存在。

### 8.23.4 组合

整体强拥有部分，部分生命周期通常依附整体。

```text
Order
→ OrderItem
```

订单项通常离开订单没有独立业务意义。

### 8.23.5 Java 语法不强制区分

聚合和组合都可能写成字段：

```java
private List<Item> items;
```

区别来自：

- 生命周期；
- 所有权；
- 是否共享；
- 是否可独立存在；
- 业务语义。

---

## 8.24 is-a 与 has-a

### 8.24.1 is-a

```text
Dog is an Animal
```

通常对应继承或接口实现。

### 8.24.2 has-a

```text
Car has an Engine
```

通常对应组合或关联。

### 8.24.3 语法成立不等于设计成立

```java
class Stack extends ArrayList {
}
```

语法可能允许，但：

```text
Stack is an ArrayList
```

是否符合替换关系值得怀疑。

### 8.24.4 优先考虑组合

复用实现时先问：

```text
真的是稳定 is-a 关系吗？
子类能替换父类吗？
父类行为对子类都成立吗？
```

否则优先组合。

完整规则见 `15-组合与设计原则.md`。

---

## 8.25 委托

委托是：

> 一个对象接收到请求后，把具体工作交给另一个对象完成。

### 8.25.1 示例

```java
public class OrderService {

    private final OrderRepository repository;

    public Order find(OrderId id) {
        return repository.find(id);
    }
}
```

### 8.25.2 委托与继承

继承：

```text
通过 is-a 关系获得行为
```

委托：

```text
通过持有协作者调用行为
```

### 8.25.3 委托的价值

- 组合替代继承；
- 隔离外部系统；
- 便于测试；
- 替换实现；
- 控制职责边界。

### 8.25.4 无意义转发

如果类只机械转发数十个方法，没有新增：

- 业务语义；
- 权限；
- 事务；
- 缓存；
- 适配；
- 不变量；

可能只是多余包装。

---

## 8.26 类的大小与拆分

不能用固定行数判断类是否过大。

### 8.26.1 应拆分的信号

- 类名难以准确概括职责；
- 字段分成互不相关的几组；
- 一部分方法只使用部分字段；
- 修改不同业务功能总要改同一类；
- 测试准备非常复杂；
- 构造器依赖过多；
- 方法数量不断增长；
- 存在大量 `if type`；
- 多个团队同时修改同一类。

### 8.26.2 不应机械拆分

过度拆分会产生：

- 大量单方法类；
- 调用链过长；
- 命名困难；
- 业务规则碎片化；
- 跳转阅读成本；
- 无意义接口。

### 8.26.3 以职责和变化为依据

```text
一起变化
+
共同维护同一不变量
+
共享核心状态
→ 倾向放在一起
```

```text
变化原因不同
+
依赖不同
+
生命周期不同
→ 倾向拆分
```

---

## 8.27 上帝类

上帝类承担过多职责。

典型特征：

```text
几十个字段
上百个方法
大量外部依赖
负责所有业务流程
任何功能都要修改
```

### 8.27.1 常见名称

- `Manager`；
- `Helper`；
- `CommonService`；
- `SystemUtil`；
- `BaseService`；
- `ApplicationContextHolder`。

名称本身不一定有问题，但经常成为职责垃圾桶。

### 8.27.2 拆分方向

按：

- 业务能力；
- 生命周期；
- 外部依赖；
- 事务边界；
- 数据所有权；
- 变化原因；

拆分。

### 8.27.3 不要一次性大爆炸重构

可以逐步：

1. 增加测试；
2. 找出稳定边界；
3. 提取无状态逻辑；
4. 提取外部依赖；
5. 收敛状态修改入口；
6. 迁移调用方。

---

## 8.28 数据类

数据类通常只保存数据。

例如 DTO：

```java
public record UserResponse(
        String id,
        String name
) {
}
```

这是合理的数据载体。

### 8.28.1 数据类不是天然坏味道

适合：

- API 请求与响应；
- 数据库投影；
- 消息事件；
- 配置；
- 查询结果；
- 序列化载体。

### 8.28.2 问题出现在复杂领域对象被写成数据类

如果对象有大量业务规则，却只有 Getter/Setter，就会导致规则外泄。

### 8.28.3 判断标准

```text
它的职责本来就是传输数据
→ 数据类合理

它本应维护业务状态和规则
→ 只有 Getter/Setter 可能贫血
```

## 8.29 工具类

工具类通常包含无状态静态方法。

```java
public final class HexUtils {

    private HexUtils() {
    }

    public static String encode(
            byte[] bytes
    ) {
        // ...
        return "";
    }
}
```

### 8.29.1 适合工具类的内容

- 纯函数；
- 通用格式转换；
- 无状态算法；
- 与领域无关的底层操作。

### 8.29.2 不适合

- 共享可变业务状态；
- 数据库访问；
- 请求上下文；
- 隐式全局依赖；
- 复杂领域规则；
- 需要替换的外部调用。

### 8.29.3 工具类滥用

```java
OrderUtils.cancel(order);
```

如果取消是订单行为，更合理：

```java
order.cancel();
```

完整静态工具类规则见 `16`。

## 8.30 record 的定位

record 适合表达透明数据载体和值对象。

```java
public record Point(
        int x,
        int y
) {
}
```

自动提供：

- final 组件字段；
- 规范构造器；
- 访问器；
- `equals()`；
- `hashCode()`；
- `toString()`。

### 8.30.1 record 可以有行为

```java
public record Point(
        int x,
        int y
) {
    public int distanceSquared() {
        return x * x + y * y;
    }
}
```

### 8.30.2 record 可以校验

```java
public record Percentage(
        int value
) {
    public Percentage {
        if (value < 0 || value > 100) {
            throw new IllegalArgumentException();
        }
    }
}
```

### 8.30.3 record 不自动深度不可变

```java
public record Group(
        List<String> members
) {
}
```

列表仍可变。

应考虑：

```java
public Group {
    members = List.copyOf(members);
}
```

### 8.30.4 record 不适合所有实体

实体通常具有：

- 稳定身份；
- 生命周期；
- 可变状态；
- 延迟加载；
- ORM 代理；
- 状态转换。

是否使用 record 需要结合框架和领域需求。

## 8.31 嵌套类概览

类内部可以声明其他类。

```java
public class Order {

    static class Builder {
    }

    class LineEditor {
    }
}
```

### 8.31.1 静态嵌套类

不隐式持有外部类实例。

适合：

- Builder；
- 辅助值类型；
- 与外部类紧密相关的实现类；
- 隐藏实现细节。

### 8.31.2 内部类

非静态内部类隐式关联外部对象。

```java
Order order = new Order();
Order.LineEditor editor =
        order.new LineEditor();
```

### 8.31.3 风险

非静态内部类可能：

- 延长外部对象生命周期；
- 增加隐式依赖；
- 序列化复杂；
- 导致内存泄漏误判；
- 降低可测试性。

完整嵌套类规则放在内部类专题。

## 8.32 对象生命周期概览

对象生命周期通常包括：

```text
创建
↓
初始化
↓
对外发布
↓
使用与状态变化
↓
不再可达
↓
可能被 GC 回收
```

### 8.32.1 创建不只通过 new

对象还可能来自：

- 反射；
- 反序列化；
- 克隆；
- 框架容器；
- 工厂；
- JVM 内部机制。

### 8.32.2 构造完成不等于安全发布

多线程中，对象被其他线程观察还涉及：

- 安全发布；
- `final` 字段语义；
- `volatile`；
- 锁；
- 并发容器。

完整规则见并发模块。

### 8.32.3 不依赖 finalize

资源释放应使用：

- `try-with-resources`；
- `AutoCloseable`；
- 明确生命周期管理。

对象终结机制见 `19`。

## 8.33 类设计与测试

### 8.33.1 易测试的类

通常具有：

- 明确依赖；
- 较少全局状态；
- 稳定输入输出；
- 可控副作用；
- 小而明确的职责；
- 不依赖系统时间和随机数的隐式调用。

### 8.33.2 注入变化源

不推荐：

```java
public boolean isExpired() {
    return expireAt.isBefore(
            LocalDateTime.now()
    );
}
```

测试依赖当前时间。

可以：

```java
public boolean isExpired(
        LocalDateTime now
) {
    return expireAt.isBefore(now);
}
```

或注入 `Clock`。

### 8.33.3 不隐藏外部依赖

不推荐：

```java
public void save() {
    new MySqlClient().insert(this);
}
```

对象很难测试和替换。

### 8.33.4 测试行为而不是字段实现

推荐：

```java
account.withdraw(100);

assertEquals(
        900,
        account.balanceInFen()
);
```

而不是只测试 Setter 是否赋值。

## 8.34 类设计与并发

对象设计会影响并发复杂度。

### 8.34.1 可变共享对象

```text
多个线程
+
同一个可变对象
→ 竞态条件风险
```

### 8.34.2 不可变对象

创建后不变，可以安全共享。

### 8.34.3 线程封闭

对象只被一个线程访问，可以减少同步。

### 8.34.4 封装同步

如果对象内部状态需要并发保护，应尽量由对象统一控制：

```java
public synchronized void deposit(...) {
}
```

而不是让所有调用方自行加锁。

具体同步工具见并发模块。

## 8.35 类设计与持久化框架

ORM 会影响类设计，但不应完全主导领域模型。

### 8.35.1 常见要求

- 无参构造器；
- 可代理类；
- 字段或方法访问；
- 主键；
- 集合代理；
- 延迟加载；
- 实体生命周期。

### 8.35.2 常见冲突

- `final` 类难以代理；
- 业务方法触发懒加载；
- `equals()` 使用数据库主键；
- 双向关联维护复杂；
- Setter 破坏不变量；
- 无参构造器产生半初始化对象。

### 8.35.3 处理策略

- 限制无参构造器可见性；
- 用领域方法修改状态；
- 将 ORM 实体与领域模型分离；
- 接受适度妥协；
- 用集成测试验证映射行为。

## 8.36 类设计与序列化

对象用于 JSON、消息或缓存时，需要注意：

- 字段暴露；
- 构造方式；
- 默认值；
- 版本兼容；
- 敏感信息；
- 多态类型；
- 空值；
- 集合可变性；
- 时间格式；
- 枚举演进。

### 8.36.1 不直接序列化复杂领域对象

可能泄露：

- 内部字段；
- 懒加载代理；
- 双向关系；
- 密码；
- 审计信息；
- 实现细节。

更适合映射为 DTO。

### 8.36.2 序列化结构是外部契约

一旦对外发布，字段名称和语义可能需要长期兼容。

不要让内部重构直接破坏外部协议。

## 8.37 常见类设计坏味道

### 8.37.1 Getter/Setter 全开放

```text
任何代码都能任意修改状态
```

### 8.37.2 布尔字段过多

```java
boolean paid;
boolean shipped;
boolean cancelled;
boolean completed;
```

可能产生互相矛盾组合。

更适合状态枚举或状态机。

### 8.37.3 魔法值

```java
if (status == 7) {
}
```

应使用枚举或常量。

### 8.37.4 构造器参数过多

说明：

- 职责过多；
- 缺少值对象；
- 缺少参数对象；
- 对象状态过于复杂。

### 8.37.5 双向关联滥用

```text
Parent 持有 Child
Child 又持有 Parent
```

会增加：

- 生命周期复杂度；
- 序列化循环；
- 状态同步；
- 内存引用；
- ORM 维护成本。

### 8.37.6 继承只为复用代码

没有稳定 `is-a` 关系时，继承会带来脆弱耦合。

### 8.37.7 静态全局状态

隐藏依赖，难测试，且有并发风险。

## 8.38 建议实验

### 实验一：类、对象和引用

```java
public class ClassAndObjectDemo {

    public static void main(String[] args) {
        User first = new User();
        User second = first;

        second.name = "Java";

        System.out.println(first.name);
        System.out.println(first == second);
    }

    static class User {
        String name;
    }
}
```

### 实验二：两个独立对象

```java
public class IndependentObjectDemo {

    public static void main(String[] args) {
        User first = new User();
        User second = new User();

        first.name = "A";
        second.name = "B";

        System.out.println(first.name);
        System.out.println(second.name);
        System.out.println(first == second);
    }

    static class User {
        String name;
    }
}
```

### 实验三：行为维护不变量

```java
public class AccountDemo {

    static class Account {

        private long balanceInFen;

        void deposit(long amountInFen) {
            if (amountInFen <= 0) {
                throw new IllegalArgumentException();
            }

            balanceInFen =
                    Math.addExact(
```

## 8.40 易错点

### 误区一：只要使用 class 就是面向对象设计

**错误。**

类只是语法载体，职责、封装、协作和不变量才是设计核心。

### 误区二：类和对象是同一个概念

**错误。**

类定义类型，对象是运行时实例。

### 误区三：声明引用变量就创建了对象

**错误。**

```java
User user;
```

只声明变量。

### 误区四：一个对象只能有一个引用

**错误。**

多个变量可以保存同一引用值。

### 误区五：字段越多，类表达的信息越丰富

**错误。**

字段越多，对象状态和不变量通常越复杂。

### 误区六：所有字段都应该生成 Getter 和 Setter

**错误。**

Setter 会扩大状态修改入口，Getter 也可能泄漏内部结构。

### 误区七：封装就是把字段改成 private

**错误。**

还包括行为入口、不变量、所有权和变化隔离。

### 误区八：对象行为就是字段赋值

**错误。**

行为应表达业务意图和规则。

### 误区九：对象不变量只需要在 Controller 校验

**错误。**

对象自身应防止非法状态进入。

### 误区十：数据库有约束，所以对象不需要校验

**错误。**

对象规则和数据库约束解决不同层次问题。

### 误区十一：一个类只能有一个职责，所以只能有一个方法

**错误。**

职责是变化原因和业务边界，不是方法数量。

### 误区十二：低耦合意味着对象之间完全不依赖

**错误。**

协作必然有依赖，目标是让依赖清晰稳定。

### 误区十三：Tell, Don’t Ask 禁止任何查询方法

**错误。**

它反对的是外部获取数据后操纵对象内部规则。

### 误区十四：实体必须一一对应数据库表

**错误。**

实体是领域身份概念，不是表映射定义。

### 误区十五：值对象没有任何状态

**错误。**

值对象有状态，只是身份不重要，通常不可变。

### 误区十六：值对象必须使用 record

**错误。**

record 很适合值对象，但普通 final 类同样可以。

### 误区十七：Service 中逻辑越多，分层越清晰

**错误。**

可能形成贫血模型和上帝服务。

### 误区十八：贫血模型永远错误

**错误。**

简单 CRUD、DTO 和查询模型中可以合理存在。

### 误区十九：充血模型要求实体自己访问数据库和网络

**错误。**

外部基础设施通常通过服务和接口协作。

### 误区二十：聚合和组合能通过字段关键字自动区分

**错误。**

它们主要由生命周期和所有权语义决定。

### 误区二十一：有 is-a 语法关系就一定适合继承

**错误。**

还必须满足行为替换和稳定类型关系。

### 误区二十二：组合只是把类作为字段，没有设计含义

**错误。**

组合表达职责协作和所有权边界。

### 误区二十三：委托一定比直接实现更好

**错误。**

无意义转发会增加层次和阅读成本。

### 误区二十四：类超过 200 行就必须拆分

**错误。**

应根据职责、内聚和变化原因判断。

### 误区二十五：类越小越符合单一职责

**错误。**

过度拆分会让业务规则碎片化。

### 误区二十六：所有 Utils 都是坏设计

**错误。**

无状态、通用、稳定的底层工具方法可以合理存在。

### 误区二十七：record 自动保证深度不可变

**错误。**

组件引用的对象仍可能可变。

### 误区二十八：record 只能保存数据，不能定义方法

**错误。**

record 可以定义行为和校验。

### 误区二十九：内部类不会影响外部对象生命周期

**错误。**

非静态内部类通常隐式持有外部实例。

### 误区三十：对象没有引用后会立即被 GC

**错误。**

对象只是具备回收资格，具体时机由 JVM 决定。

### 误区三十一：构造完成就保证其他线程安全看到所有状态

**错误。**

还需要安全发布和内存模型保证。

### 误区三十二：可测试性只取决于测试框架

**错误。**

依赖、时间、随机数和全局状态设计会直接影响可测试性。

### 误区三十三：对象自己 new 所有依赖更封装

**错误。**

这会隐藏依赖并增加替换和测试难度。

### 误区三十四：ORM 实体设计必须完全服从表结构

**错误。**

应在框架约束与领域表达之间权衡。

### 误区三十五：领域对象可以直接作为所有 API 响应

**错误。**

可能泄露内部结构和敏感字段。

### 误区三十六：多个 boolean 字段比状态枚举更灵活

**错误。**

容易产生互相矛盾组合。

### 误区三十七：设计模式越多，面向对象水平越高

**错误。**

模式应解决真实变化和复杂度，不应炫技。

### 误区三十八：面向对象排斥静态纯函数

**错误。**

纯计算和通用算法可以合理使用静态方法。

### 误区三十九：所有行为都必须属于实体

**错误。**

跨对象规则、外部交互和用例编排应由其他对象承担。

### 误区四十：类设计完成后不应再调整边界

**错误。**

职责边界会随着业务认知演进，需要持续重构。

## 8.41 工程实践建议

1. 类名使用领域名词，方法名使用业务动词。
2. 字段使用具有业务语义的类型，不滥用 `String`、`int` 和 `Map`。
3. 对象创建后立即建立合法状态。
4. 状态修改通过业务方法完成，不开放通用 Setter。
5. 将业务规则放在最了解数据和不变量的对象中。
6. 使用卫语句和私有方法保持行为清晰。
7. 一个类围绕稳定职责组织，不按行数机械拆分。
8. 构造器依赖过多时检查职责是否过重。
9. 外部系统依赖通过接口和构造器注入。
10. 应用服务负责用例编排，领域对象负责业务规则。
11. 简单 CRUD 不强行套复杂领域模型。
12. 复杂领域不把所有对象写成贫血 DTO。
13. 优先组合和委托，谨慎使用继承。
14. 聚合与组合明确生命周期和所有权。
15. 对外传输使用 DTO，避免直接暴露复杂领域对象。
16. record 用于透明数据载体和值对象时处理内部可变组件。
17. 使用枚举或状态机替代互相矛盾的布尔状态。
18. 不创建万能 `Utils`、`Manager`、`Helper` 和 `CommonService`。
19. 静态工具类只保存无状态、通用、稳定能力。
20. 时间、随机数和外部客户端作为显式依赖。
21. 不在对象内部直接创建数据库或网络客户端。
22. 减少双向关联，优先单向依赖。
23. 返回对象快照或稳定协议，而不是暴露内部对象图。
24. 不变量同时由对象、数据库和事务边界协同保障。
25. 对状态转换编写边界测试和非法路径测试。
26. 对实体和值对象分别设计合适的相等语义。
27. 多线程共享对象时优先不可变或线程封闭设计。
28. ORM 妥协通过受限构造器和领域方法控制。
29. 大类重构先补测试，再逐步提取稳定边界。
30. 设计模式只在变化和复杂度已经真实存在时使用。
31. 代码审查重点检查：职责漂移、状态泄漏、不变量破坏和隐藏依赖。
32. 定期根据业务语言调整类名、方法名和边界。

## 8.43 本章总结

### 8.43.1 类与对象

```text
类
→ 定义结构、行为和约束

对象
→ 类的运行时实例

引用变量
→ 保存引用值
→ 用于访问对象
```

### 8.43.2 状态与行为

```text
字段
→ 表达对象状态

方法
→ 表达对象行为

业务方法
→ 控制状态转换
→ 维护对象不变量
```

### 8.43.3 设计目标

```text
高内聚
→ 状态和行为围绕明确职责

低耦合
→ 依赖清晰、方向稳定

封装
→ 隐藏实现、控制状态、隔离变化

协作
→ 对象通过明确协议完成用例
```

### 8.43.4 对象类型

```text
实体
→ 身份重要
→ 状态可变化

值对象
→ 属性值重要
→ 通常不可变

服务
→ 承担不自然属于单个对象的行为

DTO
→ 跨边界传输数据
```

### 8.43.5 面试口述版

类定义一类对象的状态、行为和约束，对象是类在运行时的实例，引用变量保存引用值并用于访问对象。面向对象的核心不是把字段和方法放进 `class`，而是让合适的对象承担合适职责，并由对象维护自身不变量。

好的类通常具有高内聚和低耦合：字段与行为围绕同一业务职责，外部依赖通过明确协议协作。对象状态不应被任意 Setter 修改，而应通过 `pay()`、`cancel()`、`withdraw()` 等业务方法完成合法状态转换。Tell, Don’t Ask 强调告诉对象做什么，而不是取出数据后由外部操纵内部状态。

实体依靠身份保持连续性，值对象由属性值定义并通常设计为不可变，应用服务负责编排用例，领域服务处理跨对象规则，DTO 负责跨边界传输。贫血模型并非在所有场景都错误，但复杂领域如果只有 Getter/Setter，会导致规则散落和对象失去保护能力。类是否拆分应根据职责、内聚和变化原因判断，而不是机械使用行数或设计模式数量衡量。
